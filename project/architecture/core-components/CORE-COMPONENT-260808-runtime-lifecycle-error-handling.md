# CORE-COMPONENT-260808-runtime-lifecycle-error-handling: Runtime Lifecycle and Error Handling

## Status

Adopted

## Purpose

Keep code-server process ownership, lifecycle state, failure reporting, and recovery behavior consistent and isolated.

## Scope

Workbench registration state, start, stop, restart, health detection, backend recovery, multi-project isolation, state exposed to trusted application boundaries, and the public lifecycle state reported to application, API, and browser surfaces.

## Definition

### Rules
- Workbench process operations MUST be owned by one internal runtime-management boundary.
- Runtime state MUST be one of `stopped`, `starting`, `running`, `stopping`, or `failed`; absence represents `stopped` when no stopped snapshot is returned. `stopping` MUST mean that a selected release has claimed an exact running generation and has not yet confirmed its release.
- Public runtime state MUST be reported as exactly one of `Stopped`, `Starting`, `Running`, or `Failed`. The internal `registered` state and every other internal state MUST NOT reach a public surface, and no additional public state may be introduced.
- Every public runtime state MUST be projected by the runtime manager from its own entry map. No route, proxy, browser client, or other consumer may derive public state from process liveness, ports, snapshots, or its own health probe.
- A missing or `registered` entry MUST be reported `Stopped`; a retained failed entry MUST be reported `Failed` and MUST NOT become `Stopped` through entry absence. `Running` MUST be reported only after the documented health-gated readiness has been observed; process existence alone MUST NOT be sufficient. A `stopping` entry MUST be reported `Running` until its release is confirmed, so an in-flight selected stop MUST NOT be reported `Stopped`, `Starting`, or `Failed` and MUST NOT introduce a fifth public state.
- A start failure before readiness, an observed runtime exit after readiness, and a completed health observation that does not satisfy the documented health contract MUST each report `Failed` and MUST NOT leave that project reported `Running`.
- Every `running` to `failed` transition MUST pass through one manager-owned guarded transition operation that compare-and-sets on the exact installed entry object and its generation. Observed false liveness, a failed health observation, and process-exit settlement MUST all use it. The winning contender MUST install the failed entry, retain exactly one bounded failure category, record exactly one cleanup audit, and emit exactly one `runtime.health.changed`. A losing contender MUST NOT mutate the entry, MUST NOT terminate or audit the process again, MUST NOT emit an event, and MUST surface the retained failure of the winning transition.
- A selected project runtime MUST be released only through one manager-owned stop operation that accepts a persisted stable project ID and returns a frozen typed result. No route, proxy, browser client, CLI, or other consumer may terminate a runtime, signal a process group, probe a listener, or derive its own stop result. The operation MUST resolve every classified lifecycle outcome as a typed result and MUST reject only on an infrastructure fault; a success-shaped body for an unclassified fault is prohibited.
- Selected stop MUST claim its target with one synchronous compare-and-set on the exact installed running entry object and its generation, with no `await` between reading that entry and installing the `stopping` entry. Selected stop, observed false liveness, a failed health observation, and process-exit settlement MUST all contend through this exact-entry-and-generation discipline; a losing contender MUST NOT mutate the entry, terminate, audit, or emit.
- Selected stop MUST offer a documented finite graceful period before any escalation, MUST measure that period on a monotonic elapsed-time clock from the moment its graceful signal is confirmed delivered rather than from operation entry, MUST escalate only after that whole period has elapsed since that signal, MUST offer the documented finite force period measured the same way from the moment its force signal is confirmed delivered, and MUST settle within a documented finite overall bound derived from the configured graceful period, the configured force period, and a documented audit allowance.
- The documented audit allowance MUST bound all observation performed before the graceful signal and the settlement between phases, so the full graceful and force windows fit inside the unchanged overall bound. A selected stop whose pre-signal observation cannot complete inside that allowance MUST send no signal and MUST report an unconfirmed release; it MUST NOT shorten the graceful opportunity, shorten the force window, or exceed the overall bound. No phase window may be opened without its own confirmed delivered signal.
- Termination signal delivery MUST produce a result the sequencer acts on. The signal primitive MUST report success only when the host accepted the signal for the owned process group, MUST report a non-delivery only for the expected identity-to-signal race in which that group is already gone, and MUST surface every other signalling error as a termination fault rather than a non-delivery or a silent success. Only a confirmed delivered signal may fix a phase window's start, and that clock reading MUST be taken in the same synchronous step as the confirming send. A signal reported undelivered MUST open no window, MUST NOT be recorded, logged, or serialized as a delivered signal, and MUST NOT produce an escalated release mode; the sequence MUST settle from what a bounded observation can still confirm, and MUST report an unconfirmed release when it cannot confirm absence or when a signal was already delivered earlier in that sequence.
- A selected stop MUST report success only when the exact-ownership audit confirms that the claimed root process identity is absent, its owned process group is absent, and its loopback listener accepts no connection. On that confirmation the manager MUST install a `registered` entry that records the release, remove that generation's ownership record, and record exactly one stop-phase cleanup audit.
- A process MUST be treated as an owned descendant of a runtime only while it is a member of the process group led by that runtime's exact recorded root identity. Documentation, audits, and evidence MUST NOT describe that membership check as a stronger descendant-attribution proof than it is, MUST record that a descendant which leaves the owned process group before the audit samples it is no longer attributable by any bounded local mechanism, and MUST NOT adopt, signal, or claim any process that Ascend cannot attribute.
- A selected stop that cannot confirm release within its overall bound MUST surface an explicit non-success outcome, MUST install a retained failed entry carrying one bounded stop classification, MUST retain that generation's ownership record so manager shutdown re-attempts exact cleanup, MUST record exactly one stop-phase cleanup audit when its termination produced one, and MUST NOT report that project `Stopped`.
- A termination fault during a selected stop MUST settle that entry as an unconfirmed release and MUST then surface the underlying failure explicitly. It MUST NOT be swallowed, MUST NOT produce a success-shaped result, and MUST NOT leave an entry in the `stopping` state after settlement.
- A selected stop MUST NOT wait for its termination beyond its documented overall bound. When a termination has not returned within that bound the manager MUST cancel it, settle the entry as an unconfirmed release, and account for the abandoned settlement in its trusted audit. A cancelled or abandoned termination MUST NOT later mutate an entry, record a cleanup audit, emit an event, or signal any process.
- The one termination sequencer MUST bound itself rather than relying on its caller. It MUST measure every phase window, every deadline, and every elapsed comparison on one trusted monotonic elapsed-time clock that no wall-clock adjustment can move, and MUST NOT derive any of that arithmetic from a wall clock; unrelated lifecycle, event, and health timestamps that record when something happened are outside this rule and remain wall-clock values. It MUST derive one overall deadline from the configured graceful period, force period, and audit allowance; MUST own one cancellation signal that its caller's optional signal, its own deadline, and its own return all abort; MUST arm that deadline, and every phase deadline, through a trusted synchronous scheduling primitive that returns a cancellation handle and is never one of the awaited termination primitives, so the mechanism responsible for firing the abort can neither hang nor depend on the abort it fires; MUST pass a cancellation signal into every awaited termination primitive; and MUST abandon any awaited primitive still pending at its deadline, so no host primitive — including the one supplying its poll delay — can extend the sequence beyond the bound. An abandoned primitive result MUST NOT be read, recorded, or converted into an absence observation, a signal, an outcome, or an entry mutation, and an audit whose component observations did not all complete MUST NOT be reported as a confirmed release. Termination signal delivery MUST be synchronous and gated immediately before the send, so no cancelled or abandoned continuation can signal any process. The sequencer MUST synchronously observe an already-aborted caller signal on entry and abort itself before any audit, signal, or wait, because a signal aborted before the call never fires a listener registered during it. Every scheduled deadline handle and every abort listener MUST be released on return, so no timer, listener, or unhandled rejection survives the call. The caller-side bound remains the second enforcement point and MUST NOT be the only one.
- Cleanup cardinality MUST be stated and asserted per phase. One claimed generation MUST have exactly one stop-phase termination and at most one stop-phase cleanup audit; two cleanup attempts for one exact owned identity MUST NEVER run concurrently; and no path may terminate or audit an identity again after a cleanup audit confirmed its release. A generation whose stop phase ended unconfirmed, faulted, or deadline-abandoned MUST retain its ownership record and MUST be re-attempted exactly once by the manager-shutdown sweep, which therefore records a second termination and a second cleanup audit phase for that same generation by design; that re-attempt MUST NOT be described, asserted, or validated as an uncontrolled duplicate.
- Manager shutdown MUST re-attempt exact ownership cleanup for a retained ownership record unless a prior cleanup audit for that same exact process identity confirms process, owned process-group, and listener absence. An unconfirmed or missing prior audit MUST NOT suppress that re-attempt.
- Selected stop results MUST be drawn from a bounded documented vocabulary covering a confirmed release, a successful already-stopped no-op, an unresolved project, a project with no manager-owned runtime, a start in progress, a retained failure, an unconfirmed release, and manager shutdown.
- A selected stop request for a persisted project that has no manager-owned runtime MUST return a bounded non-success classification within a finite bound. A manager entry that no confirmed release installed MUST NOT be answered as an already-stopped success. A selected stop request for a project whose runtime this manager released through a confirmed stop MUST return the bounded successful already-stopped no-op within a finite bound, repeatably, and each such repetition MUST create and terminate no runtime identity, MUST require no restart, and MUST leave the entry map, registered metadata, public state, and project fixtures unchanged.
- Concurrent selected stops for one stable project ID MUST join one in-flight release operation and settle with the same result; stops for different stable project IDs MUST never share an entry, operation, claim, cleanup result, or event.
- A selected stop MUST recheck that its exact claimed `stopping` entry is still installed before it installs a terminal entry. A claimant that no longer owns its claim MUST NOT install an entry, MUST NOT emit a lifecycle event, MUST NOT record a further cleanup audit, and MUST NOT report a classified success or failure; because no contract-valid path may replace an installed `stopping` entry before its own settlement, that mismatch MUST be surfaced as an explicit invariant fault. Every normally owned settlement MUST emit exactly one terminal lifecycle event.
- A start requested for a project whose entry is `stopping` MUST fail with a bounded typed failure. It MUST NOT reuse the claimed snapshot, cancel the release, or launch a replacement runtime while the release is in flight.
- A selected stop MUST terminate only the exact ready runtime captured at claim time, after revalidating its root process identity against its recorded process start time. A settled stop MUST NOT terminate, audit, or evict any later replacement generation, any peer project's runtime, or any process outside its own owned group.
- A selected stop MUST NOT change any other project's entry, process identity, listener, route, readiness, public state, failure category, or cleanup audit, and MUST NOT change any process that Ascend does not own.
- Manager shutdown MUST reject new selected stop requests with the bounded manager-shutdown result and MUST await every in-flight selected stop before auditing ownership, so no exact owned identity is ever terminated or audited concurrently by a selected stop and by the shutdown sweep, and so the sweep observes each generation's settled stop-phase audit before deciding whether to re-attempt it.
- Runtime state MUST additionally include `restarting`, which MUST mean that an accepted explicit restart owns that project's generation across both its release phase and its replacement phase. `restarting` MUST be projected as `Starting`, MUST NOT be projected as `Stopped` or `Running`, and MUST NOT widen the four-value public vocabulary.
- A selected project runtime MUST be replaced only through one manager-owned restart operation that accepts a persisted stable project ID and returns a frozen typed result. No route, proxy, browser client, CLI, or other surface may release a generation, launch a replacement, or derive a restart result of its own.
- Restart eligibility MUST be decided from the installed manager entry. A `running` entry and a current-process retained `failed` entry MUST be eligible. An absent entry and a `registered` entry, released or not, MUST return a bounded no-managed-runtime non-success; a `starting` entry MUST return a bounded start-in-progress non-success; a `stopping` entry MUST return a bounded stop-in-progress non-success; an unpersisted project MUST return a bounded not-registered non-success; and a shutting-down manager MUST return the bounded manager-shutdown non-success. A project reported `Stopped` MUST NOT be restarted; it MUST use the existing start flow.
- A retained `failed` entry MUST remain eligible for an explicit restart until a restart succeeds or runtime management shuts down, including after an earlier restart settles unsuccessfully. Its prior owned resources MUST be identified as the single live handle that entry still holds — the one ownership record registered for that entry's generation, or, when no record exists, the one unresolved pending replacement admission that entry references — never as an unbounded set, and never as both at once, because a retained failed entry holds at most one unreleased generation. When the audit confirms all three absences for every such record with no signal delivered, those resources MUST be treated as already absent and the restart MUST proceed. The absence of any ownership record MUST be treated as already absent only when the manager holds no unresolved admission for that project; an entry whose project holds an unresolved admission MUST be classified as pending rather than as absent, and no missing-record shortcut may erase the manager's knowledge of an unresolved launch.
- Restart MUST claim its target with one synchronous compare-and-set on the exact installed eligible entry, with no `await` between reading that entry and installing the `restarting` entry. Concurrent restarts for one stable project ID MUST join that one in-flight operation and settle with the same project and the same result; restarts for different stable project IDs MUST never share an entry, operation, generation, snapshot, failure, or cleanup record.
- An accepted restart MUST confirm release before replacement. Its release phase MUST terminate the exact prior generation through the one termination sequencer, and its gate MUST require that audit to report process absence, owned process-group absence, and listener absence for the complete pre-restart identity. No replacement process may be created, no port acquired, and no launch scheduled before that gate passes.
- An accepted restart MUST hold one `restarting` entry across both phases and MUST NOT install a released `registered` entry between generations. Success MUST install a `running` entry only after the replacement satisfies the documented health-gated readiness contract, and its complete identity MUST differ from the pre-restart identity in at least its process identity and recorded process start time.
- An accepted restart MUST be bounded by declared finite allowances: a release-phase allowance, a replacement allowance that accounts for every configured launch collision attempt, its full readiness window, and its self-bounded cleanup termination rather than one readiness window alone, and a documented settlement allowance for its own claim, gate, sweep, install, emission, and settlement work. The release-phase allowance MUST have exactly two declared variants selected once by one synchronous read at acceptance: the delivered graceful, force, and audit-allowance sum for an ordinary release, and that sum plus a quarantine reclamation allowance of one self-bounded termination per configured launch attempt for a release that must additionally resolve a pending replacement admission. Their sum MUST be the declared overall restart bound for that variant, MUST be positive-safe-integer validated like every sibling bound, and MUST be enforced by one restart-owned deadline armed at acceptance. The larger of the two overall values is the caller-visible restart ceiling, and every client bound, document, notice, and evidence row that states a restart bound MUST state it against that ceiling.
- Every restart deadline MUST be armed by the trusted synchronous scheduling contract — a monotonic clock read and a `scheduleDeadline` call that returns a cancellation handle — and MUST NOT be armed by any fallible awaited primitive, including an injectable `sleep`. A deadline MUST abort its phase with a typed runtime failure carrying an honest bounded category, never with an untyped reason, and MUST cancel its handle on every exit path. Its settlement MUST be phase-aware: a deadline reached before the release-confirmation gate passes MUST settle as an unconfirmed release that launches nothing, and a deadline reached after that gate passes MUST settle as a replacement failure retaining a distinct bounded deadline classification.
- A restart whose release cannot be confirmed within its release bound MUST return an explicit non-success, MUST launch no replacement, MUST NOT report `Stopped` or success, MUST install a retained `failed` entry carrying one bounded restart-release classification, and MUST retain the prior ownership record for the manager shutdown sweep.
- A restart whose replacement startup or readiness fails MUST return an explicit non-success, MUST terminate and audit the replacement's exact identity, MUST remove that ownership record when the audit confirms absence, and MUST install a retained `failed` entry carrying the underlying bounded launch classification. When that cleanup audit completes, no replacement process, owned descendant, listener, timer, or in-flight startup may remain. This rule applies to every launch attempt the replacement phase makes, not only to the last one.
- A restart MUST NOT claim an absence it did not observe. When a replacement was owned but its launch could not be audited within the restart's bound, the settlement MUST record the replacement audit state as unaudited-retained, MUST retain the ownership record registered when the process was owned, and MUST leave exactly one re-attempt to terminate and audit that identity. When the launch had not reported ownership at all, the settlement MUST record the replacement audit state as admission-unresolved and MUST retain its pending admission; it MUST NOT record the replacement as absent, MUST NOT record a replacement cleanup audit, and MUST NOT report zero residuals for that replacement — it MUST publish an explicit null residual count instead. When a launch attempt was terminated but its cleanup audit did not confirm all three absences, the settlement MUST record the replacement audit state as quarantined-unconfirmed and MUST retain that exact identity as a quarantined residual. Each of these three states MUST publish an explicit null residual count rather than any number. No result, event, notice, evidence row, or document may report a residual-free replacement that was never audited, a confirmed absence for a launch that never settled, or a residual-free project holding an unconfirmed quarantined identity.
- Restart cleanup cardinality MUST be stated and asserted per phase: exactly one restart-release-phase termination and at most one restart-release-phase cleanup audit for the prior generation, and at most one restart-replacement-phase termination and cleanup audit per launch attempt, with at most one project-keyed replacement-phase cleanup record written for the whole phase however many attempts it made. A prior generation whose release ended unconfirmed, faulted, or deadline-abandoned MUST retain its ownership record and MUST be re-attempted exactly once by the manager shutdown sweep. Each quarantined late identity MUST receive exactly one termination attempt from the detached continuation that quarantined it and at most one re-attempt, and that re-attempt MUST be claimed by a synchronous compare-and-set on the quarantine record so that the next accepted restart's release phase and the manager shutdown sweep can never both take it and can never run concurrently. A quarantine record MUST be deleted exactly once, and only after an exact audit confirms process, owned process-group, and listener absence.
- A delayed prior-generation release, exit, health, connection, or startup settlement MUST NOT terminate, replace, route traffic to, emit a terminal outcome for, or change the state of a successful replacement. A launch that completes after the restart deadline MUST be terminated and audited rather than installed, and a termination abandoned at its deadline MUST record, mutate, signal, and emit nothing while its late settlement is counted.
- A start requested for a project whose entry is `restarting` MUST fail with a bounded typed failure. It MUST NOT reuse the claimed snapshot, cancel the restart, or launch a second replacement. Every awaited reuse observation whose recheck fails because a restart claimed its generation MUST surface that bounded failure instead of a snapshot.
- A restart MUST record one manager-owned pending replacement admission synchronously, immediately before it invokes the launch primitive and never after it, because the launch primitive reports ownership only after its own awaited process creation resolves and a process may therefore exist before any ownership record does. The admission MUST carry the stable project ID, the restart generation, an opaque deterministic admission identifier, the canonical path and owner token given to the launch, the monotonic admission time, one phase from a fixed vocabulary of launch-pending, materialized-quarantined, absent-confirmed, and audited-absent, one resolution signal, and whether any ownership callback has fired for it. At most one admission MUST exist per stable project ID, and an admission MUST NOT be a manager entry, a runtime snapshot, or any public state.
- A restart that settles while its launch is still in flight MUST leave its admission unresolved and MUST make the retained failed entry it installs reference that admission, so the manager's knowledge of an unresolved launch survives the operation that created it and is reported by entry inspection and by the trusted audit inspection.
- A later accepted restart MUST resolve every unresolved admission for its project inside its release phase and before its confirmation gate may pass. An admission resolved as absent-confirmed MUST record a confirmed absence with no signal attempted and MUST be deleted. An admission resolved with materialized identities MUST let the gate pass only after every quarantined identity carries an exact termination audit reporting process, owned process-group, and listener absence. An admission that does not resolve inside the release bound MUST settle the restart as an unconfirmed release that launches nothing, creates no identity, retains the bounded restart-release classification, keeps the admission unresolved, and references it again from the newly retained failed entry.
- A restart MUST pass restart-scoped launch callbacks rather than reusing the ordinary start callbacks. Before settlement they MUST behave exactly as the start callbacks do. After settlement they MUST write only quarantine state, keyed by the admission identifier together with the exact process identity, process start time, and port tuple rather than by project ID alone. A post-settlement callback MUST NOT mutate the entry map, the project ownership index, the project-keyed cleanup index, any successor snapshot or route, any lifecycle event, or any awaited task set, and MUST NOT be a no-op, because discarding a late ownership report discards the only record of a real host process the manager created.
- After a restart settles, no successor, entry, current-operation ownership record, current-operation cleanup record, or lifecycle event may be mutated by any late work, and exact late-resource quarantine and quarantine cleanup MUST be permitted and performed. A late cleanup audit MUST NOT overwrite the project's current cleanup evidence, and a late ownership report MUST NOT enter the project ownership index.
- An abandoned restart launch MUST be observed by exactly one detached late-settlement continuation that resolves its admission, quarantines and immediately terminates any exact identity the launch materialised, records that exact audit as a quarantine cleanup, and counts the late settlement. A launch that rejects without ever reporting ownership MUST resolve its admission as a confirmed absence with a created-process count of zero. A launch that materialises after manager shutdown returned MUST still be quarantined and terminated by that continuation.
- Manager shutdown MUST sweep quarantined identities alongside owned identities, MUST NOT await any abandoned launch promise, and MUST report every still-unresolved admission explicitly in its result using an opaque project token, the admission identifier, and its phase. A shutdown result MUST NOT report success while it holds an unresolved admission or a quarantined identity whose exact audit did not confirm all three absences.
- A restart-scoped cleanup callback invoked before settlement MUST delete an ownership record by the exact identity its own cleanup audit names, derived from that audit's process identity, process start time, and port, and MUST NOT delete by stable project ID and MUST NOT delete any record the audit does not name. It MUST perform that deletion only when the audit reports process, owned process-group, and listener absence, and only under the same generation guard every other ownership deletion uses.
- A settled successful restart MUST leave exactly one ownership record for its project, regardless of how many launch attempts its replacement phase made, so the next restart of a restart-created generation resolves a single live handle. A restart's release phase MUST terminate exactly one live handle — the installed entry's own runtime handle or the single ownership record registered under a retained failed entry's generation — and MUST NOT terminate any other ownership record the project holds, because a generation created by the ordinary start path may carry a record for a launch attempt that path already terminated and audited. Such a record MUST remain the manager shutdown sweep's responsibility, and no restart may report it as absent.
- A restart-scoped cleanup callback whose audit does not confirm all three absences MUST NOT allow the launch to proceed to a further attempt. It MUST quarantine that exact identity under the manager's existing exact-identity quarantine model with the audited-unconfirmed audit state, MUST record the exact audit as a quarantine cleanup, and MUST abort the operation synchronously with a typed runtime failure carrying its own bounded classification, and MUST retain that exact failure instance for settlement before it passes it to the abort controller. No port may be acquired and no process created for that operation afterwards, on any branch of the launch — whether the launch ends at its own aborted-signal check, by exhausting its attempts, or by rethrowing its own typed failure. Because a launch primitive is not required to forward an abort reason it did not raise, the operation MUST NOT infer this classification from the error the launch rejected with.
- A quarantine record MUST be treated identically regardless of whether a late settlement continuation or a blocked replacement attempt created it: the same record shape, the same audit states, the same single-claim reclamation, the same deletion cardinality of exactly one after a confirming exact audit, and the same manager shutdown sweep behaviour.
- A project holding an uncleared quarantined identity MUST be classified as holding a quarantined residual on every prior-resource classification path, MUST remain eligible for an explicit restart, and MUST NOT have a replacement port acquired or process created for it until every such identity reports process, owned process-group, and listener absence. The release-phase allowance variant that covers quarantine reclamation MUST be selected whenever the project holds an unresolved admission or an uncleared quarantined identity.
- A selected stop requested for a project whose entry is `restarting` MUST return a bounded restart-in-progress rejection without mutating, terminating, auditing, or emitting.
- Restart results MUST be drawn from a bounded documented vocabulary covering one confirmed replacement success and a bounded non-success set for an unresolved project, a project with no manager-owned runtime, a start in progress, a stop in progress, an unconfirmed prior release, a failed replacement, and a shutting-down manager. Prior identity, replacement identity, release mode, and termination audits MUST stay inside the trusted in-process result and MUST NOT reach a public payload, a log record, or a browser surface.
- Restart MUST recheck that its exact claimed `restarting` entry is still installed before it installs a terminal entry. A claimant that no longer owns its claim MUST NOT install an entry, MUST NOT emit a terminal event, MUST NOT record additional cleanup, and MUST surface an explicit invariant fault.
- Manager shutdown MUST reject new restart requests with the bounded manager-shutdown result and MUST await every in-flight restart, as well as every in-flight stop, before auditing ownership, so no exact owned identity is terminated or audited concurrently by a restart and by the shutdown sweep.
- A restart MUST NOT change any other project's entry, process identity, listener, route, readiness, public state, failure category, cleanup audit, or lifecycle evidence, and MUST NOT change any process Ascend does not own.
- Restart MUST NOT run an automatic retry loop, MUST NOT be triggered by navigation, disconnection, health observation, or process exit, and MUST NOT claim that editor or terminal session state survives a replacement.
- A set of public reports MUST be produced in one synchronous pass over the entry map, so reports observed together cannot disagree without an intervening lifecycle outcome.
- A public report MUST disclose only the project identifier, the public state, and a bounded `RuntimeFailureCategory` when the state is `Failed`. Failure diagnostics, PIDs, ports, internal authorities, canonical paths, commands, environment values, credentials, and command output MUST NOT appear in a public report or in any surface rendered from it.
- A consumer that cannot obtain a current public report MUST report that absence explicitly and MUST NOT substitute `Stopped` or any other lifecycle state.
- A consumer that reads public reports separately from its authoritative project list MUST bind each request to one authoritative list revision and MUST reconcile the response against that revision's exact ordered project identifiers. A missing, extra, duplicate, or reordered identifier MUST be treated as projection unavailability for that revision; partial rendering, per-project substitution, and attaching a settled response to a later revision are prohibited.
- Lifecycle transition targets MUST be a declared vocabulary separate from installable entry states and runtime snapshot states, and one explicit mapping MUST project each transition target to its public state. A terminal `stopped` transition target MUST map to public `Stopped` and MUST NOT become an installable entry state or an active snapshot state.
- Every public state transition MUST be announced by exactly one `PRD.md` NFR-015 lifecycle event whose `to` state maps to the new public state; no event may report start success or a healthy observation while that project's public state is `Failed`. Manager shutdown ends the reporting surface itself and is not a reportable public transition.
- Runtime process handles, PID identities, internal ports, in-flight operations, owner tokens, and lifecycle state MUST remain in runtime-manager memory and MUST NOT be persisted with project metadata.
- Registered, starting, running, and failed project lifecycle entries MUST be held in one runtime-manager-owned map keyed only by stable project ID. An exact PID/start-identity/port ownership index MAY exist solely for cleanup, but each record MUST retain its owning stable project identity.
- One active project MUST have at most one Ascend-managed workbench runtime.
- Concurrent starts for one project MUST join one in-flight spawn and readiness operation; starts for different stable project IDs MUST never share an entry, promise, snapshot, failure, or cleanup result.
- A running runtime MUST be reused only while its exact process identity is alive and its documented health check passes.
- Every awaited reuse observation MUST recheck that the exact entry object and generation it observed are still installed before it returns a snapshot or settles a failure. A reuse observation whose generation a selected stop has claimed or released MUST return the bounded stop-in-flight failure and MUST NOT return that generation's snapshot; a reuse observation superseded by another terminal winner MUST return that winner's retained failure; a reuse observation superseded by manager shutdown MUST return the bounded manager-shutdown failure. A superseded reuse observation MUST NOT mutate an entry, terminate, audit, or emit.
- Failed starts and post-running exits MUST be evicted from reusable state; a later explicit start MAY create one replacement, but the manager MUST NOT run an automatic retry loop.
- Runtime launch MUST use the persisted stable project ID and exact stored canonical path, direct argument-vector process creation, a configured non-root user, and loopback-only binding.
- Port selection and binding MUST avoid an unprotected check-then-bind result by delegating binding or applying a documented finite address-in-use retry bound without disturbing unrelated listeners.
- Readiness MUST use a documented status-and-body health contract with finite per-attempt and overall timeouts, recorded attempt timing, and cancellation.
- Caller cancellation MUST end only that caller wait while another caller still waits. When cancellation leaves an in-flight project start with zero waiting callers, the manager MUST cancel and clean that orphaned project-owned start without affecting any other project.
- Manager shutdown MUST be bounded and idempotent, reject new starts, cancel every in-flight project start, gracefully stop every exact owned process group, record project-attributed audits, and escalate only after a finite timeout. A trusted audit inspection MUST independently report entry, exact-ownership, completion-task, background-task, and settlement counts. Shutdown MUST cancel and await tracked promises until their own handlers remove them, MUST NOT clear task sets as settlement proof, and MUST expose immediate plus delayed post-return zero audits so late completion cannot repopulate state. An abandoned operation promise that no bound can force to settle MUST NOT be a tracked promise: it MUST be observed only through a detached late-settlement continuation and MUST NOT be added to any set shutdown drains, so no unbounded host primitive can make a bounded shutdown wait forever. Verification evidence MUST retain real monotonic start, end, elapsed, and configured-bound values for manager shutdown, task settlement, every project cleanup, and delayed post-return observation, and MUST reject any measured duration above its bound.
- Failure, eviction, cancellation, cleanup, or explicit replacement of one runtime MUST NOT change another project's process identity, listener, route, state, or terminal/editor/Git context.
- Invalid transitions, startup failures, health failures, cancellation, shutdown, and process exits MUST surface distinct typed actionable errors with finite diagnostic fields.
- Lifecycle snapshots, failures, diagnostics, and events MUST exclude command, environment, credential, secret, source, terminal, command-output, stack, raw-error, and redaction-sentinel content.
- Structured lifecycle events MUST include stable event names, the same deterministic opaque project token used by workbench proxy events, state transition, elapsed time, and a bounded failure classification when applicable. The one-way token MAY appear in safe logs and declared privacy-safe public evidence; raw project IDs, canonical paths, internal ports/authorities, credentials, and secrets MUST NOT be logged. Browser stable routes separately contain the encoded persisted stable project ID.
- Every immutable running snapshot MUST include its stable project ID, exact PID/start identity, loopback authority, canonical path, stable route, start timestamp, and deterministic opaque owner token; the owner token MUST match lifecycle and proxy attribution for that project and MUST NOT be treated as a credential.
- If runtime state is persisted in a future architecture, it MUST be reconciled with actual processes after backend restart; the memory-only manager instead MUST stop owned runtimes during current-process shutdown.
- Broad catches, silent failures, and success-shaped fallbacks are prohibited.
- A phase whose own operation aborted it with a typed runtime failure MUST be classified from that retained typed reason and never from the error its awaited work rejected with. At settlement the operation MUST read its phase signal first: when that signal is aborted and its reason is a typed runtime failure, that reason's category is the retained failure category and its recorded quarantine determines the replacement audit state, on every branch alike. Only when the phase signal carries no typed reason may the caught error classify the settlement, and when neither exists the underlying fault MUST propagate unchanged. No broad catch, no inspection of an error's message, and no untyped default may stand in for this selection. An abort controller retains the first reason given to it, so precedence MUST be decided by recorded reason identity and never by inferred timing.
- A residual count MUST be able to represent the absence of a claim. Every residual count MUST be published as either an integer zero, meaning a completed exact audit observed the resource absent, or an explicit null, meaning the manager withholds the claim. Null MUST be used exactly where the manager cannot prove absence — an unaudited retained replacement, an unresolved admission, a quarantined unconfirmed identity, an unconfirmed release, or any retained record outside a confirmed absence. A missing field, an omitted property, and a sentinel number are all forbidden representations of a withheld claim. Validation-owned fixture teardown MUST be recorded in its own separate field and MUST NOT be counted, merged, or substituted into a settlement residual claim. **Amended 2026-08-15 (revision 2):** that separate teardown field MUST exist only on an artifact whose scenario actually created host resources, MUST be absent or null until teardown has been attempted, MUST be finalized only from an independent re-observation whose per-class probe completion is recorded alongside each count, and MUST be written atomically so a failed teardown leaves a non-success artifact rather than a preassigned zero. A teardown claim recorded before teardown, or a zero recorded from an incomplete probe, is forbidden.
- Runtime state MUST additionally include `reconciling`, which MUST mean that one bounded API-restart reconciliation owns that project's outcome and has not settled it. `reconciling` MUST be projected as `Starting`, MUST NOT be projected as `Stopped`, `Running`, or `Failed`, and MUST NOT widen the four-value public vocabulary.
- A runtime-management boundary that starts with registered projects it did not launch MUST reconcile them exactly once per instance, before it serves its first request, and MUST install a `reconciling` entry for every registered project synchronously at that point, so a registered project with a possibly live runtime is never reported `Stopped` merely because this boundary has no record of it.
- Reconciliation MUST settle every registered project into exactly one of three outcomes: adopted, absent, or unresolved. Adopted MUST install one `running` entry from an exactly attributed candidate under the delivered readiness contract. Absent MUST install the released `registered` entry and MUST be claimed only from a positive observation as defined by the host-runtime-attribution-evidence contract. Unresolved MUST install a retained `failed` entry carrying one bounded reconciliation classification. An ambiguous, mismatched, unstable, unreadied, incompletely observed, or deadline-abandoned candidate MUST settle unresolved and MUST NOT settle absent or running.
- Reconciliation MUST NOT start, stop, restart, signal, or terminate any workbench, MUST NOT emit a start, stop, restart, or health lifecycle event, and MUST NOT report a success for an action it did not perform. Its own bounded events MUST agree with the public state they claim under the delivered event-to-state agreement check.
- Adoption MUST be the ownership boundary. Before adoption a candidate MUST NOT be signalled, terminated, routed to, claimed, counted as owned, or reported `Running`. After adoption the adopted identity MUST be an owned identity for ownership indexing, stop, restart, proxy-ownership, cleanup, ephemeral runtime-data removal, and shutdown: one ownership record keyed by exact identity under a fresh generation, one frozen running entry and snapshot, and those delivered contracts applied unchanged.
- **Amended 2026-08-15 (revision 2).** An adopted identity MUST NOT be given an automatic death observation. A boundary that adopts a process it did not launch MUST NOT create a background task, timer, interval, watcher, child-signal handler, or periodic health loop for it, and MUST NOT place an adopted handle's terminal promise in a set that shutdown drains. Between adoption and the next on-demand observation the adopted runtime MAY therefore still be reported `Running` after it has died; the boundary MUST correct that state only through its delivered on-demand paths — acquisition liveness and readiness re-checks, the selected-stop initial audit, and the explicit-restart release gate — MUST NOT publish the correction as a reconciliation event, and MUST document the limitation on its user-facing surfaces. A boundary MUST NOT describe an adopted runtime as indistinguishable from a launched one.
- Reconciliation MUST be bounded by one declared finite overall allowance composed of declared discovery, attribution, readiness, and settlement allowances, each positive-safe-integer validated, and MUST arm that deadline through the trusted synchronous scheduling contract rather than any fallible awaited primitive. **Amended 2026-08-15 (revision 2):** when a consumer's externally declared ceiling is measured from an origin earlier than that deadline is armed — for example a replacement process's own start — the internal allowance MUST be strictly smaller than that ceiling, the difference MUST be declared as explicit named segments whose sum is asserted equal to the ceiling, and the reserved startup segment MUST be proven by a measured control rather than assumed. Observations still pending at the deadline MUST be abandoned and MUST NOT mutate an entry, claim an absence, or emit an event.
- **Amended 2026-08-15 (revision 2).** Reconciliation MUST be a required capability of the runtime-management boundary, and its consumer MUST invoke it unconditionally at startup. An optional interface member, an optional invocation, or a presence test that lets startup continue without reconciling is forbidden, because a boundary that silently skips reconciliation serves fabricated state for live survivors while reporting success.
- Exactly one reconciliation MUST exist per manager instance. Public state projection MUST remain synchronous and MUST NOT await it. Workbench acquisition MUST await only its own project's settlement and then follow the settled outcome. Selected stop and explicit restart MUST NOT wait for it.
- A project whose reconciliation is pending MUST answer selected stop and explicit restart with a bounded pre-acceptance classification, MUST leave its public state unchanged, and MUST emit no lifecycle event for the unaccepted action.
- A project whose reconciliation settled unresolved MUST answer selected stop and explicit restart with a bounded unresolved classification, and MUST make workbench acquisition refuse with its bounded reconciliation failure category before any port acquisition or process creation, so no replacement generation may be launched while an unattributable candidate may still be alive. That refusal MUST persist for the life of that manager instance; a per-request re-observation loop is prohibited.
- Manager shutdown MUST abort an in-flight reconciliation, MUST NOT claim an absence it did not observe, MUST NOT signal any unattributed candidate, and MUST leave every unadopted survivor alive and unchanged. Runtimes already adopted before that abort MUST be treated as owned runtimes by the delivered shutdown sweep.
- A late, delayed, or reordered reconciliation, readiness, listener, identity, or absence observation MUST NOT overwrite, terminate, route to, emit a terminal outcome for, or otherwise change the state of a generation installed after it was issued. Every settlement MUST compare-and-set on the exact entry and generation it claimed.

### Interfaces
- Callers request lifecycle operations with a persisted stable project identifier and exact stored canonical path.
- The runtime manager returns typed `starting`, `running`, or `failed` snapshots and typed operation failures; running snapshots expose the stable route and opaque owner token only to trusted in-process consumers, and an in-memory ownership query accepts only the exact immutable snapshot object still installed in the matching running entry.
- The runtime manager exposes a read-only public reporting operation that accepts stable project IDs and returns frozen public reports; it performs no process, port, or health operation and mutates no entry.
- The runtime manager exposes one selected stop operation that accepts a persisted stable project ID and returns a frozen typed result carrying the project identity, a bounded outcome, and a bounded rejection classification when applicable. Graceful-versus-escalated release mode, termination audits, and pre-stop process identity remain trusted in-process values for validation evidence and MUST NOT appear in a public payload, log record, or browser surface.
- The runtime manager exposes one selected restart operation that accepts a persisted stable project ID and returns a frozen typed result carrying the project identity, one bounded outcome, and one bounded non-success classification; its prior-identity, replacement-identity, release-mode, admission, and audit fields remain trusted in-process values.
- The runtime manager exposes its pending replacement admissions and quarantined late identities through entry inspection and through the trusted audit inspection, using opaque project tokens, opaque admission identifiers, and bounded phase values only. Its shutdown result exposes the same bounded shape for every admission it could not resolve. Raw canonical paths, process identities, ports, and loopback authorities MUST NOT appear in any of them.
- Runtime dependencies expose injectable process, port, health, clock, cancellation, event, and exact-identity audit boundaries for finite validation. Graceful-then-force termination sequencing has exactly one implementation, and its host primitives — identity reads, owned-group membership reads, listener probes, delay, signal delivery, clock, and deadline scheduling — are injectable so validation executes that same sequence rather than replacing it. Those primitives fall into two trust classes that MUST be stated wherever they are described. The awaited primitives — identity reads, owned-group membership reads, listener probes, and delay — are treated as fallible: each accepts a cancellation signal as a required parameter, each is expected to settle promptly once it aborts, and none may be trusted to do so. The synchronous primitives — signal delivery, clock reads, and deadline scheduling — return no promise, cannot block the sequence, and are the only primitives the sequencer's bound depends on. Signal delivery MUST return whether the signal was delivered and MUST throw on an unexpected signalling failure, the clock MUST be monotonic, and deadline scheduling MUST remain an independent timer, so the delivery result and the elapsed-time source are two separate trusted contracts rather than one implicit one. Every production primitive set implements both contracts, and no surface may describe the awaited and synchronous primitives as equally fallible or treat an awaited primitive as a deadline source.

### Expectations
- Interleaved repeated starts join only the matching project's in-flight start or reuse only its health-checked running identity.
- Shared-start failure settles every participating caller with the same typed failure and permits one fresh later attempt.
- Stop and shutdown are idempotent where lifecycle semantics allow; a repeated selected stop of a project this manager already released is a bounded successful no-op rather than an error, while a stop request that resolves to no manager-owned runtime is a bounded non-success rather than a success.
- A selected stop reports `Stopped` only after its exact ownership audit confirms process, owned process-group, and listener absence, and reports `Failed` when that confirmation is unavailable.
- An accepted restart reports `Starting` from acceptance until replacement readiness or a terminal failure, never reports `Stopped` between generations, and reports `Running` only after the replacement satisfies the health-gated readiness contract.
- An accepted restart confirms prior process, owned process-group, and listener absence before any replacement process exists, and its replacement carries a distinct complete identity for the same project, canonical directory, and stable route.
- Eight concurrent restart requests for one eligible project join one accepted restart, produce exactly one prior-generation release and one replacement startup, and settle with the same project and outcome inside the declared overall bound.
- Three sequential successful restarts of one project each produce one distinct healthy replacement, and after the sequence no prior identity, attributable descendant, retained prior failure, listener, timer, or in-flight operation remains.
- A restart leaves the project registered exactly once with its stable ID, display name, canonical path, and created-at value unchanged, and leaves declared project fixtures byte-identical.
- A restart of one project leaves every peer project `Running` with the same runtime identity, readiness result, route, connections, and registered metadata, across success, unconfirmed release, and replacement failure alike.
- A restart deadline that fires while the launch primitive has not yet reported ownership settles the caller inside the declared bound, retains an unresolved admission, records the replacement audit state as admission-unresolved, and claims no replacement absence and no zero residual, publishing an explicit null residual count instead.
- An immediately accepted retry of a project holding an unresolved admission is accepted, and its replacement gate does not pass until that admission resolves: as a confirmed absence, or after every identity the abandoned launch materialised is terminated and audited absent. A retry whose predecessor admission never resolves settles as a bounded unconfirmed release inside the release bound and launches nothing.
- A late ownership report after a restart settles is quarantined by exact identity and restart generation, leaves the project ownership index, the entry map, the successor, and the lifecycle event stream unchanged, and is cleared only after one exact audit confirms process, owned process-group, and listener absence.
- A late cleanup audit after a restart settles is recorded under its exact identity and never replaces the project's current cleanup evidence or a successor restart's evidence.
- A restart that survives one or more launch port collisions and then succeeds leaves exactly one ownership record for its project, and the next restart of that project releases exactly one identity with exactly one termination.
- A restart whose launch collision cleanup cannot confirm absence starts no further process, settles as a bounded non-success under its own classification, leaves the unconfirmed identity quarantined by exact identity, and claims no absence, no zero residual — publishing an explicit null residual count instead — and no success; a later restart of that project reclaims that identity inside its release phase before any replacement exists.
- Manager shutdown completes inside its own bound when a restart launch never settles, awaits no abandoned launch promise, enumerates the unresolved admission in its result, and reports a non-success status rather than an unobserved clean shutdown.
- A termination whose host primitive never settles or ignores its cancellation signal — including the primitive supplying the sequencer's poll delay — is abandoned at the sequencer's own trusted-scheduler deadline, settles the selected stop as an unconfirmed release within the documented overall bound, and produces no later signal, audit, mutation, event, surviving timer, or unhandled rejection.
- A termination invoked with an already-aborted caller signal settles immediately as an unconfirmed release without observing, signalling, or waiting.
- An escalating selected stop delivers its force signal no sooner than the full configured graceful period, measured on the monotonic termination clock, after its confirmed delivered graceful signal, and still settles within the documented overall bound; a wall-clock adjustment in either direction during that period changes neither the escalation point nor the overall bound.
- A selected stop whose graceful signal the host reports undeliverable because the owned group is already gone opens no graceful window, records no delivered signal and no escalation, and settles as a confirmed already-absent release only when one bounded settlement audit confirms all three absences; otherwise it settles as an unconfirmed release with retained ownership.
- A selected stop whose force signal the host reports undeliverable settles immediately as an unconfirmed release and is never recorded as an escalation.
- A selected stop whose signal primitive fails unexpectedly settles through the documented termination-fault path and surfaces that failure explicitly instead of reporting an ordinary unconfirmed release.
- A selected stop leaves the project registered exactly once with its stable ID, display name, canonical path, and created-at value unchanged.
- Selected stop, start coalescing, reuse-health observation, process-exit settlement, proxy acquisition, a concurrent same-project stop, and manager shutdown settle as exactly one terminal outcome for the claimed generation, with exactly one stop-phase termination and at most one stop-phase cleanup audit, regardless of contender ordering.
- A reuse observation that settles after a selected stop claimed its generation surfaces a stop-in-flight failure to its caller and to the proxy instead of a released snapshot, in both winner orders.
- An unconfirmed selected release and a faulted selected termination both leave a retained ownership record that manager shutdown re-attempts exactly once, producing a second termination and cleanup audit phase for that same generation, and the shutdown result reports that identity honestly.
- Replacement processes always target the same persisted canonical project directory.
- Cleanup proves exact owned process identity and listener absence without sweeping names or ports.
- The runtime boundary, API response, and browser surface report the same public state for a project observed without an intervening lifecycle outcome.
- One project's start, process, health, or cleanup outcome never changes another project's reported public state or failure category.
- Concurrent false-liveness, health-observation, and exit-settlement contenders for one running project settle as exactly one terminal transition with one retained category, one cleanup audit for that transition, and one emitted event, regardless of contender ordering or delayed loser settlement.

## Rationale

Centralized memory-only lifecycle behavior prevents process handling from leaking into routes and UI code while making concurrency, ownership, failure, recovery, and exact cleanup testable. Caller cancellation preserves shared single-flight work while waiters remain; zero-waiter cancellation prevents an orphaned project startup, and manager shutdown remains the global cancellation boundary for all projects and owned processes. Projecting one public four-state vocabulary from that same memory keeps every surface truthful without adding a second lifecycle authority or a background health loop. Persisted reconciliation remains a future concern until an architecture explicitly introduces persisted runtime identity.

## Usage Examples

```ts
const snapshot = await runtimeManager.start({
  projectId: project.id,
  canonicalPath: project.canonicalPath,
  signal: requestSignal,
})
const [report] = runtimeManager.reportPublicStates([project.id])
const stopResult = await runtimeManager.stop({ projectId: project.id })
await runtimeManager.shutdown()
```

## Integration Guidelines

- Verify the ID and canonical-path pair against persisted metadata before launch.
- Emit bounded structured lifecycle events through the application logger without raw canonical paths.
- Keep process handles, PID identities, internal ports, and lifecycle state out of persistent project metadata.
- Read public state only through the manager's reporting operation and render it without adding, renaming, or inferring a state.
- Request a selected release only through the manager's stop operation, render only its bounded outcome and classification, and read the resulting public state from the manager's reporting operation rather than from the stop response.
- Request an explicit replacement only through the manager's restart operation, render only its bounded outcome and classification, and read the resulting public state from the manager's reporting operation.
- Derive every ownership deletion key from the termination audit that authorises it, so an operation that owns several sequential identities can never delete one it did not audit and can never leave one it did.
- Isolate code-server user data in an opaque runtime-owned ephemeral directory and remove that directory on exit or exact termination.
- Use exact PID/start identity and listener attribution for cleanup evidence; never kill by process name or sweep ports.
- Document health, retry, cancellation, and shutdown bounds beside the runtime-manager interface.
