# Project runtime manager

Issue #25 adds an internal, in-process runtime manager over the persisted four-field project record. BL-016 adds a separate read-only public projection, BL-017 adds manager-owned selected-runtime Stop, and BL-018 adds manager-owned Restart, and BL-019 adds required API-start reconciliation without exposing internal runtime identity.

## Interface and ownership

ProjectRuntimeManager.start({ projectId, canonicalPath, signal? }) validates the exact ID/path pair with ProjectLibrary.findById. It resolves an immutable snapshot with project ID, state, PID and process-start identity, loopback internal URL and port, canonical path, stable route, opaque owner token, startedAt, and elapsedMs. `stop({ projectId })` and `restart({ projectId })` select and claim only that manager entry. inspect(projectId) reports starting, running, or bounded failed snapshot state; absence represents stopped. lastFailure(projectId) returns the retained typed diagnostic. shutdown() owns global cleanup and resolves one memoized status plus an audit row for every retained owned runtime identity and a bounded inventory of unresolved restart admissions.

Process handles, PID identities, ports, in-flight operations, and lifecycle state are memory-only and exist only in manager memory. SQLite remains metadata-only with id, name, canonical_path, and created_at; no migration is required. Snapshots and failures never contain a command, environment, credentials, secrets, source or terminal content, command output, stacks, raw errors, or redaction sentinels.

## Public runtime state projection

The public vocabulary is exactly `Stopped`, `Starting`, `Running`, and `Failed`. A missing or registered manager entry reports `Stopped`; an accepted start or restart before readiness reports `Starting`; running and stopping entries report `Running`; and a retained failed entry reports `Failed` with one bounded category. The internal seven-state entry vocabulary is `registered`, `starting`, `running`, `stopping`, `restarting`, `reconciling`, and `failed`. The seven lifecycle transition targets are `starting`, `running`, `failed`, `stopping`, `stopped`, `restarting`, and `reconciling`; reconciling projects project as `Starting` and `stopped` is a transition target, not a persisted entry or fifth public state. Retained-failure precedence means a completed failure is never replaced by absence or process existence. `reportPublicStates` is a synchronous, read-only manager projection: it performs one ordered entry-map pass and returns only project ID, state, and the `Failed` category. It does not await or call process, port, health, launch, cleanup, audit, or event dependencies.

`GET /api/projects/runtime` lists authoritative persisted projects, applies the same `createdAt ASC, id ASC` order as `GET /api/projects`, and projects all IDs in one synchronous pass. Success is exactly `{"runtimes":[{"id":"stable-id","state":"Stopped"}]}` with `failureCategory` only on `Failed`. Library or projection failure is exactly `500 {"error":{"category":"runtime_state_failed"}}`; no partial or empty success-shaped fallback is returned. `GET /api/projects` remains the unchanged four-field `id`, `name`, `canonicalPath`, and `createdAt` contract.

Project Home owns a monotonic authoritative list revision and makes no runtime request before the first successful list. It issues exactly one request per revision, one per Retry, and one after each successful or already-stopped Stop settlement. It also issues one request after each successful Restart settlement and exactly one per settled successful close; it aborts superseded or unmounted work and has a 5,000 ms projection bound. The response must match the exact ordered project-ID set. Missing, extra, duplicate, or reordered rows make the whole list explicitly unavailable; loading, transport failure, and timeout do the same. No partial state, optimistic state, or `Stopped` fallback is rendered. Failed cards display client-owned category text only, never a server message or protected diagnostic. The browser adds no polling, event stream, or health probe.

## Selected-runtime stop state machine

`POST /api/projects/{id}/runtime/stop` and Project Home Stop delegate to `ProjectRuntimeManager.stop`; neither the stable proxy nor the route performs termination directly. The manager first confirms the persisted project, then resolves one of these bounded cases:

| Selected entry | Result | Manager state and side effects |
|---|---|---|
| no registration | `rejected/not-registered` | unchanged |
| persisted project with no entry, or unreleased `registered` entry | `rejected/no-managed-runtime` | unchanged |
| `registered` released by an earlier confirmed stop in this manager | `already-stopped` | unchanged, no process call or event |
| `starting` | `rejected/start-in-progress` | start continues unchanged |
| `restarting` | `rejected/restart-in-progress` | restart continues unchanged |
| `reconciling` | `rejected/reconcile-in-progress` | reconciliation continues unchanged |
| `failed/reconcile-unconfirmed` | `rejected/reconcile-unresolved` | retained and no process call |
| `failed` | `rejected/failure-retained` | retained category and ownership unchanged |
| `stopping` | joins the installed stop operation | one result, one cleanup phase, no duplicate event |
| `running` | exact synchronous claim before any await | installs `stopping`, then settles confirmed or retained failed |
| manager shutdown begun | `rejected/manager-shutdown` | unchanged |
| close claim installed for this project | `rejected/close-in-progress` | close continues unchanged, nothing is mutated |

The running claim reuses the exact generation, ready runtime, and pre-stop snapshot. No await occurs between reading the running entry and installing the stopping entry. Start and proxy acquisition recheck ownership after every awaited liveness or health observation; if Stop won, they return `runtime-stopping` rather than reuse the claimed snapshot. Stop-versus-exit, health, and false-liveness contenders compare-and-set the exact entry, so exactly one terminal owner mutates, cleans up, and emits; losers remain silent. Concurrent same-project Stop callers join one operation, while peer entries and unrelated controls are untouched.

Confirmed success requires the returned audit to report all three: exact process identity absent, owned process group absent, and loopback listener absent. The release label alone never establishes success. Confirmation deletes that generation's ownership record, installs `registered { released: true }`, and returns `stopped`; later stops of that entry return `already-stopped`. A fresh API process reconciles every persisted project before serving routes. A project proven absent receives a released registration and Stop returns `already-stopped`; a pending or unresolved project receives its distinct reconciliation rejection.

An incomplete or negative audit resolves `rejected/stop-unconfirmed`, installs retained `failed/stop-unconfirmed`, and keeps the ownership record for shutdown. A termination deadline does the same after cancelling the sequencer. A termination fault, including unexpected signal failure, installs the same retained failure but rejects so the route returns `runtime_stop_failed`; no entry remains stuck in stopping. A settlement that no longer owns its exact stopping object raises `RuntimeStopInvariantError`, installs nothing further, records no additional cleanup, and emits no terminal event.

## Termination bounds, signals, and attribution

The production sequencer uses `performance.now()` as its monotonic termination clock. Lifecycle event `elapsedMs` continues to use the manager's existing lifecycle clock; it is not a termination deadline or wall-clock phase measurement. The default bounds are 2,000 ms graceful, 2,000 ms force, and 1,000 ms final audit allowance. The manager's caller-side overall backstop is their 5,000 ms sum.

Four awaited observations are fallible and independently bounded: process-start identity, process-group membership, listener absence, and poll delay. Cancellation is propagated, but a primitive that hangs or ignores cancellation may be abandoned; incomplete observation never becomes absence evidence. The three trusted synchronous primitives are signal delivery, monotonic `now`, and native deadline scheduling. The deadline comes from an independent `setTimeout` scheduler rather than any awaited primitive, so a blocked delay cannot block return. A signal already aborted on sequencer entry causes immediate `unconfirmed` with no identity read, signal, wait, or audit.

Signal delivery returns `delivered`, `refused`, or faults. `ESRCH` is the only refused case and triggers one bounded settlement audit without opening a phase window or escalating. Any other signal error propagates as a termination fault. After confirmed delivered `SIGTERM`, the sequencer allows the complete 2,000 ms graceful window measured from that delivery. Only then may a confirmed delivered `SIGKILL` open its own complete 2,000 ms SIGKILL escalation window measured from that delivery. A refused force signal opens no force window and settles `unconfirmed`. The pre-signal ownership observations have their own bounded allowance; exhaustion is unconfirmed and sends no signal. No signal may occur after caller cancellation, abandonment, or the trusted deadline.

Owned-descendant attribution means membership in the exact root process group. The designated episode samples the complete observable member closure immediately before Stop and records every PID/start identity for independent absence checks. A descendant that escaped with `setsid` or `setpgid` is outside that attribution boundary, so process-group absence is not claimed as proof of arbitrary descendant absence.

Cleanup cardinality is per phase. The selected-stop phase calls terminate once and records at most one completed audit for the claimed generation. Confirmed release removes ownership, so global shutdown repeats nothing. Unconfirmed or faulted release retains ownership, and shutdown intentionally performs one new termination plus one new audit for that exact record; it does not reuse the prior unconfirmed audit and never runs concurrently with the stop phase. No third re-attempt occurs.

The public Stop route accepts an absent body or empty JSON object, rejects operation fields, and has a 1,024-byte body limit. Success is exactly `{"id":"stable-id","outcome":"stopped"}` or `{"id":"stable-id","outcome":"already-stopped"}`. Twelve bounded error categories add `runtime_reconcile_in_progress` and `runtime_reconcile_unresolved`, both HTTP 409, to the delivered invalid ID/request, project, lifecycle, shutdown, and failure categories. Responses contain no public runtime state, release/audit data, PID, port, path, authority, process identity, or server message.

Since BL-020 that route publishes one further bounded category, `runtime_close_in_progress` at HTTP 409, raising the stop vocabulary to thirteen members; the categories above keep their delivered names and statuses. It is returned only while a close claim is installed for the selected project, and the manager rejection behind it is `rejected/close-in-progress`.

## Selected-runtime restart state machine

`POST /api/projects/{id}/runtime/restart` and Project Home Restart delegate exclusively to `ProjectRuntimeManager.restart`. A running entry and a retained failed entry that still owns its exact process identity are eligible. A stopped or unowned persisted project remains an Open concern and returns `runtime_not_managed`; a start or stop already in progress returns its distinct bounded conflict. Exactly concurrent same-project Restart callers join one operation, while different projects use independent browser and manager lanes.

One internal `restarting` entry spans release and replacement and projects publicly as `Starting`; no intermediate `registered` or `Stopped` state is exposed. Replacement launch begins only after the prior exact process identity, owned process group, and listener are all confirmed absent. Success installs one new immutable running generation and returns only `{"id":"stable-id","outcome":"restarted"}` publicly. The route has the same strict absent-or-empty body contract and 1,024-byte body limit as Stop. Its twelve client-visible errors add `runtime_reconcile_in_progress` and `runtime_reconcile_unresolved`, both HTTP 409, to the delivered ten categories. The nine manager rejection categories are `not-registered`, `no-managed-runtime`, `start-in-progress`, `stop-in-progress`, `release-unconfirmed`, `replacement-failed`, `manager-shutdown`, `reconcile-in-progress`, and `reconcile-unresolved`.

Since BL-020 the restart route publishes `runtime_close_in_progress` at HTTP 409 as well, raising its vocabulary to thirteen members, and the manager rejection vocabulary to ten by adding `close-in-progress`. Restart is refused that way only while a close claim is installed for the selected project, and the refusal mutates nothing.

The trusted Restart clock uses the `RuntimeDeadlineScheduler` monotonic clock and native deadline scheduling, never the fallible process delay dependency. Production bounds are 5,000 ms for ordinary release, 15,000 ms for quarantine reclamation, 20,000 ms for admission/quarantine release, 60,000 ms for replacement, and 1,000 ms for settlement. The normal manager bound is 66,000 ms, the admission/quarantine bound is 81,000 ms, and the browser transport bound is 85,000 ms.

A pending replacement admission is installed synchronously immediately before launch. It prevents a deadline or retry from interpreting a launch whose process handle has not yet materialized as proven absence. Late materialization is keyed by admission ID plus exact PID, process-start identity, and port; detached observation may mutate only admission and quarantine state. It cannot install a successor snapshot, route, event, or project-keyed cleanup.

Restart launch cleanup is identity-keyed. A confirming collision or failed-attempt cleanup deletes exactly that attempt. A non-confirming cleanup moves that identity to quarantine and aborts the phase with `restart-replacement-unconfirmed`; the manager reads that typed phase abort before the launch error, including readiness-timeout and last-attempt collision branches. A successful collision retry leaves one ownership record for the healthy replacement.

Evidence uses `residualCount: 0` only after an exact completed audit proves the relevant process, group, and listener absent. `residualCount: null` is mandatory for an unresolved admission, unaudited retained identity, uncleared quarantine, or any other state where the manager cannot make an absence claim. Validation-owned fixture teardown is reported separately as integer `teardownResidualCount: 0` and never upgrades manager uncertainty into success.

Project Home shows Restart only for authoritative `Running` or `Failed` rows. The selected card is busy and its Open, Stop, Restart, and Close controls are disabled while its Restart is pending; another project remains independently usable. Successful settlement announces completion, performs exactly one authoritative runtime refresh, and returns focus to the selected Restart control after that refresh remounts it. Classified failures use client-owned Retry text. Timeout, abort, invalid JSON, and other indeterminate transport results remain explicitly unknown and offer only authoritative runtime-state refresh.

## Selected-project close state machine

`DELETE /api/projects/{id}` and Project Home Close delegate to `ProjectRuntimeManager.close`, which is the single authority for a running or failed project close. The close service composes three callables and owns no ordering of its own: `drainConnections` from `WorkbenchProxyManager.closeProject(id, signal)`, the synchronous `auditConnections` thunk over `WorkbenchProxyManager.audit(projectToken)`, and `commitRemoval` from `ProjectLibrary.closeProject(id)`. The body of that `commitRemoval` callable is the only construction point for durable registration removal in the repository; no route, browser client, or lifecycle path reaches it directly. Persistence keeps its delivered serialized tail, its single transactional delete, and its two-member result vocabulary.

Close admission evaluates in exactly this order after `findProjectById` resolves, and the order is the contract:

| # | Condition | Outcome |
|---:|---|---|
| 1 | manager shutdown has begun | `rejected/manager-shutdown` |
| 2 | persisted project absent | `already-absent` |
| 3 | a close claim is installed for this project | joins that claim and derives its outcome |
| 4 | entry state `reconciling` | `rejected/reconcile-in-progress` |
| 5 | entry `failed` classified `reconcile-unconfirmed` | `rejected/reconcile-unresolved` |
| 6 | entry state `starting` | `rejected/start-in-progress` |
| 7 | entry state `restarting` | `rejected/restart-in-progress` |
| 8 | entry state `stopping` | `rejected/stop-in-progress` |
| 9 | entry absent, `registered` in either released value, `running`, or non-reconcile `failed` | claim, freeze the ownership cardinality, and run the phases |

Steps 1 through 8 settle before the claim exists, so they are the eight pre-claim settlement sites `manager-shutdown`, `persisted-absence`, `contender-join`, `reconcile-in-progress`, `reconcile-unresolved`, `start-in-progress`, `restart-in-progress`, and `stop-in-progress`. A settled category never identifies a site by itself: `manager-shutdown` is also returned by the in-phase shutdown re-reads, `already-absent` is also returned by a confirmed release whose removal reports `project_not_found`, and a contender inherits the winner's bounded rejection verbatim. Evidence therefore discriminates admission by site rather than by category. A contender performs no drain, release, removal, mutation, or emission: a winning `closed` gives the contender `already-absent`, so eight concurrent closes of one running project produce one `200` and seven `404` responses and exactly one `project.closed` record.

Step 9 is one synchronous section. It reads the entry, installs the claim with no intervening await, captures the claimed entry by reference, and freezes the project's ownership-record cardinality and quarantine cardinality. `sweepUnits` is `max(1, frozenOwnershipCardinality)`; a frozen count above `closeOwnershipSweepCap` settles immediately as `rejected/ownership-cardinality-exceeded` with no drain, no signal, no termination, no removal, no retained failure, and no lifecycle event, leaving the entry, ownership records, and all four persisted fields exactly as found.

While a claim is installed for a project, `start` throws `runtime-closing`, `register` refuses without mutating and throws `runtime-closing`, and `stop` and `restart` return `rejected/close-in-progress`; every path for a peer project is unaffected. One head refusal is not sufficient, so the claim is re-evaluated after every await on the acquisition and join seams — after the persisted lookup, after reconciliation waiting, after a starting-join resolves, after the liveness observation, after the health observation, and immediately before a reused snapshot is returned. A refusal raised at those seams mutates nothing: it installs no entry, registers or revives no ownership, creates no pending admission, mints no generation, and returns no snapshot, so it is accounted as a refused acquisition and never blocks confirmation.

An admitted close runs seven phases under one overall deadline armed from the trusted deadline scheduler:

1. **Drain.** `drainConnections(signal)` under one `closeDrainAllowanceMs` deadline shared with the single re-drain phase 5 may perform.
2. **Resolve admissions and quarantine.** Reclaim the project quarantine, then await any installed replacement admission, finishing it when its phase is `absent-confirmed` or `audited-absent`.
3. **Release the attributable owned runtime** through the delivered termination sequencer, recording exactly one close-phase cleanup audit for that generation.
4. **Sweep remaining ownership.** Every remaining ownership record for the project is accepted when a recorded audit already confirms its triple, and is otherwise terminated and audited under the same sequencer.
5. **Verify zero residual by re-observation.** `auditConnections()` is read synchronously; a non-zero count permits exactly one further `drainConnections` under the drain deadline still in force, and then one re-observation.
6. **Remove.** `commitRemoval()` is the next statement after the confirmation region, with no await, branch, or other call between the last observation and it.
7. **Retire.** Delete the entry, delete its cleanup outcomes, release the claim, and record the project in the retirement set.

One close performs at most two `drainConnections` and at most two `auditConnections` calls. Draining precedes releasing so no proxy operation is waiting on an acquisition the claim already refuses; removing is last so the durable registration is the last thing to disappear.

Removal is invoked only when all eight confirmation clauses hold, read in one uninterrupted synchronous region: re-observed connections (`pendingOperations`, `upstreamHttpRequests`, `upstreamHttpResponses`, `rawSockets`, and `webSockets` all zero for this project's token), no remaining ownership record, no remaining quarantined identity, no pending admission, no in-flight lifecycle work for this project, a confirmed release audit for every generation this close terminated, generation identity, and the project not already retired. Generation identity is a reference comparison against the entry value captured at claim install, including the absent case, so a close that claimed an absent entry and finds one installed at confirmation fails closed instead of removing a registration. In-flight lifecycle work is discharged only from project-keyed state — the entry being absent or non-transient, no pending admission for the project, and the claim's identity-bearing late-work counter at zero — never from the unkeyed global stop and restart task sets, so a peer project's in-flight stop cannot block confirmation and this project's own suspended acquisition cannot pass it.

The confirmation-to-removal window is sealed rather than accounted. The claim's seal is set as the last statement of the confirmation region, immediately before removal. While it is set, every entry install for that project is refused, including the owning close, and an ownership registration for that project records a quarantined identity instead of entering the ownership index, so the identity stays reachable by the shutdown sweep. The seal is lifted in exactly one place — the `removal-failed` branch, immediately before the released `registered` entry is installed. The successful branch never lifts it, because retirement supersedes it.

After a confirmed removal the project is retired. Every entry-installing site consults the retirement set and the claim map before writing: a site that finds a retired project installs nothing, mutates nothing, emits nothing, records no cleanup, and settles a caller-visible acquisition with `unknown-project` while a continuation with no caller is accounted as a late close settlement. A stable project ID is never reissued after its row is deleted, so the retirement set never needs to expire.

A close emits exactly one `project.closed` operational record per completed close and no stop, restart, start, or reconciliation lifecycle event. It emits exactly one `runtime.health.changed` classified `close-release-unconfirmed`, and only when it installs that retained failure for an exact `running` entry it claimed; a retained `failed` entry that stays failed emits nothing because no transition occurred. Rejections, joined contenders, `already-absent`, `removal-failed`, and `ownership-cardinality-exceeded` emit no lifecycle event, and the lifecycle event catalog is unchanged.

`runtime-closing` is an acquisition failure only. No site installs it as an entry failure category and the public projection maps it nowhere; it reaches callers through the workbench failure table and the route mapping. `close-release-unconfirmed` is the one new category a close can retain on an entry, and it projects publicly as `Failed`.

## Close configuration, bounds, and settlement

Three internal configuration members are added, all validated as positive safe integers by the delivered resolved-configuration loop and all rejected when overridden with zero, a negative, or a non-integer. They are internal manager settings with fixed defaults: they are not environment variables, deployment settings, feature flags, or persisted values, and no operator action is required.

| Member | Default | Meaning |
|---|---:|---|
| `closeDrainAllowanceMs` | 5,000 ms | one deadline covering both permitted drains |
| `closeSettlementAllowanceMs` | 1,000 ms | settlement, retirement, and response |
| `closeOwnershipSweepCap` | 4 | maximum ownership records one close may sweep |

Two derived bounds are cardinality-aware. `runtimeCloseReleaseBoundMs` is the quarantine reclamation allowance when quarantine resolution is required plus `sweepUnits` multiplied by the ordinary stop bound; `runtimeCloseOverallBoundMs` adds the drain allowance and the settlement allowance to it. Both reject a `sweepUnits` that is not an integer within one and the configured cap, so the multiplier is never an unvalidated observed count. At the delivered defaults the overall bound is 11,000 ms for one record without quarantine resolution, 26,000 ms for one record with it, 16,000 ms for two records, 26,000 ms for four records without it, and 41,000 ms at the sweep cap with it. That 41,000 ms value is the caller-visible ceiling, and the browser close transport bound of 45,000 ms strictly exceeds it. Every close deadline — overall, drain, release, and each phase deadline inside the termination sequencer — is armed from the trusted deadline scheduler on its monotonic clock; no fallible awaited delay primitive paces a close phase.

Every terminal case settles explicitly:

| Terminal case | Entry after | Ownership | Registration | Public state | Outcome |
|---|---|---|---|---|---|
| confirmed release, removal reports closed | deleted and retired | none | removed | no row | `closed` |
| confirmed release, removal reports the project already absent | deleted and retired | none | already absent | no row | `already-absent` |
| confirmed release, removal throws | `registered` released | none | present, four fields unchanged | `Stopped` | `rejected/removal-failed` |
| release unconfirmed from a `running` entry | `failed` classified `close-release-unconfirmed`, one `runtime.health.changed` | retained | present, four fields unchanged | `Failed` | `rejected/release-unconfirmed` |
| release unconfirmed from a retained `failed` entry | `failed` classified `close-release-unconfirmed`, no event | retained | present, four fields unchanged | `Failed` | `rejected/release-unconfirmed` |
| frozen ownership cardinality above the sweep cap | unchanged | retained, unchanged | present, four fields unchanged | truthful, unchanged | `rejected/ownership-cardinality-exceeded` |
| admission-order rejection | unchanged | unchanged | present | truthful | `rejected/<category>` |
| persisted absence | unchanged | unchanged | absent | no row | `already-absent` |

The eleven terminal results are the distinct settled pairs: `closed`, `already-absent`, and the nine rejection categories `start-in-progress`, `stop-in-progress`, `restart-in-progress`, `reconcile-in-progress`, `reconcile-unresolved`, `release-unconfirmed`, `ownership-cardinality-exceeded`, `removal-failed`, and `manager-shutdown`. No terminal case leaves a claim installed, an entry in a transient state, or a registration absent with an unconfirmed resource. A project with no owned runtime — no entry, a released `registered` entry, or a retained `failed` entry whose ownership record is already gone — is removed with no signal sent and no process or listener probed, which is the delivered stopped-project behaviour unchanged. A close that faults for any other reason aborts its deadlines, settles the entry exactly as an unconfirmed release, releases the claim, and surfaces the fault; the route reports `500 project_close_failed` and never a success-shaped body.

Manager shutdown awaits every in-flight close before it sweeps ownership or deletes entries, exactly as it already awaits stops and restarts, and settles an in-flight close explicitly as `manager-shutdown` rather than leaving a claim behind.

## Close recovery and interruption

Three close rejections leave work for an operator or a later request, and each has one safe recovery:

| Rejection | What is true afterwards | Safe recovery |
|---|---|---|
| `release-unconfirmed` (`500 runtime_release_unconfirmed`) | the registration and its four fields are intact, the entry is retained `failed` classified `close-release-unconfirmed`, the project reports `Failed`, and its ownership record is retained for the shutdown sweep | retry Close after the workbench settles, or stop the API so its shutdown sweep performs the one retained termination and audit; a replacement API then reconciles the project from current host evidence |
| `removal-failed` (`500 project_close_failed`) | the runtime release was confirmed, the entry is `registered` released, the project reports `Stopped`, and the registration is still present with four unchanged fields | retry Close; no runtime work remains, so the retry removes the registration alone |
| `ownership-cardinality-exceeded` (`500 runtime_close_ownership_unresolved`) | nothing was attempted: entry, ownership records, quarantine, registration, and public state are exactly as they were | resolve the retained ownership first with Stop or Restart, then retry Close; raising `closeOwnershipSweepCap` is a configuration change, not a recovery step |

A close is safe to interrupt at any point because the durable removal is last and is dominated by the confirmation region. An interruption strictly before confirmation — during release or the ownership sweep — leaves the registration present, performs no durable removal, and delivers no signal that the interrupted close had not already delivered. The replacement API then settles the surviving candidate through the unchanged one-shot reconciliation conjunction: an exactly attributable, ready survivor is adopted and reports `Running`; a candidate whose attribution or readiness cannot be proven is retained `failed` classified `reconcile-unconfirmed` and reports `Failed`. Neither positive absence nor `Stopped` is reachable while a survivor is alive, because either would require an absence observation the live listener contradicts. A safe Close retry then settles on whichever branch the boot produced: it closes the adopted survivor, or it refuses with `reconcile-unresolved` while retaining the registration and sending no signal. An interruption after the confirmation region either committed the removal or did not; both are observable on the replacement boot, and a repeated close of a removed project is a bounded `404 project_not_found` with no side effect.

## Guarded terminal transition

False liveness, a failed completed health observation, and post-readiness process exit all contend through one guarded `running -> failed` compare-and-set on the exact entry and generation before cleanup awaits. The winner installs one category, performs one terminate or already-absent audit, records one cleanup, and emits one `runtime.health.changed`. A loser does not mutate, terminate, audit, or emit and reuses the winner's retained failure. Cleanup rejection surfaces after that single event without changing category or adding an event. Manager shutdown remains a non-reportable suppression.

The four reportable failure causes are start failure before readiness, post-readiness exit, failed completed health observation, and false-liveness observation. The first emits `runtime.start.failed`; the three post-readiness paths emit `runtime.health.changed`. A success or healthy event is never emitted after the project has entered `Failed`.

## Launch and readiness contract

The default executable is /home/vscode/.local/bin/code-server, and the configured user is non-root vscode. Construction accepts explicit executable, user, deterministic environment allowlist, and finite bound overrides for tests or a designated deployment. Launch writes stderr to a mode-0600 `runtime-stderr.log` in the ephemeral runtime-data directory and passes that file descriptor directly to the detached child, so API death does not close the child diagnostic sink. Launch uses direct argument-vector process creation, a canonical working directory, a detached owned process group, a 127.0.0.1 manager-selected port, and the exact stored canonical directory once as the final argument. No shell interpolation occurs.

Port reservation is loopback-only. The unavoidable reservation-to-child-bind race retries address-in-use at most three times with a fresh candidate and exact owned-group cleanup; unrelated listeners are never closed, rebound, or signalled.

Readiness polls GET /healthz/. Only HTTP 200 plus JSON status equal to alive or code-server's healthy-idle expired state is accepted. Transient mismatches remain non-ready and are polled only within the total bound; the last observed status or body mismatch becomes its distinct typed failure if readiness never succeeds. Each request is bounded to 1,000 ms, polling is 50 ms, and total readiness is 15,000 ms. Attempt timing is retained finitely. Readiness uses cancellation, never a fixed startup sleep.

Exactly concurrent starts for one project join one launch/readiness promise. A later start reuses the same PID identity and port only when the exact process remains alive and the health contract passes. Failed starts are evicted and permit an explicit fresh retry. A post-running exit retains one bounded code-or-signal failure, evicts reuse state, and starts no automatic retry.

Caller cancellation ends only that caller’s wait while other waiters remain. When the last waiter cancels, the manager aborts and cleans only that orphaned project start. Manager shutdown remains the global cancellation boundary.

## Typed failures

The 19 closed categories are unknown-project, canonical-path-invariant, spawn-error, executable-missing, early-exit-code, early-exit-signal, address-in-use-exhausted, readiness-timeout, health-status-unexpected, health-body-unexpected, caller-cancelled, manager-shutdown, stop-unconfirmed, runtime-stopping, restart-release-unconfirmed, restart-deadline-exceeded, runtime-restarting, restart-replacement-unconfirmed, and reconcile-unconfirmed. Their fixed safe messages direct callers to refresh or register the project, install or correct code-server, release listeners, check host capacity, start again, retry after lifecycle settlement, or restart Ascend as appropriate.

BL-020 appends two more, taking the closed vocabulary to twenty-one: `runtime-closing`, whose message asks the caller to wait for the close to settle before retrying, and `close-release-unconfirmed`, whose message asks the caller to retry after the runtime manager reconciles the workbench. `close-release-unconfirmed` is the only one of the two a close can install on an entry, and it projects publicly as `Failed`. `runtime-closing` is raised as an acquisition failure only: no site installs it as an entry failure category, so it is never retained and never projected, and callers see it through the workbench failure table or the route mapping instead. Neither message contains a path, identity, port, authority, command, or raw error.
