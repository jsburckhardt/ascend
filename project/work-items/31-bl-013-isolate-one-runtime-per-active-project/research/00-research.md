# Research Brief: BL-013: Isolate one runtime per active project

## GitHub Issue
- **Issue:** #31
- **Title:** BL-013: Isolate one runtime per active project
- **Work Item:** project/work-items/31-bl-013-isolate-one-runtime-per-active-project

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Ascend has evidence for host capacity, one managed project runtime, stable proxy transport, and one-project browser navigation, but it does not yet establish independent simultaneous workbenches for three registered projects. Issue #31 is bounded to immediate A/B/C runtime, route, filesystem, terminal, editor, Git, failure, cancellation, shutdown, event-attribution, privacy, and cleanup isolation. It explicitly excludes session-switching continuity, performance targets, public Stop/Restart, API-restart reconciliation, scheduling, quotas, multi-host support, and public authentication.

## Acceptance Criteria

**Core**
- [ ] The runtime manager can hold registered, in-flight, running, and failed entries for at least three projects simultaneously, keyed only by each project’s stable ID.
- [ ] Each running project snapshot contains that project’s OS PID and process start identity, loopback port, canonical path, stable route, start timestamp, and owner token. The identity tuple for each of A, B, and C is distinct from the other two.
- [ ] Concurrently starting projects A, B, and C with eight interleaved calls per project (24 calls total) produces exactly three spawn-and-readiness sequences. Each caller receives the same snapshot as other callers for its own project and never receives a promise, result, or state from another project.
- [ ] For each of A, B, and C, the observed launch arguments, working directory, user, and environment correspond to that project’s canonical directory and do not contain another fixture’s project-specific values.
- [ ] Three disposable fixtures with distinct sentinels, Git repositories, branches, status, and configuration produce matching project-specific Explorer files, `pwd -P`, `git rev-parse --show-toplevel`, branch/status, terminal output, and editor-visible sentinel for all three projects.
- [ ] Proxy HTTP requests and WebSocket upgrades for A, B, and C are resolved from the matching project’s immutable runtime snapshot, remain under that project’s stable route, and reach only that project’s upstream loopback port.
- [ ] Persisted project data remains limited to the existing four metadata fields. Runtime state, ports, PIDs, handles, owner tokens, and unique runtime-only canaries are absent from the SQLite schema and from a byte scan of the disposable database, and runtime fields remain absent from public list and registration responses.
- [ ] For each bounded A/B/C concurrency, failure, replacement, cancellation, and shutdown scenario, the lifecycle and proxy records required by the existing event taxonomy carry the matching stable opaque project token plus an allowed event, state, and elapsed classification; expected records and counts are asserted so an empty event stream fails.
- [ ] The bounded event records expose none of the fixtures’ unique raw canonical paths, internal ports, commands, environment values, terminal or Git content, source sentinels, or seeded secret-like values.

**Edge Cases**
- [ ] Reopening or retrying a project that satisfies the existing running-runtime readiness and health checks reuses only that project’s OS PID and process start identity, port, and start time and never reuses another project’s runtime.
- [ ] An unknown, malformed, or closed project ID fails without changing any running project’s snapshot, process, listener, route, or event attribution.
- [ ] A finite cross-project matrix covering each ordered A/B/C mismatch for project ID and route path, HTTP upstream target, WebSocket upstream target, and WebSocket frame destination is rejected or fails closed without reaching the nonmatching runtime. Internal ports remain loopback-only and absent from public surfaces.
- [ ] One project’s injected early exit, crash, readiness failure, health failure, or proxy failure produces its existing typed failed or evicted outcome only for that project. The other two projects retain the same OS PID and process start identities, ports, listeners, routes, and successful terminal checks.
- [ ] After one project fails, one bounded replacement start creates exactly one new runtime identity for that project without changing its peers, and no automatic retry loop occurs.
- [ ] When all eight callers for B cancel before B becomes ready during bounded simultaneous A/B/C starts, each B caller receives the existing cancellation outcome, B’s owned process is cleaned, and all A and C callers complete with their respective snapshots.
- [ ] During bounded simultaneous A/B/C starts, cancelling one of B’s eight callers gives that caller the existing cancellation outcome while the seven remaining B callers share one B snapshot from exactly one B spawn; A and C callers and snapshots are unaffected.
- [ ] Global manager shutdown cancels and cleans every owned project within the existing configured shutdown deadline, records one audit result per project, and leaves a scenario-created unrelated listener or process untouched. No per-project public stop or restart operation is added.
- [ ] A finite shutdown-race matrix covers a second global shutdown plus one start attempted during shutdown and one after shutdown. Each call receives the existing typed shutdown outcome, no new owned runtime survives, and the unrelated listener remains untouched.

**Verification**
- [ ] A deterministic fake matrix produces inspectable pass/fail evidence for the 24-call concurrency result, the five project-specific failure classes, all-callers cancellation, one replacement, early exit, the finite proxy cross-target matrix, event attribution and redaction, global shutdown, and zero residual owned resources.
- [ ] A repository contract guard rejects global singleton runtime fields and runtime maps keyed by project path or name instead of stable project ID.
- [ ] A real Chromium scenario registers three disposable Git fixtures, starts and navigates each stable route, and keeps all three runtimes active concurrently. It proves distinct runtime identities, ports, and routes plus project-specific Explorer, `pwd -P`, Git repository/branch/status, terminal output, and editor sentinel; repository-local test authority then injects B’s runtime termination without a public lifecycle operation, proves A and C retain their recorded values and pass terminal checks, and proves one explicit start replaces only B’s identity.
- [ ] Retained machine-readable evidence gives a pass/fail result and correlates all three runtime identities, stable routes, terminal/Git/sentinel results, B failure and replacement, unchanged A/C values, browser and network sockets, events, cleanup, and fixture integrity. Public evidence redacts internal ports and canonical paths; any raw authority evidence uses the repository’s verified restricted-artifact mode and ignore policy.
- [ ] Cleanup closes every browser, proxy socket, runtime, process group, listener, API/web service, database/sidecar, terminal command, and fixture created by the scenario. Per-project and global residual audits report zero scenario-owned residuals, the scenario-created unrelated listener survives until its own cleanup, and fixture integrity checks pass before fixture removal.
- [ ] Documentation records per-project runtime ownership, concurrency, reuse, isolation, failure containment, proxy and event boundaries, repeatable validation commands, fixtures, injected faults, cleanup, and observed results; it explicitly defers BL-014, BL-015, and lifecycle features.
- [ ] `just verify` completes successfully, including existing one-project runtime, stable-route, navigation, and capacity regressions.
- [ ] All designated verification and evidence generation is repeatable with repository-local fixtures and commands and requires no network access, hosted service, production resource, credential, or manual judgment.
- [ ] Real browser evidence makes no BL-014 session-switching or session-persistence claim beyond immediate isolation while all three projects are running.

## Repository Findings

- **Product requirements:** `PRD.md` FR-011 and AC-016 require a Project A process to continue while Home or Project B is active; FR-012 and AC-017 require independent VS Code and terminal state. NFR-003 requires at least three simultaneous sessions, and NFR-004 requires one code-server failure not to terminate or corrupt another runtime (`PRD.md:532-551`, `PRD.md:657-673`, `PRD.md:1137-1154`).
- **BL-004 capacity dependency:** The accepted Issue #11 record reports a direct-host diagnostic rather than application runtime isolation (`project/work-items/11-bl-004-establish-the-workbench-capacity-baseline/implementation/00-implementation.md`). Retained run `853037e6-5dab-43cf-bcf8-61f1e8bbdb18` contains ordered 1/3/5/10 cohorts; the three-member cohort has 3 ready runtimes on 3 distinct ports, a passed gate, passed cleanup, and passed fixture integrity (`project/work-items/11-bl-004-establish-the-workbench-capacity-baseline/implementation/evidence/853037e6-5dab-43cf-bcf8-61f1e8bbdb18/run.json`). Its scope expressly excludes BL-013 outcomes.
- **BL-010 runtime dependency:** `createProjectRuntimeManager` owns separate `inFlight`, `running`, `failed`, `failureOutcomes`, and `cleanupOutcomes` maps keyed with `input.projectId`; process ownership is separately keyed by PID/start-time/port identity (`apps/api/src/project-runtime-manager.ts:107-125`). `start` performs persisted ID/path validation before reuse or joining, installs the in-flight entry before callers receive the operation, freezes starting/running/failed snapshots, health-checks an existing exact process before reuse, and evicts an unhealthy or exited generation (`apps/api/src/project-runtime-manager.ts:137-327`). `inspect`, `lastFailure`, and `lastCleanup` are project-ID lookups (`apps/api/src/project-runtime-manager.ts:430-446`).
- **Current snapshot boundary:** `RuntimeSnapshot` currently contains project ID, state, PID, process start time, internal URL, port, canonical path, start timestamp, and elapsed time (`apps/api/src/project-runtime-contract.ts:6-16`). It does not contain a stable route or a field named owner token. Repository search found no `ownerToken`, `owner_token`, or `owner token` symbol. The stable route is separately derived from the route project ID by `parseStableWorkbenchRoute`, while `tokenizeWorkbenchProjectId` creates a deterministic one-way token only for serialized proxy events (`apps/api/src/workbench-proxy-contract.ts:173-190`, `apps/api/src/workbench-proxy-contract.ts:337-369`).
- **Launch, path, and host process behavior:** `buildRuntimeArgv` binds `127.0.0.1`, disables generic proxying, and places exactly the canonical project path as the final argument. `nodeRuntimeProcessAdapter.launch` uses direct `spawn`, `cwd: canonicalPath`, a detached process group, the manager configuration environment, and the current configured non-root user check (`apps/api/src/project-runtime-process.ts:218-323`). PID identity comes from Linux `/proc/<pid>/stat`; exact process group and listener audits govern termination (`apps/api/src/project-runtime-process.ts:83-198`). The environment is manager configuration, not a per-project object, while path-specific launch values are the working directory and final argument (`apps/api/src/project-runtime-contract.ts:127-184`).
- **Existing concurrency and lifecycle evidence:** Current runtime tests establish eight-call single-flight and identity equality for one project, one-caller cancellation with a continuing caller, shared failure and retry, post-running exit replacement, manager-wide in-flight cancellation, idempotent shutdown, and exact owner termination (`apps/api/test/project-runtime-manager.test.ts:97-323`, `apps/api/test/project-runtime-lifecycle.test.ts:54-262`). The retained BL-010 matrix has 25 execution records, including those cases, and a 17-identity union residual count of zero (`project/work-items/25-bl-010-start-and-reuse-one-project-workbench/implementation/evidence/fake-matrix.json`). The designated episode proves one real PID/port reuse and exact cleanup (`project/work-items/25-bl-010-start-and-reuse-one-project-workbench/implementation/evidence/episode.json`). These artifacts do not contain an interleaved three-project manager episode.
- **Proxy target and route boundary:** Every HTTP request or WebSocket upgrade resolves its project with `ProjectLibrary.findById`, calls `ProjectRuntimeManager.start` using that persisted ID/path, and derives a loopback target from the returned snapshot (`apps/api/src/workbench-proxy-manager.ts:351-374`). `safeTarget` verifies running state and agreement between `internalUrl` and `port`, but does not independently compare `snapshot.projectId` or `snapshot.canonicalPath` to the resolved project (`apps/api/src/workbench-proxy-manager.ts:139-155`). HTTP and WebSocket handlers use the parsed route prefix/path and selected loopback port; client target, forwarding, host, and authority headers cannot select upstreams (`apps/api/src/workbench-proxy-manager.ts:388-579`, `apps/api/src/workbench-proxy-manager.ts:713-840`). Proxy resources are global in-memory sets of operations, streams, sockets, and WebSockets rather than per-project inventories (`apps/api/src/workbench-proxy-manager.ts:290-327`).
- **BL-011 evidence boundary:** Existing proxy coverage includes byte streaming, WebSocket behavior, the 23-row failure table, one-project four-HTTP/four-upgrade startup coalescing, redaction, and shutdown (`apps/api/test/workbench-proxy-http.test.ts`, `apps/api/test/workbench-proxy-websocket.test.ts`, `apps/api/test/workbench-route-acceptance.test.ts`). Its real Chromium scenario performs three fresh workflows against one project and reuses one runtime, yielding three Management and three ExtensionHost sockets (`tests/e2e/workbench-route.spec.ts:87-698`; `project/work-items/27-bl-011-route-workbenches-through-stable-project-urls/implementation/00-implementation.md`). It does not establish A/B/C cross-target isolation.
- **BL-012 navigation boundary:** Home encodes only the persisted stable ID into `/projects/{id}/workbench/` and performs full-document navigation (`apps/web/src/workbench-navigation.ts`; `apps/web/src/App.tsx`, symbol `openWorkbench`). The API serves an unmarked top-level shell and delegates marked acquisition, descendants, and upgrades to BL-011 (`apps/api/src/routes/workbench.ts`; `apps/api/src/workbench-navigation-shell.ts`, symbols `browserShell` and `renderWorkbenchNavigationShell`). Existing Home matrices use project-ID keyed fake maps, but the real browser evidence is one project/runtime with continuity, fresh storage, and one `runtime.start.succeeded` log (`apps/api/test/home-workbench-matrix.test.ts:63-371`, `tests/e2e/home-workbench-real-process.spec.ts:209-650`).
- **Persistence and public data:** The Drizzle `projects` table has exactly `id`, `name`, `canonical_path`, and `created_at`; canonical path has a unique index (`apps/api/src/db/schema.ts`). `Project`, repository, and library interfaces expose the same four fields (`apps/api/src/project-persistence.ts`, `apps/api/src/project-library.ts`). API and web parsers enforce exact four-field objects (`apps/api/src/routes/projects.ts:25-86`, `apps/web/src/projects.ts`, symbol `parseProject`). `project-schema-minimization.test.ts` already inspects schema, rows, list shape, database bytes, reopen behavior, and fixed runtime/content sentinels.
- **Events and privacy:** Runtime lifecycle events currently serialize stable event name, raw `projectId`, from/to state, elapsed time, and optional runtime failure classification (`apps/api/src/project-runtime-contract.ts:104-115`, `apps/api/src/project-runtime-contract.ts:202-214`). Proxy events instead serialize a one-way `projectToken`, transport, elapsed time, and optional proxy classification (`apps/api/src/workbench-proxy-contract.ts:337-380`). The application sends both through the Fastify logger (`apps/api/src/app.ts:113-135`). Existing runtime and proxy contracts exclude canonical paths and protected development content, but their identifier field conventions differ.
- **Application lifecycle:** One application instance constructs one library, one runtime manager, and one proxy manager. Close order is proxy shutdown, runtime-manager shutdown, registration close, then library close (`apps/api/src/app.ts:105-168`). Runtime shutdown aborts every in-flight project, terminates all recorded running/owned identities, audits each identity, clears all maps, memoizes the result, and rejects later starts (`apps/api/src/project-runtime-manager.ts:335-425`). Proxy shutdown has its own 5,000 ms bound and precedes runtime cleanup (`apps/api/src/workbench-proxy-manager.ts:844-871`).
- **Documentation, commands, and harness:** `docs/project-runtime.md` explicitly says multi-project coordination remains deferred; `docs/stable-workbench-routing.md` says multi-project policy remains out of scope. `justfile` has separate BL-010, BL-011, and BL-012 gates and composes them into `just verify`, but no Issue #31 recipe exists. `.harness/engineering-harness.md` delegates checks to `just verify`, retains non-persistent test-backed boot, and documents current BL-004/010 evidence surfaces. Existing Git command coverage is in the earlier terminal-parity boundary (`apps/api/test/workbench-proof-terminal.test.ts`); current BL-011/012 Chromium scenarios do not register three distinct Git repositories and branches.

## Constraints

- Runtime process ownership, state, handles, identities, ports, and in-flight operations remain centralized and memory-only under `ProjectRuntimeManager`; SQLite and public project payloads remain the four-field project model (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`; `CORE-COMPONENT-260810-sqlite-persistence-lifecycle.md`).
- One active project may have at most one managed runtime. Concurrent same-project starts join one operation; reuse requires exact process identity plus the documented health contract; failures are evicted and replacement requires an explicit later start; automatic retries are prohibited (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`).
- Caller cancellation currently ends only that caller wait and must not mutate shared startup; manager shutdown is the existing shared cancellation boundary. Shutdown is bounded, idempotent, rejects starts, and targets exact owned process groups only (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`; `apps/api/src/project-runtime-manager.ts`, symbol `callerWait`).
- Runtime launch must use persisted stable ID plus exact stored canonical path, direct argument-vector process creation, the configured non-root host user, deterministic environment, and loopback-only binding. Canonical project directories are user-owned and must not be mutated by registration, runtime management, close, or cleanup (`CORE-COMPONENT-260808-filesystem-path-safety.md`; `CORE-COMPONENT-260808-host-process-environment.md`).
- Ascend-owned workbench HTTP and WebSocket traffic must remain under the stable project prefix. Upstream selection can come only from persisted lookup and the immutable runtime snapshot; client authority/port/path values cannot select it. Proxy socket shutdown completes before runtime and persistence shutdown (`ADR-260812-in-process-workbench-reverse-proxy.md`; `CORE-COMPONENT-260812-stable-workbench-proxy.md`).
- Runtime and proxy records use closed event/failure taxonomies and bounded fields. Logs and public evidence exclude raw canonical paths, internal authorities, commands, environment values, source/terminal/Git content, credentials, and secrets. Raw authority evidence is restricted to the existing ignored owner-readable artifact policy (`CORE-COMPONENT-260808-structured-runtime-logging.md`; `CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`; `CORE-COMPONENT-260812-stable-workbench-proxy.md`).
- Full-page code-server remains the accepted browser presentation; code-server owns Explorer, editor, terminal, Git UI, and related IDE state. Navigation uses the existing same-origin shell/transport split and native document navigation (`ADR-260810-full-page-browser-workbench-presentation.md`; `ADR-260812-browser-navigation-shell.md`).
- The root `justfile` remains the canonical command interface, and `just verify` remains the authoritative full gate. The harness wraps that command and does not provide persistent live-service boot (`CORE-COMPONENT-260806-project-command-interface.md`; `ADR-260808-governed-engineering-harness.md`; `.harness/engineering-harness.md`).
- The issue boundary excludes BL-014 session continuity, BL-015 performance targets, public per-project Stop/Restart, API restart reconciliation, scheduling/quotas, multi-host operation, and public authentication.

## Risks and Open Questions

- The issue requires stable route and owner token in each running snapshot, but neither field exists in `RuntimeSnapshot`; stable route and one-way event token currently belong to separate proxy/navigation contracts. The intended meaning, owner, lifetime, and privacy boundary of owner token are not defined in repository terminology.
- Runtime events expose raw `projectId`, while proxy events expose `projectToken`. The acceptance language asks lifecycle and proxy records to carry a matching stable opaque token, leaving the relationship to the existing runtime event schema unresolved.
- The all-callers-B cancellation criterion may be in tension with the adopted rule that caller cancellation never mutates shared startup and only manager shutdown cancels shared work. The criterion does not state whether B cleanup follows a controlled startup failure, later scenario cleanup, or a changed no-waiter lifecycle behavior.
- `safeTarget` validates loopback URL/port consistency but not the returned snapshot project ID/path against the route-resolved project. Current production manager behavior supplies the matching snapshot, while injected boundaries can return mismatched snapshots; the required fail-closed cross-project semantics are not explicit at this boundary.
- Proxy resource inventories are aggregate sets rather than project-attributed collections. Existing event tokens provide attribution, but current shutdown audit shape cannot directly partition sockets/streams by project.
- Runtime shutdown audits are identity rows and `lastCleanup` retains only the latest row per project. The acceptance language asks for one audit result per project across simultaneous in-flight/running ownership, while collision/replacement histories can create multiple owned identities for one project.
- Existing process environment is configured once for the manager and inherited by every runtime. It is unclear which project-specific environment correspondence, beyond absence of another fixture value and the project-specific cwd/final argument, the criterion intends.
- BL-004 proves host capacity but not simultaneous application proxy/browser use; BL-011 proves three workflows against one runtime; BL-012 proves one-project navigation continuity. Their retained evidence therefore does not establish three concurrent project-specific editor, terminal, Git, socket, failure, and replacement contexts.
- The repository has no existing three-project disposable Git fixture convention, no owner-token terminology, and no contract guard for singleton runtime fields or non-ID runtime map keys. Current source maps are ID-keyed, except the separate exact ownership map keyed by PID/start-time/port.
- A closed project can disappear from persistence while runtime state is memory-only. BL-009 is documented as stopped-project close, and Issue #31 excludes public lifecycle operations; the expected observation and cleanup boundary for a previously running ID that becomes closed remains unclear.
- Real code-server proof relies on the designated Linux/vscode host, `/proc` identity, local code-server 4.131.0, and Chromium. The no-network requirement also inherits the BL-011 proof-only `EXTENSIONS_GALLERY={}` constraint.
- Documentation currently states that multi-project coordination/policy is deferred, so those statements conflict with the Issue #31 boundary until the issue is implemented; this research does not resolve the wording.
