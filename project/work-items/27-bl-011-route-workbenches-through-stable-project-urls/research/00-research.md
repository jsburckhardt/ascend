# Research Brief: BL-011 Route workbenches through stable project URLs

## GitHub Issue
- **Issue:** #27
- **Title:** BL-011: Route workbenches through stable project URLs
- **Work Item:** project/work-items/27-bl-011-route-workbenches-through-stable-project-urls

## Scope Classification
- **Scope Type:** issue

## Problem Statement
BL-010 provides a reusable, loopback-only code-server runtime but intentionally exposes no browser route. Issue #27 requires Ascend to own the stable `/projects/{projectId}/workbench/` namespace for HTTP and WebSocket traffic while preserving the accepted full-page presentation, keeping the internal authority out of browser-visible surfaces, and retaining the runtime, filesystem, privacy, shutdown, and evidence boundaries already established in the repository. Project Home and header UI, multi-project behavior, public networking, authentication, TLS, multi-host operation, alternate editors, runtime-status UI, and user lifecycle controls remain outside this issue.

## Acceptance Criteria

**Core**
- [ ] Ascend owns `/projects/{projectId}/workbench/` and all descendant paths. Each request or upgrade resolves the registered project, starts or reuses its single BL-010 runtime, and forwards the route-suffix path and query unchanged to that runtime. The runtime listener remains loopback-only, and no internal loopback authority appears in browser-visible URLs, downstream HTTP response headers or bodies, cookies, or redirects; the restricted evidence exception is defined under Verification.
- [ ] The workbench base document, nested assets, and WebSocket connections operate under the stable project prefix. Finite browser evidence shows all requests and upgrades remain same-origin and under that prefix without changing the BL-003 full-page presentation.
- [ ] The HTTP fake-upstream matrix includes these exact payload cases in addition to the redirect, cookie, header, streaming, abort, and failure cases below: (1) `GET` a nested asset with a query and preserve its `200` text body, `Content-Type`, `Cache-Control`, and `ETag`; (2) `HEAD` an asset with no response body; (3) `POST` a 257 KiB deterministic binary body and echo it with `201`, valid `Content-Length`, and matching SHA-256 proof against generation input and an expected digest declared before execution; and (4) `GET` a byte range with the `Range` request and preserve `206`, `Content-Range`, and `Accept-Ranges`.
- [ ] Redirect and cookie cases in the HTTP matrix prove: (1) a `302` upstream root-relative `Location: /login?x=1` is rewritten under the stable project prefix; (2) a `302` same-upstream absolute loopback `Location` is rewritten under that prefix; (3) one predeclared absolute `https` `Location` whose host differs from the upstream is rejected with the typed `502` outcome; and (4) `Set-Cookie` with `Path=/` becomes the stable prefix root, `Path=/foo` becomes the stable prefix plus `foo`, and no `Path` receives the stable prefix root. The cookie `Domain` attribute is either removed or the cookie is rejected according to one rule declared before the matrix runs, while `Secure`, `HttpOnly`, and `SameSite` are preserved.
- [ ] The HTTP fake-upstream matrix proves `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, and `Upgrade` are stripped in both directions except for required WebSocket upgrade semantics.
- [ ] The HTTP fake-upstream matrix proves an exactly 32-chunk × 16 KiB streaming response under a consumer delay has SHA-256 equality against generation input and an expected digest declared before execution. After an observed barrier proves chunk 5 was emitted and received, a separate client abort closes the upstream stream, leaves zero matrix sockets, and leaves the shared runtime running.
- [ ] The WebSocket fake-upstream matrix is limited to these exact cases: one text echo with byte-for-byte equality; one 64 KiB binary echo with SHA-256 equality against predeclared generation input and digest; ping/pong; clean close code `1000` with the exact reason; upstream abnormal close with one exact downstream close-code or error outcome declared before execution, without claiming reserved code `1006` was transmitted in a close frame; handshake timeout; upstream refusal; client close during handshake; downstream backpressure with 16 ordered frames × 32 KiB and matching per-frame hashes; and two sequential reconnects that identify and reuse the same runtime. Each timeout has a declared finite bound. The abnormal-close case yields a downstream abnormal rather than `1000` close within that bound; handshake timeout returns the declared `504` code/message; upstream refusal returns the declared `502` code/message; an observed pending-handshake barrier precedes the client close, which is then observed upstream and produces no late downstream response; and every case ends with both matrix sockets closed.
- [ ] Exactly eight concurrent initial client operations for one project—precisely four HTTP requests and four WebSocket upgrades—are held at one observable pre-start barrier, released together, invoke one BL-010 start/readiness sequence and all use the same running PID identity and internal port.

**Edge Cases**
- [ ] One complete, non-overlapping safe-failure table is declared before any matrix runs and contains exactly one row for every category named here: malformed project ID `400`; unknown well-formed ID `404`; persistence failure `503`; each named BL-010 typed runtime failure other than manager shutdown mapped to `502` or `504`; upstream DNS, connect, reset, and invalid HTTP failures each `502`; handshake timeout and upstream-response timeout each `504`; and manager shutdown before response or upgrade commitment `503`. Every row has one exact public code and message, every category executes once, and each execution proves the table match and redaction.
- [ ] Finite project-ID validation asserts `400` for exactly `../x`, `%2f`, `%5c`, NUL encoding `%00`, and a 129-character ID, plus `404` for one well-formed unknown ID. Arbitrary client-supplied upstream `Host`, forwarded, or proxy-target headers are ignored or stripped and cannot change the resolved upstream.
- [ ] For the exact controlled security requests, access and application log events emitted between per-case start/end markers and the corresponding downstream response headers and bodies are captured and scanned for distinct sentinels representing the internal port, canonical path, authorization token, cookie, query secret, body secret, command/environment marker, and WebSocket and terminal payload. Each sentinel is a unique declared literal, and its literal and percent-encoded forms each have zero matches in those bounded captures. The opaque project token may appear only in captured stable-route URLs and its dedicated evidence field.
- [ ] After an observable barrier proves handshakes or streams are pending, manager shutdown settles within one documented finite bound and closes every proxied socket. A not-yet-committed HTTP response or upgrade returns the `503` manager-shutdown outcome; an already-committed response or upgraded socket closes with one exact abort/close outcome declared before execution and does not attempt a new HTTP status. A client disconnect closes only that client upstream stream and does not stop or invalidate the shared runtime.

**Verification**
- [ ] One real Chromium scenario executes exactly three fresh navigations/reconnects through the stable route; captured operation counts show three navigation attempts, three WebSocket connection attempts, and zero retry attempts. One runtime PID identity and internal port are reused throughout; the Explorer sentinel is visible; Preview sentinel text renders in the built-in webview; and the integrated terminal matches hostname, `vscode` user, and `pwd` while producing a 256 KiB deterministic output whose generation input and expected SHA-256 were declared before execution. Every captured browser request and WebSocket URL is same-origin and under the stable prefix, and the page URL and public network URLs contain no loopback port string.
- [ ] Final cleanup evidence proves zero open sockets owned by the fake HTTP/WebSocket fixtures or their matrix clients; every browser context and socket opened by the real scenario closed; manager shutdown complete; the exact BL-010-owned runtime PID/start identity and listener absent; the validation-owned unrelated control listener still alive; and a finite post-cleanup residual audit with no matrix/proxy socket, owned runtime process, or owned listener remaining.
- [ ] One restricted, owner-readable local evidence file may contain the internal port and records the opaque project token, stable route, runtime reuse, matrix results, browser results, redaction results, cleanup results, and residual audit. It is absent from version control and excluded from the public-documentation scan; public documentation and committed public evidence contain no raw internal port.
- [ ] Documentation records the stable route and base-path behavior, redirect, header, cookie, and WebSocket outcomes, the complete safe failure code/message table, redaction and evidence-disclosure rules, runtime ownership and reuse, exact validation commands and finite bounds, injected faults, cleanup procedure and observed result, and every out-of-scope boundary in the Problem.
- [ ] Repository-configured focused and full validation commands each exit zero, produce inspectable results for the complete HTTP and WebSocket matrices and real Chromium scenario, and end with the cleanup and residual-audit outcomes above.

## Repository Findings

### Product requirements and present boundary
- `PRD.md:620-634` defines FR-018 and its example stable route, states that internal ports do not appear in normal navigation, and maps the requirement to AC-024. `PRD.md:1233-1240` defines AC-024 around an ephemeral or allocated code-server port and Ascend-owned navigation without manual port entry.
- `PRD.md:689-694` requires loopback runtime binding and mediated browser access in NFR-007. `PRD.md:851-854` requires WebSocket traffic for code-server and the integrated terminal in NFR-021. NFR-008 through NFR-010 at `PRD.md:696-728` also preserve canonical path validation, configured-user permissions, and the prohibition on source, terminal, command, clipboard, prompt, and secret telemetry.
- `docs/project-runtime.md` and `README.md` explicitly describe stable routing or proxying as deferred from BL-010. The current route directory contains only `apps/api/src/routes/root.ts` and `apps/api/src/routes/projects.ts`; no workbench HTTP route, upgrade handler, or proxy boundary exists.

### Merged BL-010 runtime manager
- `apps/api/src/app.ts` constructs one application-owned `ProjectRuntimeManager`, decorates the Fastify instance as `projectRuntime`, and shuts it down before registration and library persistence owners. `apps/api/src/api-server.ts` then closes Fastify before telemetry.
- `apps/api/src/project-runtime-manager.ts:createProjectRuntimeManager` validates the persisted ID and exact canonical path, coalesces concurrent starts by project ID, health-checks before reuse, keeps running and in-flight state in memory, and returns immutable snapshots containing the internal URL, port, PID, and process-start identity. Caller abort ends only that caller wait; manager shutdown aborts shared starts, rejects later starts, terminates exact owned resources, clears state, and returns audited status.
- `apps/api/src/project-runtime-contract.ts:RUNTIME_FAILURE_CATEGORIES` is a closed 12-category set: `unknown-project`, `canonical-path-invariant`, `spawn-error`, `executable-missing`, `early-exit-code`, `early-exit-signal`, `address-in-use-exhausted`, `readiness-timeout`, `health-status-unexpected`, `health-body-unexpected`, `caller-cancelled`, and `manager-shutdown`. Messages and diagnostics are fixed and bounded. Persistence lookup failures are not converted to a `RuntimeFailure` by `ProjectRuntimeManager.start`.
- `apps/api/src/project-runtime-process.ts:buildRuntimeArgv` launches `/home/vscode/.local/bin/code-server` directly with `--bind-addr 127.0.0.1:<port>`, `--auth none`, telemetry/update/workspace-trust disabling flags, and the exact canonical path as one final argument. `launchReadyRuntime` exposes only an internal `http://127.0.0.1:<port>` authority and requires bounded `GET /healthz/` readiness.
- `apps/api/test/project-runtime-manager.test.ts` covers eight-call single-flight, health-checked reuse, shared failure, caller-local cancellation, and exit eviction. `apps/api/test/project-runtime-lifecycle.test.ts` covers shutdown ordering and in-flight shutdown. `apps/api/test/project-runtime-process.test.ts` covers loopback argv, readiness, collisions, typed failures, and exact cleanup. `apps/api/test/project-runtime-acceptance.test.ts` contains the BL-010 executable matrix. These tests do not exercise HTTP or WebSocket forwarding.

### Project identity and persistence
- `apps/api/src/project-registration.ts:createProjectRegistrationService` generates new IDs with `randomUUID`; persisted records contain only `id`, `name`, `canonicalPath`, and `createdAt`. `apps/api/src/project-library.ts` and `apps/api/src/project-persistence.ts` expose `findById` over that four-field SQLite model.
- Existing generic project validation only requires a nonempty string ID in `apps/api/src/routes/projects.ts:validateProject` and `apps/api/src/project-persistence.ts:validationCode`. The BL-009 close boundary deliberately treats any decoded nonempty ID as opaque: `apps/api/src/project-close.ts:createProjectCloseService` rejects only non-string or empty IDs, and `apps/api/test/project-close-route.test.ts` proves that spaces, markup, slash, and question-mark characters are delegated after decoding.
- `apps/api/src/bad-url.ts:sendSafeBadUrl` maps malformed Fastify URLs to a 400 category according to the HTTP method, but it currently has no workbench-specific category or route context.

### Fastify HTTP, upgrade, plugin, and dependency surface
- `apps/api/package.json` declares Fastify, `@fastify/autoload`, `@fastify/sensible`, and `fastify-plugin`; `pnpm-lock.yaml` resolves Fastify 5.11.0 and Autoload 6.5.0. The API does not declare `@fastify/http-proxy`, `@fastify/websocket`, `http-proxy`, or `ws` as a direct dependency. The dependency tree contains `@libsql/isomorphic-ws` only under the database client; the workspace-installed `ws` package is transitive rather than an API-owned proxy contract.
- `apps/api/src/app.ts` autoloads plugins and routes as encapsulated Fastify plugins. The installed Fastify 5.11 documentation at `node_modules/.pnpm/fastify@5.11.0/node_modules/fastify/docs/Reference/Routes.md` documents parametric and wildcard routes, per-route hooks, a default 1 MiB parsed-body limit, and automatic sibling HEAD exposure for GET unless configured otherwise.
- Fastify exposes the underlying Node server as `FastifyInstance.server` in `node_modules/.pnpm/fastify@5.11.0/node_modules/fastify/types/instance.d.ts`, and exposes the Node incoming request as `FastifyRequest.raw` in `types/request.d.ts`. `Reply.raw` and `reply.hijack()` are documented in `docs/Reference/Reply.md`; that documentation warns that raw responses skip Fastify response handling, and hijacking suppresses remaining hooks.
- No current application source registers a Node `upgrade` listener, uses `request.raw` or `reply.raw` for proxying, or owns proxy sockets. Existing Fastify handlers parse and serialize product API bodies rather than preserving arbitrary upstream byte streams.

### code-server reverse-proxy and base-path behavior
- The installed designated executable is code-server 4.131.0. Its help and `/home/vscode/.local/lib/code-server-4.131.0/out/node/cli.js` expose `--bind-addr`, `--socket`, `--trusted-origins`, `--proxy-domain`, `--disable-proxy`, and `--abs-proxy-base-path`. There is no general code-server base-path flag; `--abs-proxy-base-path` applies to code-server own `/absproxy/:port` application-proxy route, not to mounting the workbench root.
- `/home/vscode/.local/lib/code-server-4.131.0/out/node/http.js:relativeRoot` states that workbench page paths are relative so code-server can operate behind an unknown reverse-proxy base path. The same file derives cookie paths from browser-supplied `base` and `href`, performs origin checks, and gives `Forwarded` and `X-Forwarded-Host` precedence over `Host` in `getHost`.
- `/home/vscode/.local/lib/code-server-4.131.0/out/node/routes/index.js` serves root and `/vscode`, static assets, health, login/logout, update, HTTP proxy routes, and corresponding WebSocket routes. It emits `Service-Worker-Allowed: /` for the service worker. `/home/vscode/.local/lib/code-server-4.131.0/out/node/wsRouter.js:handleUpgrade` pauses upgraded sockets and routes them through a separate Express WebSocket router.
- The BL-010 argv currently leaves code-server path and domain proxy routes enabled because it does not pass `--disable-proxy`. The accepted issue explicitly keeps alternate product networking out of scope, while the upstream workbench itself has those route capabilities.

### Presentation and browser evidence already present
- `project/architecture/ADR/ADR-260810-full-page-browser-workbench-presentation.md` accepted top-level full-page code-server with a minimal Ascend header and rejected embedding based on retained browser evidence. It explicitly deferred stable routing and runtime integration.

### Security, logging, documentation, and command architecture
- `apps/api/src/request-logging.ts` adds Pino redaction for `req.url` as `[request-url-redacted]` while preserving configured redaction paths. Product bootstrap uses it in `apps/api/src/api-server.ts`; logger false remains an explicit supported test configuration.

- `justfile` owns focused and full validation commands and currently has BL-010 runtime recipes but no BL-011 route-specific recipe. `docs/project-runtime.md`, `docs/README.md`, `apps/api/README.md`, and `README.md` consistently state that stable routing was deferred, so they are relevant affected documentation surfaces.

## Constraints
- The acceptance criteria bind one stable prefix and every descendant for both ordinary HTTP and upgrade traffic. Route suffixes and queries remain unchanged toward the selected persisted project runtime, while browser-visible navigation, headers, bodies, cookies, redirects, requests, and WebSocket URLs cannot disclose the loopback authority.
- The persisted project record and canonical path remain authoritative. Runtime launch cannot accept a client-selected target, host, port, canonical path, or forwarding authority; the runtime core-component requires the stable ID and exact stored canonical path.
- BL-010 remains the sole process-ownership boundary. Concurrent route activity must preserve its single-flight start, exact PID and port reuse, caller-local cancellation, no automatic retry, finite readiness, and exact manager-shutdown behavior.
- Runtime identities, ports, handles, sockets owned by the runtime manager, and lifecycle state remain memory-only and must not expand the four-field SQLite model or create a migration.
- Runtime processes stay non-root, direct-argv, host-native, and loopback-only. Filesystem content and the canonical project directory cannot be mutated by routing, failure handling, or cleanup.
- The accepted full-page presentation remains authoritative. The issue cannot replace it with embedding or transfer Explorer, Preview, terminal, editor, Git, or extension behavior from code-server into Ascend.
- code-server 4.131.0 generates relative workbench paths but also derives origin and cookie behavior from forwarded authority and browser base data. Client-supplied `Host`, `Forwarded`, `X-Forwarded-*`, proxy-target, authorization, and cookie inputs therefore cross a security-sensitive upstream boundary.
- Fastify core supplies wildcard routing and raw Node HTTP objects, but the application has no declared HTTP/WebSocket proxy package or current upgrade ownership. Raw response handling can bypass Fastify serialization and hooks; existing parsed-body routes do not establish arbitrary byte-stream forwarding semantics.
- Request URL logging is redacted by product bootstrap, runtime event fields are closed, and raw source, terminal, command, environment, credential, secret, and payload content is prohibited from logs and telemetry. WebSocket upgrade paths and any low-level socket handling do not currently receive a Fastify request lifecycle automatically.
- Application shutdown currently awaits the runtime manager before persistence closes. The manager owns runtime process resources, not proxy HTTP streams, handshakes, client sockets, or upgraded sockets; the issue acceptance criteria add externally observable shutdown requirements across both ownership domains without changing the established manager guarantees.
- Repository commands remain rooted in `justfile`; Vitest, Playwright Chromium, strict TypeScript, formatting, linting, builds, and at least 80 percent unit coverage are established development constraints. Public behavior changes must update application documentation.
- Public documentation and committed evidence cannot contain a raw internal port. Generated evidence is ignored, but the issue additionally requires owner-only readability and a bounded disclosure exception for one local file.

## Risks and Open Questions
- What exact syntax defines a well-formed project ID for this route? Registration currently emits UUIDs, but persistence and the BL-009 route intentionally accept any decoded nonempty opaque ID. The issue names five invalid values and one well-formed unknown value without declaring the complete accepted grammar.
- The safe-failure table requires every BL-010 typed failure except manager shutdown to map to 502 or 504, while the runtime set includes caller-local `caller-cancelled`; persistence lookup can also throw a non-runtime `ProjectPersistenceError`. The intended public category and commitment behavior for these boundaries is not yet recorded.
- The issue requires exact public codes and messages for upstream DNS, connect, reset, invalid HTTP, timeout, external redirect, persistence, and shutdown outcomes, but the repository has no stable route error catalog. Those exact public strings remain unspecified by current architecture and documentation.
- code-server has no general base-path CLI flag. Its relative URL model is reverse-proxy aware, but cookie base inputs, origin validation, service-worker scope, root-relative redirects, absolute redirects, extension/webview resources, and internally generated bodies can each expose or escape the stable prefix if their observable behavior is not completely bounded.
- The issue prohibits internal authority in downstream bodies while also requiring byte-preserving streaming, binary echo, range, caching, and content-length behavior. The required treatment of encoded, compressed, integrity-tagged, streaming, or otherwise opaque bodies that contain an internal-authority literal is not clarified.
- `Forwarded` and `X-Forwarded-Host` affect code-server origin decisions. Incomplete separation of client headers from trusted upstream metadata could allow target confusion, origin bypass, public-host corruption, or secret propagation.
- HTTP hop-by-hop handling is connection-token dependent in addition to the eight explicitly named headers. The issue lists exact names but does not state how extension headers named by an incoming `Connection` field are classified.
- Fastify has no current upgrade listener or proxy-socket inventory. Upgrade routing, pre-start concurrency, handshake commitment, backpressure, abnormal close semantics, client-close races, timeout ownership, and shutdown settlement therefore have no repository precedent beyond the underlying runtime and direct code-server browser proofs.
- Browser and application logging currently have separate redaction mechanisms: product request logging redacts the complete URL, while e2e browser URL capture only redacts query keys matching token, credential, or secret. The issue requires literal and percent-encoded sentinel scans over bounded logs, responses, and browser evidence, including query, body, WebSocket, and terminal payloads; the complete capture boundary and treatment of OpenTelemetry output remain open.
- Root `test-results/` is ignored, but existing generated files are not owner-only by default. File mode, cleanup ownership, publication scanning, and the point at which internal-port evidence becomes unavailable require explicit bounded handling.
- The real Chromium criterion combines exactly three fresh navigations and reconnects with reuse of one BL-010 runtime and zero retries. Existing BL-003 evidence instead used one fresh runtime per attempt, so historical timings and warning counts do not establish this route behavior.
- The issue out-of-scope list excludes public networking, authentication, and TLS, while code-server currently runs with `--auth none` and Ascend defaults to loopback. Documentation must avoid implying security guarantees for those deferred deployment modes.
