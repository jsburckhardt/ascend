# Task Breakdown: BL-005: Persist the project library

## Task T-1: Establish closeable SQLite resources and committed migrations

- **Status:** Complete
- **Complexity:** Large
- **Dependencies:** None
- **Acceptance Criteria:** AC-1, AC-2, AC-7
- **Related ADRs:** ADR-260808-typescript-monorepo
- **Related Core-Components:** CORE-COMPONENT-260810-sqlite-persistence-lifecycle, CORE-COMPONENT-260806-project-command-interface, CORE-COMPONENT-260808-development-standards

### Description
Replace `apps/api/src/db/client.ts` module-global state with a closeable factory receiving an explicit filesystem path. Centralize the resolved developer default as `<repository>/apps/api/ascend.db`, support the documented local `ASCEND_DATABASE_URL` application override without using it for the explicit migration argument, and make close idempotent. Keep local SQLite and the installed libSQL/Drizzle stack.

Commit generated Drizzle journal and SQL for `0000_project_library` followed by `0001_project_canonical_path_unique`. The first migration establishes exactly `id`, `name`, `canonical_path`, and integer `created_at`; the second adds database-enforced canonical-path uniqueness so `0000_project_library` is a meaningful immediately previous fixture state. Keep current `schema.ts` aligned with the final migration and use integer Unix epoch milliseconds without timestamp conversion.

Implement a migration catalog that maps journal order and timestamps to stable migration IDs, compares applied state, invokes the Drizzle libSQL migrator, and returns `{ appliedMigrationIds, currentMigrationId }`. Add an API CLI and root `db-migrate database_path` recipe that requires a filesystem path, creates parent directories and the database if absent, prints one deterministic JSON result, closes in `finally`, and never resets data.

### Acceptance Criteria
- The factory owns and idempotently closes its libSQL client; no import creates a database handle.
- The committed ordered IDs are exactly `0000_project_library` and `0001_project_canonical_path_unique`, with the latter current.
- A fresh explicit path receives both migrations; a current path receives none on rerun.
- Final `projects` schema has exactly the four physical columns and unique canonical path.
- The root recipe returns the ordered migration result and closes its resource on success and failure.

- Unit coverage covers path normalization, catalog mapping, close idempotence, invalid or missing CLI arguments, and typed command failure.

### Expected Evidence

## Task T-3: Implement the project repository and in-process service

- **Status:** Complete
- **Complexity:** Large
- **Dependencies:** T-1
- **Acceptance Criteria:** AC-2, AC-3, AC-4, AC-6
- **Related ADRs:** ADR-260808-typescript-monorepo
- **Related Core-Components:** CORE-COMPONENT-260810-sqlite-persistence-lifecycle, CORE-COMPONENT-260808-filesystem-path-safety, CORE-COMPONENT-260808-structured-runtime-logging, CORE-COMPONENT-260808-development-standards

### Description
Create an issue-local project persistence contract and an in-process `ProjectLibrary` construction function. `Project` contains only `id`, `name`, `canonicalPath`, and `createdAt`; `createdAt` is a finite non-negative safe integer in Unix epoch milliseconds. Create returns a discriminated result: `created` with the inserted record, `existing` with the durable winner for canonical path, or `invalid` with one of `empty-id`, `blank-name`, `empty-canonical-path`, or `invalid-created-at`. Valid input values are returned unchanged. List returns only the four fields in deterministic order.

Validate before issuing SQL. Do not trim returned names, canonicalize paths, inspect the filesystem, or apply BL-006 policy. Use `INSERT ... ON CONFLICT(canonical_path) DO NOTHING` and read the winner so sequential and concurrent valid calls all resolve to one durable record. Convert unexpected driver failures to a typed project-persistence error so generic SQLite/libSQL errors do not cross the contract. Construct the service from the explicit closeable resource, apply migrations before repository use, and provide idempotent service close.

### Acceptance Criteria
- Create/list expose exactly four project properties with unchanged values.
- Valid creates return only explicit `created` or `existing` dispositions; an existing result contains the same winning record.
- Canonical-path uniqueness is enforced by the database, not an in-memory precheck.
- All four invalid classes return deterministic typed outcomes before SQL and preserve existing data.
- Service construction and close own every persistence resource and require no Fastify, HTTP, network, or UI boundary.

### Test Coverage
- V-3 verifies exact shape and close/reopen equality.
- V-4 verifies sequential and eight-way concurrent duplicate outcomes and database uniqueness.
- V-5 verifies typed validation and no mutation.
- V-6 verifies complete service restart.
- Unit tests force an unexpected adapter failure and assert a typed persistence error with no raw driver object exposed.

### Expected Evidence
- Type-level and runtime tests for all result variants and exact object keys.
- Raw database queries matching service results.
- Focused coverage output meeting configured thresholds for the new repository and service modules.
