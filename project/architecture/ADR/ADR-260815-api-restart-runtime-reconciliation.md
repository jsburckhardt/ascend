# ADR-260815-api-restart-runtime-reconciliation: Reconcile Surviving Workbench Runtimes After an API Restart Through Host-Derived Exact Attribution

## Status

Accepted. **Amended 2026-08-15 (revision 2 of the BL-019 plan for Issue #43), and amended again 2026-08-15 (revision 3).** The identifier and creation date are preserved; no replacement ADR was created. The revision-2 amendment corrected the attribution predicate, the listener-ownership scope, the startup obligation, the bound decomposition and its measurement origin, and recorded the adopted-runtime liveness limitation that the original text wrongly described as absent. The **revision-3 amendment changes no production behaviour**: it records the consequence of candidacy precedence for adversarial proof design, and it fixes what may count as evidence for this decision. Every amended paragraph below is the operative text; superseded wording is not retained anywhere in this document.

## Context

PRD Slice 5 and NFR-006 require Ascend to reconcile recorded runtime information with actual running processes after a backend restart instead of assuming either source is correct. Issue #43 (BL-019) makes that concrete: after a controlled abrupt API-process exit that leaves registered, ready workbench processes and their loopback listeners alive, a replacement API process must settle reconciliation within 15,000 ms, report the four delivered public states truthfully, and control only what it can attribute exactly.

The delivered system deliberately splits durable and volatile knowledge. SQLite persists exactly `id`, `name`, `canonical_path`, and `created_at`. `ProjectRuntimeManager` holds runtime identities, exact ownership records keyed `pid:processStartTime:port`, readiness, lifecycle entries, generations, released markers, retained failures, restart admissions, and quarantine in instance memory. A replacement API therefore receives the project library and nothing else. Three consequences follow directly from the delivered code: `reportPublicStates` maps a missing entry to `Stopped`, so a live survivor is reported as stopped; `stop` and `restart` classify the same project `no-managed-runtime`; and `WorkbenchProxyManager.resolveTarget` calls `projectRuntime.start()`, which — with no entry — launches a **new** generation over a possibly live predecessor for the same canonical directory, stable route, and ephemeral runtime-data directory.

Every delivered exact-identity contract is current-manager-only. Process-start time defeats PID reuse for identities this manager recorded. Termination revalidates that identity before signalling its owned process group. Confirmation requires root absence, owned process-group absence, and listener absence. None of it applies to a process this manager never launched, and `CORE-COMPONENT-260808-runtime-lifecycle-error-handling` explicitly forbids adopting, signalling, or claiming any process Ascend cannot attribute.

Two facts discovered while planning this decision are load-bearing.

First, survivorship is not free. The delivered launch spawns code-server `detached` with `stdio: ['ignore', 'ignore', 'pipe']` and `child.unref()`. A controlled probe on this host confirmed that such a child **dies** on its next stderr write once the API is killed, because the pipe has no reader and the resulting `EPIPE` is unhandled; the identical child with stderr redirected to a file descriptor survives indefinitely. The premise of Issue #43 — that ready workbenches remain alive across an abrupt API exit — is therefore false under the delivered wiring and must be repaired by this decision.

Second, the evidence needed for exact attribution already exists in the kernel and needs no new persistence. The delivered launch writes its complete identity into the process itself: `buildRuntimeArgv` places `--bind-addr 127.0.0.1:<port>`, `--user-data-dir <tmpdir>/ascend-runtime-data/<ownerToken>-<port>`, and the exact persisted canonical directory as the final argument, where `ownerToken` is `deriveProjectOwnerToken(projectId)`. `detached: true` makes the child its own process-group leader. `/proc/<pid>/stat` supplies process-start time and process-group id, `/proc/<pid>/status` supplies the owning uid, `/proc/<pid>/cmdline` supplies the exact argument vector, `/proc/net/tcp` supplies the listening socket inode for a loopback port, and `/proc/<pid>/fd` supplies that process's socket inodes. A controlled probe confirmed every one of those reads is available unprivileged to the same user.

Third — established by controlled probe during the revision-2 amendment, and the reason the original predicate could not work — **the configured executable is not what the kernel shows**. `config.executablePath` is `<prefix>/bin/code-server`, a symlink to `<installation-root>/bin/code-server`, which is a POSIX shell launcher whose final line is `exec "$ROOT/lib/node" "$ROOT" "$@"`. A real workbench spawned exactly as the delivered adapter spawns it therefore reports `/proc/<pid>/cmdline` as `[<installation-root>/lib/node, <installation-root>, ...buildRuntimeArgv(...)]`. `argv[0]` is the bundled interpreter and the delivered argument vector begins at index **2**. Any predicate comparing `argv[0]` to the configured executable path refuses every genuine survivor while remaining satisfiable by a fabricated observation, which is the exact inversion of the property this decision exists to provide.

Fourth, **the listening socket is not owned by the process-group leader**. The same probe observed the leader holding no listening socket and a forked group member — same process group, argument vector `[<installation-root>/lib/node, <installation-root>/out/node/entry]` — holding the loopback listener inode. The delivered BL-017 and BL-018 designated proofs already attribute listeners across the owned process-group closure rather than the leader's own descriptors, so requiring the inode in the leader's own file-descriptor set contradicts both the host and the repository's own prior art.

Fifth, **an adopted process cannot be watched the way a launched one is**. A launched or restarted runtime installs `ready.process.exit.then(...)` into the manager's background task set, so its death transitions the entry automatically. A process this API did not spawn has no such event, and this issue adds no background monitor, poller, or supervisor. That asymmetry is real and is recorded here rather than glossed over.

Sixth, **the issue's 15,000 ms ceiling is end-to-end, not internal**. It is measured from the replacement API process spawn, so Node boot, project-library open, and manager construction are inside it. Three timed spawns of the compiled API on this host measured spawn to first served response at 1,531, 1,510, and 1,149 ms with zero registered projects, so an internal deadline equal to the whole ceiling necessarily breaches it.

Out of scope and unchanged: running-or-failed project close (BL-020), BL-021, BL-022, automatic recovery beyond one API-restart reconciliation, background or periodic health monitoring, auto-sleep, scheduling, quotas, bulk lifecycle actions, multi-host or multi-user operation, and adoption of any process that is not an exact Ascend workbench for an exact registered project.

## Decision

Reconcile surviving workbench runtimes once per API process, from host-derived exact attribution, with adoption as the sole ownership boundary.

**Make the kernel the evidence and the manager the authority.** Ascend persists no runtime identity, port, handle, state, owner token, epoch, or release marker. Reconciliation derives candidates from the current user's live processes and corroborates them against the persisted project library. A durable file, database column, or lock file is refused as an authority: a same-user writable record can be stale or tampered, and it can only ever be a claim about a process, never the process itself.

**Derive the expected argument vector from the installed runtime, never from the configured path string.** One helper resolves the configured executable to its installation identity: `launcherRealPath` = `realpath(executablePath)`; `installationRoot` = the parent of the resolving `bin` directory; `interpreterPath` = `<installationRoot>/lib/node`, asserted executable; and `launcherArgvPrefix` = `[interpreterPath, installationRoot]`. This mirrors, term for term, what the delivered launcher computes for itself before it `exec`s. If the real path cannot be resolved or the interpreter is missing or not executable, the helper yields nothing and **every** registered project settles unresolved. There is no fallback prefix, no heuristic, and no attempt to compare `argv[0]` to the configured path.

**Adopt only under one complete conjunction, evaluated in a fixed order.** A pid becomes a *candidate* for registered project `P` when either its argument vector's final element is `P`'s exact persisted canonical path or its `--user-data-dir` basename carries `P`'s derived owner token; a pid with neither marker is not evidence at all, and a pid whose two markers name different projects is a candidate for both and is refused for both. A candidate is attributable to `P` only when every one of these holds for the same pid within one bounded observation window, checked in this order and stopping at the first failure: the installation identity resolved; exactly one candidate exists for `P`; the process is owned by the current non-root uid; the argument vector begins with the derived launcher prefix; its final element is `P`'s exact persisted canonical path; its `--user-data-dir` owner token is `P`'s derived owner token; the `--user-data-dir` port and the `--bind-addr` port are the same integer; the remainder of the vector after the prefix is byte-equal to the vector the current build would produce for `P` at that port; the process is its own process-group leader; the bounded enumeration of that process group completes and contains it; a loopback listening socket exists on that port; **that socket's inode is held by exactly one exactly observed conforming member of that same process group — the leader or a forked member, and never a process outside the group**; the delivered `/healthz/` readiness contract is satisfied on that port; and a second read of the candidate's process-start time, the candidate's argument vector, and the listener-owning member's process-start time, taken after the readiness observation, is identical to the first. Any failed, missing, incomplete, or duplicated element refuses adoption. There is no partial credit, no heuristic, and no operator override.

The three specific argument checks are deliberately evaluated **before** the wholesale byte-equality check. A single wholesale comparison first would subsume them, leaving the mismatched-path, mismatched-owner-token, and mismatched-port refusals unreachable and therefore unprovable.

**Accept that candidacy precedence bounds what any single pass can prove, and isolate adversarial controls instead of weakening it (revision 3).** Exactly-one-candidate is evaluated before every signature check, so any process carrying a registered project's canonical-path or owner-token marker makes that project ambiguous for as long as it is alive, whatever else is true of it. A negative control that impersonates a project with a live survivor therefore cannot produce a signature refusal, and demanding both an adoption and a named refusal from one pass over both processes is unsatisfiable. The resolution is proof structure, not predicate relaxation: a control that carries a project marker must be the sole candidate for its own registered project in the pass that observes it, must not be alive during a pass that must adopt a genuine survivor of the project it marks, and must be removed and independently proven absent before such a pass begins. A control that coexists with survivors must carry neither marker, proven by observing its own argument vector rather than by assertion. No control may be excluded from candidacy, evaluated outside reconciliation, pre-classified, bypassed, or otherwise exempted; every control is settled by this predicate exactly like any other candidate. Candidacy is not narrowed, the conjunction is not weakened, and `ambiguous-candidates` remains the correct and required settlement whenever two candidates exist for one project.

**Require evidence for this decision to be executed, not written (revision 3).** A claim about reconciliation counts only when it is produced by running this decision's code. A deterministic scenario record must be produced by invoking the runtime manager, its admission and acquisition paths, the delivered route handlers, and the public projection, and every settled value in it must be read back from that run; a record assembled from expectation constants, a static serialized fixture, or a validator run over an artifact the run did not produce is not evidence. A claimed API generation must be an execution of the repository's compiled API entry, recorded with operating-system-observed process identity, argument vector, listening socket ownership, real loopback requests, and its real database file; a placeholder process, an in-process application or manager instance presented as a generation, a synthesized record, and an assigned identity are not evidence. These rules are enforced mechanically by source guards and by the evidence validators, so a written claim fails rather than passes.

**Adopt into the delivered ownership shape.** A successful adoption constructs an owned runtime handle carrying that exact pid, process-start time, port, loopback internal URL, and the observed runtime-data directory, registers one ownership record keyed `pid:processStartTime:port` under a fresh generation, and installs one frozen `running` entry whose snapshot is indistinguishable in shape from a launched one. Stop, Restart, the stable proxy, the ownership index, cleanup, and manager shutdown then operate on adopted runtimes through exactly the delivered contracts, including removal of the ephemeral runtime-data directory on termination. Adoption is the ownership boundary: before it, reconciliation may observe but must never signal, terminate, route to, claim, or report `Running`; after it, an adopted runtime is an owned runtime for ownership indexing, Stop, Restart, proxy target resolution, cleanup, ephemeral-directory removal, and manager shutdown. It differs from a launched runtime in exactly one respect, decided and recorded below: its death is not observed automatically.

**Accept, and publish, that an adopted runtime's death is corrected only on demand.** This decision adds no background task, timer, interval, watcher, `SIGCHLD` handler, or periodic health loop for adopted runtimes, and the adopted handle's terminal promise is never placed in the manager's drained background task set. Between adoption and the next on-demand observation, an adopted runtime that dies is therefore still reported `Running`. The delivered on-demand paths correct it without any new mechanism: workbench acquisition re-checks liveness and readiness and transitions the entry to `Failed`; selected Stop's initial audit answers already-absent and settles `Stopped`; explicit Restart's release gate confirms the prior generation absent before readying a replacement. The delivered sequencer revalidates process-start time before signalling, so a recycled pid at that identity yields an unconfirmed result with zero signals delivered. This limitation is a decided consequence of excluding background monitoring from this issue, it is stated in the user-facing documentation, and it is proven by a dedicated validation group rather than assumed away.

**Settle every registered project into exactly one of three outcomes, publicly projected through the delivered four states.** Add one internal entry state `reconciling`, projected as `Starting`, installed synchronously for every registered project before the API accepts its first request, so a live survivor is never reported `Stopped` while it is still unknown. `adopted` installs `running` and reports `Running`. `absent` installs the released `registered` entry and reports `Stopped`, and is claimed only from a positive observation: either a completed uninterrupted candidate scan that enumerated the whole process set and found no candidate for that project, or a completed delivered audit triple showing the single candidate's process, owned process group, and listener all absent. `unresolved` installs a retained `failed` entry carrying the one new bounded category `reconcile-unconfirmed` and reports `Failed`. An incomplete scan, an ambiguous or duplicated candidate, a signature, uid, group-leader, identity-stability, or listener-ownership refusal, an unconfirmed readiness, a partial absence audit, and the settlement deadline all produce `unresolved`; none of them may become `absent`, and none may become `Running`. Process existence alone never produces `Running`.

**Measure the issue ceiling from one authoritative origin and leave the startup segment inside it.** The 15,000 ms ceiling is measured from the replacement API process spawn instant to the first runtime-state response in which no registered project is still pending, and it decomposes as an asserted identity into exactly three declared segments: a 3,000 ms startup headroom covering process spawn, Node boot, library open, and manager and proxy construction up to the reconciliation call; an 11,000 ms internal reconciliation bound; and a 1,000 ms response allowance. The internal bound is itself the sum of four declared configuration allowances — 2,000 ms candidate scan, 1,000 ms attribution, 7,000 ms readiness, 1,000 ms settlement — validated as positive safe integers exactly like every sibling bound. The internal deadline is armed at installation and is therefore strictly smaller than the ceiling it must fit inside; the previous decomposition armed a 15,000 ms internal deadline after startup had already consumed part of the ceiling, which no valid run could satisfy. The startup headroom is proven each run by a zero-project control measured against 4,000 ms, not assumed. The deadline is armed by the trusted synchronous `RuntimeDeadlineScheduler` monotonic clock and `scheduleDeadline` handle, never by the fallible injectable `sleep`. Every awaited host observation receives a cancellation signal, and an observation still pending at the deadline is abandoned; an abandoned result is never read, recorded, converted into an absence claim, or allowed to mutate an entry.

**Own reconciliation exactly once, and make it a required capability rather than an optional one.** One memoized reconciliation exists per manager instance, declared as a **required** member of the runtime-manager boundary and awaited by the application without optional chaining or a presence test, so a manager that cannot reconcile is a type error rather than a silent startup skip that would serve a fabricated `Stopped` for every project. It is installed by the application at startup, before routes accept traffic, and a failure to list the persisted library at that point fails API startup explicitly through the delivered initialization-failure path rather than serving a fabricated `Stopped` for every project. Concurrent runtime-state projection, proxy acquisition, Open, Stop, Restart, and shutdown never start a second reconciliation. Runtime-state projection remains synchronous and read-only and never awaits it. Workbench acquisition awaits its own project's settlement and then follows the settled state; Stop and Restart never wait — they refuse.

**Refuse control and launch while a project is pending or unresolved.** A `reconciling` entry rejects Stop and Restart with the bounded pre-acceptance category `reconcile-in-progress`, changing no state and emitting no lifecycle event. A retained `reconcile-unconfirmed` entry rejects Stop and Restart with the bounded category `reconcile-unresolved` and makes `start` refuse with `reconcile-unconfirmed` **before** any port acquisition or spawn, so an ambiguous survivor can never be shadowed by a duplicate generation, and so no ambiguous process is ever signalled. That refusal persists for the life of the API process; the documented operator path is to resolve the ambiguity outside Ascend and restart the API, whose next reconciliation is computed from nothing but fresh host evidence.

**Emit four reconciliation events and nothing else.** `runtime.reconcile.requested`, `runtime.reconcile.succeeded`, `runtime.reconcile.absent`, and `runtime.reconcile.failed` map to `Starting`, `Running`, `Stopped`, and `Failed` under the delivered event-to-state agreement check. Reconciliation emits no start, stop, restart, or health event, because it performs none of those actions. Public surfaces disclose only the delivered opaque project token, bounded state, and bounded category; the finer refusal reasons exist only as bounded enum names in trusted in-process inspection and retained validation evidence, and never in an HTTP body, event, or browser-visible surface.

**Make survivorship real.** The workbench child's standard error is redirected to a per-runtime file descriptor opened at mode 0600 inside its existing mode-0700 ephemeral runtime-data directory, instead of a pipe owned by the API process, so the child's lifetime no longer depends on its parent's. The delivered address-in-use collision contract is preserved by reading a bounded 4,096-byte prefix of that file when a child exits early, applying the same classification. That file is never published, copied into evidence, or read for any other purpose, and it is removed with its runtime-data directory when the runtime exits or is terminated — including when reconciliation adopts a survivor and thereby restores ownership of that directory.

## Alternatives

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| Persist runtime identity, port, and state in SQLite | Survives restart directly; simple lookup | Breaks the delivered four-field project contract and its validators, makes a writable same-user row the authority over a live process, and leaves stale rows after every abrupt exit | A record is a claim about a process, never the process; the four-field boundary is a delivered contract |
| Write a durable runtime registry or lock file per runtime | No schema change; survives restart | Same-user writable, therefore forgeable and stale-prone; still requires full host corroboration before any adoption, so it adds a trust surface without removing a check | The kernel already holds unforgeable evidence that the file would only mirror |
| Adopt any live code-server, or any process holding a plausible loopback port | Recovers more cases | Arbitrary process adoption; a foreign or unrelated process could be signalled, routed to, or reported `Running` | Explicitly out of scope and forbidden by the delivered attribution rule |
| Terminate every survivor at startup and start clean | Trivially unambiguous | Destroys live user sessions, and signals processes that have not yet been attributed | Contradicts AC-1 and the rule that Ascend signals only what it owns |
| Ignore survivors and launch on demand | No new mechanism | Produces duplicate generations for one canonical directory, stable route, and runtime-data directory | The exact defect this issue exists to remove |
| Reconcile lazily on first acquisition | No startup cost | Leaves a window in which a registered project with a live survivor is reported `Stopped`, a false state | AC-3 forbids substituting a false state |
| Run a background supervisor that re-reconciles periodically | Detects later divergence | Adds automatic recovery, scheduling, and a health loop | All three are out of scope for this issue |
| Keep the parent stderr pipe and accept whatever survives | No launch change | A controlled probe proved the child dies on its next stderr write after an abrupt API exit | Survivorship is the premise of the whole issue |
| Redirect the child's stderr to `/dev/null` | Simplest survivorship fix | Destroys the delivered address-in-use evidence and therefore the collision-retry contract and its `address-in-use-exhausted` category | A delivered contract may not be silently weakened |
| Resolve an unresolved project by re-observing on each later request | Self-healing | A per-request re-observation loop is automatic recovery, and it can launch over an ambiguous survivor | Out of scope; the honest refusal plus an operator restart is bounded and truthful |
| Compare `argv[0]` to the configured executable path | Simplest possible signature check | The configured path is a shell launcher, so the kernel never shows it; the check refuses every real survivor and is satisfiable only by fabricated evidence | Disproved by controlled probe against the delivered executable |
| Accept any `argv[0]` and rely on the remaining flags | Tolerates a relocated or re-packaged install | Removes the installation anchor, so a byte-perfect argument vector from a foreign installation root would adopt | The installation root is the only thing that ties a candidate to *this* Ascend host |
| Require the listening inode in the group leader's own descriptors | Smallest possible read set | The leader holds no listening socket on this host; a forked group member does | Disproved by controlled probe and contradicted by the repository's own BL-017/BL-018 attribution prior art |
| Attribute a listener by port alone, without the process group | Trivial | Any process may bind a recycled port; port alone proves nothing about ownership | Would permit adoption of an unrelated listener |
| Declare startup reconciliation optional on the manager boundary | Avoids migrating typed test doubles | A missing implementation starts the API successfully and serves fabricated `Stopped` rows for live survivors | A silent success-shaped skip is the defect this decision exists to prevent |
| Add a background monitor so adopted deaths transition automatically | Removes the liveness asymmetry | Introduces periodic health monitoring and automatic recovery, both explicitly out of scope for this issue | Deferred deliberately and documented as a limitation instead of smuggled in |
| Arm the internal deadline at the full 15,000 ms ceiling | One number to remember | Startup has already consumed part of the ceiling before the deadline is armed, so a valid internal run breaches the issue bound | Arithmetically impossible against the measured origin |
| Narrow candidacy, or let a marked control be skipped, so an adversarial control can coexist with the survivor it impersonates | One proof episode; fewer moving parts | Either reintroduces the unreachable refusal classes that revision 2 repaired, or gives validation a bypass around the production predicate, which is exactly the trust surface this decision removes | The predicate is correct; the proof structure was wrong, so isolate the control instead |
| Expose the internal refusal classification over HTTP so an out-of-process proof can read it | Simple to observe | Publishes a finer classification on a public surface, contradicting the privacy boundary this decision sets | Witness the class where it legitimately exists — trusted in-process inspection over the same live host evidence |
| Accept a deterministic scenario record assembled from the expected values | Cheap and hermetic | Proves only that the catalog agrees with itself; no production code runs, so no acceptance criterion is actually exercised | Evidence must be a record of execution |
| Accept a placeholder process or an in-process instance as an API generation | Faster proof, fewer host resources | The issue's premise is a real API process being lost and replaced; a placeholder never restarts, never serves HTTP, and never opens the database | The generation is the thing under test |

## Consequences

### Positive
- A replacement API reports and controls exactly the survivors it can prove, and never launches a duplicate generation over one it cannot.
- No schema, migration, persisted runtime field, or new writable authority is introduced; the four-field project contract is untouched.
- Adopted runtimes reuse the delivered ownership, Stop, Restart, proxy, cleanup, and shutdown contracts unchanged, so no second lifecycle authority appears.
- Survivorship becomes a property of the launch contract rather than an untested assumption, and the address-in-use contract is preserved.
- Absence is claimed only from a completed positive observation, so `Stopped` never means "we did not look".

### Negative
- Reconciliation depends on Linux `/proc` and on the replacement API running as the same user with the same temporary directory as the process that launched the survivor; a different user or `TMPDIR` yields an honest refusal rather than an adoption.
- A project whose reconciliation is unresolved stays unusable in that API process until an operator resolves the ambiguity and restarts Ascend.
- Every registered project now holds a manager entry from startup, so a project proven absent answers Stop with the already-stopped no-op instead of the previous no-managed-runtime rejection.
- API startup now depends on one successful project-library list.
- The workbench child's stderr accumulates in its ephemeral runtime-data directory while it runs, and a survivor that outlives its API keeps appending until it is adopted and released.
- **An adopted runtime's death is not observed automatically.** Unlike a launched or restarted runtime, an adopted one has no child-exit observation, and this decision adds no background monitor. It continues to be reported `Running` until the next workbench acquisition, selected Stop, or explicit Restart observes it, at which point the delivered on-demand paths correct it. This is a real, user-visible difference, it is documented for users and operators, and it is proven by validation rather than assumed absent.
- Attribution is anchored to **this host's configured code-server installation**. A survivor launched from a different installation root — including an upgrade that relocates the installation while a workbench is still running — is refused by name rather than adopted.
- The 15,000 ms ceiling now reserves a fixed 3,000 ms startup headroom and a 1,000 ms response allowance, so the internal reconciliation window is 11,000 ms rather than the whole ceiling. A host slower than the measured startup profile fails the zero-project control explicitly instead of silently breaching the issue bound.
- Proving a signature refusal against a live impersonating process costs a separate, fully torn-down reconciliation episode with its own registered project, database, and clearance proof. That is more validation machinery than a single episode, and it is the price of not weakening the predicate.
- Evidence is more expensive to produce: every deterministic scenario runs production code, and every claimed API generation is a real compiled-API process with real HTTP and a real database file.

### Neutral
- The four public states, the single projection authority, the one-synchronous-pass rule, and the no-polling rule are unchanged.
- The listener owner may be the process-group leader or a forked group member; the decision asserts neither, requiring only an exactly observed conforming member of the candidate's own group.
- The finer refusal classifications remain absent from every HTTP body, event, and browser-visible surface; a proof that needs one reads it from trusted in-process inspection over the same live host evidence, never from a public surface.
- Reconciliation never invokes Start, Stop, or Restart, and explicit Restart remains an explicit user action that is not a substitute for reconciliation.
- BL-020 running-or-failed close, BL-021, BL-022, automatic recovery, auto-sleep, scheduling, quotas, bulk actions, and multi-host operation remain deferred.
