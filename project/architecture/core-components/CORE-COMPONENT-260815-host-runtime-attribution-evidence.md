# CORE-COMPONENT-260815-host-runtime-attribution-evidence: Host Runtime Attribution Evidence

## Status

Adopted. **Amended 2026-08-15 (revision 2 of the BL-019 plan for Issue #43), amended again 2026-08-15 (revision 3), amended again 2026-08-15 (revision 4), and amended again 2026-08-15 (revision 5), and amended again 2026-08-16 (BL-020, Issue #45).** The **2026-08-16 amendment changes no element of the conjunction, no refusal class, and no count**: it binds a destructive durable-removal operation to these same exact-attribution rules and states the evidence obligations such an operation must meet. The identifier and creation date are preserved; no replacement core-component was created. The revision-2 amendment replaced the executable-path element of the conjunction with a derived installed-runtime launcher prefix, scoped listener ownership to the candidate's own process group, fixed the check evaluation order so three refusal classes are reachable, added the required-capability and no-automatic-adopted-death rules, and restated the refusal vocabulary at eighteen classes. The **revision-3 amendment changes no attribution behaviour**: it adds the negative-control isolation rules and the executed-evidence rules that a consumer must satisfy before its refusal classes and its restart proofs may be believed. The **revision-4 amendment changes no attribution behaviour either**: it corrects the revision-3 enforcement wording, which stated a per-project readiness-observation rule on a single record-level counter and was therefore unsatisfiable for a record carrying several projects whose evaluations stopped at different elements. The **revision-5 amendment changes no element of the conjunction, no refusal class, and no count**: it states the group-membership precondition as its own enforceable rule and refusal semantics, extends the trusted-scheduling rule to every intermediate pause including a readiness poll gap, and repairs the disclosure boundary, which a consumer's documentation had read as forbidding bounded refusal-reason enum names from committed evidence. The **2026-08-16 revision-7 amendment changes no element of the conjunction, no refusal class, and no count either**: it adds the participant-attribution rule and the episode-phase rule that executing a multi-participant race and a restart-spanning interruption showed to be missing. The **2026-08-16 revision-6 amendment changes no element of the conjunction, no refusal class, and no count either**: it corrects the timing-origin rule, which discriminated an admitted operation by its settled classification although a classification can be reachable on both sides of the claim, and it adds the capture-instant and reachable-choreography rules that executing a matrix against a real boundary showed to be missing. Superseded wording is not retained anywhere in this document.

## Purpose

Give Ascend one reusable, unprivileged, deterministic way to decide whether a live host process is an exact Ascend workbench runtime belonging to an exact registered project, so that any component which must reason about a runtime it did not itself launch — API-restart reconciliation today, residual audits and later recovery work tomorrow — refuses foreign, stale, recycled, mismatched, and ambiguous processes by construction rather than by judgement.

## Scope

Discovery, corroboration, and refusal of live workbench candidates on the local host, and the evidence classes those observations may publish. It governs the observation primitives, the conjunction that authorizes attribution, the positive-absence rule, and the disclosure boundary for attribution evidence. It does not govern what a caller does after attribution succeeds; ownership, lifecycle transitions, termination, and public state remain owned by `CORE-COMPONENT-260808-runtime-lifecycle-error-handling` and the delivered termination sequencer.

## Definition

### Rules
- Attribution evidence MUST be derived from live host facts about the process itself. A file, database row, environment variable, lock, or any other writable record MUST NOT be treated as an authority for attribution; it may at most be a claim that still requires the full conjunction below.
- The expected argument-vector prefix MUST be **derived from the installed runtime**, never assumed to be the configured executable path. A single resolver MUST resolve the configured executable to its real path, take the installation root as the parent of the resolving `bin` directory, assert the bundled interpreter under that root is executable, and yield the two-element prefix `[interpreterPath, installationRoot]`. When that resolution fails, attribution MUST refuse for every project with a distinct classification; a fallback prefix, a heuristic, and a comparison of `argv[0]` to the configured path string are all forbidden. A consumer MUST NOT construct an expected prefix by any other means.
- Candidacy MUST be decided by two independent project markers — the argument vector's final element matching a project's exact persisted canonical path, and the per-runtime data directory's owner-token segment matching a project's derived owner token. A process carrying neither marker is not evidence and MUST NOT be counted or refused. A process whose two markers name different projects MUST be a candidate for both and MUST be refused for both.
- Attribution MUST be a single complete conjunction evaluated for one pid within one bounded observation window. Every element MUST hold: the installed-runtime identity resolved; exactly one candidate exists for the project; the process is owned by the current effective uid, which MUST NOT be root; the argument vector begins with the derived launcher prefix; its final element is that project's exact persisted canonical path; the per-runtime data directory's owner-token segment derives from that project's id; the bind port and the data-directory port are the same integer; the remainder of the vector after the prefix is byte-equal to the vector the current build produces for that project at that port; the process is its own process-group leader; the bounded enumeration of that process group completes and contains it; a loopback listening socket exists on that port; that socket's inode is held by exactly one exactly observed conforming member of that same process group; the documented health-gated readiness contract is satisfied on that port; and a second read of the candidate's process-start time, the candidate's argument vector, and the listener-owning member's process-start time, taken after the readiness observation, is identical to the first. A missing, failed, incomplete, or unreadable element MUST refuse attribution.
- The specific argument checks — final element, owner token, and port agreement — MUST be evaluated **before** the wholesale byte-equality check. A wholesale comparison evaluated first subsumes them and makes their refusal classes unreachable and therefore unprovable.
- Listener ownership MUST be scoped to the candidate's **own process group**, never to the candidate's own file descriptors alone. A conforming member is a pid exactly observed to share the candidate's process group, run as the same non-root uid, present the derived interpreter as its `argv[0]`, and resolve its entry argument inside the same installation root. The owner MAY be the group leader or a forked member, and a consumer MUST NOT assume either. An inode held outside the group, held by a non-conforming member, held by an unobservable holder, or observed in more than one member MUST refuse attribution.
- **Group membership is a precondition of listener attribution, not a by-product of it (added in revision 5).** The candidate leader identifier MUST be supplied by the attribution boundary that already established leadership for that candidate, and MUST NOT be inferred from, defaulted to, or re-read out of the enumeration being tested. The process-group enumeration MUST be refused as `group-scan-incomplete` when it did not complete **or** when it completed without containing that exact candidate leader identifier, tested by strict numeric identity against the enumerated member identifiers. A completed enumeration whose member set is empty, or whose members do not include the candidate leader, is exactly as refusable as an enumeration that never completed, and completeness alone MUST NOT be accepted as evidence of membership. Both refusals MUST be decided **before** any listening-socket lookup, any file-descriptor read, and any readiness observation for that candidate, so a refused candidate produces no listener observation, no readiness observation, and no attribution.
- Exactly one candidate MUST be attributable to one project. Two or more candidates for one project MUST refuse attribution for that project, MUST NOT be disambiguated by recency, port order, or any other heuristic, and MUST NOT be signalled.
- One candidate MUST NOT be attributable to two projects. Owner token, canonical path, and port MUST all agree with the same persisted project, and a candidate that satisfies one but not the others MUST be refused.
- **Negative-control isolation.** A live process that carries either project marker is a candidate-bearing control. A validation that uses one MUST make it the sole candidate for exactly one registered project in the pass that observes it, and MUST therefore give it its own registered project, canonical path, and owner token; two candidate-bearing controls MUST NOT share a registered project. A candidate-bearing control MUST NOT be alive during a pass that must attribute a genuine survivor of the project it marks, because the exactly-one-candidate refusal precedes every signature check and is then the only correct settlement. A candidate-bearing control MUST be removed and independently proven absent — by completed probes over its identity, its listener, and its disposable paths — before such a pass begins. A control that coexists with survivors MUST carry neither marker, and its non-candidacy MUST be proven by computing both markers from its own observed argument vector against every registered project.
- **No control exemption.** A control MUST be settled by the same production predicate as any other candidate. Excluding a control from candidacy through a validation-only path, evaluating it outside a reconciliation pass, pre-classifying it, bypassing the predicate, or granting it any exception is forbidden; a refusal class claimed for a control MUST be the class that pass actually produced.
- **Executed evidence.** A recorded observation of this component's behaviour MUST be produced by executing the boundary that owns it. A deterministic scenario record MUST come from invoking the runtime-management, admission, routing, and public-projection paths with injected primitives, and every settled value in it MUST be read back from that run together with a per-record execution witness derived from the run itself. Any element-reachability evidence in that witness — readiness observation above all — MUST be keyed to the individual project it belongs to, never aggregated into a single record-level counter that several projects would have to share. A record assembled from expectation constants, a static serialized fixture, or a validator run over an artifact that run did not produce MUST NOT be accepted as evidence.
- **Real replacement processes.** Where a consumer claims a restart of its own host boundary, each claimed generation MUST be an execution of the repository's compiled entry point, recorded with operating-system-observed process identity, argument vector, listening-socket ownership, real requests served, and its real persistence file. A placeholder process, an in-process instance presented as a generation, a synthesized record, and an assigned identity MUST NOT be accepted as a generation.
- A boundary that consumes this component at process startup MUST expose reconciliation as a **required** capability, and its consumer MUST invoke it unconditionally. An optional member, an optional invocation, or a presence test that permits startup to continue without reconciling is forbidden, because it produces a success-shaped startup that publishes fabricated state for live survivors.
- An adopted runtime's death MUST NOT be published as an automatic transition. This component adds no background task, timer, interval, watcher, child-signal handler, or periodic health loop, and an adopted handle's terminal promise MUST NOT be placed in a drained background task set. A consumer MUST correct a dead adopted runtime only through its delivered on-demand paths, and MUST document that limitation on its user-facing surfaces.
- A refused candidate MUST NOT be signalled, terminated, adopted, routed to, claimed as owned, reported as ready or running, or counted as a residual belonging to Ascend. Refusal MUST be recorded as one bounded classification and nothing else.
- Positive absence MUST be an observation, never a default. Absence for a project MAY be claimed only from a completed, uninterrupted enumeration of the host process set that found no candidate for that project, or from a completed delivered audit triple for that project's single candidate showing process absence, owned process-group absence, and listener absence together. An interrupted, cancelled, deadline-abandoned, faulted, or partial observation MUST NOT be converted into absence.
- Every awaited host observation MUST be bounded and cancellable, MUST receive a cancellation signal, and MUST be abandoned at its deadline. An abandoned observation's result MUST NOT be read, recorded, published, or converted into an attribution, a refusal reason other than the deadline, an absence claim, or a state mutation. The deadline MUST be armed by the trusted synchronous monotonic scheduling primitive, never by a fallible awaited primitive. **Amended in revision 5:** the same rule governs every intermediate pause on that path, including the gap between two readiness attempts. A poll gap MUST be armed from the trusted scheduling primitive, MUST be at most the declared poll interval, MUST NOT extend past the enclosing bounded window, MUST resolve on that window's cancellation signal, MUST never reject, and MUST cancel its scheduled handle on every exit path, with a callback delivered after cancellation changing nothing. A fallible awaited delay primitive MUST NOT participate in any bounded observation, wait, or pacing on this component's paths; a consumer's other paths keep it unchanged.
- Observation MUST be read-only with respect to the host. Discovery and corroboration MUST NOT send a signal, open a listener, bind a port, write to a project directory, or modify any process, and MUST NOT require elevated privileges, PID-space exhaustion, or indefinite waiting.
- Attribution primitives MUST be injectable behind one explicit dependency surface so that every refusal branch is provable deterministically without real processes, and the production implementations MUST be the only default.
- Published attribution evidence MUST be limited to bounded enum classifications, one-way project tokens, counts, and elapsed measurements. Raw canonical paths, argument vectors, executable paths, process identifiers, process-start times, ports, loopback authorities, socket inodes, environment values, credentials, terminal or source content, stacks, and raw errors MUST NOT appear in any browser-visible surface, HTTP body, lifecycle event, or committed evidence artifact.
- Finer refusal classifications MAY be exposed to trusted in-process inspection and retained validation evidence, but the public classification for an unattributable or unreadied candidate MUST remain the single bounded failure category defined by the consuming lifecycle contract. **Amended in revision 5, because a consumer's user documentation contradicted this rule:** retained validation evidence explicitly **includes committed evidence artifacts**, so a bounded refusal-reason enum name MAY appear in a committed artifact and MUST NOT appear in a browser-visible surface, an HTTP body, or a lifecycle event. The prohibition on the raw values enumerated in the rule above is unchanged and absolute on public surfaces **and** in committed artifacts. A consumer's user-facing documentation MUST state the boundary at that granularity and MUST NOT claim that refusal classifications are absent from committed evidence.

- **Amended 2026-08-16 (BL-020, Issue #45). No element of the attribution conjunction, no refusal class, and no count changes.** A destructive operation that removes a subject's durable registration MUST establish that subject's resource absence through this component's existing exact-attribution rules and through no weaker mechanism: the same recorded root identity, the same owned process-group membership precondition, the same group-scoped loopback listener ownership, the same bounded cancellable observation, and the same audit triple. It MUST NOT adopt, signal, or claim any process it cannot exactly attribute, MUST NOT treat entry absence or a state label as absence, and MUST NOT accept a previously recorded audit that did not itself confirm the triple.
- **Amended 2026-08-16 (BL-020, Issue #45).** Retained evidence for such an operation MUST distinguish a completed zero-residual observation from an unresolved claim, and MUST be produced by executing the production paths with an execution witness rather than by asserting expected values. A scenario row MUST carry its declared bound, its observed elapsed classification measured from the operation's own admission instant, its per-subject release observations, its connection audit, its registration observations before and after, its authoritative public state, its stable-route result, its emitted-event set, its peer and control correlations, and its fixture manifest digests, all correlated by opaque subject token. The independent residual audit MUST be a separate re-observation taken after capture, MUST report per class either an integer zero backed by a completed probe or an explicit withheld claim, and MUST NOT report a zero assigned before teardown was attempted or derived from an incomplete probe. A negative control MUST be settled through the production predicate rather than by exemption or pre-classification, and a control that must coexist with the operation MUST have its non-candidacy proven from its observed argument vector. **Amended 2026-08-16 (Plan revision 7):** a row committed as evidence MUST be an execution of the scenario it names. A structurally copied row re-keyed to another scenario's identity MAY be used only as a substrate for proving the validator's own rejection classes, MUST be published as such by naming the rows that are executions of themselves, MUST validate clean before any corruption is applied, and MUST NOT be written to, merged into, or used to satisfy any claim of a committed artifact.

- **Amended 2026-08-16 (Plan revision 2, BL-020, Issue #45).** The timing origin of a row MUST be inhabitable rather than implied. A row MUST carry its route-entry instant, MUST carry its admission instant as a value that is non-null **if and only if** the operation actually installed its exclusive claim, and MUST carry an explicit origin discriminator naming which of the two the row's elapsed value was measured from. The validator MUST cross-check the three against the row's outcome and MUST reject: a refused-before-admission outcome carrying an admission instant, an admitted outcome declaring the route-entry origin, an admission instant earlier than the route-entry instant, and any elapsed value that is not reproducible from the declared origin. No row may be accepted whose origin, timestamps, and outcome are mutually consistent only under an assumption the artifact does not state, because that is precisely how a fabricated elapsed value survives review.

- **Amended 2026-08-16 (Plan revision 6, BL-020, Issue #45). The origin discriminator MUST be the settlement site, never the settled classification.** A boundary that admits work through an ordered set of conditions settles some of them *before* it installs the exclusive claim that admission grants. Which side of that claim a row fell on is a fact about **where the operation settled**, not about **what it settled as**: the same classification can be reachable both before the claim and from inside the admitted phases, and an operation that joins an already-claimed peer inherits the winner's classification verbatim without ever having installed a claim of its own. A row MUST therefore carry an explicit settlement-site discriminator drawn from a **closed, frozen enumeration of the boundary's pre-claim settlement sites**, and the validator MUST derive "this operation was admitted" from that discriminator alone. It MUST reject a row whose discriminator names a site the boundary does not have, whose discriminator disagrees with the row's classification where the site determines it, whose admission instant is non-null on a row naming a pre-claim site, whose admission instant is null on a row naming none, and whose admission-only witnesses — the frozen cardinality record, the confirmation record, and every phase-scoped invocation count — are present on a pre-claim row or absent from an admitted one. Deriving admission from the classification is prohibited outright, because it silently mislabels every classification the boundary can reach twice.
- **Amended 2026-08-16 (Plan revision 6, BL-020, Issue #45). Every witness MUST be captured at the production instant it describes.** A witness that names a condition holding at one instant of the production path — the values a confirmation predicate read, a counter's value while a claim was still held, the resources observed immediately before an irreversible effect — MUST be sampled at that instant, through a callable the production path itself invokes there, and MUST NOT be reconstructed afterwards from post-settlement observation. Reconstruction is prohibited even when the reconstructed value would be equal, because equality after the fact is exactly what a broken ordering also produces. Where the observing harness cannot reach a boundary-internal value, the row MUST record the strongest observation available **at that instant** and the artifact MUST state what that observation is; the boundary-internal discharge MUST then be proven separately, by a deterministic test of the boundary itself, and the two proofs MUST NOT be conflated.
- **Amended 2026-08-16 (Plan revision 7, BL-020, Issue #45). Every witness MUST be attributed to the participant that produced it.** Where an invariant needs more than one concurrent participant — because the participating boundaries' ordering forbids one participant from carrying every role — the proof MUST declare each participant's role, MUST record each participant's own settlement as the production path actually produced it, and MUST NOT merge, borrow, or relabel one participant's settlement as another's. A settlement raised by one mechanism MUST NOT be recorded as a settlement raised by a different mechanism even when both are non-success, because the classification is the witness that the mechanism ran. The evidence MUST carry exactly as many recorded settlements of a given kind as the production path produced, and the validator MUST reject a fabricated additional one on the same rule it rejects a fabricated classification.
- **Amended 2026-08-16 (Plan revision 7, BL-020, Issue #45). An episode that spans a boundary restart MUST attribute each count to the phase that produced it, and MUST state an outcome it cannot force as a conditioned disjunction.** An interruption episode contains several distinct phases — the interrupted operation, the transition to the replacement boundary, the replacement boundary's own recovery, and any later retry — and a count that more than one phase can produce MUST be recorded per phase. A single aggregate claim over the whole episode, such as “no signal was delivered”, is prohibited: it is unfalsifiable where it is true and false where an orderly transition legitimately signals its own records. Where the episode's outcome is decided by another boundary's contract, the evidence MUST state the expectation as that contract's own disjunction, MUST record which branch was taken and the element that decided it, and MUST NOT demand a fixed branch. Demanding an outcome the governing contract does not require is a defect in the proof, not in the system: it makes the correct behaviour fail and hides the branch that actually needs guarding.
- **Amended 2026-08-16 (Plan revision 6, BL-020, Issue #45). A scenario MUST be reachable through the participating boundaries' own ordering.** A declared choreography whose steps require a causal coupling the production ordering forbids MUST be replaced by a reachable one that proves the same invariant, or split into scenarios that each prove one half of it. It MUST NOT be made to pass by injecting a call the production path would not make, by bypassing a registration or refusal the ordering performs, or by relaxing the invariant. A scenario whose reachability rests on an ordering claim MUST record the production-observed witness of that ordering — the counter, settlement, or seam the production path itself increments or enters — so an unexecuted or mis-sequenced run is rejected as unexecuted rather than passing as a clean zero.

### Interfaces
- One discovery primitive that enumerates candidate process identifiers and reports explicitly whether its enumeration completed.
- One identity primitive that reports process-start time, process-group id, and owning uid for a pid.
- One argument-vector primitive that reports the exact argument vector for a pid.
- One installed-runtime identity resolver that yields the launcher real path, installation root, interpreter path, and two-element argument-vector prefix, or nothing at all.
- One process-group membership primitive that reports the member pids of a process group and whether its enumeration completed.
- One listener primitive that reports the listening socket inode bound to a loopback port, and one that reports the socket inodes held by a pid.
- One composed listener-ownership helper that, given a group leader, a port, and the installed-runtime identity, returns either the exactly observed owning member or one of the three bounded group-scoped refusals.
- One adoption constructor that turns a proven candidate into the delivered owned-runtime handle shape — exact identity, port, loopback internal URL, per-runtime data directory, bounded termination, bounded audit, and liveness — so downstream ownership, termination, cleanup, and shutdown contracts are reused unchanged.

### Expectations
- A caller receives either one exactly attributed candidate, a positive absence, or one bounded refusal. It never receives a probability, a best guess, or a partially verified candidate.
- A caller that cannot attribute MUST NOT fall back to launching a replacement while the ambiguity stands, because the unattributable process may be alive and holding that project's directory, port, and route.

## Rationale

The kernel already records everything needed to prove that a live process is the exact workbench Ascend launched for an exact project: the owning user, the executable, the complete argument vector containing the project's derived owner token and its persisted canonical path, the process-group leadership that the detached launch creates, and the socket inode that ties the listening port to that same process. Those facts cannot be forged by a process that was not launched that way, and they need no new writable state, no schema change, and no privileged facility. Requiring the full conjunction, plus a stability re-read, makes stale identity, recycled identity, replaced listeners, mismatched project evidence, and unrelated control processes fail deterministically instead of being argued about.

Two of those facts are subtler than they first appear, and getting them wrong inverts the component's guarantee. The configured executable path is a shell launcher, so the kernel shows the bundled interpreter and the installation root ahead of the built argument vector; anchoring to the *installation* rather than to the configured path string is what makes a byte-perfect vector from a foreign installation root refuse. And the process that binds the loopback port is frequently a forked member of the workbench's process group rather than its leader; scoping ownership to the group — while still requiring an exactly observed conforming member — is what keeps a genuine survivor attributable without widening into adoption of an unrelated listener.

## Usage Examples

```
# Deterministic refusal classes a consumer must be able to produce and prove:
#   ambiguous-candidates      two candidates for one project
#   launcher-unresolved       the installed-runtime identity could not be resolved at all
#   launcher-prefix-mismatch  argv does not begin with the derived interpreter and installation root
#   argv-mismatch             argument vector differs from the built vector
#   canonical-path-mismatch   final argument is not the project's persisted path
#   owner-token-mismatch      data directory token does not derive from the project id
#   port-mismatch             bind port and data-directory port disagree
#   uid-mismatch              process is owned by another user, or by root
#   not-group-leader          process is not its own process-group leader
#   group-scan-incomplete     process-group enumeration did not complete, or completed without the candidate leader
#   listener-absent           no loopback listener exists on the recorded port
#   listener-not-owned        listening inode not held by an observed conforming group member
#   readiness-unconfirmed     health-gated readiness was not observed in the bound
#   identity-unstable         second identity, argv, or listener-owner read differs from the first
#   absence-unconfirmed       candidate disappeared without a complete audit triple
#   scan-incomplete           process enumeration did not complete
#   deadline-exceeded         the bounded window closed first
#   manager-shutdown          the owning boundary shut down first
#
# Eighteen classes, closed and frozen. Declaration order is not evaluation order.
```

## Integration Guidelines

- Consume this component only from the runtime-management boundary that already owns process lifecycle. A route, proxy, browser client, or CLI MUST NOT perform attribution of its own.
- Derive the expected argument vector from the same builder the launch path uses, so a change to launch arguments cannot silently break or widen attribution.
- Treat a successful attribution as the start of ownership: register the exact identity in the delivered ownership index and let the delivered termination, cleanup, and shutdown contracts operate on it unchanged.
- Record refusals and absences with the same bounded classification vocabulary in inspection output and retained evidence, so validation can assert the exact class rather than a message.

## Exceptions

- A host without readable process, listener, or file-descriptor information MUST refuse attribution rather than relax any element of the conjunction. Refusal is the only permitted degraded mode.
- An independent residual audit MAY read the same primitives out of process for absence checking without performing adoption; it MUST still refuse to signal anything it did not attribute.

Source guards assert that the adoption predicate is one conjunction containing every element; that the expected argument-vector prefix is produced only by the installed-runtime resolver and that no source compares `argv[0]` to the configured executable path; that listener ownership is decided over the candidate's process-group member set rather than the leader's own descriptors, and that the candidate leader's membership in that set is tested immediately after completeness and strictly before any listening-socket or file-descriptor read; that a second identity read exists and is compared for the candidate and for the listener owner; that absence is claimed only from a completed enumeration or a completed audit triple; that no signal or launch occurs on a candidate path before adoption; that reconciliation is declared and invoked as a required capability; that no adopted handle's terminal promise enters a drained background task set; and that the deadline is armed by the trusted scheduler, that no reconciliation path awaits a fallible delay primitive for a deadline or for a poll gap, and that its end-to-end ceiling is the declared sum of its segments. A deterministic matrix proves at least one scenario per refusal class with injected primitives, a real-host conformance proof establishes that the derived launcher prefix and the group-scoped listener owner match a genuinely spawned runtime with negative controls for a foreign installation root and a listener outside the group, and a privacy scan proves no protected value reaches any public surface or committed artifact.

Three further enforcement obligations are added in revision 3, and each MUST fail mechanically rather than by review. A source guard asserts that the deterministic scenario module contains no expected outcome, refusal-class, public-state, event-name, or liveness literal and does invoke the manager, inspection, and public-projection entry points, and a mutation class rejects a record whose execution witness is missing, zero, duplicated, or inconsistent with the settled outcomes it claims.

**Amended in revision 4, because the readiness rule above was stated per project but enforced on one record-level counter.** Readiness observation MUST be recorded per project, in a map keyed by the record's own opaque project tokens whose key set equals that record's project set exactly, and MUST NOT be recorded in a single record-level counter that several projects share; a record with no project records an empty map. For each project independently, the count MUST be exactly zero when that project's evaluation settled or was refused before the readiness element, or never reached it; MUST be at least one when that project settled adopted, was refused at the readiness element, or was refused at the identity re-read that the order reaches only after readiness; and MUST be left unconstrained by class — but still observed — when an interruption leaves the evaluation order genuinely undetermined about where it stopped, namely a candidate that disappeared mid-window, a fired deadline, a boundary shutdown, and a settlement still pending at capture. Each count MUST be attributed from the recorded primitive call ledger by observed call target and observed boundary instance, MUST NOT be derivable from any expected outcome, classification, or public state, and MUST fail closed rather than be guessed when one observation cannot be attributed to exactly one project. A record-level aggregate total MAY be retained alongside the map provided it carries no per-project claim and is never below the map's sum. The mutation class MUST reject, at minimum, a cross-project swap of two counts, a missing project key, an extra or foreign project key, a nonzero count on a project refused before readiness, and a zero count on a project that reached readiness. A source guard asserts that a designated real-restart proof references the compiled entry point and constructs no in-process boundary instance of its own, and the evidence validator rejects, by name, a generation whose observed argument vector is not that compiled entry, whose argument vector carries an evaluation flag, whose listening socket is attributed to another process, that served no request, or whose persistence file was never observed. The evidence validator also rejects, by name, a missing control subepisode, a control that was not the sole candidate for its registered project, a control settlement or refusal class other than the declared one, a signalled control, a control not proven clear before the survivor phase, and a coexisting control whose observed markers are not both absent.

**Amended in revision 6, and each obligation MUST fail mechanically rather than by review.** The evidence validator asserts the settlement-site enumeration is closed and frozen, that every row names exactly one site or explicitly names none, that the site agrees with the row's classification wherever the site determines it, and that admission-only witnesses are present on exactly the rows that name no site; a mutation class rejects each of those corruptions by name. A source guard asserts that no validator or matrix module derives admission from a settled classification list. A deterministic control proves the capture-instant rule by executing a scenario in which the reconstructed value and the instant value differ, and asserting the row carries the instant value. A scenario whose choreography rests on an ordering claim carries that ordering's production-observed witness, and the validator rejects the row as unexecuted when the witness did not move. **Added in revision 7:** a mutation class rejects a recorded settlement the production path did not produce, including one participant's settlement relabelled as another's, and an episode spanning a boundary restart carries one labelled account per phase for every count more than one phase can produce, with the validator rejecting an aggregate claim over the episode and a recorded branch that names no deciding element.

**Amended in revision 5, and each obligation MUST fail mechanically rather than by review.** A source guard asserts that the composed listener-ownership helper tests the candidate leader's membership in the enumerated member set between the completeness test and the listening-socket lookup, and fails a source in which that test is absent or placed after the lookup. A deterministic scenario proves the whole predicate refusing a **completed** enumeration that omits the candidate leader, and records zero listener observations, zero file-descriptor reads, and zero readiness observations for that project; the enumeration-did-not-complete branch keeps its own deterministic negative controls at the primitive and boundary layers, so the two branches remain distinguishable in evidence. A source guard asserts that the consumer's reconciliation region contains no awaited fallible delay primitive and arms its poll gaps from the trusted scheduler, and a deterministic control injects a delay primitive that fails when invoked, so a reconciliation that depended on it could not settle. The documentation expectation asserts the disclosure boundary at the granularity stated above: bounded classifications in trusted inspection and committed validation evidence, raw values in neither.
