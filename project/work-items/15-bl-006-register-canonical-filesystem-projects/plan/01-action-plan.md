# Action Plan: BL-006: Register canonical filesystem projects

## Feature
- **ID:** 15
- **Research Brief:** `project/work-items/15-bl-006-register-canonical-filesystem-projects/research/00-research.md`

## ADRs Created
- None. The accepted TypeScript/SQLite stack and existing filesystem-path-safety contract already determine the architectural boundaries; this issue adds an in-process, issue-local registration service rather than selecting a new technology or system structure.

## Core-Components Created
- None. `CORE-COMPONENT-260808-filesystem-path-safety` already governs canonicalization, readability, canonical equivalence, policy containment, and non-mutation, while `CORE-COMPONENT-260810-sqlite-persistence-lifecycle` governs persistence ownership. The more detailed categories, fields, configured-home/allowed-roots inputs, and registration orchestration are Issue #15 product contracts, not a new reusable cross-cutting component. `DECISION-LOG.md` therefore requires no change.

## Acceptance Criteria

- **AC-1:** Service construction validates the complete configured-home and allowed-roots set before registration is available. The configured home and every allowed root are accepted only when they are absolute, existing, readable directories; each is canonicalized once for that constructed service, canonically equivalent allowed roots are deduplicated, and an empty allowed-roots set is a valid deny-all policy. Disposable symlink checks prove that later retargeting of an allowed root or configured home does not change the roots or home expansion used by an already constructed service.
- **AC-2:** With valid configuration, registration supports absolute paths plus exactly `~` and `~/...` home notation, expands supported home notation from the configured home before canonicalization, and registers an existing readable directory inside policy as one project. The record has exactly the persisted project fields—stable ID, display name, canonical path, and created-at value—and remains unchanged after all registration and persistence resources close and fresh service instances reopen the same database. The display name is the canonical directory basename, or the canonical root path when no basename exists.
- **AC-3:** An empty or whitespace-only submitted path returns the typed `path_required` category before filesystem access, while a submitted path containing a NUL code point returns the typed `unsupported_path_syntax` category before filesystem access. Nonempty supported paths are not globally trimmed: valid absolute and supported home-relative directory names containing whitespace, including leading or trailing whitespace in a path segment, register with that whitespace preserved in the canonical path and display name. These cases, missing paths, existing non-directory paths, unreadable directories, other unsupported input syntax, and directories outside the opening policy each return their distinct typed validation category where applicable. Every failure identifies only its category and the submitted-input field, includes no stack trace, raw platform error, or configured path value, and leaves project persistence unchanged.
- **AC-4:** Opening-policy decisions use canonical path-segment boundaries: an allowed root and its descendants can register, while prefix-sibling paths, lexical traversal outside a root, and symlinks resolving outside every allowed root are rejected; a symlinked allowed root is evaluated by its canonical target.
- **AC-5:** Sequential registration through absolute, supported home-relative, normalized, or symlinked expressions that resolve to the same allowed directory returns the same four-field existing project record and leaves exactly one durable canonical-path record.
- **AC-6:** Exactly eight concurrent registrations whose expressions resolve to the same allowed directory all return the same four-field project record, including the same stable ID, display name, canonical path, and created-at value, and leave exactly one durable record with no partial row.
- **AC-7:** Any invalid configured home or any invalid allowed root makes the entire service unavailable with one typed `invalid_opening_policy` configuration outcome. The outcome identifies only `configured_home` or the indexed `allowed_roots` field and includes no configured value, stack trace, or raw platform error; valid roots in a mixed set do not remain active, construction leaves the project row count and existing rows unchanged, performs none of the project-content mutations prohibited below, and registration cannot proceed until the complete configuration is valid.
- **AC-8:** Successful, duplicate, concurrent, and rejected registration paths do not create, delete, copy, move, rename, truncate, or write project content and leave fixture tree membership, file bytes, modification timestamps for every fixture node, and permission modes unchanged.
- **AC-9:** Finite repository validation uses disposable fixtures and covers all-valid configuration, canonically duplicate roots, empty roots, one invalid root among valid roots, invalid configured home, non-directory root, symlinked-root and symlinked-home canonicalization and retargeting, empty, whitespace-only, and NUL-containing submitted paths, whitespace-containing directories and path segments, valid absolute and supported home-relative inputs, missing paths, files, traversal, prefix siblings, symlink escape, equivalent paths, and cleanup. A bounded capability probe determines whether the current process can enforce host-permission unreadability: when it can, disposable unreadable-root and unreadable-project fixtures prove both typed outcomes; otherwise validation emits an inspectable skip artifact containing the failed probe result and does not claim host-permission proof. A controlled repository-local denial case always proves denied root and project access map to the unreadable typed outcomes.
- **AC-10:** Documentation records the registration boundary, configured-home and allowed-roots contract, empty-roots deny-all behavior, all-or-nothing `invalid_opening_policy` outcome and safe field identifiers, supported path syntax, canonical boundary and symlink behavior, typed registration categories and safe fields, display-name rule, duplicate and concurrency outcomes, permission-capability handling, non-mutation guarantee, disposable-fixture cleanup, and the out-of-scope boundaries.
- **AC-11:** The repository-configured finite full-validation command exits zero and its finite output identifies passing configuration, registration, persistence, non-mutation, fixture-cleanup, documentation, and permission-capability checks.

## Implementation Tasks

1. **T-1 — Define typed registration construction and fail-closed opening policy (AC-1, AC-3, AC-7).** Add an API-owned in-process registration module whose asynchronous factory first validates the complete `configuredHome` and `allowedRoots` set and only then opens `ProjectLibrary`. Return a discriminated ready result or the issue-local `{ category: "invalid_opening_policy", field: "configured_home" | "allowed_roots[n]" }` failure shape; never return a partially usable service. Canonicalize each configured entry once, deduplicate canonical roots, retain immutable canonical home/root strings for the service lifetime, and accept `[]` as deny-all. Keep failures value-free and keep Fastify, HTTP, UI, list, workbench, scan, clone/import, close-project, Git, network, and picker behavior out.
2. **T-2 — Implement submitted-path parsing, filesystem validation, and canonical containment (AC-2, AC-3, AC-4).** Accept only absolute paths, `~`, and `~/...`; classify blank and NUL before filesystem calls; preserve all nonblank input whitespace; expand against the constructed canonical home; and map missing, non-directory, unreadable, unsupported syntax, and outside-policy cases to distinct issue-local categories with only `field: "path"`. Canonicalize before policy checks and use path-segment containment so root/self/descendants pass while traversal, prefix siblings, and escaping symlinks fail. Use only read/inspection filesystem operations behind a narrow module-local test seam.
3. **T-3 — Orchestrate four-field persistence, identity, display names, equivalence, and restart (AC-2, AC-5, AC-6).** Derive the name from the canonical basename with canonical-root fallback, generate first-create UUID/time values through injectable defaults, and pass exactly the BL-005 `Project` fields to `ProjectLibrary.create`. Preserve BL-005 database conflict arbitration so sequential and exactly eight concurrent equivalent registrations return the same durable winner. Expose idempotent close ownership, prove a fresh registration service at the same database path returns the unchanged record, and do not expose listing as product behavior.
4. **T-4 — Build disposable filesystem safety and permission-capability fixtures (AC-7, AC-8, AC-9).** Add BL-006 helpers below `test-results/bl-006/fixtures` for unique trees, symlinks, whitespace names, files, modes, and controlled access denial. Snapshot every fixture node using relative membership/type, regular-file bytes, symlink target, high-resolution modification time, and permission mode. Bound a mode-`000` host-permission probe, always restore permissions in `finally`, write an inspectable `test-results/bl-006/permission-capability.json` with proved or skipped status and failed probe result, and always run deterministic injected-denial cases. Cleanup only the allocated fixture roots and prove absence while retaining the capability artifact.
5. **T-5 — Implement the complete registration acceptance matrix (AC-1 through AC-9).** Add unit and integration suites for every configuration, syntax, policy, persistence, equivalence, concurrency, fail-closed, non-mutation, readability, retargeting, and cleanup case in the issue. Reuse the production BL-005 database lifecycle and unique database paths; compare serialized existing rows around every rejected call/construction; verify exact result keys; and keep the matrix finite, deterministic, Linux-host-aware, and independent of routes or browser code.
6. **T-6 — Document registration and expose named finite validation signals (AC-9, AC-10, AC-11).** Update API/application docs and `.harness/engineering-harness.md` with the full Issue #15 boundary and generated evidence locations. Add a root `verify-project-registration` recipe that executes the finite BL-006 suites with verbose named groups, and call it from `just verify` so output explicitly identifies configuration, registration, persistence, non-mutation, fixture-cleanup, documentation, and permission-capability results. Keep harness checks delegating to `just verify` and add a documentation regression test synchronized to source constants and result categories.
7. **T-7 — Run focused and complete repository validation (AC-11).** Run the named BL-006 suites through `just verify-focused` while implementing, then run `just verify` without reducing coverage or skipping existing checks. Record category output, permission artifact status, coverage, build, Playwright, retained BL-004 audit, cleanup, and Git-status evidence in the later implementation record.
