# Research Brief: BL-007: Display the registered projects on Project Home

## GitHub Issue
- **Issue:** #17
- **Title:** BL-007: Display the registered projects on Project Home
- **Work Item:** `project/work-items/17-bl-007-display-the-registered-projects-on-project-home`

## Scope Classification
- **Scope Type:** issue

## Problem Statement

Project Home is a static empty scaffold even though BL-005 project persistence and BL-006 canonical filesystem registration are merged. The Fastify application does not initialize or close the persisted project library as part of its lifecycle, exposes no project-list route, and the React application does not load persisted projects. Issue #17 requires the registered-project collection to cross that existing persistence, API, and browser boundary with deterministic, accessible states while retaining the stated exclusions for registration, close, workbench behavior, navigation, search, sorting controls, tags, path mutation, and polished design.

## Acceptance Criteria

**Core**
- [ ] Before accepting requests, API startup initializes the project library from the documented database configuration and applies or validates all current migrations; after stopping that API and closing its resources, a fresh API instance against the same database lists projects persisted before the restart.
- [ ] API shutdown closes the initialized project-library resources and leaves no API-owned database handle open; repeated shutdown signaling has one documented safe outcome.
- [ ] Persistence initialization failure prevents the API from opening its listener and exits with one documented typed startup-failure category plus a structured log event. A finite repository-defined sentinel matrix proves the event contains the category but no supplied secret, SQL text, stack text, or database-path sentinel.
- [ ] The documented project-list endpoint returns 200 with one stable JSON contract containing every project in an unchanged persisted library exactly once and no project fields beyond ID, display name, canonical path, and created-at.
- [ ] The endpoint documents and consistently applies one deterministic total ordering, with ID as the final tie-breaker, so repeated requests against unchanged data return the same record order.
- [ ] An empty project library returns 200 with an empty project array in the same success contract.
- [ ] A persistence/list failure returns one documented non-2xx error contract with a stable safe error category and no success project array or partial records. A finite repository-defined sentinel matrix proves the response contains none of the supplied secret, SQL, stack, database-path, or internal-error sentinels.
- [ ] Project Home starts one initial list request per mount with a documented finite timeout and displays distinct accessible loading, empty, populated, and failure states; loading is announced to assistive technology.
- [ ] The empty state explains that registered projects will appear on Project Home without providing or simulating project registration.
- [ ] The failure state provides an actionable accessible message and one explicit retry control; each retry activation starts one new bounded list request.
- [ ] The populated state displays every valid returned project exactly once with its visible display name, complete canonical path, and one semantic keyboard-focusable Open action. Each action has an inspectable identity equal to the stable project ID in that record and an accessible name that identifies the project; automated evidence compares those identities with the returned records.
- [ ] Each Open activation, including rapid repeated activation, starts no workbench and performs no navigation. It produces an accessible status associated with that project which identifies its display name and states that opening is not available in BL-007; repeated activation leaves the same status outcome.

**Edge Cases**
- [ ] Long paths and paths containing leading, internal, or trailing whitespace or HTML/script metacharacters are rendered as text without interpretation; the complete canonical value remains available through accessible text or title and is not trimmed, normalized, or otherwise mutated.
- [ ] A valid API project record has a non-empty string ID, non-blank display name, non-empty string canonical path, and finite non-negative safe-integer created-at; a response containing a duplicate ID or any malformed record produces one deterministic safe failure state with no project cards.
- [ ] Rapid repeated retries use newest-request-wins behavior: each newer retry cancels or supersedes the prior in-flight request, a stale response cannot replace newer state, and unmount aborts the current in-flight request without a later state update.
- [ ] No control, API operation, or navigation outcome is added for project registration, project close, workbench startup or status, search, user-controlled sorting, tags, or path mutation; no fake workbench destination is introduced.

**Verification**
- [ ] Finite component validation covers loading, empty, populated, and failure states; retry and rapid repeated retry; stale-response suppression; unmount abort; keyboard tab and Open activation; repeated Open activation; project action identities; accessible roles, names, announcements, and deferred status; malformed and duplicate records; and path text safety.
- [ ] Finite API validation uses isolated databases and covers empty results, populated deterministic ordering, complete restart visibility, safe redacted initialization and list failures with no partial response, repeated shutdown, and resource closure.
- [ ] One bounded desktop Chromium scenario runs the real web and API applications against an isolated database; proves the empty state; proves a pre-seeded populated state displays every project card and supports keyboard Open activation with the deferred status and matching project identity; and proves failure followed by successful retry through a repository-controlled fault.
- [ ] Chromium cleanup requests graceful shutdown of each server it started and observes each process exit within a documented finite timeout, then proves its listeners are absent and removes only its isolated database and database sidecars; no scenario-owned process, listener, or database artifact remains.
- [ ] Documentation records database startup and configuration, migration-before-serving and restart behavior, endpoint success and error contracts and ordering, record validity, all Project Home states and accessibility outcomes, retry and stale-request behavior, the deferred Open boundary, exact validation commands, isolation, controlled fault, cleanup, and the observed bounded result.
- [ ] The root full-validation command, just verify, exits zero.

## Repository Findings

- `PRD.md` defines Project Home as one of the two primary MVP surfaces (`DD-009`), requires every registered project to display its name, filesystem path, and Open action (`FR-001` and `AC-001`), requires the Projects and Workbench distinction to be clear (`NFR-017`), and makes modern desktop Chromium the primary browser target (`NFR-019`). The Slice 2 text includes broader Project Home capabilities, but Issue #17 narrows this delivery to listing and deterministic states.
- Git history shows the prerequisite slices are merged into the branch base: `c2f28d0` is `feat(api): persist project library (#14)` and `b437e6c` is `feat(api): register canonical filesystem projects (#16)`. Their verification records are `project/work-items/13-bl-005-persist-the-project-library/verify/summary.md` and `project/work-items/15-bl-006-register-canonical-filesystem-projects/verify/summary.md`.
- `apps/api/src/project-library.ts` exposes `createProjectLibrary(databasePath)` and `createApplicationProjectLibrary(databaseUrl)`. Construction normalizes and creates the parent directory, opens one closeable database resource, runs `migrateDatabase` before constructing the repository, closes on construction failure, and returns an idempotent `ProjectLibrary.close()`.
- `apps/api/src/db/client.ts` resolves `ASCEND_DATABASE_URL` from a filesystem path or local `file:` URL, with `apps/api/ascend.db` as `DEFAULT_DATABASE_PATH`. `createDatabase` owns a libSQL client and exposes an idempotent close operation. `apps/api/src/db/migrations.ts` applies the two committed ordered migrations `0000_project_library` and `0001_project_canonical_path_unique`.
- `apps/api/src/db/schema.ts` and `apps/api/src/project-persistence.ts` define exactly four project fields: `id`, `name`, `canonicalPath`, and `createdAt`. `createdAt` validation requires a finite non-negative safe integer. `ProjectRepository.list()` wraps adapter failures as `ProjectPersistenceError` without a cause or raw driver message; the Drizzle adapter currently orders only by ascending project ID.
- `apps/api/src/project-registration.ts` constructs the BL-006 service over `createProjectLibrary`, persists canonical paths and canonical-basename display names, preserves valid path whitespace, and closes its library idempotently. It adds no HTTP behavior. `apps/api/test/project-registration-persistence.test.ts` records that canonical paths and names, including a whitespace-bearing basename, survive a fresh reopen unchanged.
- `docs/README.md` and `apps/api/README.md` document the default database, `ASCEND_DATABASE_URL`, explicit migration command, migration-before-repository behavior, four-field model, deterministic ID ordering, typed persistence failures, restart behavior, and BL-005/BL-006 cleanup boundaries. Both explicitly state that Fastify startup, HTTP listing, and UI integration are deferred to BL-007.
- `apps/api/src/app.ts` currently autoloads all plugins and routes without constructing application persistence. `apps/api/src/routes/root.ts` exposes only `GET /` with `{ name: "ascend", status: "ok" }`. The route autoload guidance in `apps/api/src/routes/README.md` treats route modules as encapsulated Fastify plugins and points shared functionality to the plugins boundary.
- `apps/api/src/server.ts` creates one module-scoped Fastify instance. `startServer()` registers the application and then listens. `stopServer()` closes Fastify and telemetry, is private, and is attached separately with `process.once` to both SIGINT and SIGTERM. Startup rejection currently logs the raw error object with `server.log.error(error, "Ascend API failed to start")` and sets `process.exitCode = 1`.
- `apps/api/src/instrumentation.ts` starts OpenTelemetry at import time and exposes `stopTelemetry()` as a direct SDK shutdown call. No repository code documents or exercises repeated telemetry shutdown, combined repeated signal delivery, a finite API shutdown bound, or listener-absence auditing for the product API.
- `apps/api/test/helper.ts` builds fresh Fastify instances through `appPlugin`, calls `ready()`, and closes every instance after each test. Because the application plugin owns no persistence today, the helper has no database configuration or project-library lifecycle. `apps/api/test/routes/root.test.ts` covers only the root health route.
- Existing BL-005 tests already establish useful current behavior: `project-library-contract.test.ts` checks four unchanged fields and idempotent close; `project-library-restart.test.ts` closes one generation and lists both records through a fresh generation; `project-persistence-unit.test.ts` checks safe typed list failure; and `project-migrations-integration.test.ts` covers fresh, current, and prior migration states.
- `apps/api/test/project-database-test-helper.ts` allocates unique databases below `test-results/bl-005/databases`, refuses the developer default path, closes registered callbacks in reverse order, removes only the selected database and `-wal`, `-shm`, and `-journal` sidecars, and confirms those files are absent. Its disposable root and error names remain BL-005-specific.
- Current documentation regression tests encode the deferred boundary. `apps/api/test/project-persistence-documentation.test.ts` requires exact statements that Fastify does not construct the library and that BL-007 owns HTTP/UI behavior. `apps/api/test/project-registration-documentation.test.ts` requires listing and UI to remain among BL-006 exclusions.
- `apps/web/src/App.tsx` is a static Project Home scaffold with an Ascend heading, an existing `Open Project` button, and one empty-workbench message. It has no effect, request, project type, response validation, timeout, retry, status announcement, card collection, or navigation behavior. `apps/web/src/main.tsx` renders under React `StrictMode`.
- `apps/web/src/App.test.tsx` uses Testing Library and currently checks only the heading and existing button. The web Vitest configuration uses jsdom and enforces 80 percent line, function, branch, and statement coverage. React 19.2.8 and Testing Library 16.3.2 are the installed component stack (`apps/web/package.json`).
- `tests/e2e/project-home.spec.ts` currently checks the same static heading and button. `playwright.config.ts` runs desktop Chromium against Vite at `127.0.0.1:5173`, starts only the web application, permits an existing local Vite server outside CI, and enables full parallelism. It does not start the API, allocate a database, configure an API origin, or own API cleanup.

- The root `justfile` is the command surface. `just verify` currently runs formatting, linting, strict type checks, package tests with coverage, the BL-006 named gate, builds, Playwright, and the retained capacity audit. `.harness/engineering-harness.md` delegates `harness checks` to this recipe and describes boot as non-persistent and test-backed; live API/web startup remains a recorded back-pressure gap.

## Constraints

- The scope is the issue-scoped registered-project listing and its deterministic Project Home states. Registration, close, workbench startup/status, navigation, search, user sorting, tags, path mutation, fake destinations, and polished design remain excluded by Issue #17.
- The accepted application stack remains the pnpm TypeScript monorepo with React/Vite in `apps/web`, Fastify in `apps/api`, SQLite/Drizzle persistence, Vitest, and Playwright (`ADR-260808-typescript-monorepo`; decision log decisions 26-29).
- API-owned SQLite access must remain explicit-path and closeable, committed ordered migrations must run before repositories operate, and database validation must remain isolated from the documented default database (`CORE-COMPONENT-260810-sqlite-persistence-lifecycle`).
- The existing durable project contract is exactly `id`, `name`, `canonicalPath`, and `createdAt`; canonical-path uniqueness is database enforced, timestamps are finite non-negative safe integers, and list failures are wrapped as typed persistence errors (`apps/api/src/project-persistence.ts`; `apps/api/src/db/schema.ts`).
- Canonical registered paths and display names originate at the server-side BL-006 boundary. The listing boundary must not reinterpret registration, mutate project membership, or mutate project files (`CORE-COMPONENT-260808-filesystem-path-safety`; `apps/api/src/project-registration.ts`).
- Structured runtime records must use the Fastify logger and must not expose source, terminal, command, clipboard, prompt, credential, or secret content. Stable fields and redaction are required (`CORE-COMPONENT-260808-structured-runtime-logging`).
- Project Home must remain clearly distinct from Workbench and usable in modern desktop Chromium (`PRD.md`, `NFR-017` and `NFR-019`). The accepted full-page workbench presentation defers routing and Project Home integration and does not authorize workbench behavior in this issue (`ADR-260810-full-page-browser-workbench-presentation`).
- Strict TypeScript, repository formatting and linting, Vitest, Playwright, 80 percent unit coverage thresholds, and application-documentation consistency are existing repository constraints (`CORE-COMPONENT-260808-development-standards`).
- Raw operating commands remain behind root `justfile` recipes. Harness checks delegate to `just verify`, and harness boot currently leaves no live server (`CORE-COMPONENT-260806-project-command-interface`; `ADR-260808-governed-engineering-harness`; `.harness/engineering-harness.md`).
- Existing BL-005 and BL-006 documentation and documentation-contract tests describe HTTP/UI integration as deferred. Those statements are current repository facts, not a contract that can remain accurate after BL-007 behavior exists.

## Risks and Open Questions

- The endpoint path, success-envelope property names, safe error-envelope shape/category, ordering keys before the required final ID tie-breaker, startup-failure category, and finite browser request timeout are not specified by current repository documentation or Issue #17.
- The module-scoped Fastify instance in `apps/api/src/server.ts` is unlike the fresh-instance test helper and exposes no public stop function. The ownership boundary needed to observe complete API restart, repeated shutdown, telemetry shutdown, listener absence, and database closure is therefore not represented in current application APIs.
- Startup currently logs the raw rejected error object. Driver, migration, SQL, stack, secret, or database-path detail could be present in that object, while the issue requires a bounded safe startup event.
- SIGINT and SIGTERM each have their own one-shot handler. Receiving both can call `stopServer()` twice, while repeat behavior for Fastify close plus `NodeSDK.shutdown()` is neither documented nor covered in current source tests.
- Repository list validation occurs on create input, not on rows returned by `list()`. The React scaffold has no runtime response validation. Malformed records and duplicate IDs therefore have no current safe browser boundary.
- `ProjectPersistenceError` safely hides adapter details, but no HTTP error mapping exists. Fastify default error handling could produce a contract different from the issue-required stable error category.
- The web development server has no API proxy or configured API origin, and Fastify has no cross-origin plugin. The browser-to-API topology for both local operation and the real two-server Chromium scenario remains unspecified.
- React `StrictMode` can expose mount, unmount, and effect cleanup behavior during development. Current code has no request ownership or abort behavior against which the one-request-per-mount, newest-request-wins, stale-response, and unmount requirements can be assessed.
- Project Home already renders an `Open Project` registration-labelled button even though this issue excludes registration controls and requires the empty state not to provide or simulate registration. The intended status of that pre-existing control within the BL-007 boundary is unresolved.
- The complete canonical path must remain available and unchanged for long, whitespace-bearing, and metacharacter paths. Current scaffold CSS and component behavior provide no established overflow or accessible full-value convention.
- Current Playwright configuration starts only Vite, can reuse an unrelated existing server, and runs files fully in parallel. It has no ownership model for a real API process, isolated database, controlled list fault, graceful dual-server shutdown, listener audit, or exact database-sidecar cleanup.
- The reusable database helper is named and rooted for BL-005. Whether its current `test-results/bl-005/databases` boundary is also the repository-defined isolation boundary for BL-007 is not stated.
- Current application documentation and regression tests deliberately assert that Fastify and UI integration do not exist. They will be stale once the Issue #17 behavior exists unless repository documentation changes in lockstep.
- RPIV pre-flight encountered a transient cancelled-process `startTimeTicks` assertion after the process exited (`.harness/temp/agent/session-buffer.md`, `DL-150`). Per the run observation, an immediate rerun succeeded without a code change. The initiating race or environmental condition remains unknown.
