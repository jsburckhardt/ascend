# Research Brief: BL-005: Persist the project library

## GitHub Issue
- **Issue:** #13
- **Title:** BL-005: Persist the project library
- **Work Item:** `project/work-items/13-bl-005-persist-the-project-library`

## Scope Classification
- **Scope Type:** issue

## Problem Statement

Ascend has an accepted SQLite and Drizzle metadata stack and a preliminary project schema, but it does not yet have a durable project-persistence contract, committed migrations, a repository-owned migration command, or an in-process application-service boundary. The issue requires project metadata to survive complete database and in-process service restarts, with bounded migration, duplicate, validation, isolation, cleanup, and documentation outcomes. HTTP, a network server, UI, filesystem existence, and path canonicalization behavior are explicitly outside this issue.

## Acceptance Criteria

**Core**
- [ ] A paved repository command accepts an explicit database path, creates the database when no file exists, applies every migration committed in the repository, reports the finite ordered set of applied migration IDs and the current migration ID, and on rerun reports zero newly applied migrations while retaining the same current migration ID.
- [ ] Inspection limited to the project table proves it has exactly these persisted project columns and no others: stable project ID, display name, canonical path, and created-at timestamp. The persistence contract creates and lists exactly those fields and returns their values unchanged after all database handles close and reopen.
- [ ] A bounded restart test creates exactly two project records, closes all database, persistence, and in-process application-service resources, constructs fresh instances against the same explicit database path, and proves exactly those two records reappear once each through the same in-process boundary. No HTTP route, network server, or UI is required.
- [ ] Canonical path has a database-enforced unique constraint. A sequential duplicate-create case and a fresh case of eight concurrent same-path create attempts each leave exactly one durable row for that path. Every persistence operation deterministically returns either the created record or that same existing record with an explicit duplicate/existing disposition; no generic database error escapes and no partial row is retained. This disposition is a persistence outcome only and does not define BL-007 HTTP behavior.

**Edge Cases**
- [ ] A finite repository-defined set of synthetic sentinels representing source text, terminal output, ports, PIDs, handles, environment data, credentials, and secrets is used for bounded schema, row, and database-byte inspection. The project table contains only the four allowed columns and their values, and those sentinels are absent from database bytes; when one sentinel is deliberately supplied as an allowed display-name or canonical-path value, row inspection proves it appears only in that allowed column. This is a check of the fixed sentinel set, not an exhaustive claim about all possible data.
- [ ] Empty stable ID, empty or whitespace-only display name, empty canonical path, and invalid or non-finite created-at input are rejected before write with typed deterministic validation outcomes defined by the persistence contract. Each case leaves the row count and the serialized values of all four fields in existing rows byte-for-byte unchanged. Filesystem existence and canonicalization policy are explicitly deferred to BL-006 and are not validated here.
- [ ] Migration validation covers exactly these starting states: no database, a current database rerun, and one committed repository fixture representing the immediately previous committed migration ID and containing two valid project records. Upgrade from the fixture applies only pending migrations, preserves the serialized values of all four allowed fields in both records byte-for-byte, and reaches the current migration ID.
- [ ] Every BL-005 persistence, migration, and restart test creates and records a unique database path under the repository-defined disposable directory, closes all handles, removes only that database and its SQLite sidecars, and proves cleanup. The test boundary refuses to run when pointed at the developer/default database location documented by this issue.

**Verification**
- [ ] Documentation records the default database location, explicit override, paved migration/init command, migration IDs and output, exact four-column schema, duplicate/existing persistence disposition, restart proof, prior-version fixture, test isolation and refusal behavior, and cleanup.
- [ ] The configured full repository validation passes.

## Constraints

- The accepted persistence technology is local SQLite with Drizzle ORM, not a remote database or new service (`project/architecture/ADR/ADR-260808-typescript-monorepo.md`; `project/architecture/ADR/DECISION-LOG.md`, decision 27).
- Persistence is metadata-only. The project table is limited to stable ID, display name, canonical path, and created-at timestamp; project source and runtime internals such as terminal output, ports, PIDs, handles, environment values, credentials, and secrets must not become additional persisted fields (`PRD.md:218-230`, `PRD.md:418-428`, Issue #13).
- Filesystem existence, readability, and canonicalization policy belong to BL-006. This issue receives a canonical path as persistence data and enforces its uniqueness, but does not validate the host directory (`PRD.md:394-410`; `project/architecture/core-components/CORE-COMPONENT-260808-filesystem-path-safety.md`).
- The required boundary is in-process and must be restartable after all persistence resources close. The issue excludes HTTP routes, network-server behavior, UI, runtime state, backups, authentication, multi-user behavior, and production deployment (Issue #13).
- Migration behavior is constrained to committed repository migrations and exactly three specified starting states, including a committed fixture for the immediately previous committed migration ID. The repository currently has no migration history or established migration-ID convention.
- Canonical-path uniqueness is database-enforced and operations must produce typed deterministic validation or created/existing outcomes rather than leaking generic database errors (Issue #13; `project/architecture/core-components/CORE-COMPONENT-260808-filesystem-path-safety.md`).
- Runtime state must not be treated as durable project metadata. The runtime lifecycle contract requires reconciliation with actual processes and keeps process handles and internal ports out of persistent metadata (`project/architecture/core-components/CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`).
- Structured logs and telemetry must not expose source, terminal, command, clipboard, prompt, credential, secret, or environment content (`project/architecture/core-components/CORE-COMPONENT-260808-structured-runtime-logging.md`; `project/architecture/core-components/CORE-COMPONENT-260808-host-process-environment.md`).
- Repository operating commands remain root `justfile` recipes, and harness checks continue to delegate to `just verify` (`project/architecture/core-components/CORE-COMPONENT-260806-project-command-interface.md`; `project/architecture/ADR/ADR-260808-governed-engineering-harness.md`).
- Strict TypeScript, configured formatting and linting, Vitest, Playwright where applicable, 80 percent unit coverage thresholds, and application-documentation updates are existing repository constraints (`project/architecture/core-components/CORE-COMPONENT-260808-development-standards.md`).
- Database work must respect the issue-specific unique disposable path, exact database-and-sidecar cleanup, closed-handle, and default-location refusal boundaries. Existing broad workbench cleanup conventions do not by themselves establish these database-specific boundaries.

## Risks and Open Questions

- The acceptance criteria require a fixture for the immediately previous committed migration ID, but the repository has no committed migration ID at present. What baseline qualifies as the immediately previous committed migration for this first persistence delivery is unresolved.
- The issue says explicit database path, while existing code and documentation expose `ASCEND_DATABASE_URL` with `file:ascend.db`. The accepted override syntax and whether path and URL are interchangeable are not specified.
- The resolved developer/default database location is not documented. Because the current default is relative, the exact location to protect with the refusal boundary is unresolved.
- Migration ID format, ordering semantics, current-ID semantics when no migration has run, and the machine-readable or human-readable output contract are not established anywhere in the repository.
- Physical column names currently use `id`, `name`, `canonical_path`, and `created_at`, while the issue describes semantic fields. Whether those current physical names are part of the required contract is not explicit.
- The persistence contract has no defined TypeScript input/output types, created-at representation, validation outcome taxonomy, or created/existing disposition vocabulary. Drizzle timestamp mode also introduces a Date-to-integer mapping whose relationship to byte-for-byte serialized preservation is not documented.
- No in-process project application-service boundary exists. The ownership and lifecycle meaning of application-service resources, distinct from database and persistence resources, are therefore unresolved at the repository level.
- No current connection, transaction, or concurrency policy establishes behavior for eight simultaneous same-path creates. The database uniqueness declaration exists, but deterministic per-operation dispositions and non-leaking error behavior do not.
- The finite sentinel values and repository-defined database disposable directory are not named. Existing `test-results/` conventions are broad and currently include no database-specific path recorder or default-location guard.
- The global client in `apps/api/src/db/client.ts` is created at import time and is not closed by Fastify or telemetry shutdown. This can conflict with complete close-and-reopen semantics and exact cleanup if the current lifecycle remains unchanged.
- NFR-006 also mentions runtime-state reconciliation, but Issue #13 explicitly excludes runtime state. Only project-library recovery is attributable to this issue; later ownership of runtime reconciliation remains outside this research scope.
- Database-byte sentinel inspection can be affected by SQLite file and sidecar lifecycle. The repository has no current convention defining when handles are closed, when sidecars are removed, or which file state is authoritative for that bounded inspection.
