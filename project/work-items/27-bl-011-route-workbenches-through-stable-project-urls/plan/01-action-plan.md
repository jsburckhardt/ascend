## Architecture and Repository Impact
- Add a direct API dependency on `ws` 8.x and its declarations; do not rely on the transitive database-client copy and do not add a general proxy plugin.
- Add small pure contract modules for project-ID validation, public failures, safe headers, redirects, cookies, stable paths, and evidence validation; add one memory-only proxy manager for raw HTTP, upgrades, sockets, and shutdown.
- Register the stable Fastify base/descendant route and one removable Node `upgrade` listener. Integrate proxy shutdown before the existing runtime-manager, registration, library, and telemetry shutdown sequence.
- Extend the BL-010 launch arguments only to disable generic code-server port-proxy routes. Keep loopback binding, direct argv, one runtime per active project, four-field SQLite metadata, filesystem non-mutation, and full-page presentation unchanged.
- Add focused Vitest fake-upstream matrices, lifecycle/security tests, one real Playwright Chromium scenario, one owner-readable ignored evidence file, a residual-audit command, and documentation contract tests.
- Update `justfile`, `README.md`, `apps/api/README.md`, `docs/README.md`, `docs/project-runtime.md`, and a dedicated stable-routing runbook. No web UI, schema, migration, BL-012 header or Project Home wiring, multi-project policy, public authentication, TLS, or multi-host behavior is added.

## Acceptance Criteria

### Core
- **AC-1:** Ascend owns `/projects/{projectId}/workbench/` and all descendant paths. Each request or upgrade resolves the registered project, starts or reuses its single BL-010 runtime, and forwards the route-suffix path and query unchanged to that runtime. The runtime listener remains loopback-only, and no internal loopback authority appears in browser-visible URLs, downstream HTTP response headers or bodies, cookies, or redirects; the restricted evidence exception is defined under Verification.
- **AC-2:** The workbench base document, nested assets, and WebSocket connections operate under the stable project prefix. Finite browser evidence shows all requests and upgrades remain same-origin and under that prefix without changing the BL-003 full-page presentation.
- **AC-3:** The HTTP fake-upstream matrix includes these exact payload cases in addition to the redirect, cookie, header, streaming, abort, and failure cases below: (1) `GET` a nested asset with a query and preserve its `200` text body, `Content-Type`, `Cache-Control`, and `ETag`; (2) `HEAD` an asset with no response body; (3) `POST` a 257 KiB deterministic binary body and echo it with `201`, valid `Content-Length`, and matching SHA-256 proof against generation input and an expected digest declared before execution; and (4) `GET` a byte range with the `Range` request and preserve `206`, `Content-Range`, and `Accept-Ranges`.
- **AC-4:** Redirect and cookie cases in the HTTP matrix prove: (1) a `302` upstream root-relative `Location: /login?x=1` is rewritten under the stable project prefix; (2) a `302` same-upstream absolute loopback `Location` is rewritten under that prefix; (3) one predeclared absolute `https` `Location` whose host differs from the upstream is rejected with the typed `502` outcome; and (4) `Set-Cookie` with `Path=/` becomes the stable prefix root, `Path=/foo` becomes the stable prefix plus `foo`, and no `Path` receives the stable prefix root. The cookie `Domain` attribute is either removed or the cookie is rejected according to one rule declared before the matrix runs, while `Secure`, `HttpOnly`, and `SameSite` are preserved.
- **AC-5:** The HTTP fake-upstream matrix proves `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, and `Upgrade` are stripped in both directions except for required WebSocket upgrade semantics.
- **AC-6:** The HTTP fake-upstream matrix proves an exactly 32-chunk × 16 KiB streaming response under a consumer delay has SHA-256 equality against generation input and an expected digest declared before execution. After an observed barrier proves chunk 5 was emitted and received, a separate client abort closes the upstream stream, leaves zero matrix sockets, and leaves the shared runtime running.
- **AC-7:** The WebSocket fake-upstream matrix is limited to these exact cases: one text echo with byte-for-byte equality; one 64 KiB binary echo with SHA-256 equality against predeclared generation input and digest; ping/pong; clean close code `1000` with the exact reason; upstream abnormal close with one exact downstream close-code or error outcome declared before execution, without claiming reserved code `1006` was transmitted in a close frame; handshake timeout; upstream refusal; client close during handshake; downstream backpressure with 16 ordered frames × 32 KiB and matching per-frame hashes; and two sequential reconnects that identify and reuse the same runtime. Each timeout has a declared finite bound. The abnormal-close case yields a downstream abnormal rather than `1000` close within that bound; handshake timeout returns the declared `504` code/message; upstream refusal returns the declared `502` code/message; an observed pending-handshake barrier precedes the client close, which is then observed upstream and produces no late downstream response; and every case ends with both matrix sockets closed.
- **AC-8:** Exactly eight concurrent initial client operations for one project—precisely four HTTP requests and four WebSocket upgrades—are held at one observable pre-start barrier, released together, invoke one BL-010 start/readiness sequence and all use the same running PID identity and internal port.

### Edge Cases
- **AC-9:** One complete, non-overlapping safe-failure table is declared before any matrix runs and contains exactly one row for every category named here: malformed project ID `400`; unknown well-formed ID `404`; persistence failure `503`; each named BL-010 typed runtime failure other than manager shutdown mapped to `502` or `504`; upstream DNS, connect, reset, and invalid HTTP failures each `502`; handshake timeout and upstream-response timeout each `504`; and manager shutdown before response or upgrade commitment `503`. Every row has one exact public code and message, every category executes once, and each execution proves the table match and redaction.
- **AC-10:** Finite project-ID validation asserts `400` for exactly `../x`, `%2f`, `%5c`, NUL encoding `%00`, and a 129-character ID, plus `404` for one well-formed unknown ID. Arbitrary client-supplied upstream `Host`, forwarded, or proxy-target headers are ignored or stripped and cannot change the resolved upstream.
- **AC-11:** For the exact controlled security requests, access and application log events emitted between per-case start/end markers and the corresponding downstream response headers and bodies are captured and scanned for distinct sentinels representing the internal port, canonical path, authorization token, cookie, query secret, body secret, command/environment marker, and WebSocket and terminal payload. Each sentinel is a unique declared literal, and its literal and percent-encoded forms each have zero matches in those bounded captures. The opaque project token may appear only in captured stable-route URLs and its dedicated evidence field.
- **AC-12:** After an observable barrier proves handshakes or streams are pending, manager shutdown settles within one documented finite bound and closes every proxied socket. A not-yet-committed HTTP response or upgrade returns the `503` manager-shutdown outcome; an already-committed response or upgraded socket closes with one exact abort/close outcome declared before execution and does not attempt a new HTTP status. A client disconnect closes only that client upstream stream and does not stop or invalidate the shared runtime.

### Verification
- **AC-13:** One real Chromium scenario executes exactly three fresh navigations/reconnects through the stable route; captured operation counts show three navigation attempts, three WebSocket connection attempts, and zero retry attempts. One runtime PID identity and internal port are reused throughout; the Explorer sentinel is visible; Preview sentinel text renders in the built-in webview; and the integrated terminal matches hostname, `vscode` user, and `pwd` while producing a 256 KiB deterministic output whose generation input and expected SHA-256 were declared before execution. Every captured browser request and WebSocket URL is same-origin and under the stable prefix, and the page URL and public network URLs contain no loopback port string.
- **AC-14:** Final cleanup evidence proves zero open sockets owned by the fake HTTP/WebSocket fixtures or their matrix clients; every browser context and socket opened by the real scenario closed; manager shutdown complete; the exact BL-010-owned runtime PID/start identity and listener absent; the validation-owned unrelated control listener still alive; and a finite post-cleanup residual audit with no matrix/proxy socket, owned runtime process, or owned listener remaining.
- **AC-15:** One restricted, owner-readable local evidence file may contain the internal port and records the opaque project token, stable route, runtime reuse, matrix results, browser results, redaction results, cleanup results, and residual audit. It is absent from version control and excluded from the public-documentation scan; public documentation and committed public evidence contain no raw internal port.
- **AC-16:** Documentation records the stable route and base-path behavior, redirect, header, cookie, and WebSocket outcomes, the complete safe failure code/message table, redaction and evidence-disclosure rules, runtime ownership and reuse, exact validation commands and finite bounds, injected faults, cleanup procedure and observed result, and every out-of-scope boundary in the Problem.
- **AC-17:** Repository-configured focused and full validation commands each exit zero, produce inspectable results for the complete HTTP and WebSocket matrices and real Chromium scenario, and end with the cleanup and residual-audit outcomes above.
