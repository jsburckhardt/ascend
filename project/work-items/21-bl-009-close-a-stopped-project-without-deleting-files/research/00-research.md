# Research Brief: BL-009: Close a stopped project without deleting files

## GitHub Issue
- **Issue:** #21
- **Title:** BL-009: Close a stopped project without deleting files
- **Work Item:** project/work-items/21-bl-009-close-a-stopped-project-without-deleting-files

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Project Home can list and register durable projects but cannot remove a registration. Issue #21 is limited to closing one persistence-only registered project, treated as stopped because Ascend has no product runtime manager, by stable project ID. The registration must be removed only after explicit confirmation while the project directory and files remain unchanged. Running or failed workbench close is deferred to BL-020, and runtime status, stop, restart, bulk close, undo, soft delete, archive, and product filesystem cleanup are outside this issue.

## Acceptance Criteria

**Core**
- [ ] Closing by stable project ID removes exactly one matching metadata row in one transaction and returns the stable ID with an explicit `closed` disposition. An unknown or already-absent ID returns typed `project_not_found` and leaves all metadata unchanged; a persistence failure rolls back and leaves the matching row and all other metadata unchanged.
- [ ] The close service invokes no project-filesystem API for success, unknown or already-absent ID, malformed input, persistence failure, transport ambiguity, retry, or concurrent requests; database-resource access is outside this project-filesystem prohibition.
- [ ] The documented DELETE project operation (`DELETE /projects/{id}` or a repository-consistent equivalent) delegates each accepted close once and returns a success response containing the stable ID and `closed` disposition. Malformed ID, unknown or already-absent ID, and persistence failure have distinct documented non-2xx statuses or categories and contain no partial success data.
- [ ] Close responses, logs exposed by bounded validation, and user-facing errors contain none of the supplied stack, SQL, database-path, project-content, secret, or internal-error sentinels.
- [ ] Project Home provides exactly one semantic, keyboard-focusable Close action for each project card. Activating it opens a modal dialog named `Close <project name>?` whose exact body copy is: `Closing removes this project registration from Ascend. The filesystem directory and files will not be deleted.`
- [ ] The dialog keeps focus within its controls for Tab and Shift+Tab. Escape and Cancel close it without a close request or metadata mutation and restore focus to the activating Close action.
- [ ] Closing requires explicit activation of a destructive Confirm control. Repeated Confirm activation during one close attempt sends no additional request. Cancel remains available while cancellation is known to prevent transmission; once transmission has occurred and the outcome cannot be known, Cancel is unavailable and the pending or recovery state is programmatically announced.
- [ ] A confirmed successful close removes only the matching stable-ID card without reloading the page and announces success. Focus moves to the next card Close action, otherwise the previous card Close action, otherwise the Project Home heading; closing the final card displays the existing empty state.

**Edge Cases**
- [ ] A definitive validation, API, persistence, or pre-transmission transport failure preserves the matching card and the dialog or stable-ID recovery state, announces the failure category without internal detail, and identifies the next recovery action. Retry of the same stable ID is available only when the outcome proves no close mutation or an authoritative refresh proves that the ID remains present; every other post-transmission outcome requires reconciliation before retry.
- [ ] A timeout, connection reset, or other ambiguous post-transmission outcome makes no optimistic card change and locks the close interaction for the original stable ID while the documented project-list operation refreshes the authoritative list. If that ID is present, retry becomes available; if absent, the UI applies the same card-removal, announcement, focus, and empty-state outcome as confirmed success; if refresh fails or is invalid, the interaction remains locked, announces that the result is still unknown, and offers refresh again without guessing.
- [ ] Retry and reconciliation use only the original stable project ID. Repeated retry or refresh activation creates at most one active request, and completion from an older attempt, reconciliation, cancellation, or unmounted page cannot change cards, dialog state, focus, announcements, or recovery state.
- [ ] Exactly eight concurrent DELETE requests for one registered stopped project complete within repository validation bounds with one `closed` response and seven typed `project_not_found` responses, zero remaining rows for that ID, no raw database error exposure, and an unchanged project-filesystem manifest.
- [ ] Project names, paths, IDs, and error text containing whitespace, HTML or script metacharacters, and values at each documented supported length bound remain inert text in cards, dialog copy, announcements, and errors.

**Verification**
- [ ] Before-and-after recursive manifests for a disposable registered fixture prove identical directory membership, file bytes, permissions, and recorded timestamps after Cancel, successful close, unknown ID, persistence failure, transport ambiguity, retry, and repeated already-absent close. Manifest collection and comparison are repository-local, bounded, and complete before test-only fixture removal.
- [ ] Finite isolated persistence, service, and close-operation evidence covers success, unknown and already-absent ID, malformed ID, persistence failure with complete rollback, sentinel redaction, no project-filesystem calls, the exact eight-request concurrency result, restart with the closed ID absent from the authoritative list, resource closure, and removal of only the isolated database and test fixtures after integrity evidence is captured.
- [ ] Finite component and client evidence covers dialog copy and accessible role/name, focus containment and restoration, Tab and Shift+Tab, Escape and Cancel with zero close requests, destructive Confirm, repeated activation prevention, pending announcements, success and final-card empty state, definitive errors and same-ID retry eligibility, timeout/list reconciliation for present, absent, failed, and invalid results, stale completion, unmount, supported-bound and metacharacter text rendering.
- [ ] One bounded real desktop Chromium scenario uses keyboard interaction with the merged BL-008 flow to register a disposable project, cancel Close once, then confirm Close and prove card and authoritative-list removal plus an unchanged sentinel file. A separate repository-controlled persistence or transport fault proves the documented error and recovery outcome without external services or credentials.
- [ ] After project-content integrity is recorded, browser success and controlled-failure validation removes only test-owned process groups, listeners, isolated database and sidecars, and disposable fixtures, then proves that none remain. This cleanup is test-harness ownership and adds no product cleanup or archive behavior.
- [ ] Documentation records the DELETE operation and outcomes, the persistence-only stopped-project boundary, exact confirmation copy, keyboard and focus behavior, same-ID ambiguous-outcome recovery, non-mutation evidence, validation commands, controlled faults, test-only cleanup result, and deferral of running or failed workbench close to BL-020.
- [ ] The repository-configured focused validations and root full-validation command exit zero and leave no close-scenario process, listener, database, sidecar, or disposable fixture behind.

## Repository Findings
- `PRD.md` defines FR-014 as removing the project from Project Home, stopping Ascend-managed runtime resources, and never deleting or modifying the project directory. AC-019 requires removal after confirmation, AC-020 requires the directory and contents to remain unchanged, NFR-018 requires explicit safe-close language, and CON-005 states that Ascend does not own project contents. Metric 5 targets zero filesystem modifications caused by Close Project, and the risk register calls for no filesystem-delete path.
- The merged history contains BL-005 persistence, BL-006 registration, BL-007 listing, and BL-008 Open Project interaction (`c2f28d0`, `b437e6c`, `2356284`, and `831ec7a`). Current application documentation in `docs/README.md`, `apps/api/README.md`, and `apps/web/README.md` records the resulting project library, list, registration, recovery, and cleanup contracts.
- `apps/api/src/db/schema.ts` defines one `projects` table with `id` as the primary key and only `name`, `canonical_path`, and `created_at` in addition. No runtime status, soft-delete marker, or close disposition is persisted.
- `apps/api/src/project-persistence.ts` exposes `ProjectPersistenceAdapter.insert`, `findByCanonicalPath`, and `list`, while `ProjectRepository` exposes only `create` and `list`. `ProjectPersistenceError.operation` currently permits only `create` or `list`. The Drizzle adapter orders lists by `createdAt` and then `id`; it has no row-removal operation or explicit transaction boundary.
- `apps/api/src/project-library.ts#createProjectLibrary` resolves an explicit database path, creates its parent directory, opens a closeable database resource, applies migrations, and exposes `create`, `list`, and idempotent `close`. `apps/api/src/db/client.ts#createDatabase` wraps a local libSQL client and has idempotent close ownership.
- `apps/api/src/app.ts` constructs two closeable owners against the configured database path: a listing `ProjectLibrary` and a BL-006 `ProjectRegistrationService`, then closes both in the Fastify `onClose` hook. The product application decorates Fastify only with `projectLibrary` and `projectRegistration`; no product runtime manager or workbench state is present.
- Product project HTTP behavior is centralized in `apps/api/src/routes/projects.ts`. Existing routes are `GET /api/projects` and `POST /api/projects`. The list route validates the complete four-field list, rejects duplicate IDs, and returns only `project_list_failed` on failure. The registration route strictly validates media type and shape, delegates accepted requests once, maps typed outcomes, and redacts unexpected detail behind `project_registration_failed`. There is no DELETE route.
- The project-route plugin installs a route-local error handler whose generic unexpected path emits `project.registration.failed` and `project_registration_failed`. That behavior is registration-specific even though the plugin contains the project list route as well.
- `apps/api/src/project-registration.ts` is the only project-filesystem seam in the product path. Its `RegistrationFileInspector` performs canonicalization, directory inspection, and readability checks for registration. Persistence and list code do not receive that inspector. `apps/api/test/project-registration-acceptance.test.ts` records that registration uses only read and inspection operations and leaves fixture manifests unchanged.
- Workbench lifecycle code under `apps/api/src/workbench-*` and the proof CLI is bounded proof infrastructure, not integrated product runtime management. `docs/workbench-proof.md` describes BL-001 and BL-004 as proof or diagnostic surfaces rather than a multi-project product runtime. `apps/web/src/App.tsx` announces that Open is unavailable and performs no workbench request or navigation. ADR-260810 likewise defers product routing and lifecycle integration.
- `apps/web/src/projects.ts` strictly parses list and registration envelopes. `loadProjects` uses the authoritative `GET /api/projects` operation. `sendRegistrationPayload` has a controlled `not_transmitted` result only before fetch invocation; timeout, reset, abort after invocation, invalid status, unreadable content, malformed JSON, or invalid contract all become `unknown`.
- `apps/web/src/use-project-home.ts#useProjectHome` owns list, registration, retry, and refresh through one active `Owner`, an `AbortController`, and a monotonic generation. Invalidated, timed-out, cancelled, or unmounted owners cannot update cards, input, focus identifiers, announcements, or recovery mode. Registration recovery preserves one serialized payload and reconciles an authoritative list by stable IDs.
- `apps/web/src/App.tsx` renders the existing loading, failure, empty, and populated states. Cards are keyed by stable ID and currently contain exactly one semantic Open button. A stable-ID map supports scroll and focus of Open actions after registration. A polite live status region announces application state. Names and paths are emitted as React text with whitespace-preserving styles. There is no Close action, dialog, focus trap, close recovery UI, or installed dialog-specific dependency in `apps/web/package.json`.
- Card order is a repository contract: API and web comparators use `createdAt ASC, id ASC`. The existing empty state is headed `No registered projects`, and the page heading is `Ascend` beneath the `Project home` label.
- Existing API tests establish relevant patterns: `apps/api/test/project-persistence-unit.test.ts` verifies typed persistence wrapping without raw causes; `apps/api/test/project-list-route.test.ts` verifies exact ordering, malformed-row rejection, and sentinel redaction; `apps/api/test/project-registration-route.test.ts` verifies one delegation, exact envelopes, eight-way concurrency for canonical-path registration, restart durability, and no content mutation.
- Existing web tests establish relevant interaction patterns: `apps/web/src/project-client.test.tsx` covers bounded list ownership and stale suppression; `apps/web/src/project-registration-client.test.ts` covers byte-identical retry and unknown transport classification; `apps/web/src/use-project-home.test.tsx` and `apps/web/src/App.test.tsx` cover one active owner, cancellation, authoritative refresh, stable-ID focus, inert metacharacter text, announcements, and unmount suppression.
- `apps/api/test/project-registration-fixture-helper.ts#snapshotFixture` recursively records relative membership, type, mode, nanosecond modification time, file bytes, and symlink targets. It is already used before fixture removal in BL-006 and BL-008 integrity checks.

- Browser cleanup in `tests/e2e/project-home.spec.ts`, `apps/api/test/helpers/project-home-process-group.ts`, and `apps/api/test/helpers/open-project-cleanup.ts` owns detached API and web process groups, bounded graceful stop with exact-group escalation, listener absence, isolated database sidecars, fixture allocations, and final residual counts. ## Constraints
- Issue #21 is a persistence-only stopped-project slice. It must not claim runtime status or close running or failed workbenches; BL-020 remains the deferred owner of those cases. Existing proof runtime modules are not a product runtime-management boundary.
- The stable project ID is the database primary key and the identity used by list ordering, card keys, focus, retry, and reconciliation. Current validation documents only a non-empty string; no maximum ID, name, or canonical-path length is documented beyond the 4,096-byte registration request bound.
- The persisted project model currently has exactly four physical and contract fields. Existing documentation and schema-minimization checks exclude runtime state and other metadata.
- CON-005 and `CORE-COMPONENT-260808-filesystem-path-safety.md` prohibit delete, move, rename, copy, write, chmod, or other project-directory modification during close. The issue additionally prohibits invoking a project-filesystem API across every close outcome; database-file access remains separate.
- SQLite ownership must remain explicit-path and closeable, migrations must run before repository use, and isolated database handling must refuse the documented default location and remove only selected database sidecars after handles close.
- Existing API contracts use `/api/projects`, exact response shapes, typed safe categories, one accepted delegation, and structured redacted errors. Raw stack, SQL, database path, project content, secrets, and internal text are outside observable responses and logs.
- The existing authoritative list rejects malformed records and duplicate IDs as a whole; it does not expose partial cards. Its deterministic order is `createdAt ASC, id ASC`.
- Current web request ownership permits one active list or registration-related operation, uses bounded AbortControllers and monotonic generations, and treats post-fetch transport or contract uncertainty as unknown. Stale completion and unmounted-page completion are inert.
- Existing Project Home accessibility uses semantic controls, keyboard activation, focus by stable ID, an `aria-live` status region, associated alerts, and React text rendering. The current application has no dialog or focus-containment abstraction to rely on as repository evidence.
- Test-harness cleanup owns only allocated processes, listeners, databases, sidecars, and disposable fixtures. Product cleanup or archive behavior is excluded.
- Repository operation and validation commands must remain behind root `justfile` recipes. TypeScript strictness, configured formatting and linting, Vitest, Playwright desktop Chromium, and coverage thresholds remain adopted project constraints.
- Documentation currently states the full MVP close meaning in `docs/README.md`, while API and web READMEs say project close is deferred. Issue #21 requires the persistence-only boundary and BL-020 deferral to be explicit without implying that runtime close already exists.

## Risks and Open Questions
- **Boundary mismatch:** FR-014 and the filesystem-safety core-component describe Close Project as stopping managed resources as well as removing metadata, but Issue #21 treats every persistence-only registration as stopped and defers running or failed runtime close to BL-020. Documentation or behavior that generalizes this slice to all projects would conflict with that boundary.
- **No observable runtime state:** The schema, service construction, HTTP list, and UI contain no runtime status. The issue supplies the stopped classification externally; the repository cannot currently distinguish a future running or failed project.
- **Undefined identifier bounds:** Current code accepts any non-empty project ID and does not document maximum lengths for ID, name, or canonical path. What exact malformed-ID syntax and supported length bounds govern the DELETE path and rendered close interaction?
- **Persistence semantics gap:** No delete adapter, repository outcome, close service, explicit transaction, rollback behavior, or delete concurrency behavior exists. The behavior of eight concurrent row removals through the current libSQL and Drizzle stack has not been recorded in repository evidence.
- **Multiple database owners:** API startup opens a listing library and a separate registration-owned library against the same SQLite file. Which existing owner is authoritative for close lifecycle and failure injection is not stated by current documentation or interfaces.
- **Error-handler coupling:** The project route error handler labels generic unexpected failures as registration failures. A close failure passing through that path could be miscategorized or logged under the wrong event unless the boundary is made explicit in later stages.
- **Transmission certainty:** The current browser transport can prove non-transmission only through a controlled pre-send hook. Once `fetch` is invoked, timeout, reset, parse failure, contract failure, and cancellation all collapse to unknown. The repository has no current signal that marks the exact point at which Cancel ceases to guarantee non-transmission.
- **Shared interaction ownership:** Registration, list load, retry, and refresh currently share one page-level owner and generation. The required per-stable-ID close lock, modal state, focus restoration, and authoritative refresh can conflict with registration or list activity unless ownership interactions are unambiguously bounded in later stages.
- **Focus targets after removal:** The current focus map contains Open actions only. Repository behavior does not yet establish Close-action refs, modal focus containment, restoration after Escape or Cancel, or next, previous, and heading fallback after card removal.
- **Authoritative refresh distinction:** Current registration reconciliation detects IDs added relative to a snapshot. Close reconciliation instead depends on presence or absence of one original stable ID. That behavior is required by the issue but has no current source or test evidence.
- **Fault controllability:** Existing browser support injects list and lifecycle cleanup faults, but there is no repository-controlled close persistence or post-transmission transport fault surface. Availability and isolation of such a fault are unresolved.
- **Concurrent response ordering:** The issue fixes aggregate eight-request outcomes but does not state which request receives `closed`; scheduling order may be nondeterministic even when the aggregate is deterministic.
- **Documentation consistency:** Root docs already summarize full close semantics, while application READMEs defer close entirely. The persistence-only stopped boundary must avoid claiming either product runtime shutdown or filesystem ownership.
