# Project runtime manager

Issue #25 adds an internal, in-process runtime manager over the persisted four-field project record. BL-016 adds a separate read-only public projection, BL-017 adds manager-owned selected-runtime Stop, and BL-018 adds manager-owned Restart for a running or retained failed runtime without exposing internal runtime identity.

## Interface and ownership

ProjectRuntimeManager.start({ projectId, canonicalPath, signal? }) validates the exact ID/path pair with ProjectLibrary.findById. It resolves an immutable snapshot with project ID, state, PID and process-start identity, loopback internal URL and port, canonical path, stable route, opaque owner token, startedAt, and elapsedMs. `stop({ projectId })` and `restart({ projectId })` select and claim only that manager entry. inspect(projectId) reports starting, running, or bounded failed snapshot state; absence represents stopped. lastFailure(projectId) returns the retained typed diagnostic. shutdown() owns global cleanup and resolves one memoized status plus an audit row for every retained owned runtime identity and a bounded inventory of unresolved restart admissions.

Process handles, PID identities, ports, in-flight operations, and lifecycle state are memory-only and exist only in manager memory. SQLite remains metadata-only with id, name, canonical_path, and created_at; no migration is required. Snapshots and failures never contain a command, environment, credentials, secrets, source or terminal content, command output, stacks, raw errors, or redaction sentinels.

## Public runtime state projection

The public vocabulary is exactly `Stopped`, `Starting`, `Running`, and `Failed`. A missing or registered manager entry reports `Stopped`; an accepted start or restart before readiness reports `Starting`; running and stopping entries report `Running`; and a retained failed entry reports `Failed` with one bounded category. The internal six-state entry vocabulary is `registered`, `starting`, `running`, `stopping`, `restarting`, and `failed`. The six lifecycle transition targets are `starting`, `running`, `failed`, `stopping`, `stopped`, and `restarting`; `stopped` is a transition target, not a persisted entry or fifth public state. Retained-failure precedence means a completed failure is never replaced by absence or process existence. `reportPublicStates` is a synchronous, read-only manager projection: it performs one ordered entry-map pass and returns only project ID, state, and the `Failed` category. It does not await or call process, port, health, launch, cleanup, audit, or event dependencies.

`GET /api/projects/runtime` lists authoritative persisted projects, applies the same `createdAt ASC, id ASC` order as `GET /api/projects`, and projects all IDs in one synchronous pass. Success is exactly `{"runtimes":[{"id":"stable-id","state":"Stopped"}]}` with `failureCategory` only on `Failed`. Library or projection failure is exactly `500 {"error":{"category":"runtime_state_failed"}}`; no partial or empty success-shaped fallback is returned. `GET /api/projects` remains the unchanged four-field `id`, `name`, `canonicalPath`, and `createdAt` contract.

Project Home owns a monotonic authoritative list revision and makes no runtime request before the first successful list. It issues exactly one request per revision, one per Retry, and one after each successful or already-stopped Stop settlement. It also issues one request after each successful Restart settlement; it aborts superseded or unmounted work and has a 5,000 ms projection bound. The response must match the exact ordered project-ID set. Missing, extra, duplicate, or reordered rows make the whole list explicitly unavailable; loading, transport failure, and timeout do the same. No partial state, optimistic state, or `Stopped` fallback is rendered. Failed cards display client-owned category text only, never a server message or protected diagnostic. The browser adds no polling, event stream, or health probe.

## Selected-runtime stop state machine

`POST /api/projects/{id}/runtime/stop` and Project Home Stop delegate to `ProjectRuntimeManager.stop`; neither the stable proxy nor the route performs termination directly. The manager first confirms the persisted project, then resolves one of these bounded cases:

| Selected entry | Result | Manager state and side effects |
|---|---|---|
| no registration | `rejected/not-registered` | unchanged |
| persisted project with no entry, or unreleased `registered` entry | `rejected/no-managed-runtime` | unchanged |
| `registered` released by an earlier confirmed stop in this manager | `already-stopped` | unchanged, no process call or event |
| `starting` | `rejected/start-in-progress` | start continues unchanged |
| `restarting` | `rejected/restart-in-progress` | restart continues unchanged |
| `failed` | `rejected/failure-retained` | retained category and ownership unchanged |
| `stopping` | joins the installed stop operation | one result, one cleanup phase, no duplicate event |
| `running` | exact synchronous claim before any await | installs `stopping`, then settles confirmed or retained failed |
| manager shutdown begun | `rejected/manager-shutdown` | unchanged |

The running claim reuses the exact generation, ready runtime, and pre-stop snapshot. No await occurs between reading the running entry and installing the stopping entry. Start and proxy acquisition recheck ownership after every awaited liveness or health observation; if Stop won, they return `runtime-stopping` rather than reuse the claimed snapshot. Stop-versus-exit, health, and false-liveness contenders compare-and-set the exact entry, so exactly one terminal owner mutates, cleans up, and emits; losers remain silent. Concurrent same-project Stop callers join one operation, while peer entries and unrelated controls are untouched.

Confirmed success requires the returned audit to report all three: exact process identity absent, owned process group absent, and loopback listener absent. The release label alone never establishes success. Confirmation deletes that generation's ownership record, installs `registered { released: true }`, and returns `stopped`; later stops of that entry return `already-stopped`. A fresh API process has no released entry, so the same persisted project returns `runtime_not_managed` until API-restart reconciliation is delivered by BL-019.

An incomplete or negative audit resolves `rejected/stop-unconfirmed`, installs retained `failed/stop-unconfirmed`, and keeps the ownership record for shutdown. A termination deadline does the same after cancelling the sequencer. A termination fault, including unexpected signal failure, installs the same retained failure but rejects so the route returns `runtime_stop_failed`; no entry remains stuck in stopping. A settlement that no longer owns its exact stopping object raises `RuntimeStopInvariantError`, installs nothing further, records no additional cleanup, and emits no terminal event.

## Termination bounds, signals, and attribution

The production sequencer uses `performance.now()` as its monotonic termination clock. Lifecycle event `elapsedMs` continues to use the manager's existing lifecycle clock; it is not a termination deadline or wall-clock phase measurement. The default bounds are 2,000 ms graceful, 2,000 ms force, and 1,000 ms final audit allowance. The manager's caller-side overall backstop is their 5,000 ms sum.

Four awaited observations are fallible and independently bounded: process-start identity, process-group membership, listener absence, and poll delay. Cancellation is propagated, but a primitive that hangs or ignores cancellation may be abandoned; incomplete observation never becomes absence evidence. The three trusted synchronous primitives are signal delivery, monotonic `now`, and native deadline scheduling. The deadline comes from an independent `setTimeout` scheduler rather than any awaited primitive, so a blocked delay cannot block return. A signal already aborted on sequencer entry causes immediate `unconfirmed` with no identity read, signal, wait, or audit.

Signal delivery returns `delivered`, `refused`, or faults. `ESRCH` is the only refused case and triggers one bounded settlement audit without opening a phase window or escalating. Any other signal error propagates as a termination fault. After confirmed delivered `SIGTERM`, the sequencer allows the complete 2,000 ms graceful window measured from that delivery. Only then may a confirmed delivered `SIGKILL` open its own complete 2,000 ms SIGKILL escalation window measured from that delivery. A refused force signal opens no force window and settles `unconfirmed`. The pre-signal ownership observations have their own bounded allowance; exhaustion is unconfirmed and sends no signal. No signal may occur after caller cancellation, abandonment, or the trusted deadline.

Owned-descendant attribution means membership in the exact root process group. The designated episode samples the complete observable member closure immediately before Stop and records every PID/start identity for independent absence checks. A descendant that escaped with `setsid` or `setpgid` is outside that attribution boundary, so process-group absence is not claimed as proof of arbitrary descendant absence.

Cleanup cardinality is per phase. The selected-stop phase calls terminate once and records at most one completed audit for the claimed generation. Confirmed release removes ownership, so global shutdown repeats nothing. Unconfirmed or faulted release retains ownership, and shutdown intentionally performs one new termination plus one new audit for that exact record; it does not reuse the prior unconfirmed audit and never runs concurrently with the stop phase. No third re-attempt occurs.

The public Stop route accepts an absent body or empty JSON object, rejects operation fields, and has a 1,024-byte body limit. Success is exactly `{"id":"stable-id","outcome":"stopped"}` or `{"id":"stable-id","outcome":"already-stopped"}`. Ten bounded error categories cover invalid ID/request, project not found, runtime not managed, start or restart in progress, retained failure, unconfirmed stop, manager shutdown, and unexpected stop failure. Responses contain no public runtime state, release/audit data, PID, port, path, authority, process identity, or server message.

## Selected-runtime restart state machine

`POST /api/projects/{id}/runtime/restart` and Project Home Restart delegate exclusively to `ProjectRuntimeManager.restart`. A running entry and a retained failed entry that still owns its exact process identity are eligible. A stopped or unowned persisted project remains an Open concern and returns `runtime_not_managed`; a start or stop already in progress returns its distinct bounded conflict. Exactly concurrent same-project Restart callers join one operation, while different projects use independent browser and manager lanes.

One internal `restarting` entry spans release and replacement and projects publicly as `Starting`; no intermediate `registered` or `Stopped` state is exposed. Replacement launch begins only after the prior exact process identity, owned process group, and listener are all confirmed absent. Success installs one new immutable running generation and returns only `{"id":"stable-id","outcome":"restarted"}` publicly. The route has the same strict absent-or-empty body contract and 1,024-byte body limit as Stop. Its ten client-visible errors cover invalid ID/request, missing registration, unowned runtime, start/stop conflicts, unconfirmed release, replacement failure, manager shutdown, and an unexpected route failure.

The trusted Restart clock uses the `RuntimeDeadlineScheduler` monotonic clock and native deadline scheduling, never the fallible process delay dependency. Production bounds are 5,000 ms for ordinary release, 15,000 ms for quarantine reclamation, 20,000 ms for admission/quarantine release, 60,000 ms for replacement, and 1,000 ms for settlement. The normal manager bound is 66,000 ms, the admission/quarantine bound is 81,000 ms, and the browser transport bound is 85,000 ms.

A pending replacement admission is installed synchronously immediately before launch. It prevents a deadline or retry from interpreting a launch whose process handle has not yet materialized as proven absence. Late materialization is keyed by admission ID plus exact PID, process-start identity, and port; detached observation may mutate only admission and quarantine state. It cannot install a successor snapshot, route, event, or project-keyed cleanup.

Restart launch cleanup is identity-keyed. A confirming collision or failed-attempt cleanup deletes exactly that attempt. A non-confirming cleanup moves that identity to quarantine and aborts the phase with `restart-replacement-unconfirmed`; the manager reads that typed phase abort before the launch error, including readiness-timeout and last-attempt collision branches. A successful collision retry leaves one ownership record for the healthy replacement.

Evidence uses `residualCount: 0` only after an exact completed audit proves the relevant process, group, and listener absent. `residualCount: null` is mandatory for an unresolved admission, unaudited retained identity, uncleared quarantine, or any other state where the manager cannot make an absence claim. Validation-owned fixture teardown is reported separately as integer `teardownResidualCount: 0` and never upgrades manager uncertainty into success.

Project Home shows Restart only for authoritative `Running` or `Failed` rows. The selected card is busy and its Open, Stop, Restart, and Close controls are disabled while its Restart is pending; another project remains independently usable. Successful settlement announces completion, performs exactly one authoritative runtime refresh, and returns focus to the selected Restart control after that refresh remounts it. Classified failures use client-owned Retry text. Timeout, abort, invalid JSON, and other indeterminate transport results remain explicitly unknown and offer only authoritative runtime-state refresh.

## Guarded terminal transition

False liveness, a failed completed health observation, and post-readiness process exit all contend through one guarded `running -> failed` compare-and-set on the exact entry and generation before cleanup awaits. The winner installs one category, performs one terminate or already-absent audit, records one cleanup, and emits one `runtime.health.changed`. A loser does not mutate, terminate, audit, or emit and reuses the winner's retained failure. Cleanup rejection surfaces after that single event without changing category or adding an event. Manager shutdown remains a non-reportable suppression.

The four reportable failure causes are start failure before readiness, post-readiness exit, failed completed health observation, and false-liveness observation. The first emits `runtime.start.failed`; the three post-readiness paths emit `runtime.health.changed`. A success or healthy event is never emitted after the project has entered `Failed`.

## Launch and readiness contract

The default executable is /home/vscode/.local/bin/code-server, and the configured user is non-root vscode. Construction accepts explicit executable, user, deterministic environment allowlist, and finite bound overrides for tests or a designated deployment. Launch uses direct argument-vector process creation, a canonical working directory, a detached owned process group, a 127.0.0.1 manager-selected port, and the exact stored canonical directory once as the final argument. No shell interpolation occurs.

Port reservation is loopback-only. The unavoidable reservation-to-child-bind race retries address-in-use at most three times with a fresh candidate and exact owned-group cleanup; unrelated listeners are never closed, rebound, or signalled.

Readiness polls GET /healthz/. Only HTTP 200 plus JSON status equal to alive or code-server's healthy-idle expired state is accepted. Transient mismatches remain non-ready and are polled only within the total bound; the last observed status or body mismatch becomes its distinct typed failure if readiness never succeeds. Each request is bounded to 1,000 ms, polling is 50 ms, and total readiness is 15,000 ms. Attempt timing is retained finitely. Readiness uses cancellation, never a fixed startup sleep.

Exactly concurrent starts for one project join one launch/readiness promise. A later start reuses the same PID identity and port only when the exact process remains alive and the health contract passes. Failed starts are evicted and permit an explicit fresh retry. A post-running exit retains one bounded code-or-signal failure, evicts reuse state, and starts no automatic retry.

Caller cancellation ends only that caller’s wait while other waiters remain. When the last waiter cancels, the manager aborts and cleans only that orphaned project start. Manager shutdown remains the global cancellation boundary.

## Typed failures

The 18 closed categories are unknown-project, canonical-path-invariant, spawn-error, executable-missing, early-exit-code, early-exit-signal, address-in-use-exhausted, readiness-timeout, health-status-unexpected, health-body-unexpected, caller-cancelled, manager-shutdown, stop-unconfirmed, runtime-stopping, restart-release-unconfirmed, restart-deadline-exceeded, runtime-restarting, and restart-replacement-unconfirmed. Their fixed safe messages direct callers to refresh or register the project, install or correct code-server, release listeners, check host capacity, start again, retry after lifecycle settlement, or restart Ascend as appropriate.

Diagnostics allow only finite attempt count, exit code, signal, health status, timeout, and port fields. Every caller participating in one failed shared attempt receives the same typed failure object.

## Events and shutdown

Structured lifecycle events are `runtime.start.requested`, `runtime.start.succeeded`, `runtime.start.failed`, `runtime.health.changed`, `runtime.stop.requested`, `runtime.stop.succeeded`, `runtime.restart.requested`, `runtime.restart.succeeded`, and `runtime.restart.failed`. The Stop subset is `runtime.start.requested`, `runtime.start.succeeded`, `runtime.start.failed`, `runtime.health.changed`, `runtime.stop.requested`, and `runtime.stop.succeeded`. An accepted selected stop emits exactly one requested event from running to stopping. Confirmed release emits exactly one succeeded event from stopping to stopped; unconfirmed, deadline, and termination-fault settlements emit one health-changed event from stopping to failed with `stop-unconfirmed`. An accepted Restart emits only its one requested and one terminal succeeded or failed event; it never emits start, stop, or health events. Rejections, already-stopped, joined callers, race losers, and unowned settlements emit no additional event. Route records `project.runtime.stop.rejected` and `project.runtime.stop.failed` are operational records, not lifecycle events. The corresponding Restart route records are also operational.

Allowed lifecycle fields are event name, deterministic opaque project token, from/to state, non-negative elapsedMs, and a bounded failure classification. Raw project IDs are excluded from events and logs; the browser stable URL separately contains the encoded stable project ID. The one-way project token may be retained for safe public event correlation. Raw canonical paths, internal ports/authorities, credentials, secrets, and protected development content are excluded from public evidence.

Application close calls the one manager before registration and SQLite owners close. Confirmed selected stops have already removed ownership; unconfirmed and faulted selected stops receive the intended one shutdown-phase re-attempt. Repeated shutdown calls join one promise and result, reject new starts, stops, and restarts, cancel in-flight readiness with manager-shutdown, await in-flight selected stops, and prevent late launch, exit, or abandoned termination completion from installing state after shutdown. The manager then inventories retained ownership and quarantine and applies the same exact-group sequencer. It audits every recorded PID/start identity, process group, port, and loopback listener after termination and returns each graceful, escalated, already-absent, or unconfirmed outcome with an aggregate ok or failed status. Unresolved admissions are returned as bounded opaque admission records and force failed shutdown; a never-settling abandoned launch is observed only by its detached continuation and is not awaited. Unrelated processes and listeners remain alive.
