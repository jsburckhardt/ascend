# Research Brief: BL-010: Start and reuse one project workbench

## GitHub Issue
- **Issue:** #25
- **Title:** BL-010: Start and reuse one project workbench
- **Work Item:** project/work-items/25-bl-010-start-and-reuse-one-project-workbench

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Selecting or activating a registered project cannot currently start or reconnect to a code-server process. The issue requires one centrally owned, in-memory runtime for one project with bounded readiness, duplicate-start prevention, safe lifecycle failures, and cleanup. BL-001, BL-002, and BL-006 are merged dependencies, but the existing workbench launcher is explicitly a proof harness rather than product runtime ownership. The issue excludes multi-project coordination, stable proxy routes, Project Home navigation, user Stop or Restart UI, API-restart reconciliation, persisted runtime handles, automatic sleep, scheduling, and containers.

## Acceptance Criteria
<!-- ACCEPTANCE_CRITERIA_START -->

**Core**
- [ ] A documented runtime-manager interface accepts a persisted project ID and canonical path, starts one code-server process as the configured non-root user, passes the exact canonical directory as one argument-vector item, binds only to loopback on a manager-selected available port, and returns a typed snapshot containing project ID, `starting`, `running`, or `failed` state, PID identity, internal URL and port, canonical path, `startedAt`, and `elapsedMs`; command, environment, credentials, and secrets are absent from the snapshot.
- [ ] For this ticket, runtime process handles, PID identities, ports, and `starting`/`running`/`failed` state exist only in runtime-manager memory and project persistence remains metadata-only. Finite sentinel checks of the repository SQLite schema, project rows, database bytes, and captured structured events show that these runtime values are not persisted or logged wholesale.
- [ ] Exactly eight concurrent start calls for one project before readiness invoke one spawn and one readiness sequence, and all eight resolve to snapshots identifying the same running process and port; subsequent starts while that process remains alive and passes the documented health check return the same PID identity and port without another spawn.
- [ ] Port acquisition has no unprotected check-then-bind outcome: binding is delegated safely or address-in-use causes no more than a documented finite number of retries. A controlled collision leaves an unrelated listener alive on its original address, and exhaustion returns the documented address-in-use failure without killing, closing, or rebinding that listener.
- [ ] Readiness uses a documented health request to the started code-server rather than a fixed sleep, accepts only the documented expected status and body, records each attempt timing, and enforces documented finite per-attempt and overall timeouts plus cancellation.
- [ ] Unknown project, invalid persisted canonical-path invariant, spawn error, missing executable, early exit with code or signal, and address-in-use exhaustion each produce a distinct typed failure whose documented safe message identifies the failure category and a corrective or retry action.
- [ ] Readiness timeout, unexpected health status, unexpected health body, caller cancellation, and manager shutdown each produce a distinct typed failure whose documented safe message identifies the failure category and a corrective or retry action.
- [ ] Every failure retains only documented finite diagnostic fields and limits sufficient to distinguish its category, including exit code or signal when applicable; snapshots, diagnostics, messages, and events expose no command, environment, credentials, secrets, source or terminal content, command output, stack, raw internal error, or redaction sentinel.
- [ ] Structured startup success and failure events contain project ID, state transition, `elapsedMs`, and a bounded failure classification when applicable. They exclude source or terminal content, command output, command and environment data, credentials, and secrets; a canonical path classified as sensitive by the documented logging policy is absent in raw form.

**Edge Cases**
- [ ] Every failed shared start settles all callers still participating in that attempt with the same typed failure, atomically removes or replaces its in-flight entry, terminates only an owned process group when one was started, records bounded evidence that its exact PID identity and listener are absent, and permits one later retry to create exactly one fresh runtime.
- [ ] If an owned process exits after reaching `running`, it is removed from reusable-running state, one bounded failed/exit diagnostic is retained, and the next start creates one replacement runtime; no automatic retry loop starts.
- [ ] The interface documentation defines whether caller cancellation ends only that caller wait or the shared start attempt. Finite cancellation evidence matches the documented choice and proves no duplicate process, owned orphan process or listener, stale completion mutation, or effect on a later retry.
- [ ] Manager shutdown is bounded and idempotent, rejects or cancels in-flight starts with the manager-shutdown failure, gracefully stops every runtime process it owns, escalates only after a documented finite timeout, and confirms each exact owned PID identity and listener is absent while leaving an unrelated process and listener alive.
- [ ] Bounded before-and-after manifests for disposable project fixtures show unchanged directory membership and file bytes after representative successful start and reuse, failed start cleanup and retry, post-running exit replacement, and manager shutdown scenarios.

**Verification**
- [ ] Finite repository-controlled fake process and health fixtures cover exactly-eight-call single-flight concurrency, healthy reuse, port collision and unrelated-listener survival, every typed failure, caller and shutdown cancellation, early and post-running exits, failed-attempt retry, bounded diagnostics, redaction sentinels, exact process ownership, idempotent shutdown, and project-file integrity.
- [ ] One designated real code-server validation, using the repository-provided BL-001 fixture and documented designated-host prerequisites, proves the expected health response, exact canonical-path argument item, configured process user, loopback-only listener, same PID identity and port on repeated start, and observed startup elapsed time compared with the 15-second target, then shuts down the manager and records fixture integrity plus exact owned PID/listener absence.
- [ ] Documentation records the runtime-manager interface and ownership boundary, `starting`/`running`/`failed` state, configured executable and user, argument/path safety, loopback port ownership and retry bound, health contract and readiness bounds, single-flight and reuse behavior, typed failures and retry behavior, event fields and redaction, caller-cancellation ownership, shutdown escalation and cleanup bounds, exact validation commands, the real-host observed elapsed time versus the 15-second target, and all deferred boundaries named in the Problem.
- [ ] Repository-configured focused and full validation commands exit zero, and a final bounded residual audit records that no PID identity or listener created by the validation remains.

## Repository Findings
- **Product requirements:** `PRD.md` FR-004 requires starting a missing workbench and reconnecting to an existing one; FR-005 and AC-008 require the registered canonical directory. AC-006 and AC-007 separately identify initial start and healthy reuse. NFR-002 sets a 15-second cold-start target but requires measurement before it becomes a release gate. NFR-011 requires lazy startup, NFR-013 isolates process lifecycle behind a small runtime-management boundary, and NFR-016 requires startup timing in logs. The NFR-015 event catalog includes `runtime.start.requested`, `runtime.start.succeeded`, `runtime.start.failed`, stop/restart events, and `runtime.health.changed`.
- **Merged proof runtime:** Commit `fa32a6f` merged BL-001 and `e87c5c7` merged BL-002. Their accepted records are `project/work-items/5-bl-001-prove-a-host-code-server-workbench/verify/summary.md` and `project/work-items/7-bl-002-prove-host-native-terminal-parity/verify/summary.md`. Those records establish direct non-root host execution, the canonical metacharacter fixture, exact process/listener cleanup, and host-native terminal parity, while explicitly limiting the capability to a proof surface.
- **Proof launcher contract:** `apps/api/src/workbench-proof-contract.ts` fixes code-server 4.131.0 at `/home/vscode/.local/bin/code-server`, the BL-001 fixture, and startup/stop/browser bounds of 15,000/10,000/60,000 ms. `docs/workbench-proof.md` identifies the designated Ubuntu host, `vscode` uid 1000, canonical fixture, exact handle, loopback behavior, readiness range, diagnostic categories, and disposable `test-results/bl-001` boundary.
- **Proof process behavior:** `startWorkbenchProof` in `apps/api/src/workbench-proof-runtime.ts` canonicalizes and checks the directory, rejects root, directly calls `spawn` with an argument array and `detached: true`, sets the canonical path as `cwd` and the final argv item, and passes `127.0.0.1:0`. It constructs a deterministic child environment, captures the child streams in `launch.log`, parses the emitted URL, writes `state.json` containing PID identity, URL, and project path, and accepts any HTTP status from 200 through 399. `terminateExactProcessGroup` uses bounded SIGTERM then SIGKILL handling. `stopWorkbenchProof` validates the stored handle and process start identity before group termination.
- **Proof/runtime boundary mismatch:** The proof module has no project-keyed manager, single-flight map, healthy-running reuse, post-running exit eviction, shared-start semantics, manager shutdown boundary, health-body contract, per-attempt health timeout, or address-in-use retry classification. Its disposable `state.json` and `launch.log` are incompatible with Issue #25's product requirement that runtime identity/state remain only in manager memory and that command output not appear in exposed diagnostics or events. The proof CLI events in `apps/api/src/cli/proof-start.ts` and `proof-stop.ts` omit project ID and state transition; proof failure details can include paths, executable paths, and raw spawn/cleanup messages.
- **Existing process evidence helpers:** `apps/api/src/workbench-proof-audit.ts` supplies Linux `/proc` process-tree, argv, user, exact PID/start-time, and listener attribution/absence helpers. `apps/api/test/workbench-proof-runtime.test.ts` covers one spawn, exact final path argument, cancellation cleanup, and repeated stop. `apps/api/test/workbench-proof-failures.test.ts` covers five bounded startup failures, exact ownership, unrelated-process survival, loopback attribution, and escalation. `apps/api/test/fixtures/fake-code-server.mjs` currently models ready, timeout, early-exit, and ignored-SIGTERM behavior and responds with status 200/body `ready` when healthy.
- **Capacity proof remains separate:** `apps/api/src/workbench-capacity-coordinator.ts` starts independent BL-001 proof members sequentially for diagnostic cohorts and delegates exact cleanup/auditing. `docs/workbench-proof.md` states that BL-004 does not establish product lifecycle policy, multi-project coordination, or BL-010 outcomes.
- **Persisted registration baseline:** Commit `b437e6c` merged BL-006; its acceptance is recorded in `project/work-items/15-bl-006-register-canonical-filesystem-projects/verify/summary.md`. `createProjectRegistrationService` in `apps/api/src/project-registration.ts` validates configured home/roots before persistence, canonicalizes submitted paths, enforces segment-boundary opening policy, and persists a stable ID, name, canonical path, and creation time. Its exactly-eight concurrent coverage proves one durable registration winner, not runtime-start single flight.
- **Metadata-only schema:** `apps/api/src/db/schema.ts` and migrations `0000_project_library.sql`/`0001_project_canonical_path_unique.sql` define only `id`, `name`, `canonical_path`, and `created_at`, with canonical-path uniqueness. `Project` in `apps/api/src/project-persistence.ts` has exactly `id`, `name`, `canonicalPath`, and `createdAt`. `apps/api/test/project-schema-minimization.test.ts` inspects schema, rows, reopened data, and raw database bytes and already excludes fixed source, terminal, port, PID, handle, environment, credential, and secret sentinels.
- **Project lookup boundary:** `ProjectLibrary` in `apps/api/src/project-library.ts` exposes `create`, `list`, `closeProject`, and `close`; it has no stable-ID lookup operation. The registration service returns the persisted canonical path at creation time, and the list route returns persisted four-field projects, but no current runtime-facing boundary validates an ID/path pair as a persisted invariant.
- **Application lifecycle:** `createApiServerController` in `apps/api/src/api-server.ts` memoizes start and stop promises; stop closes Fastify and telemetry. The Fastify plugin in `apps/api/src/app.ts` constructs and decorates project library, registration, and close services and closes the SQLite owners in `onClose`; no runtime manager is constructed, decorated, or shut down. `apps/api/test/api-lifecycle.test.ts` confirms repeated API shutdown joins one close and preserves project metadata across a fresh process-level service construction.
- **Current HTTP/UI boundary:** `apps/api/src/routes/projects.ts` only lists, registers, and closes stopped project metadata. In `apps/web/src/App.tsx`, each card's Open action only announces `Opening the workbench is not available yet.` and performs no request or navigation; `apps/web/src/App.test.tsx` pins that deferred behavior. The issue expressly defers Home navigation and stable routing, so these files identify the current boundary rather than an existing runtime entry point.
- **Logging baseline:** `CORE-COMPONENT-260808-structured-runtime-logging.md` requires structured standard-stream events and excludes source, terminal, command output, clipboard, credentials, and secrets. `apps/api/src/request-logging.ts` always adds `req.url` redaction when Fastify logging is enabled, but the repository contains no documented canonical-path sensitivity classifier or runtime-specific bounded diagnostic schema.
- **Command and harness surfaces:** The root `justfile` owns focused/full validation and the BL-001, BL-002, BL-004, BL-006, BL-008, and BL-009 commands; it has no BL-010-focused recipe. `.harness/extensions/checks/extension.ts` delegates `harness checks` to `just verify`, while `.harness/extensions/boot/extension.ts` returns test-backed readiness and leaves no server running. `.harness/engineering-harness.md` records BL-001/002 process sensors, BL-006 signals, generated evidence locations, and the explicit live API/web boot gap. The executable used for governed observations resolves to `/usr/local/lib/node_modules/@ai-substrate/engineering-harness/harness/cli/bin/harness.js`.
- **Repository stack and gate:** `package.json` pins Node 22 and pnpm 10.34.5; `apps/api/package.json` uses Fastify, strict TypeScript, Vitest, Drizzle, libSQL, and OpenTelemetry. `vitest.config.ts`, `playwright.config.ts`, and the root `justfile` define the existing repository validation surfaces. The current branch `feat/25-start-reuse-project-workbench` starts at `f78408b`, where BL-001, BL-002, BL-006, and the APS-governed RPIV harness profile are merged.

## Constraints
- Issue #25 is limited to one project runtime and explicitly excludes BL-013 multi-project coordination, BL-011 stable proxy routes, BL-012 Home navigation, BL-017/BL-018 Stop or Restart UI, BL-019 API-restart reconciliation, persisted runtime handles, automatic sleeping, scheduling, and containers.
- The accepted stack requires direct host code-server processes, one runtime per active project, Node/Fastify ownership, and SQLite/Drizzle only for metadata (`ADR-260808-typescript-monorepo.md`).
- Runtime operations must stay behind one internal boundary, expose typed outcomes, keep at most one managed workbench per active project, avoid broad/silent catches, and keep handles and ports out of project persistence (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`).
- Workbenches must run as the configured non-root host user without privilege escalation, receive canonical paths through argument arrays, bind to loopback, and use a documented deterministic environment (`CORE-COMPONENT-260808-host-process-environment.md`).
- Runtime launch must use the stored canonical directory. Project contents remain user-owned and must not be created, deleted, moved, renamed, copied, chmodded, or otherwise mutated by lifecycle operations (`CORE-COMPONENT-260808-filesystem-path-safety.md`).
- Runtime events must be structured, stable, timing-bearing, and free of source, terminal, command output, environment secrets, credentials, and other protected content. Fastify application logging and standard OpenTelemetry environment configuration remain the accepted observability boundaries (`CORE-COMPONENT-260808-structured-runtime-logging.md`).
- The existing database lifecycle requires explicit paths, ordered committed migrations, closeable resources, and isolated tests; the current project model is exactly four metadata fields and has no runtime columns (`CORE-COMPONENT-260810-sqlite-persistence-lifecycle.md`, `apps/api/src/db/schema.ts`).
- Full-page code-server with a minimal Ascend header is the accepted authoritative desktop presentation. Product routing, navigation, and lifecycle integration were left outside that decision and remain outside this issue where named (`ADR-260810-full-page-browser-workbench-presentation.md`).
- Repository operating and validation commands remain root `justfile` recipes; strict TypeScript, configured lint/format checks, Vitest, Playwright, and 80 percent unit coverage are adopted constraints (`CORE-COMPONENT-260806-project-command-interface.md`, `CORE-COMPONENT-260808-development-standards.md`).
- Harness checks must continue to delegate to `just verify`; harness boot is currently non-persistent and test-backed. Research is a leaf stage and does not own lifecycle hooks (`ADR-260808-governed-engineering-harness.md`, `CORE-COMPONENT-260808-engineering-harness-delivery-contract.md`, `CORE-COMPONENT-260806-rpiv-stage-contract.md`).
- The designated real-host baseline is Ubuntu 24.04.4 LTS, non-root `vscode` uid 1000, repository `/workspaces/ascend`, and code-server 4.131.0. Existing process/listener auditing depends on Linux `/proc` (`docs/workbench-proof.md`, `apps/api/src/workbench-proof-audit.ts`).

## Risks and Open Questions
- The lifecycle core-component names `Stopped`, `Starting`, `Running`, and `Failed`, while Issue #25 snapshots name lowercase `starting`, `running`, and `failed` and omit a stopped snapshot. The repository does not state whether these are distinct public/internal vocabularies.
- The lifecycle core-component requires persisted runtime state to be reconciled after backend restart, while Issue #25 requires memory-only runtime identity/state and expressly defers API-restart reconciliation and persisted handles. The applicability of that core rule to a deliberately non-persistent ticket boundary is unresolved in repository text.
- The product has configuration for API bind/database/project-opening policy, but no documented product configuration for code-server executable or runtime OS user. The proof hard-codes the executable and runs as the current non-root process user.
- `ProjectLibrary` has no lookup-by-ID operation, and no current boundary verifies that an incoming project ID and canonical path still correspond to one persisted row. The ownership of the issue's unknown-project and invalid-persisted-path classifications is not stated.
- The existing proof discovers its URL from child output and accepts any 200-399 response without checking a body. The exact real code-server health path, expected status/body, redirect treatment, and behavior during transient statuses are not documented for product runtime.
- The proof delegates binding to code-server with port zero, but it does not expose a selected port before readiness or classify address-in-use exhaustion. The repository has no existing controlled collision fixture or documented retry bound.
- Existing cancellation stops the one proof child and classifies the operation as cancelled. There is no repository precedent for whether one caller cancellation detaches only that waiter or cancels a shared project start.
- Existing proof diagnostics can retain canonical/input paths, executable paths, and raw internal spawn or cleanup messages. No repository path-sensitivity classification policy or finite runtime diagnostic field limits currently define the stricter Issue #25 event contract.
- Existing process identity and listener audits are Linux `/proc`-specific and designated-host facts are fixed to uid 1000. Portability beyond the named host is deferred by the accepted ADR but remains a limitation of reusable repository evidence.
- The current fake code-server does not model unexpected body/status, address collision/exhaustion, post-running exit, signal-specific early exit, or shared-start concurrency. The current proof state is persisted below disposable test results, so proof behavior cannot be treated as evidence of memory-only product ownership.
- Fastify shutdown is idempotent for current services, but no runtime owner participates in `app.ts` construction or `onClose`. The ordering and failure interaction between server close, runtime shutdown, SQLite close, and telemetry stop is unstated.
- The accepted presentation requires later product routing, but Issue #25 defers stable routes and Home navigation. No current HTTP or browser contract consumes a runtime snapshot, leaving the external consumer boundary intentionally unresolved in this ticket.
- Harness boot explicitly leaves no services running, and `harness checks` has a 120,000 ms wrapper timeout while the full `just verify` gate includes real browser/process checks. The repository does not document whether Issue #25 changes either bound; no assumption can be made from the current harness wrapper.
