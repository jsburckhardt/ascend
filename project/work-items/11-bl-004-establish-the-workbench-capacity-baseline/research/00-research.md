# Research Brief: BL-004: Establish the workbench capacity baseline

## GitHub Issue
- **Issue:** #11
- **Title:** BL-004: Establish the workbench capacity baseline
- **Work Item:** project/work-items/11-bl-004-establish-the-workbench-capacity-baseline

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Ascend has a merged proof for one host-native code-server workbench, but it has no bounded and comparable capacity baseline for multiple simultaneous workbenches on the designated Ubuntu host. Issue #11 requires one diagnostic run over cohorts of 1, 3, 5, and 10 under the same active workload, with ordered partial records, responsiveness safety behavior, anchored host and process-tree sampling, exact cleanup, and retained fixture integrity. The three-member cohort is the only MVP capacity gate. Product runtime management, scheduling, quotas, multi-host operation, unbounded load, BL-010, and BL-013 remain outside this issue.

## Acceptance Criteria
**Core**
- [ ] One paved repository command checks and records the documented designated Ubuntu host prerequisites, code-server 4.131.0, and non-root `vscode` execution before member starts; uses a documented finite overall timeout; assigns one unique run ID to all retained output; and returns a prerequisite-specific nonzero result without starting a member when a prerequisite fails.
- [ ] The command processes cohort records in the exact order 1, 3, 5, and 10. Member starts for a cohort cannot begin until the prior cohort cleanup and fixture-integrity result is complete; after a safety stop, later cohorts still receive ordered records with their slots explicitly `unstarted`.
- [ ] Within each cohort, every requested member is attempted sequentially with a 30-second readiness timeout. Each slot ends as `ready`, `failed` with reason, or `unstarted` with reason; a member start failure is recorded and later requested members are still attempted unless the responsiveness safety stop has occurred.
- [ ] One host responsiveness probe definition and finite timeout are fixed in repository documentation and copied into run evidence. The probe runs before each cohort, with every scheduled host sample in both sampling windows, and after cleanup. On its first failure, no further member starts occur anywhere in the run, every not-yet-attempted slot in the current and later cohorts is recorded `unstarted` with that failure reason, and cleanup begins for already managed members.
- [ ] Idle stabilization lasts exactly 5 seconds after all permitted start attempts finish. The five idle positions are scheduled from a monotonic window anchor at offsets 0, 1, 2, 3, and 4 seconds for every ready process tree and the host; actual timestamps are retained, a missed position is not replaced, and its record is explicitly absent with reason.
- [ ] Every ready member is assigned the same single repository-defined terminal workload command used for every member and cohort. Each workload is bounded to 5 through 10 seconds, has a documented finite maximum output size, and retains its complete command text, PID, start time, end time, exit result, stdout, and stderr.
- [ ] The active window is anchored only after workload start has been attempted for every ready member. Its five positions are scheduled at monotonic offsets 0, 1, 2, 3, and 4 seconds; all ready-member workloads must overlap each retained active position, actual timestamps are retained, and a missed or non-overlapped position is not replaced and is explicitly absent with reason. When no member is ready, all five host and process-tree active positions are explicitly absent with `no ready workload` as the reason.
- [ ] Every process-tree sample records timestamp, root PID, aggregate CPU percent, aggregate RSS KiB, and member PIDs. Every host sample records timestamp, load average, available memory KiB, used memory KiB, and that sample’s responsiveness-probe result. One measurement method is used consistently for the complete run and documented without prescribing its utility.
- [ ] Retained run evidence contains host, code-server, cohort, slot, run ID, PID, port/listener, and readiness metadata; raw sample JSON; a workload result for every ready member; and a concise comparison table showing each cohort’s requested/ready/failed/unstarted counts, workload pass/fail counts, sample completeness, host and process-tree resource summaries, responsiveness result, cleanup/integrity result, findings, and gate status.
- [ ] A cohort result is complete only when every requested slot has a terminal state with reason where applicable, all scheduled idle and active positions are samples or explicit absences with reason, every ready member has a workload result, and cleanup plus fixture-integrity checks finish. A failed member or an explicitly absent sample may be a complete finding, not a successful member.
- [ ] Cleanup after every cohort confirms every PID and listener attributed to that run is absent and the merged BL-001 fixture tree membership and sentinel hashes match their before-cohort values. Cleanup does not claim or remove unrelated host processes, listeners, or fixture content.

**Edge Cases**
- [ ] The one-member cohort is proof plumbing with no independent success threshold: its member outcome is a finding when the cohort record is complete, and it does not determine MVP acceptance.
- [ ] The three-member cohort is the only MVP gate. It passes only when all three members are ready, each workload exits successfully, each listener has a distinct PID/port and passes the documented readiness check, no managed member exits between readiness and the beginning of intentional cleanup, all five idle and all five active positions contain samples for each ready process tree and the host, and every required responsiveness probe passes. Any gate failure records a blocker and makes the paved command nonzero.
- [ ] Five- and ten-member start, workload, unexpected-exit, responsiveness, and resource failures are retained as findings and never rewrite the recorded three-member gate decision when their cohort records are complete.
- [ ] The paved command is nonzero when the three-member gate fails, any cohort record is incomplete, cleanup or fixture integrity is incomplete or fails, evidence cannot be retained, or the overall timeout expires. Incomplete five- or ten-member evidence therefore makes the command nonzero even after a passing three-member gate, without changing that gate decision.
- [ ] A failed start, port/listener conflict, workload failure, unexpected exit, process-inspection failure, or unavailable sample remains attributable to its cohort and slot, preserves previously collected evidence, and cannot be reported as a ready or successful member. Scheduled evidence unavailable after a responsiveness safety stop is explicitly absent with the stop reason.
- [ ] Concurrent paved-command invocation or pre-existing run-owned state is deterministically rejected with a documented nonzero result before member starts unless complete run isolation and unambiguous attribution are proven; evidence from different run IDs is never combined.

**Verification**
- [ ] Finite repository validation uses controlled evidence to prove correct and incorrect outcomes for sequential continuation after member failure, probe-triggered safety stop and `unstarted` slots, exact anchored sample positions and fields, workload overlap and early exit, zero-ready cohorts, cohort completeness, the three-member gate, five/ten finding semantics, concurrent-run isolation, evidence-write failure, overall timeout, cleanup failure, managed-resource leakage, and fixture mutation; each negative control returns the documented nonzero or finding result.
- [ ] One run on the repository-documented designated Ubuntu host invokes the paved command, processes all four ordered cohort records, retains raw JSON and the comparison table, reports the independent three-member gate and overall exit disposition, and finishes with no run-attributed PID, listener, or terminal workload and unchanged BL-001 fixture membership and sentinel hashes.
- [ ] Documentation records the designated Ubuntu host prerequisites, paved command and overall timeout, probe and timeout, workload command, duration, and output bound, measurement method, cohort and partial-result rules, sample schedule and fields, gate and exit semantics, comparison fields, evidence interpretation, run isolation, cleanup, and the observed run identity and baseline without claiming runtime scheduling, quotas, multi-host support, BL-010, or BL-013 outcomes.
- [ ] The configured repository full-validation command exits zero, and its final bounded audit reports no run-attributed resource leak or BL-001 fixture-integrity change.

## Constraints
- Scope is diagnostic and fixed to one ordered run over cohorts 1, 3, 5, and 10. It cannot claim product runtime management, scheduling, quotas, multi-host support, unbounded load behavior, BL-010, or BL-013 outcomes.
- The three-member cohort is the only MVP gate. One member is plumbing only, while five and ten remain findings. A complete five- or ten-member record can contain failures without changing the recorded three-member decision, but any incomplete cohort still makes the overall command nonzero.
- Every requested slot needs one terminal state, and the issue distinguishes member readiness, workload success, cohort completeness, the independent three-member gate, and overall command disposition. Existing BL-001 start success alone cannot stand for any of those broader states.
- The Issue #11 30-second per-member readiness bound supersedes the current BL-001 default of 15 seconds for this diagnostic scope. Sequential attempts must continue after an ordinary member failure and stop only under the defined responsiveness safety condition.
- Idle and active windows have exactly five anchored positions at monotonic offsets 0 through 4 seconds. Missed and non-overlapped positions remain explicit absences; replacement samples would violate the issue contract.
- Every ready member receives the same repository-defined terminal workload with a 5-through-10-second duration and finite output bound. Required command-output retention belongs in proof evidence, not structured runtime logs, because `CORE-COMPONENT-260808-structured-runtime-logging.md` prohibits terminal and command output in logs.
- Host samples necessarily include unrelated host activity because the inspected cgroup has no finite resource limits and shares the cgroup root with existing development processes. Process-tree samples must remain attributable to each managed member and cannot include unrelated VS Code Remote trees.
- Cleanup is exact and non-destructive. It can remove only run-attributed PIDs, listeners, terminal workloads, and disposable state; it cannot use process-name killing or broad listener sweeps. Fixture tree membership and merged BL-001 sentinel hashes must match their before-cohort values (`docs/workbench-proof.md`; `CORE-COMPONENT-260808-filesystem-path-safety.md`).
- Workbenches remain direct host processes under non-root `vscode`, with canonical fixture path, argument-array invocation, deterministic environment, isolated run state, and loopback listeners (`ADR-260808-typescript-monorepo.md`; `CORE-COMPONENT-260808-host-process-environment.md`).
- Runtime and cleanup failures cannot be converted into success-shaped records. Existing lifecycle ownership, explicit error, exact identity, and idempotent-stop requirements remain applicable (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`).
- One run ID must own all retained output. Concurrent invocation or pre-existing run-owned state must be rejected before member starts unless isolation and attribution are complete; current UUID-per-member behavior is not itself proof of run-level isolation.
- Prerequisite checks, the responsiveness probe, every member start, both sampling windows, workloads, evidence retention, cohort cleanup, fixture checks, and final disposition all remain inside one documented finite overall timeout. No overall timeout value is currently defined in source or documentation.
- The root `justfile` remains the command interface. Harness checks continue to delegate to `just verify`, and harness boot remains non-persistent under the accepted harness decision (`CORE-COMPONENT-260806-project-command-interface.md`; `ADR-260808-governed-engineering-harness.md`).
- Strict TypeScript, repository formatting and linting, Vitest, Playwright where browser behavior is involved, coverage thresholds, and the configured full gate remain repository standards (`CORE-COMPONENT-260808-development-standards.md`).
- The accepted full-page browser presentation decision is presentation-only. It does not supply or authorize a product runtime manager, route, lifecycle policy, quota, or capacity threshold for this diagnostic (`ADR-260810-full-page-browser-workbench-presentation.md`).
- Raw evidence may contain complete bounded workload stdout/stderr, while tracked documentation and runtime logs have stricter sensitive-content exclusions. The present ignored `test-results/` boundary and committed BL-003 evidence boundary do not yet define where Issue #11 run evidence is retained.

## Risks and Open Questions
- The repository does not define the responsiveness probe, its timeout, or the prerequisite-specific and probe-failure result codes. It is also unresolved which later probe records remain scheduled after the first safety-stop failure beyond the explicit absent sample records required by the issue.
- The repository does not define the terminal workload command, its exact duration within 5 through 10 seconds, its output bound, or whether terminal means a command launched through each integrated code-server terminal or another member-attributed terminal boundary.
- Aggregate process-tree CPU percent semantics are unspecified, including interval calculation, normalization across 20 logical CPUs, and treatment of processes that appear or exit during a sample. Aggregate RSS semantics and the exact host used-memory calculation are also unspecified.
- The host sample requires load average but does not state whether the retained field is the 1-, 5-, or 15-minute value or all three. The concise resource-summary calculations are likewise undefined.
- Existing `/proc` tree discovery is race-prone by design and silently omits processes that disappear during inspection. Issue #11 instead requires unavailable samples and process-inspection failures to remain explicit and attributable, so current audit output is not equivalent to a capacity sample.
- Existing terminal command capture has no finite output-size enforcement and does not return a complete result object on timeout, nonzero exit, spawn failure, or evidence-tracking failure. Those current semantics do not satisfy the required result record for every ready member.
- Existing BL-001 and BL-003 proof paths have no run-level concurrency guard. BL-003 also clears fixed evidence roots before its designated run. Overlap with another proof invocation could destroy or combine generated state unless rejected or fully isolated, and the current repository does not establish that boundary.
- The designated environment is Ubuntu user space on a WSL2 kernel with no finite cgroup CPU, memory, swap, or PID limit. It is unresolved whether this exact WSL-backed devcontainer remains the authoritative target host identity for future baseline comparisons and how changes in externally assigned host resources are recognized.
- Existing VS Code Remote processes consume substantial memory and CPU and own loopback listeners. Host load and available-memory samples will include that activity, so repeatability depends on background conditions that the repository currently records only partially and does not control.
- `auditHandleCleanup` can report a listener leak when an unrelated process rapidly reuses a released port, while broad listener cleanup is prohibited. Port reuse and listener-owner changes are therefore an attribution risk for exact cleanup evidence.
- The root code-server PID may outlive, lose, or gain descendants between readiness and cleanup. Current source has no continuous unexpected-exit monitor or complete process-membership history, leaving the precise observed boundary for the three-member no-unexpected-exit gate unresolved.
- Five anchored positions in a 5-second active window leave little scheduling margin when workloads are permitted to run for only 5 seconds. Host contention at cohorts five and ten can cause missed positions or loss of overlap; the issue correctly treats those as explicit findings, but the exact timing relationship remains operationally sensitive.
- A responsiveness failure during sampling stops all further starts, but managed workloads and workbenches may still be live until cleanup. The current proof has no cohort-wide safety-stop state, so partial-record consistency and bounded cleanup under host distress are uncharacterized.
- The existing fixture is shared by every proof workbench even though user and extension data are isolated per run. Concurrent code-server access and the workload must leave fixture membership and sentinels unchanged; other possible fixture side effects are outside the merged BL-001 integrity definition.
- The issue requires retained raw JSON and a comparison table from one designated-host run, but it does not name a repository path or clarify which raw workload output is committed versus generated and ignored. Evidence-write failure must be distinct even though the current retention boundary is split between work-item files and `test-results/`.
- The finite overall timeout is not specified. Its relationship to up to 19 sequential 30-second start attempts, four idle windows, four active windows, workloads, repeated probes, cleanup, evidence writes, and the existing `just verify` and harness durations remains unresolved.
- The three-member gate requires distinct listener PID and port for each ready member. Existing evidence can identify listener-owner PIDs and root handles, but the required identity relationship between a member root PID and a descendant listener PID is not further defined.
- No architecture decision is requested by Issue #11. Any capacity result may inform later lifecycle policy, but this research cannot convert diagnostic findings into scheduling, quota, sleeping, or runtime-management decisions.
