## The close model, decided

### 1. Authority, ownership, and composition

`ProjectRuntimeManager` gains one required member and becomes the single authority for the entire close:

```ts
export interface ProjectRuntimeCloseInput {
  readonly projectId: string
  readonly drainConnections: (signal: AbortSignal) => Promise<WorkbenchProxyAudit>
  readonly auditConnections: () => WorkbenchProxyAudit
  readonly commitRemoval: () => Promise<CloseProjectResult>
}

close(input: ProjectRuntimeCloseInput): Promise<RuntimeCloseOutcome>
```

The manager owns admission, the claim, the phase order, every deadline, the confirmation predicate, the settlement, and the retirement. The three effects it does not own arrive as callables. `auditConnections` is **synchronous by contract**: the final confirmation must read the authoritative per-token counts and reach `commitRemoval` in one uninterrupted synchronous region, and an asynchronous re-observation would reopen the window it exists to close. `WorkbenchProxyManager.audit(projectToken)` is already synchronous, so no proxy member is added for it. `ProjectCloseService` is the only composer:

```ts
export interface ProjectCloseServiceDependencies {
  readonly library: Pick<ProjectLibrary, 'closeProject'>
  readonly runtime: Pick<ProjectRuntimeManager, 'close'>
  readonly proxy: Pick<WorkbenchProxyManager, 'closeProject' | 'audit'>
}
export function createProjectCloseService(
  dependencies: ProjectCloseServiceDependencies
): ProjectCloseService
```

`ProjectCloseService.closeProject(id): Promise<RuntimeCloseOutcome>` validates the identifier exactly as delivered — a non-string or empty identifier throws `ProjectCloseError('invalid_project_id')` — then calls `runtime.close({ projectId: id, drainConnections, auditConnections, commitRemoval })` — **all four `ProjectRuntimeCloseInput` members, at one call site**. It composes `drainConnections` from `proxy.closeProject(id, signal)`; `auditConnections` as the synchronous thunk `() => proxy.audit(projectToken)` over `projectToken = deriveProjectOwnerToken(id)` derived once per close; and `commitRemoval` from `library.closeProject(id)`. The service therefore binds **two** proxy members, which is why its dependency type is `Pick<WorkbenchProxyManager, 'closeProject' | 'audit'>`: a `Pick` naming only `closeProject` does not typecheck at the `auditConnections` construction site, and `audit` is the member whose synchronous, uncached, live-derived contract the confirmation region depends on. **The body of `commitRemoval` is the only place in the repository that names durable removal**, and `createProjectCloseService` is its only construction point. The service performs no ordering, no bounding, and no release of its own. `createLibraryProjectCloseService` is removed; `AppOptions.createProjectCloseService` becomes `(dependencies: ProjectCloseServiceDependencies) => ProjectCloseService`, and `app.ts` constructs it after the proxy so all three dependencies exist. No construction cycle is created because the manager never holds the proxy.

**Interface member deltas.** `ProjectRuntimeManager` 15 → 16. `WorkbenchProxyManager` 4 → 5. `ProjectRuntimeConfig` 17 → 20. `PROJECT_RUNTIME_DEFAULTS` 19 → 22. `ProjectRuntimeManagerAudit` 16 → 21 (`closeTasks`, `closeClaims`, `retiredProjects`, `lateCloseSettlements`, and — added in revision 4 — `refusedLateAcquisitions`). `ProjectRuntimeCloseInput` is new with 4 members. `ProjectCloseService.closeProject` return type changes. `AppOptions.createProjectCloseService` signature changes. `ProjectHomeState` replaces `close?: ProjectCloseState` with `closes: ReadonlyMap<string, ProjectCloseState>`, adds `closeDialogId?: string` and `closeSettlementVersion`, and widens `focusTarget`. The module-local `Owner` record in `use-project-home.ts` also gains `closeSettlementVersionAtIssue` and the controller gains a `closedProjectIds` ref (section 13); neither is exported, so neither changes a published surface. That is **eight changed type or interface surfaces** and **four new exported types** (`RuntimeCloseOutcome`, `RuntimeCloseOutcomeName`, `RuntimeCloseRejectionCategory`, `ProjectRuntimeCloseInput`).

### 2. The claim, and what it locks

A close claim is a per-project record keyed by stable project ID, held in a manager-local `Map<string, CloseClaim>`. It is installed by one synchronous compare-and-set with no `await` between reading `entries.get(projectId)` and installing the claim. It is **orthogonal to the entry**: the entry keeps its own state and keeps projecting truthfully, so a claimed `running` entry still reports `Running` and a claimed retained `failed` entry still reports `Failed`. No entry state is added (`RUNTIME_ENTRY_STATES` stays at 7) and no public state is added (`PUBLIC_RUNTIME_STATES` stays at 4).

While a claim for P is installed:

| Path | Behaviour |
|------|-----------|
| `start(P)` | throws `RuntimeFailure('runtime-closing')` |
| `stop(P)` | returns `{ outcome: 'rejected', category: 'close-in-progress' }` |
| `restart(P)` | returns `{ outcome: 'rejected', category: 'close-in-progress' }` |
| `register(P, path)` | refuses without mutating; throws `RuntimeFailure('runtime-closing')` |
| `close(P)` | joins the claim (section 4) |
| any path for a peer Q | unaffected |

The claim is released on settlement in every path, including faults, and `audit().closeClaims` is asserted zero after every settled scenario.

**One refusal at the head of a path is not enough.** `start()` can be suspended when a claim is installed, and its running-reuse branch would then return a live snapshot the proxy uses to open a *new* upstream connection — after the close's phase-1 drain has already audited zero. Every acquisition and join seam therefore re-evaluates the claim after every `await`, using one manager-local helper:

```ts
const closeClaimFailure = (projectId: string): RuntimeFailure | undefined =>
  closeClaims.has(projectId) ? new RuntimeFailure('runtime-closing') : undefined

const reuseGuard = (current: RunningEntry): RuntimeFailure | undefined =>
  closeClaimFailure(current.projectId) ?? reuseOwnershipFailure(current)
```

`reuseOwnershipFailure` is the delivered helper that already re-checks entry ownership after exactly these awaits; `reuseGuard` extends the same discipline to the claim. The re-check points in `start()` are fixed here: after `await dependencies.findProjectById`, after `await waitForReconciliation`, after a `waitForStarting` join resolves, after `await current.ready.process.isAlive()`, after `await processDependencies.health.check(...)`, and once more immediately before `return current.snapshot`. `register()` re-checks before it mutates. `installEntry` (section 8) re-checks before every install. `registerOwnership` records the record and accounts it as identity-bearing late work when the project is claimed, so a late launch is *visible* to confirmation rather than hidden from it — and confirmation then fails closed rather than removing a registration whose runtime just appeared.

**What the rechecks leave behind, corrected in revision 6.** Revision 2 justified the confirmation re-observation with the residue above — a reuse that passes its final claim check and hands a live snapshot to the proxy in the same event-loop turn. Executing `T-11` against the delivered proxy shows that residue is **unreachable**, and that a different and more ordinary one takes its place. `handleHttp` and `handleUpgrade` each execute `pending.set(controller, projectToken)` — and `handleUpgrade` additionally `rawSockets.set(socket, projectToken)` — **before** they call `resolveTarget`, which is the only path to `projectRuntime.start`, and each releases that registration only in its own `finally`. Phase 1's drain aborts every selected pending controller and does not settle until all five per-token counts, `pendingOperations` among them, reach zero. So an acquisition that is in flight when phase 1 runs cannot survive it, and an acquisition that arrives after it is refused by the claim before `resolveTarget` can return a target: **no proxy-originated upstream connection can be opened under an installed claim.**

The real residue is the arrival's own registration. An arrival that reaches the proxy after phase 1 settled registers its per-token pending operation **before** it requests an acquisition, and holds that registration until it unwinds. **Corrected in revision 7:** how it unwinds depends on where the close reaches it — through the head refusal the claim raises before every `await` on the acquisition path, or through the cancellation the re-drain's own synchronous abort delivers when the drain reached it first — and those are two different settlements that evidence must report as what they were rather than as one. What is common to both is the audited interval. An acquisition suspended at a **post-`await`** seam necessarily entered `start()` *before* the claim existed, so phase 1 cannot settle until it unwinds: that arrival is the refusal witness and can never also be the stale one (section 15). The phase-1 audit is therefore stale at confirmation on the **ordinary** path — the path where every mechanism in this section worked — and not only on a defective one. That is what phase 5 re-observes and what the single permitted re-drain clears (sections 5 and 6), and it is what `S-69` and `S-70` now execute (section 15). The escaped-snapshot case is retained as a **negative control**: it becomes reachable exactly when a post-`await` recheck is deleted, which is what makes `G-21`'s deletion observable in execution as well as in source.

**A refusal is not late work (revision 4).** Every refusal in the table above, and every post-`await` recheck refusal, is the mechanism working, not a fault. Such a refusal is a **refused acquisition**: it is raised *before* the path installed an entry, registered or revived an ownership record, created a pending admission, minted a generation, or returned an existing snapshot to its caller; it mutates nothing; its caller settles with the bounded failure it was given. A refused acquisition increments the manager-wide counter `refusedLateAcquisitions`, reported by `audit()`, and it does **not** increment `claim.lateWork` and does **not** block confirmation. The counter is evidence — and, because it is incremented inside the production recheck, it is the *production-observed* witness that a scenario's held acquisition actually reached the seam it claims to exercise (section 15). The confirmation predicate never reads it.

The reason is exact rather than convenient. A refused acquisition leaves the entry untouched, so clause 7 still holds; it registers no ownership, so clause 2 still holds; it creates no admission, so clause 4 still holds; and the only externally observable residue it can have produced — a connection opened from a snapshot handed out *before* the refusal — is precisely what clause 1's re-observation and the single permitted re-drain exist to catch. Counting it as late work would add no safety and would remove correctness: any caller that merely asked for P while a close was in flight would permanently make that close unconfirmable, so `S-69` could never confirm, and `AC-1`, `AC-9`, and `AC-10` successes would become load-dependent. Revision 3's text read literally as counting these refusals, which is the contradiction `T-3` returned to Plan with; revision 4 settles it here, in section 6, and in `ADR-260816`.

### 3. Admission, in one fixed order

`close()` resolves `dependencies.findProjectById(projectId)` first, then evaluates in exactly this order. The order is the contract; a validator asserts it.

| # | Condition | Outcome |
|---|-----------|---------|
| 1 | `shuttingDown` | `rejected: manager-shutdown` |
| 2 | persisted project absent | `already-absent` |
| 3 | close claim installed for P | join (section 4) |
| 4 | entry state `reconciling` | `rejected: reconcile-in-progress` |
| 5 | entry state `failed` with `failure.category === 'reconcile-unconfirmed'` | `rejected: reconcile-unresolved` |
| 6 | entry state `starting` | `rejected: start-in-progress` |
| 7 | entry state `restarting` | `rejected: restart-in-progress` |
| 8 | entry state `stopping` | `rejected: stop-in-progress` |
| 9 | entry absent, `registered` (either `released` value), `running`, or `failed` (non-reconcile) | claim, freeze cardinality, and proceed to the phases |

`shuttingDown` is re-read after the `findProjectById` await, exactly as `stop()` and `restart()` already do. Case 2 is a **successful no-op**, not a rejection, because the delivered route maps an absent project to `404 project_not_found` and AC-4 requires that behaviour preserved.

**The pre-claim boundary is step 9, and eight settlements precede it (revision 6).** Steps 1 – 8 each return before `closeClaims.set(projectId, claim)` executes, so a close that settles at any of them never held a claim. That is **eight** settlement sites, not three, and they are frozen here as the closed enumeration the evidence contract names `BL020_PRE_CLAIM_SETTLEMENTS`, in admission order:

| # | Admission step | Settlement site | Settled outcome |
|---|---|---|---|
| 1 | 1 | `manager-shutdown` | `rejected: manager-shutdown` |
| 2 | 2 | `persisted-absence` | `already-absent` |
| 3 | 3 | `contender-join` | the winner's own settlement, with the winner's `closed` mapped to `already-absent` |
| 4 | 4 | `reconcile-in-progress` | `rejected: reconcile-in-progress` |
| 5 | 5 | `reconcile-unresolved` | `rejected: reconcile-unresolved` |
| 6 | 6 | `start-in-progress` | `rejected: start-in-progress` |
| 7 | 7 | `restart-in-progress` | `rejected: restart-in-progress` |
| 8 | 8 | `stop-in-progress` | `rejected: stop-in-progress` |

The site is not the category, and the two must never be conflated. Three settled results are reachable on **both** sides of the claim: `manager-shutdown` is returned by the head checks *and* by the five `shuttingDown` re-reads inside the phases; `already-absent` is returned by step 2 *and* by phase 6 when `commitRemoval` reports `project_not_found` after a confirmed release; and a contender inherits whichever bounded rejection the winner produced, including `release-unconfirmed` and `removal-failed`, without ever installing a claim. Only `ownership-cardinality-exceeded` is unreachable at a pre-claim site *and* unreachable to a contender, because the over-cap refusal installs, tests, and deletes its claim in one synchronous section that no other close can observe. Anything that must distinguish an admitted close from a refused one therefore discriminates by **site**, never by category; section 15 fixes the row representation and `V-16` asserts it.

**The in-claim cardinality gate.** Step 9 is one synchronous section. It reads the entry, installs the claim, and — in the same section, before any `await` — freezes two counts for P: `ownershipCardinality` (ownership records whose `projectId === P`) and `quarantineCardinality`. It then derives `sweepUnits = max(1, ownershipCardinality)` **only when that value is admissible**. If `ownershipCardinality > config.closeOwnershipSweepCap` the close settles immediately as `rejected: ownership-cardinality-exceeded`: it drains nothing, signals nothing, terminates nothing, removes nothing, installs no failure, emits no event, leaves the entry and all four durable fields exactly as they were, releases the claim, and returns. No `sweepUnits` above the cap is ever resolved, passed to the bound functions, or recorded: the refused close authorises no sweep at all, so the multiplier it carries is the floor value `1`, and the ceiling it declares is `runtimeCloseOverallBoundMs(config, requiresQuarantineResolution, 1)` — a bound the refusal, which performs no phase, settles far inside. The claim **is** installed before the freeze, so an over-cap refusal is an admitted close for evidence purposes: it carries a non-null `claimInstalledAt` and `elapsedOrigin: 'claim'` (section 15). This is the only branch in which the sweep arithmetic could otherwise grow without a declarable ceiling, and it is fail-closed by construction. The admission order stays nine steps; the gate is part of step 9's claim install, not a tenth ordered condition, so `ADR-260816`'s nine-step contract is unchanged.

### 4. Contenders join and never report success

A close that finds a claim installed opens no second operation. It awaits the claim's settlement promise and then derives its outcome from the durable fact the winner established:

- winner settled `closed` → contender returns `already-absent` (route `404`);
- winner settled `already-absent` → contender returns `already-absent`;
- winner settled `rejected: C` → contender returns `rejected: C`.

A contender performs no drain, no release, no removal, no mutation, and no emission. Exactly one close per completed removal returns `closed`, so exactly one `project.closed` is emitted. Eight concurrent closes of one running project therefore produce one `200` and seven `404`s, which is byte-identical to the delivered stopped-path concurrency behaviour.

### 5. The phases, in one fixed order

An admitted close runs seven phases under one overall deadline armed from `deadlineScheduler`:

1. **Drain.** `drainConnections(signal)` with the signal bounded by **one** `closeDrainAllowanceMs` deadline armed here and shared with the single re-drain phase 5 may perform. Its returned `WorkbenchProxyAudit` must report `pendingOperations`, `upstreamHttpRequests`, `upstreamHttpResponses`, `rawSockets`, and `webSockets` all `0`. An admitted close invokes `drainConnections` **at most twice** and arms **exactly one** drain deadline.
2. **Resolve admissions and quarantine.** `reclaimProjectQuarantine(P)` then await any installed `PendingReplacementAdmission.resolution`, finishing it when its phase is `absent-confirmed` or `audited-absent`. This is the delivered restart release-gate sequence, reused unchanged.
3. **Release the attributable owned runtime.** When `ownedReadyFor(entry)` yields a `ReadyRuntime`, terminate it through `process.terminate(gracefulShutdownMs, forceShutdownMs, port, signal)` — the one delivered termination sequencer — and record exactly one close-phase cleanup audit for that generation.
4. **Sweep remaining ownership.** For every remaining `ownership` record whose `projectId === P`: accept it when a recorded cleanup audit for that exact identity already confirms the triple, otherwise terminate and audit it under the same sequencer and record its audit.
5. **Verify zero residual by re-observation.** `auditConnections()` synchronously. If any of the five counts is non-zero, invoke `drainConnections(signal)` **once more** under the phase-1 deadline still in force, then re-observe. Then evaluate the confirmation predicate of section 6 as one uninterrupted synchronous region. An admitted close invokes `auditConnections` **at most twice**.
6. **Remove.** `commitRemoval()` — the **next statement** after the phase-5 synchronous region, with no `await`, no branch, and no intervening call between the last observation and it, other than the single synchronous seal assignment the region ends with (section 6).
7. **Retire.** Delete the entry, delete `cleanupOutcomes` for P, delete the claim, and add P to the tombstone set. The seal is superseded by the tombstone and is never lifted on this branch.

Draining precedes releasing so no proxy operation is awaiting an acquisition the claim already refuses and no stream is torn down by a process exit it could have avoided; removing is last so the durable registration is the last thing to disappear. Phase 5 re-observes rather than trusting phase 1 because a per-token proxy resource can appear after phase 1 audited zero. **Corrected in revision 6 and made exact in revision 7:** the ordinary source of that resource is an arrival that registered its per-token pending operation before it requested an acquisition and has not yet unwound — whether the claim refuses it or this re-drain's own abort cancels it (section 2) — while the escaped-snapshot case is reachable only when the claim's refusals on the acquisition path have been deleted, and is separable from the ordinary case because only it can make an upstream or socket count non-zero at this phase (section 15). The single permitted re-drain clears the ordinary case; anything it cannot clear fails the close closed.

### 6. The confirmation predicate

Removal is invoked only when **all eight** of the following hold, read inside one uninterrupted synchronous region whose next statement is `commitRemoval()`:

1. **connections** — the phase-5 `auditConnections()` re-observation reports all five per-token counts `0` (`pendingOperations`, `upstreamHttpRequests`, `upstreamHttpResponses`, `rawSockets`, `webSockets`). The phase-1 audit is evidence of progress, never of the final state. `pendingOperations` is a live per-token resource in its own right, not a bookkeeping detail: a proxy arrival the claim refuses holds one from before it requests the acquisition until its refusal unwinds (section 2), so a non-zero clause-1 observation is an **ordinary** event the single re-drain clears, and clause 1 is exercised on the normal path rather than only against a defect. **Revision 7 adds the discriminator:** on the ordinary path `pendingOperations` is the *only* one of the five counts that can be non-zero at this re-observation, because a refused or cancelled arrival never obtains a target; a non-zero upstream request, upstream response, raw socket, or bridged WebSocket count here proves an acquisition escaped the claim and opened a connection under it, which is a different failure from a stale pending operation and is caught separately (section 15);
2. **ownership** — no `ownership` record with `projectId === P` remains;
3. **quarantine** — no `quarantinedOwnership` record for P remains;
4. **pending admissions** — no `pendingAdmissions` entry for P remains;
5. **in-flight lifecycle work** — no start, stop, restart, or reconciliation operation **for P** is in flight, discharged only from project-keyed state as defined below;
6. **release audits** — for every generation this close terminated, its recorded audit has `processAbsent && processGroupAbsent && listenerAbsent`;
7. **generation identity** — `entries.get(P)` is reference-identical to the value this close captured at claim install — **including the case where that value was `undefined`** — or to the `registered` entry this close itself installed;
8. **retirement** — `retiredProjects` does not already contain P.

Clauses 1 – 4 are the identity-bearing runtime, admission/quarantine/pending, and connection counts the review requires at zero; clauses 5 and 7 are the lifecycle/generation counts; clause 6 is the attribution conjunction, unchanged.

**How clauses 5 and 7 are discharged, exactly.** Both are snapshot-then-compare against project-keyed state, and neither may be discharged from an aggregate. Implement builds them from the claim record, not from the manager's global counters.

The claim record captures, inside the same synchronous section that installs it: `claimedEntry` — the exact value `entries.get(P)` returned at that instant, held **by reference** and permitted to be `undefined`; `frozenOwnershipCardinality` and the resolved `sweepUnits` of section 3; and `lateWork`, a counter initialised to `0`.

*Clause 7* is `Object.is(entries.get(P), claim.claimedEntry) || Object.is(entries.get(P), claim.installedRegisteredEntry)`. Entry objects are immutable in the delivered manager and every transition installs a **new** object, so reference identity is exactly the generation test this clause needs. `Object.is` compares the absent case correctly, so "absent when I claimed and absent now" and "absent when I claimed but something installed one since" are distinguishable — which a truthiness test, a `state` string comparison, or a structural equality cannot do. No structural comparison and no snapshot deep-equality is permitted.

*Clause 5* is the conjunction of three project-keyed observations read in the same synchronous region: `entries.get(P)` is `undefined` or in a non-transient state (`registered`, `running`, or `failed` — never `starting`, `stopping`, `restarting`, or `reconciling`); `pendingAdmissions.has(P) === false`; and `claim.lateWork === 0`.

**What increments `claim.lateWork`, exactly (revision 4).** `lateWork` counts **identity-bearing** late work for P and nothing else. It is incremented by exactly three events, each of which is a site that attempted or created state carrying a runtime identity for P while the claim was held:

| # | Event | Why it is identity-bearing |
|---|-------|---------------------------|
| 1 | `installEntry(P, …)` **refuses** an install | The calling path had already materialised the generation it was about to install — a launched process, an adopted identity, or a settlement entry — so a live or unresolved identity for P exists outside the frozen cardinality |
| 2 | `registerOwnership` observes P claimed or retired | An exact `pid:processStartTime:port` identity was reported for P after the sweep cardinality was frozen, so the declared release bound never covered it |
| 3 | A late or reordered settlement for P is accounted in `lateCloseSettlements` | A continuation with no caller reached a claimed or retired P; it applies nothing, but it proves an earlier generation is still settling |

It is **not** incremented by a refused acquisition, join, or registration — the `start()` post-`await` rechecks, the `start()`/`register()` head refusals, and the `stop()`/`restart()` `close-in-progress` rejections — because each of those is refused *before* producing identity-bearing state (section 2). Those are counted on `refusedLateAcquisitions` instead.

**What increments `lateCloseSettlements`, exactly (revision 4).** `lateCloseSettlements` keeps its delivered meaning and is not widened: it counts continuations **with no caller** that arrive for a claimed or retired project and are accounted rather than applied — late stop, restart, start, reconciliation, readiness, exit, health, proxy, persistence, and cleanup settlements. A reconciliation observation whose reconciling entry has since been claimed or retired is one of these continuations and is accounted on exactly this rule — for a claimed subject and a retired one alike, the claimed case additionally raising that claim's `lateWork` and the retired case raising `lateCloseSettlements` alone, because retirement has already released the claim there is nothing left to charge (`S-55`). Every such increment for P while P is claimed also increments `claim.lateWork` (row 3 above). A caller-visible refusal is never counted here, so `lateCloseSettlements`, `refusedLateAcquisitions`, and `claim.lateWork` are three distinct, separately inspectable facts and `S-53 … S-55` are unaffected.

**Sealing the confirmation-to-removal window (revision 4).** Clause 5 is read once; `commitRemoval()` is then awaited. A counter incremented during that await cannot change a predicate already evaluated, so the window is closed structurally rather than by accounting. The claim carries `sealed: boolean`, initialised `false` and set to `true` by the **last statement of the confirmation region**, immediately before `commitRemoval()`. While `claim.sealed` is `true`:

- `installEntry` refuses **every** caller for P, including the close that owns the claim, so no entry can be installed while removal is in flight;
- `registerOwnership` for P does **not** enter the ownership index; it records the exact identity as a `quarantinedOwnership` record for P and accounts it as late work, so the identity remains reachable by the manager shutdown sweep and is never orphaned;
- the seal is lifted **only** by the close itself, **only** on the `removal-failed` branch, and **only** in the statement immediately before it installs its released `registered` entry; the successful branch never lifts it, because retirement supersedes it.

The window is also unreachable by construction, and the plan asserts both: every ownership-registering site in the manager is reachable only from an operation whose transient entry state — `starting`, `restarting`, or `reconciling` — close admission refuses at steps 4, 6, and 7, and every path that could begin such an operation is refused at its head by the claim. The seal is therefore defence in depth over a proven-empty window, and `V-5` proves the emptiness with a forced-arrival negative control rather than by assertion.

The delivered `stopTasks` and `restartTasks` are `Set<Promise<…>>` values that are **not keyed by project**. They are retained for shutdown settlement and for the `audit()` counts, and they **may not** be read to discharge clause 5, in either direction: a peer project's in-flight stop would block P's confirmation (a false negative that would make `S-64` and every peer-isolation scenario unprovable), while P's own identity-bearing late work — a refused install, an ownership registration under the claim, or a late settlement, none of which holds a promise in either set — would pass it (a false positive, which is the exact defect clause 5 exists to prevent). `V-5` proves both directions with a peer-busy fixture and the three identity-bearing late-work fixtures, and separately proves with the refused-acquisition control that a refusal is not late work; the `execution.confirmation` record's `inFlightLifecycle` and `generationIdentity` booleans are computed from these observations and from nothing else.

Absence is never inferred from an entry label, from entry absence, or from a prior audit that did not itself confirm the triple. A project with **no owned runtime** — no entry, a `registered` entry in either `released` value, or a retained `failed` entry whose ownership record is already gone — satisfies (2)–(5) vacuously and is removed with **no signal sent, no process probed, and no listener probed**. That is precisely the delivered stopped-project behaviour, and it is what AC-4 preserves.

### 7. Settlement of every terminal case

| Terminal case | Entry after | Ownership | Registration | Public state | Outcome | Route |
|---|---|---|---|---|---|---|
| Confirmed release, `commitRemoval` → `{ disposition: 'closed', id }` | deleted, tombstoned | none | removed | no row | `closed` | `200 { id, disposition: 'closed' }` |
| Confirmed release, `commitRemoval` → `{ disposition: 'project_not_found' }` | deleted, tombstoned | none | already absent | no row | `already-absent` | `404 project_not_found` |
| Confirmed release, `commitRemoval` throws | `registered { released: true }` | none | present ×1, fields unchanged | `Stopped` | `rejected: removal-failed` | `500 project_close_failed` |
| Release unconfirmed from a `running` entry | `failed`, `close-release-unconfirmed`, one `runtime.health.changed` emitted | retained | present ×1 | `Failed` | `rejected: release-unconfirmed` | `500 runtime_release_unconfirmed` |
| Release unconfirmed from a retained `failed` entry | `failed`, `close-release-unconfirmed`, **no** event | retained | present ×1 | `Failed` | `rejected: release-unconfirmed` | `500 runtime_release_unconfirmed` |
| Drain audit non-zero at deadline | as above, per prior entry state | retained | present ×1 | truthful | `rejected: release-unconfirmed` | `500 runtime_release_unconfirmed` |
| Frozen ownership cardinality above `closeOwnershipSweepCap` | unchanged | retained, unchanged | present ×1, fields unchanged | truthful (whatever the entry already reported) | `rejected: ownership-cardinality-exceeded` | `500 runtime_close_ownership_unresolved` |
| Admission-order rejection (cases 1, 4–8) | unchanged | unchanged | present ×1 | truthful | `rejected: <category>` | `409` or `503` |
| Persisted absence | unchanged | unchanged | absent | no row | `already-absent` | `404 project_not_found` |

**Eleven terminal cases**, counted as the distinct settled `(outcome, category)` pairs the close can produce: `closed`, `already-absent`, and the nine members of `RUNTIME_CLOSE_REJECTION_CATEGORIES`. The nine rows above group them — the `release-unconfirmed` category occupies three rows because its entry disposition differs by prior state, and the admission-order row stands for the six admission-time rejection categories. Revision 1's count of ten was the same arithmetic over eight rejection categories. The cardinality refusal deliberately installs **no** retained failure and emits **no** event: no release was attempted, the runtime may be perfectly healthy, and labelling it `Failed` would be untruthful. It is a distinct named condition, so it gets a distinct bounded category rather than being folded into `release-unconfirmed` behind a flag. No terminal case leaves a claim installed, an entry in a transient state, or a registration absent with an unconfirmed resource. A close that faults for any other reason aborts its deadlines, settles the entry exactly as an unconfirmed release, releases the claim, and then surfaces the fault explicitly; the route reports `500 project_close_failed` and never a success-shaped body.

### 8. One install authority, retirement, and the end of stale work

**`installEntry` is the manager's only entry write (revision 4).** The literal `entries.set(` appears **exactly once** in `project-runtime-manager.ts`, inside the body of `installEntry`. Every entry transition in the manager — `register()`, `start()`'s `starting`, `running`, and `failed` installs and its completion settlement, `stop()`'s `stopping` install and both settlement installs, `restart()`'s `restarting` install and its success settlement, every reconciliation install, and the close's own `removal-failed` rollback install — calls `installEntry` and observes its boolean result. No site is grandfathered.

The refusal contract for its callers is fixed here, in two classes:

- **Refusable installs** — every install that can be reached after an `await` on its own path. A `false` result means nothing was written: the caller MUST NOT emit an event, register ownership, record a cleanup audit, register a task, or return success, and MUST settle its own caller with the bounded failure `entryInstallRefusal` computed for that project (`unknown-project` when retired, `runtime-closing` when claimed). `start()`'s completion install and every reconciliation install are in this class.
- **Unrefusable-by-construction installs** — an install performed in the same synchronous region as its own path's refusal check, with no `await` between them, so no claim or tombstone can appear in between. `stop()`'s `stopping` install, `restart()`'s `restarting` install, `start()`'s `starting` install, and both stop settlement installs guarded by their delivered `entries.get(input.projectId) !== stopping` recheck are in this class. These MUST assert the result with their own path's invariant error — `RuntimeStopInvariantError`, `RuntimeRestartInvariantError`, or `RuntimeCloseInvariantError` — rather than discard it. Ignoring a boolean refusal is a silent default and is prohibited.

This is strictly stronger than "every install site consults the retirement set and the claim map", which a manager can satisfy while still writing `entries` from nine places. It is the property `G-4` asserts, and it is why three delivered BL-017/018 source guards that count literal `entries.set(` occurrences are migrated to semantic assertions rather than being used to justify literal writes (section 16.1).

After a confirmed removal the manager records P in `retiredProjects: Set<string>`. Every entry-installing site consults `retiredProjects` and the claim map before installing: `register()`, `start()`'s `starting`/`running`/`failed` installs and its completion settlement, `stop()`'s settlement installs, `restart()`'s installs, and reconciliation's installs. A site that finds P retired installs nothing, mutates nothing, emits nothing, records no cleanup, and settles its own caller with an explicit bounded failure: `unknown-project` for a caller-visible acquisition, and an accounted stale settlement (`lateCloseSettlements`) for a continuation with no caller. A stable project ID is never reissued after its row is deleted, so the set never needs to expire and can grow only with the number of successful closes in one API-process lifetime.

### 9. Bounds: one origin, one arithmetic

Phase 4 sweeps **every** ownership record for P, and P can hold more than one: an unconfirmed stop or restart release retains its record — the delivered `stop()` deletes an ownership record only when its audit confirms the triple — and a later successful start registers another. Two retained records with no quarantined identity are therefore reachable, and a release bound covering one termination would be exceeded by a correct close. The bound is cardinality-aware.

Three configuration members are added, all internal, all positive-safe-integer validated by the delivered `createProjectRuntimeConfig` loop:

| Member | Default | Meaning |
|---|---|---|
| `closeDrainAllowanceMs` | `5_000` | one deadline covering both permitted drains |

### 11. Events

- A completed close emits exactly one `project.closed`, and only a completed close emits it.
- A close emits **no** `runtime.stop.*`, `runtime.restart.*`, `runtime.start.*`, or `runtime.reconcile.*` event, even though it consumes the same sequencer and audit primitives. This is the same rule `ADR-260815-explicit-workbench-restart-control` already established for restart.

### 12. Proxy drain

```ts
closeProject(projectId: string, signal: AbortSignal): Promise<WorkbenchProxyAudit>
```

Derives `projectToken = deriveProjectOwnerToken(projectId)` and acts on that token only: aborts each `pending` controller whose token matches, destroys each matching `httpRequests` entry, destroys each matching `httpResponses` entry, terminates each matching `webSockets` entry, then waits until the five per-token counts reach zero or the caller's signal aborts, then terminates and destroys any remaining matching WebSockets and raw sockets, removes exactly those keys, and returns `audit(projectToken)`. It never sets `shuttingDown`, never calls `resolveTarget`, never calls `projectRuntime.start`, never reads or removes another token's keys, and never clears a whole map. The global `shutdown()` path is untouched.

**The wait, decided exactly (revision 5).** The drain owns **no authority over time** — which is not the same as owning no timer, and revision 4's literal "no timer" wording was unsatisfiable against this proxy. The five resource maps are mutated from eleven independent sites inside Node stream callbacks and `ws` callbacks and publish no aggregate settlement event, so the only way the drain can observe settlement is to re-read the same synchronous per-token audit its caller uses. The wait is therefore specified as follows, and `G-7` asserts every clause of it:

- **Termination is exactly two conditions.** The wait ends when `audit(projectToken)` reports `pendingOperations`, `upstreamHttpRequests`, `upstreamHttpResponses`, `rawSockets`, and `webSockets` all `0`, or when the caller's `AbortSignal` aborts. Nothing else may end it.
- **The observation gap declares nothing.** Between two readings of that predicate the drain may schedule one **fixed non-authoritative observation gap**, written as the literal `setTimeout(check, 1)`. The delay is a literal in the source; it is never read, compared, accumulated, or counted; it defines no success, no failure, no deadline, no retry count, no attempt budget, no fallback, and no elapsed limit; it appears in no returned value and in no evidence field. It decides only *when to look again*.
- **Prohibited outright.** `setInterval`, `setImmediate`, `queueMicrotask`, `scheduleDeadline`, `AbortSignal.timeout`, `Date.now()`, `performance.now()`, `process.hrtime`, and any counter or accumulator — no `++`, no `+=`, no `-=` anywhere in the drain body.
- **Nothing survives settlement.** The gap is captured in one handle named `pollHandle`; the drain settles at most once; and on that settlement path it calls `clearTimeout(pollHandle)` and `signal.removeEventListener('abort', check)` before it resolves. No timer, listener, or callback may observe or mutate the proxy's resources after the returned promise settles, and a callback delivered after settlement changes nothing. This is the delivered `awaitTrustedReconciliationDelay` hygiene in `project-runtime-manager.ts`, applied to the drain.
- **Why not an event.** Making the maps event-driven — a settlement notification emitted at each of the eleven mutation sites, with the drain subscribing — was considered and rejected. It buys no bound (the caller's signal is the only bound in both designs, so `B-1` and every other declared bound is unchanged), it adds a cross-cutting notification surface to third-party callbacks, and its failure mode is strictly worse: a missed or unregistered notification hangs the drain to the caller's deadline and silently converts an ordinary drain into `release-unconfirmed`, which no guard could distinguish from a genuinely stuck socket. Re-reading live state cannot be missed. Section 14's boundaries hold: no new member, no new configuration, no new dependency.

The correction is confined to the wait. The token derivation, the four termination steps, the key removal, the returned audit, the prohibitions on `shuttingDown`, `resolveTarget`, `projectRuntime.start`, foreign tokens, and whole-map clearing, and the untouched global `shutdown()` path are exactly as revision 4 fixed them.

### 13. Project Home

Revision 1 asked for two things that cannot both be true: the delivered modal dialog kept open through settlement, and peer controls usable while a close is pending. A focus-trapped `aria-modal` dialog makes every peer control unreachable for as long as it is open, and the delivered dialog stays open through `pending`, `retry`, `unknown`, and `refreshing`. Revision 2 resolves the contradiction in one direction and specifies the whole model. The delivered per-project restart lane — `restarts: ReadonlyMap<string, ProjectRestartState>` plus a `restartOwners` map, with per-card `retry` and `unknown` regions already rendered in `App.tsx` — is the shape close now adopts.

**State shape.** `ProjectHomeState.close?: ProjectCloseState` is replaced by `closes: ReadonlyMap<string, ProjectCloseState>` keyed by project ID, plus `closeDialogId?: string` naming the at-most-one project whose confirmation dialog is open, plus `closeSettlementVersion: number`. `ProjectCloseState` keeps its delivered members (`id`, `name`, `originalIndex`, `phase`, `transmitted`, `message?`) unchanged. The controller keeps `closeOwners: Map<string, CloseOwner>` where `CloseOwner = { projectId, generation, controller, active }`, mirroring `RestartOwner` exactly, and an `ownsClose(projectId, owner)` predicate identical in shape to the delivered `ownsRestart`. It also keeps two values that exist solely to keep the two lanes aligned: `closedProjectIds: Set<string>`, the client-side mirror of the manager's retirement set, and one added field on the delivered global `Owner` record, `closeSettlementVersionAtIssue: number`. Both are defined by the stale-list rule below.

**The dialog is exclusive and pre-transmission only.** It renders only while `closeDialogId === project.id` and that project's phase is `confirming`, or `pending` with `transmitted === false`. It keeps `role="dialog"`, `aria-modal`, `aria-labelledby`, `aria-describedby`, the delivered `CLOSE_DIALOG_BODY`, contained focus, and `Escape`/Cancel — all of which stay safe for its entire life, because its life ends at transmission. At transmission the dialog is dismissed (`closeDialogId: undefined`, `transmitted: true`) and the close continues as a per-card state.

**Admission, exactly.**

| Action | Admitted iff |
|---|---|
| `openClose(id)` | `listStatus === 'success'` and `mode === 'editing'` and `closeDialogId === undefined` and `closes.get(id) === undefined` and `!closeOwners.has(id)` and `!restartOwners.has(id)` and `stop?.id !== id` and the global owner lane is idle |
| `cancelClose()` | `closeDialogId !== undefined` and its record is `confirming`, or `pending` with `transmitted === false` |
| `confirmClose()` | `closeDialogId !== undefined`, its record is `confirming`, and `!closeOwners.has(closeDialogId)` |
| `retryClose(id)` | `closes.get(id)?.phase === 'retry'` and `!closeOwners.has(id)` — transmits directly; the destructive confirmation for that record was already given |
| `refreshClose(id)` | `closes.get(id)?.phase === 'unknown'` and `!closeOwners.has(id)` **and the global owner lane is idle** — it loads the authoritative project list, so it joins the list-bearing lane rather than the per-project lane |
| `stop(id)` / `restart(id)` | refused only when *that same* project has a close record or a close owner; a peer's pending close never refuses them |
| `submit()` / `retrySameSubmission()` / `retryList()` / `refreshProjects()` | exactly as delivered — the global owner lane is idle. A pending or transmitted close, for this project or any other, never refuses them |

**Concurrency, stated in full.** Two pending *dialogs* are impossible by construction: `closeDialogId` is a single optional and `openClose` refuses while it is set. Two pending *submissions* are possible and independent: each project has its own `CloseOwner`, its own `AbortController`, and its own generation, and a settlement applies only through `ownsClose(projectId, owner)`, so it can never mutate another project's record, owner, focus target, or announcement. Same-project duplicates are excluded twice over — `closeOwners.has(id)` refuses a second transmission and `transmitted` refuses a second send within one record. The delivered global owner lane keeps serializing registration, list, retry, and refresh work only; **the close transport no longer takes the global owner**, which is precisely what makes `S-64` reachable.

**List-bearing work during a pending close, and the stale-list rule.** Taking the close transport out of the global lane also takes away the property that made the delivered lane safe: with one owner and one generation, no response could ever be applied after newer state had superseded it. A close now settles *outside* that lane, so without a rule, a project-list response issued before a close settled could land after it and re-add the very card the close removed, or leave `state.projects` disagreeing with the runtime-state read that same settlement triggered. Four rules close that gap, and none of them serializes a per-project runtime control.

1. **Lane membership is by kind, not by card.** Every *list-bearing* action — `submit()`, `retrySameSubmission()`, `retryList()`, `refreshProjects()`, and each card's `refreshClose(id)` — keeps the delivered single global owner lane, because each replaces `state.projects` wholesale and two concurrent replacements have no defined winner. Every *per-project runtime control* — `openClose`, `confirmClose`, `retryClose`, `stop`, `restart`, and `open` — takes no global owner and is admitted per card. AC-7's peer-usability obligation is about the second group, and the second group is exactly the group that never serializes, so the rule below cannot violate it. A card's Refresh-close-result control is a list load wearing a per-card label; it renders `disabled` exactly on its full admission conjunction, including lane idleness, so the disabled-exactly-when-refused rule of `V-13` covers it unchanged.
2. **A list-bearing action is never refused because a close is pending.** A pending or transmitted close for any project imposes no additional refusal on the global lane; the lane refuses only what it already refuses, a second list-bearing action while one is in flight.
3. **A superseded list response is discarded and re-issued, never applied.** Each global-lane owner records `closeSettlementVersionAtIssue` at creation. On resolution the controller evaluates the delivered `owns(current)` check **and** compares `closeSettlementVersion` as it stands then against that stamp. If it advanced, the response is discarded without mutating `state.projects`, the owner finishes, the generation advances, and exactly one replacement request of the same kind is issued. The chain is finite: each replacement is stamped with a strictly greater settlement version, and the version advances at most once per successful close.
4. **A removed card can never be re-added, under any ordering.** `closedProjectIds` holds every project ID whose close settled `closed` or `already-absent` in this page's lifetime, and every applied list response is filtered through it before it becomes `state.projects`. This is sound because a project ID is a `randomUUID` minted once at registration and never reissued — re-registering the same directory yields a fresh ID — so the filter can never hide a legitimately re-registered project. Rule 3 keeps *runtime-state alignment* honest by re-reading rather than patching; rule 4 keeps the *card set* honest even under an interleaving rule 3 did not anticipate.

`closeSettlementVersion` therefore has two consumers — the one additional runtime-state request per settled successful close, and the staleness stamp above — and both are plain per-page counters. No timer, poll, stream, or second authority is introduced, and the close control itself stays per project.

**Focus restoration, deterministic per transition.**

| Transition | Focus target |
|---|---|
| Cancel or `Escape` | that card's Close control (`focusTarget: 'close'`) |
| Transmission | that card's close status region (`focusTarget: 'close-status'`, a `role="status"` element with `tabIndex={-1}`) |
| Settled success | next card's Close, else previous card's Close, else the Ascend heading — the delivered rule, computed from the settling record's own `originalIndex` |
| Settled failure | that card's Retry close control (`focusTarget: 'close-retry'`) |
| Settled unknown | that card's Refresh close result control (`focusTarget: 'close-refresh'`) |

`focusTarget` widens from the delivered **five** members — `'open' | 'close' | 'stop' | 'restart' | 'heading'`, read from `apps/web/src/use-project-home.ts` at the base SHA — to **eight**: `'open' | 'close' | 'close-status' | 'close-retry' | 'close-refresh' | 'stop' | 'restart' | 'heading'`. Three members are added and none is removed or renamed, so every delivered focus behaviour keeps its target name and its meaning.

**Announcements.** Three classes as delivered — success, failure, unknown — plus the delivered cancel text and a new transmission text, and every one is prefixed with its project's display name so two concurrent settlements are never ambiguous: `'<name>: Close request sent.'`, `'<name>: Project closed.'`, `'<name>: ' + CLOSE_FAILURE_MESSAGES[category]`, `'<name>: Close outcome unknown. Refresh projects to determine the result.'`, `'<name>: Close cancelled.'`.

- **Disabled exactly when refused.** Each card's Close, Stop, and Restart control renders `disabled` exactly when the controller would refuse its activation for that card. `V-13` asserts the equivalence for every card in every rendered matrix row, so no rendered-enabled control is a silent no-op and no rendered-disabled control is a refused-in-appearance-only control.
- **Close settlement refresh.** A settled successful close increments `closeSettlementVersion`, and `App` performs exactly one additional runtime-state request per increment, exactly as it already does for stop and restart settlements.
- **Unknown outcome.** Unchanged in behaviour, relocated to the card: the card is preserved, the phase is `unknown`, no automatic repeat occurs, and the card's own manual refresh loads the authoritative list. Because that refresh replaces `state.projects`, the project-list revision advances and the runtime-state read is re-issued, so both authoritative observations settle before the outcome resolves to confirmed absence with normal success or to retained registration with its truthful state.

### 15. What must be proven, and how it cannot self-certify

`apps/api/src/project-close-evidence.ts` declares the contract; the matrix runner produces rows by executing production paths; the validator refuses a row that cannot have been produced that way.

- **Scenario catalog.** 75 scenarios `S-1 … S-75`, declared as a frozen ordered tuple. The committed matrix must carry exactly 75 rows in declared order with unique execution identifiers.
- **Execution witness.** Each row carries `execution` with `boundaryInstanceId`, `productionPathsEntered` (the ordered close-phase names actually entered), `primitiveCalls` (aggregate totals for `terminate`, `audit`, `isAlive`, `probeHealth`, `signal`), `signalCallsByProject` (an opaque-token-keyed map whose key set equals the row's project set exactly), `drainInvocations` and `connectionAuditInvocations` (each an integer in `0 … 2`), `routeEnteredAt`, `claimInstalledAt`, and `elapsedOrigin`. A row whose `productionPathsEntered` is empty, whose `boundaryInstanceId` is absent, whose `signalCallsByProject` key set differs from its project set, or whose drain or connection-audit invocation count exceeds two is rejected. **Attribution, fixed in revision 6:** every `execution` member describes the row's **subject close** — the one close whose outcome, route status, elapsed value, and declared bound the row reports. `drainInvocations` and `connectionAuditInvocations` count invocations of the callables the close service composed *for that subject*, never a boundary-wide total, so a scenario in which a peer or a contender also drains cannot inflate them.
- **Timing origin, inhabitable rather than implied — discriminated by settlement site, corrected in revision 6.** Every row carries `preClaimSettlement: Bl020PreClaimSettlement | null`, the admission-site discriminator for its subject close, drawn from the frozen eight-member enumeration `BL020_PRE_CLAIM_SETTLEMENTS` of section 3 in admission order: `manager-shutdown`, `persisted-absence`, `contender-join`, `reconcile-in-progress`, `reconcile-unresolved`, `start-in-progress`, `restart-in-progress`, `stop-in-progress`. `routeEnteredAt` is always a number. `claimInstalledAt` is `number | null` and is non-null **if and only if** `preClaimSettlement === null`. `elapsedOrigin` is the literal union `'claim' | 'route-entry'` and must equal `'claim'` exactly when `claimInstalledAt !== null`.   **Why the site and not the category.** Revision 2 derived admission from the settled outcome, listing three outcomes as pre-claim. ### 16.2 The governed production scope of `G-23` (revision 8)

`G-23` needs a scope that is **computed from the repository**, not asserted by prose and not chosen by the file being judged. This section fixes that computation. It is stated as an algorithm over frozen inputs so that it yields the same answer for any change set, and so that no incidental property of the current branch — not the number of changed files, not the number of governed files, not which files happen to be selected sources today — is load-bearing. The counts observed on this branch are recorded at the end as *witnesses*, and no guard, task, or validation may assert them as constants.

**Frozen inputs.** Four, each declared in `apps/api/src/project-close-evidence.ts` and asserted by `V-16`.

| Symbol | Members | What it is |
|---|---|---|
| `BL020_PRODUCTION_ENTRYPOINTS` | 2 — `apps/api/src/server.ts`, `apps/web/src/main.tsx` | The processes a deployed Ascend actually starts: the API entry the `justfile` builds and runs, and the browser entry the web bundle is built from. Each must exist at the branch head; a missing or unreadable entry point is a guard failure, never an empty closure |
| `SELECTED_CLOSE_SOURCE_PATHS` | 15 — unchanged | The frozen selected Close sources of section 16. Unioned into the governed scope so the scope can never fall below what this plan already declared it scans |
| `BL020_VALIDATION_ONLY_MODULES` | 5 — `apps/api/src/cli/project-close-residual-audit.ts`, `apps/api/src/project-close-evidence.ts`, `apps/api/src/runtime-stop-evidence.ts`, `apps/api/src/runtime-restart-evidence.ts`, `apps/web/src/project-close-component-evidence.ts` | The **only** modules outside a test location that this plan ratifies as validation-owned. They live under `src/` for build and type-checking reasons and are never imported by a deployed entry point. Membership is a Plan decision recorded here, not a property a module may claim for itself |
| `BL020_WRITE_CAPABLE_FS_MEMBERS` | unchanged | The frozen write-capable member set shared with `G-15` |

**Step 1 — the change set `C`.** Every source file the branch adds, modifies, or renames relative to the base SHA, plus every untracked non-ignored source file, restricted to the source suffixes `.ts .tsx .mts .cts .js .jsx .mjs .cjs`. Renames are detected, and a renamed file's base text is read from its **pre-rename** path so a move is compared against what it actually moved from. `C` is measured once, independently of every other step, and is the census against which the measured entry list is checked.

**Step 2 — the entry-point closure `K`.** The least fixed point of the static relative-import relation starting from `BL020_PRODUCTION_ENTRYPOINTS`. The specifier grammar must recognise **every** static form the repository can use to pull a module into a deployed bundle: `import … from '…'`, `export … from '…'`, bare side-effect `import '…'`, and dynamic `import('…')`, in both single and double quotes. A grammar that recognises only `from '…'` is explicitly rejected: it silently drops bare side-effect imports, which is a real hole in the delivered `T-14` walk — `apps/web/src/main.tsx:2` reaches `./index.css` by exactly that form, and any future production module reached only by `import './x.js'` would escape governance entirely. Specifier resolution must try the TypeScript rewrites of an emitted `.js`/`.mjs` specifier, the literal path, each source suffix, and the directory `index` forms.

**Step 3 — governance.** `Governed = (K ∪ SELECTED_CLOSE_SOURCE_PATHS) ∩ C`. Governance is therefore a *derived* property of a file's reachability, never an attribute stored on it.

**Step 4 — the role of every changed file**, computed in this exact precedence, first match winning:

| # | Role | Condition |
|---|---|---|
| 1 | `production` | The file is in `K` or in `SELECTED_CLOSE_SOURCE_PATHS` |
| 2 | `validation-harness` | The file is in `BL020_VALIDATION_ONLY_MODULES`, **or** its repository-relative path lies under `apps/*/test/` or `tests/`, **or** its basename matches `*.test.*` or `*.spec.*` |
| 3 | `unclassified` | Anything else — a **hard failure** |

Precedence 1 beating precedence 2 is the property that makes the location rule non-gameable: a file placed in a test directory, or named `*.test.ts`, that is nevertheless reachable from a deployed entry point is classified `production` and governed. A production module moved out of a conventional `src/` directory, or introduced outside one, is likewise governed the moment an entry point can reach it, because reachability and not location decides precedence 1. And role 3 means the scope fails closed: a new non-test module under `src/` that this plan has not ratified as validation-owned does not become silently exempt — it fails the guard until Plan ratifies it into `BL020_VALIDATION_ONLY_MODULES` or production reaches it.

**Step 5 — the assertion.** For each entry, `added = headMembers \ baseMembers` over `node:fs` and `node:fs/promises`; a file absent at the base carries an empty base set rather than being skipped. The write-capable subset of `added` is a violation **iff** the file's role is `production`. Files with role `validation-harness` are measured, their added and added-write-capable members are reported, and no assertion is made against them — because their job under this same plan is to create, write, rename, link, and remove validation-owned fixtures and artifacts, and because they are proven unreachable from every deployed entry point in step 6.

**Step 6 — the seven failure conditions.** Each is a distinct violation code with its own negative control, so none can pass vacuously and none can absorb another's failure.

| Code | Fails when | Negative control |
|---|---|---|
| `governed-write-capable-import-added` | A `production`-role entry added a write-capable member | Inject `writeFile` into `apps/api/src/workbench-proxy-manager.ts` (delivered control, retained); **and** a second control injecting one into an entry absent at the base, proving the empty-base rule is enforced rather than skipped |
| `selected-source-degoverned` | A changed member of `SELECTED_CLOSE_SOURCE_PATHS` carries any role but `production`, or is marked ungoverned | Mark the changed `apps/api/src/project-close.ts` `validation-harness` |
| `changed-file-unmeasured` | The measured entry list is not exactly `C` — a changed file missing, an entry not in `C`, or a duplicate entry | Drop one changed file from the entry list; and supply the same file twice |
| `base-comparison-incomplete` | A file present at the base has no resolved base text, a renamed file's pre-rename text was not resolved, or a file absent at the base carries a non-empty base member set | Mark an existing file `presentAtBase: false`; and give an added file a non-empty base set |
| `role-misclassified` | A file in `K ∪ SELECTED_CLOSE_SOURCE_PATHS` carries a non-`production` role, a role is absent or outside the three-value enumeration, or any file is `unclassified` | Relabel `apps/api/src/app.ts` as `validation-harness`; and present a changed non-test module under `src/` that is in no frozen declaration |

| `governed-scope-reduced` | The supplied closure is not the closure recomputed from `BL020_PRODUCTION_ENTRYPOINTS`, the entry-point list is not the frozen pair, an entry point is unreadable, or `Governed ⊉ (K ∩ C)` | Supply a closure with `apps/api/src/project-runtime-manager.ts` removed |

**Eight negative controls in total**, which `V-16` executes alongside every other guard's controls.

**What this boundary is, and what it is not.** `G-23` is a *capability* guard: it prevents a change set from quietly granting the shipped product a filesystem write capability it did not previously have, and it is deliberately blind to what validation code does with its own fixtures. `G-15` is the *behavioural* authority: it observes real call arguments during every executed close scenario and fails if any write-capable call receives a path under any registered project root, with its marker-file negative control. The safety property the filesystem core-component states is proven by `G-15` and the recursive before-and-after manifests; `G-23` is the defence in depth that keeps the surface over which `G-15` must hold from growing unnoticed. Neither is weakened by the other, and neither is a substitute for the other.
