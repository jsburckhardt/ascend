# ADR-260815-explicit-workbench-restart-control: Replace One Selected Workbench Runtime Through a Manager-Owned Restart Control

## Status

Accepted

## Context

FR-016 and AC-022 require Ascend to launch one healthy replacement workbench for a project that is running or failed, against the same project path. Issue #41 (BL-018) delivers exactly that operation as an explicit user action on one selected project.

The delivered system already contains every part except the operation itself. `ProjectRuntimeManager` owns memory-only entries keyed by stable project ID, gates `running` behind the `/healthz/` readiness contract, retains a bounded typed failure, and exposes `start`, `stop`, `reportPublicStates`, inspection, and shutdown. `ADR-260815-selected-runtime-stop-control` delivered a manager-owned selected release with an exact synchronous generation claim, an exact-ownership confirmation audit, a bounded result vocabulary, and retained ownership after an unconfirmed release. `ADR-260815-termination-sequencer-boundary` delivered the single bounded, cancellable, attributable termination control flow. `ADR-260815-public-runtime-state-projection` delivered the four-value read-only public projection. `PRD.md` NFR-015 already names `runtime.restart.requested`, `runtime.restart.succeeded`, and `runtime.restart.failed`, and no surface emits them.

What is missing is a single operation that releases one generation and creates its successor as one accepted unit. Four properties make that operation an architectural decision rather than a composition of the delivered ones.

First, `stop()` followed by `start()` cannot satisfy Issue #41. A confirmed stop installs a released `registered` entry, which the delivered projection reports as `Stopped`, and emits `runtime.stop.succeeded`, whose declared transition target is `stopped`. Issue #41 forbids reporting `Stopped` between generations and requires exactly one `runtime.restart.requested` and exactly one terminal restart event per accepted restart. A composed stop-then-start therefore produces both a forbidden public observation and a forbidden event sequence.

Second, the retained-failed case has no owner today. `start()` reaching a `failed` entry falls through to the ordinary launch path without releasing whatever the failed generation still owns, and `stop()` rejects a retained failure with `failure-retained`. Issue #41 requires an explicit restart of a retained failure to release its prior owned resources, or to confirm they are already absent, before any replacement begins, and to stay eligible until a restart succeeds or the manager shuts down.

Third, ordering is a safety property, not an implementation detail. Issue #41 requires evidence tied to the complete pre-restart identity — process absent, no attributable owned descendant, listener refusing connections — *before* replacement startup begins. Overlapping a release with a launch would allow two generations of one project to hold host resources at once and would make the "distinct complete identity" claim unprovable.

Fourth, a restart creates a new class of stale work. A prior generation's delayed release, exit, health, connection, or startup settlement now has a live successor it must not touch. The delivered guarded transitions are generation-sensitive, but no delivered decision states what a restart's own late settlements may do.

Issue #41 excludes automatic recovery, API-restart reconciliation (BL-019), running-or-failed project close (BL-020), persisted runtime handles or state, automatic idle shutdown, bulk lifecycle actions, and adoption of arbitrary processes.

## Decision

Add one manager-owned selected restart operation and expose it through one dedicated write route.

Make `ProjectRuntimeManager.restart({ projectId })` the only producer of an explicit replacement. It resolves the persisted project, reads its own entry map, and returns a frozen typed `RuntimeRestartOutcome`. It never throws for a classified lifecycle outcome; it rejects only on an infrastructure fault, which the route surfaces explicitly rather than converting into a success-shaped body. No route, proxy, CLI, or browser client releases a generation, launches a replacement, reads process liveness, probes a listener, or derives a restart result of its own.

Define eligibility by manager state, not by public state alone. A `running` entry is eligible. A `failed` entry retained in the current API process is eligible, repeatedly, until a restart succeeds or runtime management shuts down, including after an earlier restart settled unsuccessfully. Everything else is a bounded non-success: an absent entry and a `registered` entry — released or not — return `no-managed-runtime`, because a project reported `Stopped` uses the existing Open flow rather than Restart; a `starting` entry returns `start-in-progress`; a `stopping` entry returns `stop-in-progress`; a project that is not persisted returns `not-registered`; and a manager that is shutting down returns `manager-shutdown`. A `restarting` entry is not a rejection: it is an accepted restart already in flight, and the caller joins it.

Own the retained-failure resource question explicitly. A `failed` entry's prior owned resources are exactly the ownership records registered for that entry's generation. When such a record exists — the case a `stop-unconfirmed` failure deliberately retains — the release phase terminates and audits that exact identity like any other. When no such record exists, or when the audit confirms all three absences with no signal delivered, the prior resources are already absent, the release phase records `already-absent` with no signal attempted, and the restart proceeds. A retained failure is therefore never a reason to skip release, and never a reason to fail a restart whose prior resources are provably gone.

Claim the restart synchronously and let concurrent callers join. Restart resolves the persisted project first, then performs one synchronous section that reads the installed entry and, for an eligible entry, immediately installs a manager-owned `restarting` entry carrying the same stable project ID, canonical path, a fresh restart generation, the prior generation's ready runtime or retained failure, the complete pre-restart identity when one exists, and the operation promise. No `await` occurs between that read and that install, so the claim cannot interleave with the guarded `running -> failed` transition, a concurrent restart, a stop, or a start. A caller that finds a `restarting` entry returns that entry's operation promise, so any number of concurrent restart requests for one project — the eight Issue #41 requires — join one accepted restart, produce exactly one prior-generation release and one replacement startup, emit one requested and one terminal event, and settle with the same project and the same outcome inside the same declared bound.

Treat the claim as an invariant, exactly as selected stop does. Once `restarting` is installed for a restart generation, no contract-valid path may replace it before its own settlement: the guarded terminal transition compare-and-sets on an exact `running` entry, `start` refuses a `restarting` entry without mutating it, `stop` rejects a `restarting` entry without mutating it, `register` never overwrites an existing entry, and manager shutdown awaits every in-flight restart before it sweeps ownership or deletes entries. Settlement rechecks that the exact `restarting` object is still installed, and a mismatch is an invariant violation rather than a lost race: the settlement installs nothing, emits nothing, records no additional cleanup, and rejects with an explicit invariant fault the route surfaces as an unexpected failure.

Sequence release strictly before replacement, and make the gate the thing that authorises a launch. An accepted restart runs two phases in order. The release phase terminates the exact prior generation through the single termination sequencer and produces one audit. The gate then requires that audit to report process absence, owned process-group absence, and listener absence for the complete pre-restart identity; only that conjunction authorises the replacement phase. No replacement process is created, no port is acquired, and no launch is scheduled before the gate passes. When the gate does not pass within the declared release bound, the restart settles as a non-success with no replacement attempted.

Hold one entry across both phases so the public projection never lies. Add `restarting` to the internal entry vocabulary and project it as `Starting`: from acceptance until replacement readiness or a terminal failure the selected project is `Starting`. It is never `Stopped` between generations, because the release phase does not install a released `registered` entry, and it is never `Running` from process existence alone, because success installs a `running` entry only after the replacement satisfies the existing health-gated readiness contract. Add `restarting` to the lifecycle transition-target vocabulary and map it to `Starting`. The public four-value vocabulary, its single projection authority, and its one-synchronous-pass contract are unchanged, and no fifth public state is introduced.

Arm every restart deadline with the trusted synchronous scheduler, never with a fallible awaited primitive. `ADR-260815-termination-sequencer-boundary` already separates four fallible awaited primitives from three trusted synchronous ones and already rejects arming a deadline with awaited work. That separation is named here as its own boundary and given to the manager: `RuntimeDeadlineScheduler` is exactly `now(): number` and `scheduleDeadline(milliseconds, onDeadline): () => void`, `RuntimeTerminationPrimitives` extends it so the two contracts can never drift, and `defaultRuntimeDeadlineScheduler` is the delivered trusted implementation itself — the monotonic `performance.now()` clock and the native `setTimeout` timer whose returned handle cancels any later invocation. `ProjectRuntimeManagerDependencies` gains one optional `deadlineScheduler` defaulting to that implementation; validation injects a recorded scheduler that fires deadlines deterministically. `RuntimeProcessDependencies.sleep` is a fallible injectable promise and MUST NOT bound any restart phase, gate, or settlement: a `sleep` that never settles or ignores cancellation would defeat exactly the deadline it is supposed to fire. The restart therefore reads `deadlineScheduler` only, and every arm captures and invokes its cancellation handle on every exit path so no timer survives the operation.

Bound the operation with two declared, code-enforced deadlines and one honest replacement allowance. The release phase is bounded by the delivered `gracefulShutdownMs + forceShutdownMs + stopAuditAllowanceMs`, enforced by the sequencer self-bound and by a restart-owned release backstop armed through `scheduleDeadline` and cancelled when the release settles. The replacement phase is NOT bounded by `readinessTimeoutMs` alone: the delivered `launchReadyRuntime` loops up to `collisionAttempts` times, spends a full `readinessTimeoutMs` readiness window per attempt, and performs one self-bounded, non-cancellable cleanup termination between collisions and on failure. Restart deliberately keeps the delivered launch configuration unchanged — the same `config` object `start` uses, with every configured collision attempt — so a transient loopback-port race is recovered exactly as the Open flow recovers it and `address-in-use-exhausted` stays honestly reachable from a restart. The declared replacement allowance therefore accounts for all of it: `runtimeReplacementBoundMs(config) = config.collisionAttempts * (config.readinessTimeoutMs + runtimeStopOverallBoundMs(config))`. The restart's own work — the synchronous claim, the gate evaluation, the ownership-record sweep, the entry installs, the event emissions, and the final settlement — is bounded by a new internal `restartSettlementAllowanceMs` with a fixed default. The release phase has two declared variants, chosen once by one synchronous read at acceptance: an ordinary release is bounded by the delivered stop bound, and a release that must additionally resolve a pending replacement admission is bounded by that stop bound plus a quarantine reclamation allowance of `config.collisionAttempts * runtimeStopOverallBoundMs(config)`, because one abandoned launch can create at most one owned identity per configured attempt and each re-attempt is self-bounded by the sequencer. `runtimeRestartOverallBoundMs(config, hasPendingAdmission)` returns the sum of the selected release bound, the replacement allowance, and the settlement allowance, and one restart-owned overall deadline armed at acceptance through `scheduleDeadline` enforces it. Its two values are the whole caller-visible ceiling, and the larger one is what every client bound, document, and evidence row must be stated against. Both `restartSettlementAllowanceMs` and the two derived bounds are internal runtime values with fixed defaults, not environment variables, flags, or deployment settings. No new termination primitive, sequencer, or control flow is introduced: the restart consumes `ADR-260815-termination-sequencer-boundary` unchanged and only widens the visibility of its already-trusted scheduling pair. The delivered selected-stop backstop keeps its `processDependencies.sleep` race unchanged; BL-018 neither repairs nor inherits that delivered ceiling, and no restart surface may describe the stop backstop as trusted-scheduler armed.

State the replacement bound as an allowance and the deadline as the guarantee. `runtimeReplacementBoundMs` is arithmetic over configured allowances, and the launch path still awaits `assertLaunchable`, `ports.acquire`, and `process.launch` without a bound of their own, so the allowance is a declared expectation rather than a property the launch path enforces. The guarantee is the restart-owned overall deadline: whatever any launch or termination primitive does, the caller-visible restart settles within `runtimeRestartOverallBoundMs`. Two ceilings follow and MUST be recorded wherever the bound is documented, serialized, or validated. When a launch primitive respects cancellation, its own failure path terminates and audits the owned replacement, the restart records a completed replacement cleanup audit with all three absences, and the zero-residual claim is proven. When a launch primitive ignores cancellation or never settles, the restart MUST NOT claim absence it did not observe: it records the replacement audit state as unaudited, retains the ownership record registered through `onOwned`, and leaves exactly one manager-shutdown ownership sweep to terminate and audit that identity. No settlement, evidence row, notice, or document may report a residual-free replacement that was never audited.

Settle every accepted restart into exactly one manager entry. A replacement that reaches readiness installs a `running` entry for the new generation, registers its ownership record, removes the prior generation's ownership record because its release was confirmed, records exactly one restart-release-phase cleanup audit, reports `Running`, and returns `restarted`. A release that cannot be confirmed within the release bound installs a `failed` entry with the new bounded `restart-release-unconfirmed` category, retains the prior ownership record so manager shutdown re-attempts exact cleanup, launches nothing, and returns the bounded non-success `release-unconfirmed`. A replacement whose startup or readiness fails terminates and audits the replacement's exact identity, removes its ownership record when that audit confirms absence, installs a `failed` entry carrying the underlying bounded launch failure category, and returns the bounded non-success `replacement-failed`; when that audit is completed, no replacement process, owned descendant, listener, timer, or in-flight startup survives. Both failure settlements leave the project `Failed`, eligible for another explicit restart, and reported with a bounded actionable category. `Running` is therefore never reported on an unconfirmed release or an unready replacement, and no entry is ever left stuck in `restarting`.

Make the overall deadline phase-aware and give it an honest retained category of its own. The overall deadline aborts the restart's phase controller with exactly `new RuntimeFailure('restart-deadline-exceeded')`, never with an untyped reason, because the delivered launch path maps an untyped abort reason to `manager-shutdown` and reporting a healthy manager as shut down would be false. Which settlement the deadline produces depends on whether the confirmation gate had already passed, and the restart records that gate outcome synchronously so the branch is deterministic rather than inferred. A deadline that arrives before the gate passes is a release that was never confirmed: it settles exactly as an unconfirmed release — retained `failed` with `restart-release-unconfirmed`, prior ownership record retained, zero launches, zero identities created, no `Stopped` observation — which is what a project whose prior runtime may still hold host resources requires. A deadline that arrives after the gate passed is a confirmed release whose replacement did not become the installed healthy successor, so it settles as the bounded non-success `replacement-failed` and installs a `failed` entry carrying the new bounded `restart-deadline-exceeded` category. Reusing `replacement-failed` at the operation level is deliberate: the operation-level meaning is identical to a spawn-class or readiness-class replacement failure, and the retained category is what distinguishes which one occurred — the same relation the delivered replacement failures already have to their underlying launch categories. The restart result vocabulary therefore stays at seven rejection categories and the route mapping is unchanged: `replacement-failed` remains `runtime_replacement_failed` at `500`. The retained `restart-deadline-exceeded` entry reports public `Failed` with that category, carries it as the classification of the single terminal `runtime.restart.failed` event, is eligible for another explicit restart exactly like every other retained failure, and is swept by manager shutdown through the ordinary retained-ownership path. A launch, termination, audit, or health observation that settles after the deadline installs nothing, mutates nothing, emits nothing, and routes nothing; it is counted as a late settlement, and a late launch that resolves is terminated and audited rather than installed.

Admit every replacement to the manager before it can exist. The delivered `launchReadyRuntime` reports ownership only after its awaited `process.launch` resolves, so between the moment a restart calls `launch` and the moment its first `onOwned` fires a real host process may already exist while no manager record describes it. A restart deadline can fire inside that window. Revision 2 settled that case as a retained failure and then classified its prior owned resources from the ownership index alone, which reported *no record at all* — indistinguishable from a pre-spawn `spawn-error`. An immediately accepted retry passed its gate on that unobserved absence and installed a healthy successor while the abandoned launch was still able to materialise a second live generation for the same project. That is a defect in the decision rather than in any implementation of it, so the decision changes here.

`ProjectRuntimeManager` creates one **pending replacement admission** synchronously, immediately before it calls `launch`, and never after. An admission is a manager-owned record — not an entry, not a snapshot, not a public state, and explicitly not a fifth public state. It holds the stable project ID, the restart generation that created it, an opaque deterministic admission identifier, the canonical path and owner token the launch was given, the monotonic admission time read from the trusted scheduler, one phase drawn from a fixed four-member vocabulary (`launch-pending`, `materialized-quarantined`, `absent-confirmed`, `audited-absent`), one resolution promise, and one flag recording whether any ownership callback has fired for it. At most one admission exists per stable project ID at any moment, because no restart may create one until every earlier admission for that project has resolved and been consumed. A restart that settles while its launch is still in flight leaves its admission in `launch-pending`, and the retained `failed` entry it installs references that admission by identifier, so the manager's knowledge of an unresolved launch outlives the operation that created it and is visible to inspection and to the trusted audit.

Resolve every pending admission before any later restart may pass its gate. Eligibility, the synchronous claim, and joining are unchanged, so a retained `failed` entry stays immediately eligible and Issue #41's retryability is preserved exactly. What changes is the release phase. Prior owned resources are the set of ownership records registered under the retained entry's generation **plus** any unresolved admission referenced by that entry, and the prior-resource classification gains a fourth value: an entry whose project holds an unresolved admission is classified `pending-admission` and MUST NOT be classified `no-record`. The `no-record` shortcut that authorised the false absence is permitted only when the manager holds no admission for that project. A `pending-admission` release phase awaits that admission's resolution, raced against the same restart-owned release backstop and against no other timer. Three resolutions are possible and each has exactly one defined outcome. `absent-confirmed` — the launch rejected without any ownership callback ever firing, which the delivered launch path guarantees means no process was created — records a confirmed absence with no signal attempted, deletes the admission, and lets the gate proceed. `materialized-quarantined` or `audited-absent` means exact identities exist and are quarantined; the gate may pass only after every one of them carries a termination audit reporting process absence, owned process-group absence, and listener absence, which this release phase performs for any identity the quarantine has not already confirmed. No resolution inside the release bound settles the bounded non-success `release-unconfirmed`, retains `restart-release-unconfirmed`, launches nothing, creates no identity, keeps the admission unresolved, and references it again from the newly retained `failed` entry. None of this requires a new operation outcome, rejection category, failure category, route status, public state, notice, or proxy row: an unresolved predecessor launch *is* a release whose confirmation is unavailable, which `release-unconfirmed` and `restart-release-unconfirmed` already mean honestly.

Confine every post-settlement launch callback to quarantine and never to the current operation. Revision 2 told the restart to reuse `start`'s callbacks. Those callbacks unconditionally call `registerOwnership(projectId, generation, record)` and the project-keyed `recordCleanup(projectId, audit)`, so a callback arriving after the restart settled could inject an ownership record for a dead generation and could overwrite `lastCleanup(projectId)` — the successor restart's own cleanup evidence, and a value the shutdown sweep consults. A blanket no-op is equally wrong, because it would silently discard the only record of a real process the manager just created. The restart therefore passes restart-scoped wrappers whose behaviour is decided by one synchronous guard: the restart has not settled and its exact `restarting` entry is still installed. Before settlement the wrappers behave exactly as `start`'s do. After settlement they write only quarantine state — the late ownership record into a quarantine index keyed by the admission identifier together with the exact `(pid, processStartTime, port)` tuple rather than by project ID alone, and the late cleanup audit into a quarantine cleanup index under that same exact key. A late callback MUST NOT write the entry map, the project ownership index, the project cleanup index, any successor snapshot or route, any lifecycle event, or any awaited task set. The revision-2 statement that nothing after a deadline may register ownership or record cleanup is replaced by the honest constrained rule it should always have been: after settlement no successor, entry, current-operation ownership record, current-operation cleanup record, or event may be mutated, and exact late-resource quarantine and quarantine cleanup are permitted and required.

Observe an abandoned launch through one detached late-settlement continuation, and let shutdown report what it cannot know. A restart that settles with its launch still in flight attaches exactly one detached `void launchPromise.then(...)` continuation, mirroring the delivered late-termination observation in selected stop, and adds that promise to no awaited set — not `completionTasks`, not `backgroundTasks`, not `restartTasks`. This is load-bearing: manager shutdown drains `completionTasks` and `backgroundTasks` in a loop until both are empty, so a never-settling launch placed in either set would block shutdown forever, which is exactly what reusing `start`'s aborted-launch path would have produced. Only the public restart operation promise, itself bounded by the restart's own deadline, is tracked in `restartTasks` and awaited by shutdown. The continuation is what resolves the admission: a resolved launch quarantines the exact identity, immediately terminates it through the single termination sequencer without a caller signal, records that exact audit as a quarantine cleanup, and resolves the admission `audited-absent` when all three absences are confirmed and `materialized-quarantined` otherwise; a rejected launch that never fired an ownership callback resolves the admission `absent-confirmed` with a created-process count of zero; and a rejected launch that did fire one resolves `audited-absent` only when every quarantined identity carries a confirming exact audit. Each quarantined identity receives exactly one termination attempt from the continuation and at most one re-attempt, claimed by a synchronous compare-and-set on that record, so the next accepted restart's release phase and the manager shutdown sweep can never both take it and can never run concurrently. Manager shutdown sweeps quarantine alongside ownership, deletes a quarantine record only when an exact audit confirms all three absences, awaits no abandoned launch promise, and reports every still-unresolved admission explicitly in its result as an opaque project token, an admission identifier, and a phase. A shutdown holding an unresolved admission or an unconfirmed quarantined identity MUST report `failed` rather than `ok`, because the manager cannot audit a handle it never received and reporting success would be exactly the unobserved zero-residual claim this ADR forbids. A launch that materialises after shutdown returned is still quarantined and terminated by its continuation, because the alternative is a knowingly leaked process.

State cleanup cardinality per phase, as selected stop does. One accepted restart has exactly one restart-release-phase termination and at most one restart-release-phase cleanup audit for the prior generation, and at most one restart-replacement-phase termination and cleanup audit for a failed replacement. A prior generation whose release ended unconfirmed, faulted, or deadline-abandoned keeps its ownership record and is re-attempted exactly once by the manager shutdown sweep, which is the intended behaviour of retained ownership and is never described or validated as an uncontrolled duplicate. Quarantine has its own stated cardinality: each quarantined exact identity receives exactly one termination attempt from the detached continuation that quarantined it, and at most one re-attempt taken by exactly one of the next accepted restart's release phase or the manager shutdown sweep, claimed by a synchronous compare-and-set so the two can never both take it and can never run concurrently. A quarantine record is deleted exactly once, only after an exact audit confirms process, owned process-group, and listener absence.

Isolate the successor from every stale predecessor settlement. A prior-generation release, exit, health, connection, or startup settlement that arrives after its generation stopped being installed may not terminate, replace, route traffic to, emit a terminal outcome for, or change the state of the successful replacement. The mechanisms are the delivered ones, extended to the new state: the guarded `running -> failed` transition compare-and-sets on the exact entry and generation, so a prior exit or health contender loses silently once `restarting` or the successor `running` entry is installed; every awaited reuse observation rechecks the exact installed entry and generation and returns the bounded `runtime-restarting` failure when a restart claimed its generation; a termination abandoned at the release deadline records nothing, mutates nothing, signals nothing, and emits nothing, and its late settlement is counted rather than applied; and a launch that completes after the restart deadline is terminated and audited rather than installed. `ownsSnapshot` continues to answer for the exact installed running snapshot only, so a prior-generation snapshot held by the proxy fails ownership immediately when the claim is installed.

Add no proxy-side restart coordination, and claim no session continuity. Prior-generation browser and proxy connections stop being able to communicate with the released runtime because that runtime's process, owned group, and listener are confirmed absent before any replacement exists; the proxy is not asked to broadcast, drain, or reconnect. A fresh navigation through the unchanged stable workbench route resolves the persisted project and acquires the successor snapshot through the ordinary path. A navigation that arrives while the entry is `restarting` receives the bounded `runtime-restarting` failure rather than a stale snapshot or an optimistic wait. Because the proxy resolves every classified category through a table that throws `Unknown workbench failure category` for an unlisted category, that bounded failure MUST be published as a `WORKBENCH_FAILURE_TABLE` row, `runtime:runtime-restarting` at `503` `workbench_restarting`, so a restart-window navigation is a categorised, documented `503` rather than an uncategorised `500`. Publishing one row is not sufficient, because the table is not exhaustive today. `classifyRuntime` maps every `RuntimeFailure` except `manager-shutdown` to `runtime:${category}`, and the delivered `reuseOwnershipFailure` can hand a proxy-path `start` a retained winner's failure or an in-flight-operation failure, so `runtime:stop-unconfirmed` and `runtime:runtime-stopping` are already reachable and already have no row — a delivered latent `500`. BL-018 adds two more reachable categories, `runtime:restart-release-unconfirmed` and `runtime:restart-deadline-exceeded`. The table MUST therefore be closed over the whole proxied category union rather than extended by one row: every member of `RuntimeFailureCategory` except `manager-shutdown` gets exactly one row, in `RUNTIME_FAILURE_CATEGORIES` order, taking the `runtime:` group from 11 to 17 rows and the table from 23 to 29 rows once the replacement-cleanup decisions below add their category, with the six additions published as `503` because each names a transient lifecycle state or a retained failure that a later explicit action can clear. Exhaustiveness MUST be mechanically checked rather than asserted in prose: the table's literal category union and the `WorkbenchFailureCategory` union must each be provably free of members the other lacks, so a future runtime category cannot be added without a row. Rejecting rather than joining is deliberate: joining would hold a proxy request for up to the full restart bound and degrade the responsiveness the per-project lane exists to protect. Restart makes no claim that editor or terminal session state survives replacement, and every surface that documents it says so.

Refuse conflicting lifecycle operations with bounded classifications instead of queueing them. `start()` on a `restarting` entry throws the new bounded `runtime-restarting` failure instead of reusing the doomed snapshot, cancelling the restart, or launching a second replacement. `stop()` on a `restarting` entry returns the new bounded rejection `restart-in-progress`, and the stop route surfaces it as one additional bounded 409 category. Manager shutdown rejects new restarts with `manager-shutdown` and awaits every in-flight restart before auditing ownership, so no owned identity is terminated or audited concurrently by a restart and by the sweep.

Serve the operation from `POST /api/projects/:id/runtime/restart` in its own route plugin. The request carries one path identifier, no body, and no query. The success body is exactly `{ "id", "outcome" }` with the single success value `restarted`. A non-success body is exactly `{ "error": { "category" } }` drawn from a fixed vocabulary with fixed status codes. The response carries no public runtime state, no process identity, no release audit, no path, and no diagnostic, so Project Home continues to read state only from the existing `GET /api/projects/runtime` projection and no second reporting authority is created. `GET /api/projects`, its validators, `POST /api/projects`, `DELETE /api/projects/:id`, `GET /api/projects/runtime`, and the stable workbench routes are unchanged; `POST /api/projects/:id/runtime/stop` changes only by gaining one bounded 409 category.

Announce settled restarts only through the `PRD.md` NFR-015 catalog, and only from the restart itself. An accepted restart that claims a generation emits exactly one `runtime.restart.requested`; its settlement emits exactly one terminal event — `runtime.restart.succeeded` on a ready replacement, or `runtime.restart.failed` on either bounded non-success. A request rejected before acceptance emits no restart lifecycle event, and a caller that joins an in-flight restart emits nothing. The restart's internal release and replacement emit no `runtime.stop.*`, `runtime.start.*`, or `runtime.health.changed` event, because a restart produces one public transition sequence and its internal phases are not separately observable public transitions; this is why the restart consumes the termination sequencer and the launch primitive directly rather than calling `stop()` and `start()`. The restart route's own operational records are not lifecycle events and never substitute for one.

Delete an ownership record by the exact identity its own cleanup audit names, never by project. The delivered `launchReadyRuntime` calls `onOwned` once per launch attempt and, on an `address-in-use` collision, terminates that attempt, calls `onCleanup` with the resulting `RuntimeTerminationAudit` for that exact identity, and continues to the next attempt. A restart-scoped `onCleanup` that merely recorded a project-keyed cleanup would therefore leave every collided attempt's ownership record installed, so an eventually successful restart could settle holding two or three records for one project and the next restart would classify a plural prior inventory and terminate more than one handle. The installed cleanup branch MUST derive the ownership key from the audit itself as `pid:processStartTime:port` — the same derivation the delivered shutdown sweep already performs on a prior record's audit — and, when the audit reports process, owned-process-group, and listener absence, delete exactly that record under the existing generation guard. A settled successful restart therefore leaves exactly one ownership record for its project, the prior-resource inventory of the next restart of a restart-created generation is a single handle, and every restart release phase terminates exactly one live handle. The ordinary start path is deliberately left unchanged even though it has the same shape of defect: it passes the manager's ownership callbacks directly, so a collided attempt's record survives there. Repairing it would change delivered start behaviour, evidence, and source guards for a defect this issue did not introduce; the restart therefore releases only the entry's live handle, never sweeps a project's other records, and the manager shutdown sweep remains their authority. That limit is recorded as a proof ceiling rather than absorbed into a claim. The per-attempt audits are retained in restart-owned state for evidence; the restart body still writes exactly one project-keyed cleanup per phase, so `lastCleanup(projectId)` keeps meaning "this operation's phase audit" and no attempt can overwrite another's evidence.

Treat a collision cleanup that does not confirm all three absences as a quarantined residual and stop the attempt loop. The audit's `listenerAbsent` member comes from a port probe, so a collided attempt whose port is still held, or whose own process or owned group is still present, produces a non-confirming triple that says exactly one thing: the manager does not know that identity is gone. Continuing the loop would launch a successor while a possibly live generation of the same project persists, and a later success would then be able to claim a zero residual over an unaudited one. The installed cleanup branch MUST instead move that exact identity into the existing exact-identity quarantine index with `auditState: 'audited-unconfirmed'`, store its exact audit under the existing quarantine cleanup key, and synchronously abort the operation with a typed `RuntimeFailure('restart-replacement-unconfirmed')`. The delivered attempt loop begins by throwing the typed abort reason before it acquires a port, so a collision on an attempt before the last blocks the very next attempt with no change to the launch path. **Corrected 2026-08-15 (Plan revision 5):** that single sentence previously stood for every branch and was wrong. The delivered `catch` rethrows an already-typed `RuntimeFailure` before it consults the aborted signal, and a collision on the last configured attempt exits the loop and throws `address-in-use-exhausted`; so blocking holds on every branch — by the loop head, by the loop's own exhaustion, or by the rethrow leaving the function — but only a mid-loop collision and a non-typed error carry the wrapper's reason out of the launch primitive.

Classify an aborted replacement phase from the restart's own typed abort reason and never from the launch error. Because the launch primitive does not forward the wrapper's reason on every branch, the manager MUST NOT read the caught launch error to decide what a blocked replacement means. The restart MUST retain the exact `RuntimeFailure` instance it passed to its phase abort controller, and at settlement it MUST consult that typed signal reason first: when the replacement phase's signal is aborted and its reason is a `RuntimeFailure`, that reason's category is the retained failure category and its quarantine record determines the replacement audit state, on the collision branch and the readiness, health, early-exit, and exhaustion branches alike. Only when the phase signal carries no typed reason may the caught launch error classify the settlement, and when neither exists the underlying fault propagates unchanged — no broad catch, no string inspection of an error, and no untyped default. The abort controller keeps the first reason it is given, so a deadline that fired before the wrapper still retains `restart-deadline-exceeded` while the quarantine record it did not create still forces the unconfirmed audit state; precedence is decided by recorded reason identity, never by inferred timing.

Publish a withheld residual claim as an explicit null and a proven absence as an integer zero. A residual count is a claim about what the manager knows, so it needs a value that means *no claim*: an unaudited retained replacement, an unresolved admission, and a quarantined unconfirmed identity each MUST publish a null residual count, while a completed exact audit that observed absence MUST publish the integer zero. A zero and a missing field are both false absence claims, and a sentinel number is a zero in disguise. Validation-owned fixture teardown is a different fact from settlement residual knowledge and MUST be recorded in its own separate field, so that proving a test harness cleaned up after itself can never be mistaken for the manager proving a runtime is gone. Blocking immediately rather than continuing under a quarantined identity is the safe reading of an unconfirmed triple: the unconfirmed resource may be our own live process, and one runtime and one listener per project is an invariant no attempt count may trade away. The operation settles as a bounded non-success, MUST NOT claim absence or success while that record stands, and MUST publish an explicit null residual claim rather than a zero.

Publish `restart-replacement-unconfirmed` as an eighteenth bounded failure category and gate the next restart on the quarantine. A blocked replacement is retained on the `failed` entry under its own category, because no delivered category is true of it: `restart-release-unconfirmed` means nothing was launched, `stop-unconfirmed` names a selected stop, and overloading either would repeat the conflation this ADR already rejected. Because the workbench failure table is exhaustive over the proxied runtime union by construction, it follows to twenty-nine rows with a `503`. A project holding an uncleared quarantine record is classified `quarantined-residual`, a fifth prior-resource class, and its next restart is accepted — retryability is never gated — but MUST reclaim every quarantined identity through the already-declared reclamation path and MUST NOT acquire a port or launch until every one of them reports all three absences. Reclamation costs exactly the work `restartQuarantineReleaseBoundMs` was derived to cover, so the release-phase variant selector widens from "an unresolved admission exists" to "an unresolved admission or an uncleared quarantine record exists" and no bound value changes. A quarantine record created by a blocked replacement is indistinguishable from one created by a late continuation: same shape, same states, same reclamation, same shutdown sweep, same deletion cardinality of exactly one.

## Alternatives

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| Compose restart from the delivered `stop()` then `start()` | No new manager operation; reuses two proven paths | Installs a released `registered` entry between generations, which the projection reports as `Stopped`; emits `runtime.stop.succeeded` and `runtime.start.requested` instead of the restart pair; cannot join eight concurrent callers into one accepted operation; leaves a window in which a start can be lost or a stop rejected | Issue #41 forbids reporting `Stopped` between generations and fixes restart event cardinality at one requested plus one terminal |
| Let the route or the browser call stop and then start | No manager change at all | Creates a second lifecycle authority, makes the two phases independently cancellable and independently failing, and lets a client decide when a replacement is authorised | The runtime manager must stay the sole owner of lifecycle truth and ordering |
| Overlap the replacement launch with the prior release | Lower observed latency | Two generations of one project hold host resources at once, the "distinct complete identity" claim becomes unprovable, and a failed release can leave a live successor bound to a port the predecessor still holds | Issue #41 requires confirmed prior absence before replacement startup begins |
| Report an in-flight restart as `Stopped` after release and `Starting` after launch | No new entry state | Publishes a transient `Stopped` that Issue #41 explicitly forbids and that a client could act on | Truthful reporting requires one entry spanning both phases |
| Add a fifth public state such as `Restarting` | Most precise public vocabulary | Breaks the delivered four-value contract, its validators, its clients, and its documentation for no behavioural gain, since `Starting` already means "not yet ready" | The four-value public vocabulary is a delivered contract this issue must not widen |
| Reuse `stop-unconfirmed` for a restart whose release fails | No new failure category | Conflates an explicit stop outcome with a restart outcome in retained state, evidence, and notices, and makes the retained category unable to explain which operation produced it | Bounded categories must stay honest about their producing operation |
| Keep a retained `Failed` project ineligible for Restart, as `stop()` does | Symmetric with the delivered stop rejection | Removes the only recovery path Issue #41 requires and leaves a failed project with no explicit action but Close | FR-016 and AC-022 require restart of a failed workbench |
| Make Restart also apply to a project reported `Stopped` | One control for every state | Duplicates the delivered Open flow, changes Open's meaning, and creates a second start path with different events | A stopped project keeps the existing Open flow by decision |
| Proactively close prior-generation proxy sockets during restart | Deterministic client teardown | Adds proxy-side lifecycle coordination the stable-proxy boundary deliberately excludes, and is unnecessary because the released process and listener are confirmed absent | No proxy-side stop or restart coordination is added |
| Automatically retry a failed restart | Higher apparent success rate | Introduces an automatic recovery loop that Issue #41 and the lifecycle core-component both exclude | Restart is an explicit user action with one attempt per request |
| Persist the pre-restart identity so a later API process can finish the restart | Survives an API restart | Contradicts the memory-only runtime boundary and implements BL-019 | API-restart reconciliation remains BL-019 |
| Arm the restart deadlines with `processDependencies.sleep`, as the delivered selected-stop backstop does | One mechanism, identical to the delivered stop path | The deadline trigger becomes the same class of fallible awaited work it exists to bound, so an injected `sleep` that never settles or ignores cancellation defeats both the release backstop and the overall deadline while the ADR still claims a trusted deadline | A deadline may not be armed by fallible awaited work; the trusted synchronous scheduler is already delivered and already trusted |
| Give the manager the whole `RuntimeTerminationPrimitives` set | No new type | Hands the manager signal delivery, `/proc` reads, and listener probing it must never perform, widening a boundary far beyond deadline arming | Expose only the trusted `now` + `scheduleDeadline` pair as `RuntimeDeadlineScheduler` |
| Also migrate the delivered selected-stop backstop to the trusted scheduler | One consistent deadline mechanism across both operations | Changes accepted BL-017 behaviour, its source guards, and its retained evidence for a defect this issue did not introduce | Out of Issue #41 scope; the delivered ceiling is recorded honestly instead of silently inherited |
| Keep `readinessTimeoutMs` as the declared replacement bound | Matches the number a reader expects from the readiness contract | False for the shipped control flow: `launchReadyRuntime` retries up to `collisionAttempts` times and performs a self-bounded cleanup termination between collisions, so the real allowance is several times larger | A declared bound must be true of the code that runs |
| Run the restart's replacement with a derived single-attempt configuration | Small, tight replacement bound | Diverges restart's launch behaviour from `start`'s for no safety gain, turns a recoverable transient port race into a terminal restart failure, and makes `address-in-use-exhausted` unreachable from a restart while it stays reachable from Open | Restart keeps the delivered launch configuration and declares the honest allowance |
| Let the overall deadline abort with an untyped reason and accept the delivered mapping | No new failure category | The delivered launch path maps an untyped abort reason to `manager-shutdown`, so a healthy manager would report itself shut down and every downstream notice, event, and evidence row would repeat that falsehood | Abort with a typed `RuntimeFailure` carrying an honest category |
| Add an eighth restart rejection category for the post-gate deadline | Most precise operation-level vocabulary | The operation-level meaning is identical to every other confirmed-release replacement failure, and the retained category already distinguishes the cause | Reuse `replacement-failed` and distinguish by retained category |
| Keep classifying an abandoned launch as *no record* and let a retry proceed | No new manager state at all | A deadline can fire while `process.launch` is still pending, so the retry passes its gate on an absence nobody observed and the abandoned launch can later materialise a second live generation for one project | Missing ownership is not absence; a pending admission records the difference |
| Store the pending marker only on the retained `failed` entry | Fewer manager indexes | The retained entry is replaced by the very next restart's claim, so the marker would disappear exactly when it is needed | The admission is manager-owned and outlives every entry until it resolves |
| Add a fifth public state for a project holding an unresolved admission | Most explicit to a reader | Widens a delivered four-value public contract for an internal bookkeeping condition that Issue #41 forbids widening | Report `Failed` with a bounded category and keep the admission internal |
| Add an eighth restart rejection category for an unresolved predecessor launch | Most precise operation-level vocabulary | The operation-level meaning is exactly a release whose confirmation is unavailable, which the delivered category already means | Reuse `release-unconfirmed` and record the admission in trusted evidence |
| Refuse the retry outright while an admission is unresolved | Simplest safety story | Removes the explicit recovery action Issue #41 requires to stay available on a retained failure | Accept the retry and resolve the predecessor inside its release phase |
| Reuse `start`'s `onOwned` and `onCleanup` callbacks for the restart launch | No new wiring | A late `onOwned` injects ownership for a dead generation, and a late project-keyed `onCleanup` overwrites the successor restart's cleanup evidence | Restart-scoped wrappers that write only quarantine after settlement |
| Make late restart callbacks no-ops after settlement | Trivially safe for manager state | Silently discards the only record of a real host process the manager just created, guaranteeing a leak nobody can find | Quarantine the exact identity so it can be terminated and audited |
| Track the abandoned launch promise in `completionTasks`, as `start` tracks its operation | One task-tracking discipline for both operations | Shutdown drains that set until it is empty, so a never-settling launch blocks shutdown forever | Detached continuation only; the admission, not the promise, informs retry and shutdown |
| Have shutdown await the abandoned launch so it can audit the replacement | Strongest possible residual claim | Unbounded by construction, and shutdown is required to complete | Report the unresolved admission honestly and let the continuation terminate any late identity |
| Report `ok` from a shutdown that still holds an unresolved admission | Simplest result vocabulary | Claims a zero-residual outcome for a handle the manager never received | Report `failed` and enumerate the unresolved admissions |
| Publish only the `runtime:runtime-restarting` row and leave the delivered gaps | Smallest table change | Leaves `runtime:stop-unconfirmed` and `runtime:runtime-stopping` reachable with no row, so a proxy-path reuse race still throws and returns an uncategorised `500`, and the new restart categories add two more such gaps | The table must be exhaustive over every proxy-reachable runtime category |
| Record only a project-keyed cleanup from the restart's installed `onCleanup` | Mirrors the delivered `start` callback exactly | Every collided attempt's ownership record survives, so a success can settle holding two or three records for one project and the next restart sees a plural prior inventory and terminates more than one handle | An ownership record must be deleted by the identity its own audit names |
| Delete every ownership record for the project when any collision cleanup arrives | Trivially leaves one record | Deletes the record of the attempt that is still running or about to run, so a live identity becomes untracked | Deletion must be exact and generation-guarded |
| Continue the attempt loop after a non-confirming collision cleanup | Preserves collision recovery in every case | A possibly live process, owned group, or listener of the same project persists while a successor is launched, and a later success can claim a zero residual over an unaudited residual | An unconfirmed absence blocks; one runtime and one listener per project is not tradeable for an attempt |
| Classify a blocked replacement from the caught launch error | Uses the value the launch primitive already returns, with no extra manager state | The delivered launch rethrows an already-typed failure before reading its aborted signal, so a readiness, health, early-exit, or last-attempt-collision failure would be retained as its launch category and its quarantined identity would be reported as an ordinary bounded failure | Rejected: it reports the wrong cause for the exact branches the quarantine exists to make honest |
| Change `launchReadyRuntime` to forward the abort reason on every branch | Makes one reason authoritative at its source | Rewrites a delivered primitive shared with `start` for a restart-only concern, and widens the blast radius of Issue #41 well past its scope | Rejected: the restart already holds the typed reason it created and can select it at settlement without touching the shared launch path |
| Represent a withheld residual claim as the integer zero | Keeps one numeric type and one simple schema | Makes an unaudited, unresolved, or quarantined identity indistinguishable from a proven absence, which is precisely the false-absence defect this ADR exists to prevent | Rejected: a claim that cannot be made must be representable as no claim |
| Continue the attempt loop but mark the operation non-forwardable | Keeps the retry while withholding the success claim | Still permits two live generations of one project during the remaining attempts, which no downstream claim can undo | Blocking is the only settlement that preserves the invariant |
| Reuse `restart-release-unconfirmed` or `stop-unconfirmed` for a blocked replacement | No new failure category | Both are false: one asserts nothing was launched, the other names a selected stop, and a user who pressed Restart would be told about a Stop | Bounded categories must stay honest about their producing operation |
| Add a separate quarantine model for blocked replacements | Explicit about origin | Duplicates an existing exact-identity model with identical shape, reclamation, and sweep behaviour, doubling the surface a reader and a sweep must reason about | Reuse the delivered admission-and-identity quarantine model unchanged |

## Consequences

### Positive
- One authority performs every explicit replacement, so no surface can release, launch, report, or classify a restart independently.
- An exact synchronous claim makes restart-versus-start, restart-versus-stop, restart-versus-health, restart-versus-exit, restart-versus-proxy, concurrent restart, and shutdown interleavings settle as exactly one terminal outcome, with one release phase, one replacement phase, and one terminal event.
- A replacement is authorised only by a confirmed exact-ownership audit of the complete pre-restart identity, so two generations of one project never hold host resources at once.
- The selected project is `Starting` for the whole operation and `Running` only after the delivered readiness contract, so no client can observe a transient `Stopped` or infer readiness from process existence.
- A retained current-process failure has an explicit, repeatable recovery action with bounded outcomes.
- Prior-generation release, exit, health, connection, and startup settlements are structurally unable to affect the successor.
- Public disclosure stays inside a small bounded result vocabulary with no process, port, path, command, environment, or message content.
- The restart settles for its caller within one declared bound even when an injected or hostile termination or launch primitive never settles or ignores cancellation, because both restart deadlines are armed by the trusted synchronous scheduler rather than by awaited work.
- Every proxy-reachable runtime failure category resolves to a published bounded status, code, and safe message, closing two delivered gaps that could turn a normal stop-window or restart-window navigation into an uncategorised `500`.
- A settled successful restart holds exactly one ownership record for its project however many port collisions it survived, so the prior-resource inventory of the next restart is a single handle, its release phase performs exactly one termination, and the one-record guarantee is provable by counting rather than by inspection.
- No cleanup evidence can be overwritten: each collision attempt's audit is retained under its own identity key, and the single project-keyed cleanup written per phase keeps meaning exactly one thing.
- A collision cleanup that cannot confirm absence stops the operation instead of being discarded, so no restart can pass a gate, install a successor, or report a zero residual over a host resource nobody observed leaving.
- No replacement can exist without a manager record that predates it, so no later restart can mistake missing ownership for observed absence and no abandoned launch can install an untracked second live generation for one project.
- A late launch callback can neither resurrect a dead generation nor overwrite a live operation's ownership or cleanup evidence, while a leaked identity is still recorded, terminated, and audited rather than discarded.
- Manager shutdown completes within its own bound even when a launch primitive never settles, and says exactly what it could not audit instead of implying it audited everything.

- A blocked replacement now reports the same cause on every launch branch, so a readiness, health, early-exit, or exhausted-collision failure whose cleanup did not confirm absence is no longer misattributed to its launch category while a quarantined identity of the same project stands.
- A residual claim now has an explicit representation for *no claim*, so no reader, artifact, or downstream story can mistake an unaudited, unresolved, or quarantined identity for a proven absence, and validation-owned fixture teardown can be proven separately without ever standing in for manager knowledge.

### Negative
- A transient port collision whose cleanup audit cannot confirm absence now fails an otherwise recoverable restart, so a user may see a bounded failure where revision 3 would have retried. The recovery action is unchanged and immediately available, and the next restart reclaims the quarantined identity inside its already-declared release allowance.
- A project can hold up to `collisionAttempts` quarantined identities from one blocked replacement, each of which a later restart or the shutdown sweep must terminate and re-audit before that project can run again.
- The bounded failure vocabulary grows to eighteen and the workbench failure table to twenty-nine, so every mirror, count assertion, and documented number moves once more before implementation begins.
- The runtime contract grows: one internal entry state, one lifecycle transition target, four bounded failure categories, one internal allowance and two derived bounds, one trusted deadline-scheduler boundary and one optional manager dependency, one result vocabulary with two outcomes and seven rejection categories, three lifecycle event names, and one route; the stop rejection vocabulary and the stop route each gain one bounded category, and the published workbench failure table grows from 23 to 29 rows.
- The honest restart bound is large and now has two declared values: at the delivered defaults the replacement allowance is `3 * (15,000 + 5,000) = 60,000 ms`, an ordinary restart is bounded at `5,000 + 60,000 + 1,000 = 66,000 ms`, and a restart that must resolve a pending predecessor admission is bounded at `20,000 + 60,000 + 1,000 = 81,000 ms` because its release phase may have to reclaim up to one quarantined identity per configured launch attempt. A worst-case restart is therefore a long operation, and every user-facing surface must render a truthful pending state for its whole duration rather than a bound it cannot honour.
- The manager gains three durable indexes it did not have — pending admissions keyed by stable project ID, quarantined ownership keyed by admission identifier and exact identity tuple, and quarantine cleanup audits under that same key — plus the inspection and audit fields that expose them.
- A shutdown that still holds an unresolved admission or an unconfirmed quarantined identity reports `failed`, so an operator sees a failed shutdown for a condition Ascend detected rather than caused, and must read the enumerated unresolved admissions to understand it.
- A retry whose predecessor admission never resolves consumes its whole release bound and then fails, so a project whose launch primitive is genuinely wedged is retryable but not recoverable inside this issue.
- The browser restart transport bound must exceed the manager bound, so one Project Home request may stay in flight far longer than the delivered stop request.
- A replacement whose launch primitive ignores cancellation cannot be audited by the restart, so that settlement retains an ownership record and defers exact cleanup to the manager shutdown sweep instead of proving zero residuals.
- A restart is a strictly sequential operation, so its worst-case duration is the release bound plus the readiness bound plus the settlement allowance rather than the larger of the two phases.
- A start or a workbench navigation requested during a restart fails with a bounded classification instead of waiting, which a user experiences as "try again once the restart settles".
- A failed restart leaves a retained `Failed` entry that only another explicit restart, manager shutdown, or a future recovery story can clear.
- Editor and terminal session state does not survive a replacement, and every surface must say so rather than implying continuity.
- Project Home performs one additional read-only state request per settled successful restart and must render pending, success, failure, and unknown outcomes accessibly.

- The manager must retain the exact typed failure instance it passed to its replacement-phase abort controller and consult it before the caught launch error, which is one more piece of restart-owned state and one more ordering rule a reviewer must check.
- Every consumer of a residual count must handle a null, so the field is no longer a plain number and each reader must decide what a withheld claim means for it.

### Neutral
- The proxy remains a consumer of an exact manager-owned running snapshot; its ownership check already rejects a released generation, and no proxy-side restart coordination is added.
- The published workbench failure table grows from 23 to 29 rows, which changes `WORKBENCH_FAILURE_TABLE_SHA256`. BL-011 retains no committed evidence artifact: its failure matrix is constructed at run time from `WORKBENCH_FAILURE_TABLE` inside its acceptance and evidence tests, so the added rows execute six additional real route cases and the recomputed hash is compared in memory. No committed BL-010 through BL-017 evidence artifact changes.
- Widening the stop route vocabulary changes one delivered BL-017 source guard: `validateSelectedStopSource` asserts a fixed `RUNTIME_STOP_ROUTE_ERROR_CATEGORIES` count in `apps/api/src/runtime-stop-evidence.ts`, which must move from nine to ten. The delivered BL-017 committed matrix, its bounds, and its rows are unaffected.
- `RuntimeTerminationPrimitives` is refactored to extend `RuntimeDeadlineScheduler`. The seven primitives, their two trust classes, their implementations, the sequencer's internals, and its self-bound are unchanged; only the trusted `now` + `scheduleDeadline` pair becomes separately nameable and separately injectable for manager-owned deadlines.
- The workbench navigation shell keeps its delivered 15,000 ms document timeout. It is never the binding constraint during a restart, because a navigation that arrives while the entry is `restarting` is refused immediately with the bounded `503`. The delivered case in which a shell navigation times out while a slow `start` is still running is unchanged, pre-existing, and not a restart claim.
- The pending-admission and quarantine model widens no public vocabulary. The four public states, the two restart outcomes, the seven restart rejection categories, the ten restart route categories, the ten stop route categories, and the nine lifecycle event names are all unchanged by it, as are the bounded failure categories and the workbench failure table, which are widened only by the separately recorded replacement-cleanup decisions to eighteen and twenty-nine respectively; the additions are internal manager state, internal classification vocabularies, and trusted evidence fields.
- The ordinary start path keeps its delivered collided-attempt ownership record behaviour, so a pre-restart generation created by an Open flow that survived a port collision may carry one stale record that the restart does not terminate and the shutdown sweep still audits. No BL-018 claim, evidence row, or document converts that record into a proven absence.
- Runtime identity, ports, handles, and state remain memory-only; no schema, migration, configuration variable, or deployment topology changes.
- The single termination sequencer, its primitive boundary, its monotonic clock, its trusted deadline scheduler, and its attribution ceiling are consumed unchanged.
- API-restart reconciliation (BL-019), running-or-failed project close (BL-020), automatic recovery, persisted runtime state, background health monitoring, automatic idle shutdown, bulk operations, and arbitrary-process adoption remain deferred.

### Revision

- **2026-08-15 (Plan revision 2, Issue #41, pre-implementation).** This ADR was created and then corrected inside the same uncommitted Plan stage after independent validation. Four decisions changed before any code existed: restart deadlines are armed by the trusted synchronous scheduler instead of the fallible injectable `sleep`; the overall deadline is phase-aware and aborts with a typed `restart-deadline-exceeded` failure instead of an untyped reason; the replacement allowance accounts for every configured collision attempt and its cleanup instead of a single `readinessTimeoutMs`; and the workbench failure table is closed over the whole proxied runtime category union instead of gaining one row. Decisions 154-191 remain accurate and are not superseded; decisions 192-203 record the additions.

- **2026-08-15 (Plan revision 3, Issue #41, pre-implementation).** A narrowed independent recheck of revision 2 found one critical and two related defects, all repaired here before any code exists. The critical one is architectural: the delivered launch path reports ownership only after `process.launch` resolves, so a deadline firing inside that window left a real process possible with no manager record, and revision 2's `no-record` classification let an immediately accepted retry pass its gate on that unobserved absence and install a successor beside a still-materialising predecessor. The repair is the manager-owned pending replacement admission created before every launch, the fourth `pending-admission` prior-resource class, and the gate rule that resolves it. The second is the unguarded reuse of `start`'s launch callbacks, repaired by restart-scoped wrappers and the exact-identity quarantine indexes, and by amending the revision-2 absolute prohibition into the honest constrained rule. The third is shutdown, repaired by observing an abandoned launch only through a detached continuation that no awaited task set tracks and by reporting unresolved admissions honestly instead of blocking. Decisions 154-203 remain accurate and none is rewritten; decisions 204-219 record the additions, and 216 refines 163 rather than replacing it.

- **2026-08-15 (Plan revision 4, Issue #41, pre-implementation).** Final narrowed validation of revision 3 rejected the Plan for two collision-cleanup defects, both repaired here before any code exists. Revision 3's installed `onCleanup` recorded a project-keyed cleanup and deleted nothing, so each collision attempt's ownership record survived and an eventually successful restart could settle holding several records for one project, contradicting the one-record guarantee and the singular prior handle this ADR asserts elsewhere; and the per-attempt audit triple was discarded, so an unconfirmed collision cleanup could be followed by a successor launch and a later zero-residual claim over an unaudited resource. The repair makes the installed cleanup branch identity-keyed on `pid:processStartTime:port` derived from the audit itself, deletes exactly the confirming attempt's record, quarantines a non-confirming identity as `audited-unconfirmed`, and aborts the attempt loop with the new bounded `restart-replacement-unconfirmed` category, which also adds the fifth `quarantined-residual` prior-resource class and closes the workbench table at twenty-nine rows. No bound value changes; the release-phase variant selector is renamed and its definition widened to include an uncleared quarantine record. Decisions 154-219 remain accurate and none is rewritten; decisions 220-229 record the additions, and 224, 226, and 227 refine 210, 216, and 180 respectively.

- **2026-08-15 (Plan revision 5, Issue #41, pre-implementation).** Independent adjudication of revision 4 rejected the Plan for three defects, two of which are architectural and are repaired here. First, revision 4's evidence schema was uninhabitable: it required a scalar residual count while simultaneously forbidding a zero-residual claim for unaudited, unresolved, and quarantined replacements, so those rows could not be represented at all. The Decision now publishes a withheld residual claim as an explicit null, a proven absence as an integer zero, and validation-owned fixture teardown in its own separate field. Second, revision 4 asserted that the delivered attempt loop throws the typed abort reason before acquiring a port on every branch; reading `apps/api/src/project-runtime-process.ts` shows the `catch` rethrows an already-typed `RuntimeFailure` before consulting the aborted signal, and a collision on the last configured attempt throws `address-in-use-exhausted` instead. Blocking does hold on every branch, but the wrapper's reason only leaves the launch primitive on two of them, so the Decision now requires the manager to classify an aborted replacement phase from its own retained typed abort reason. The prior sentence is corrected in place with its correction recorded rather than removed. The launch primitive itself is unchanged. The third defect was count drift confined to Plan instructions and required no change here.
