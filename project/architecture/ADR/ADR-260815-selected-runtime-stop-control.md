# ADR-260815-selected-runtime-stop-control: Release One Selected Workbench Runtime Through a Manager-Owned Stop Control

## Status

Accepted

## Context

FR-015 and AC-021 require Ascend to stop a project's code-server runtime while the project remains registered on Project Home. Issue #39 (BL-017) delivers exactly that operation: it must apply to one selected Ascend-managed runtime, confirm release through a finite ownership audit, retain the project registration and its filesystem contents, and report `Stopped` only after release is confirmed.

The delivered system has release machinery but no selected release operation. `ProjectRuntimeManager` owns registered, starting, running, and failed entries keyed by stable project ID; `apps/api/src/project-runtime-process.ts` already terminates an exact owned process group with a documented graceful period, a documented force period, and an audit reporting root-process absence, process-group absence, and loopback listener absence. Every existing caller of that machinery is an involuntary path: readiness failure, the guarded `running -> failed` transition, or global `shutdown()`. `apps/api/src/routes/README.md` states today that global application shutdown is the only exposed runtime shutdown path, and `DELETE /api/projects/:id` deletes registration metadata rather than releasing a runtime.

`ADR-260815-public-runtime-state-projection` recorded Stop and Restart controls as deferred while it delivered read-only reporting. That deferral was correct for Issue #37 and is now partially spent: Issue #39 delivers selected stop only. Restart, automatic recovery, API-restart reconciliation, persisted runtime handles, background or distributed health monitoring, automatic idle shutdown, bulk operations, arbitrary-process adoption, and running/failed project close remain deferred to BL-018, BL-019, BL-020, and later work. This ADR narrows that earlier deferral explicitly rather than contradicting it silently.

Six properties constrain any selected stop. The runtime manager must remain the single process and lifecycle owner, so no route, proxy, or browser client may terminate anything. The public vocabulary is exactly `Stopped`, `Starting`, `Running`, and `Failed`, so an in-flight stop must not introduce a fifth public state. Public payloads must not disclose PIDs, start times, process groups, ports, listeners, canonical paths, commands, environments, credentials, or server message text. Persisted metadata is exactly `id`, `name`, `canonicalPath`, and `createdAt`, and stop must leave all four unchanged. Selected stop races with start coalescing, reuse-health observation, process-exit settlement, proxy acquisition, a concurrent stop for the same project, and global shutdown, so its ownership claim must be as exact as the existing guarded terminal transition. And a request that resolves to no Ascend-managed runtime at all must be answered differently from a repeated request against a runtime this manager already released, because Issue #39 requires the first to be a documented non-success and the second to be a documented successful no-op.

The delivered manager already distinguishes those two cases, and this decision preserves that distinction rather than inventing one. A persisted project that has never been started has no manager entry: `register` is called only from inside `start`, synchronously, immediately before the starting claim is installed, so no registration, list, projection, close, or proxy path creates an entry. An entry in the `registered` state therefore only exists inside that synchronous start window or because a settlement installed it.

## Decision

Add one manager-owned selected stop operation and expose it through one dedicated write route and one Project Home control.

Make `ProjectRuntimeManager.stop({ projectId })` the only producer of a selected release. It resolves the persisted project, reads its own entry map, and returns a frozen typed `RuntimeStopOutcome`. It never throws for a classified lifecycle outcome; it rejects only on an infrastructure fault, which the route surfaces explicitly rather than converting into a success-shaped body. No route, proxy, CLI, or browser client terminates a process, reads process liveness, probes a listener, or derives a stop result of its own.

Separate "no managed runtime" from "already stopped". A request whose project is not persisted is `not-registered`. A request for a persisted project that this manager has no runtime for — no entry at all, or a `registered` entry that no confirmed release installed — resolves to no selected Ascend-managed runtime and returns the bounded non-success `no-managed-runtime`. A request for a project whose runtime this manager already released through a confirmed stop returns the bounded successful no-op `already-stopped`, repeatably and indefinitely, because that project is genuinely an already-stopped project rather than one that was never running. A confirmed stop therefore installs a `registered` entry that records the release, and that recorded release is the only thing that makes a later stop a successful no-op.

Claim the exact running generation synchronously. Stop resolves the persisted project first, then performs one synchronous section that reads the installed entry and, for a `running` entry, immediately installs a manager-owned `stopping` entry carrying the same stable project ID, canonical path, generation, ready runtime, and pre-stop snapshot. No `await` occurs between that read and that install, so the claim cannot interleave with the guarded `running -> failed` transition, a concurrent stop, or a start. A contender that finds the entry replaced loses without mutating, terminating, auditing, or emitting, exactly as the existing guarded transition already requires.

Treat the claim as an invariant, not a hope. Once `stopping` is installed for a generation, no contract-valid path may replace it before its own settlement: the guarded terminal transition compare-and-sets on an exact `running` entry, `start` refuses a `stopping` entry without mutating it, `register` never overwrites an existing entry, and manager shutdown awaits every in-flight stop before it sweeps ownership or deletes entries. Settlement therefore rechecks that the exact `stopping` object is still installed, and a mismatch is an invariant violation rather than a lost race: the settlement installs nothing, emits nothing, records no additional cleanup, and rejects with an explicit invariant fault that the route surfaces as an unexpected failure. No claimant may ever emit a terminal event or report success for state it did not install.

Keep public reporting truthful without a fifth public state. Add `stopping` to the internal entry vocabulary and project it as `Running`: a runtime whose release has not been confirmed is still running, is not `Starting`, is not `Failed`, and must not be reported `Stopped`. The public four-value vocabulary, its projection authority, and its one-synchronous-pass contract are unchanged.

Keep lifecycle transition targets out of the entry and snapshot vocabularies. A stop announces a transition whose target is `stopped`, but `stopped` is not an entry state and not a runtime snapshot state — entry absence and a `registered` entry are what represent a stopped project, and the internal entry vocabulary gains only `stopping`. The lifecycle event vocabulary therefore carries its own transition-target type covering `starting`, `running`, `failed`, `stopping`, and `stopped`, and one explicit mapping projects each target to its public state. The event-to-public-state agreement check consumes that mapping instead of the entry projection, so `stopped` maps to `Stopped` without ever becoming an installable entry or an active snapshot state.

Settle every accepted stop into exactly one manager entry. A release confirmed by the exact-ownership audit — root process absent, owned process group absent, and loopback listener absent — installs a `registered` entry marked as released, removes that generation's ownership record, records exactly one stop-phase cleanup audit, and reports `Stopped`. A release that cannot be confirmed within the documented overall bound installs a `failed` entry with the new bounded `stop-unconfirmed` category, retains its ownership record so manager shutdown re-attempts exact cleanup, records exactly one stop-phase cleanup audit when its termination produced one, and reports `Failed`. A termination fault, and a termination that does not settle inside the overall bound, settle the entry the same way; the fault is then surfaced explicitly rather than swallowed, so no entry is ever left stuck in `stopping`. `Stopped` is therefore never reported on an unconfirmed release.

Make retained ownership actually re-attemptable, and state cleanup cardinality per phase. Manager shutdown previously reused any prior cleanup audit recorded for the same exact process identity, which would let a recorded but unconfirmed stop audit suppress the very re-attempt that retaining ownership is supposed to guarantee. Shutdown reuses a prior audit only when that audit confirms process, owned process-group, and listener absence; an unconfirmed or missing audit makes shutdown re-attempt the exact retained ownership cleanup and record its own audit. Shutdown also awaits every in-flight stop before that sweep, so no owned identity is ever terminated or audited concurrently by a stop and by the sweep, and no generation is left unswept because a `failed` entry replaced a `running` one.

The cardinality this guarantees is therefore per phase, not per identity. One claimed generation has exactly one stop-phase termination and at most one stop-phase cleanup audit; two cleanup attempts for one owned identity never run concurrently; and no path terminates or audits an identity again once a cleanup audit has confirmed its release. A generation whose stop phase ended unconfirmed, faulted, or deadline-abandoned deliberately keeps its ownership record and is re-attempted exactly once by that shutdown sweep, which by design records a second termination and a second cleanup audit for the same generation. That re-attempt is the intended behavior of retained ownership and is never described, asserted, or validated as an uncontrolled duplicate.

Bound the operation and prove the bound in code. A stop offers the full documented `gracefulShutdownMs` graceful opportunity measured on a monotonic elapsed-time clock from the moment its graceful signal is confirmed delivered, escalates only after that whole period has elapsed since that signal, offers the full `forceShutdownMs` window after the force signal is confirmed delivered, and completes within `gracefulShutdownMs + forceShutdownMs + stopAuditAllowanceMs`. A signal the host reports undeliverable because the owned group is already gone opens no window at all, is never recorded as a delivered signal or as an escalation, and settles the stop from what the audit can still confirm; an unexpected signalling failure is a termination fault rather than an ordinary unconfirmed release. `stopAuditAllowanceMs` is an internal runtime bound with a fixed default, not a new environment variable, flag, or deployment setting, and it is what bounds the observation performed before the graceful signal and the settlement between phases so those full windows fit inside the unchanged overall bound. A stop whose pre-signal observation cannot complete inside that allowance is an unconfirmed release with no signal sent, never a shortened graceful shutdown. The sequencing, the self-imposed deadline and the trusted synchronous scheduler that arms it independently of every awaited primitive, the primitive cancellation contract, the entry check for a caller signal that was already aborted, the abandonment of any primitive still pending at that deadline, the signal-delivery result that every phase window depends on, the monotonic clock that measures those windows, the phase windows measured from their own delivered signals, and the attribution rule that make that bound real are decided in `ADR-260815-termination-sequencer-boundary`; this decision consumes them and adds the second enforcement point — the caller-side backstop that settles the entry when a termination does not return in time.

Never return a reuse observation that a stop has already invalidated. `start` may await liveness and health for an installed running entry, and those awaits can outlast a stop claim on the same generation. Every awaited reuse observation therefore rechecks that the exact entry object and generation are still installed before returning its snapshot or settling a failure. If the recheck fails because a selected stop claimed or released that generation, the caller receives the bounded `runtime-stopping` failure instead of a snapshot that is being torn down; if it fails because another terminal contender installed a retained failure, the caller receives that winner's retained failure; if it fails because the manager is shutting down, the caller receives `manager-shutdown`. A losing observation mutates nothing, terminates nothing, audits nothing, and emits nothing, so the delivered one-winner cleanup and event guarantees are unchanged and no stale snapshot can be forwarded.

Bound disclosure with a small result vocabulary. A successful outcome is `stopped` or `already-stopped`. A non-success outcome is `rejected` with exactly one of `not-registered`, `no-managed-runtime`, `start-in-progress`, `failure-retained`, `stop-unconfirmed`, or `manager-shutdown`. Graceful versus escalated release, the termination audit, and the pre-stop identity stay inside the trusted in-process result for validation evidence and never reach a public payload, a log record, or a browser surface.

Refuse a start while its own stop is in flight. `start()` on a `stopping` entry throws the new bounded `runtime-stopping` failure instead of reusing the doomed snapshot, cancelling the stop, or launching a replacement. Selected stop therefore never terminates a replacement runtime: a new generation can only be created after the stop settles, and termination always targets the exact ready runtime captured at claim time, whose root identity is revalidated before any signal.

Serve the operation from `POST /api/projects/:id/runtime/stop` in its own route plugin. The request carries one path identifier and no body. The success body is exactly `{ "id", "outcome" }` with `outcome` of `stopped` or `already-stopped`. A non-success body is exactly `{ "error": { "category" } }` drawn from a fixed vocabulary with fixed status codes. The response carries no public runtime state, so Project Home continues to read state only from the existing `GET /api/projects/runtime` projection and no second reporting authority is created. `GET /api/projects`, its validators, `POST /api/projects`, `DELETE /api/projects/:id`, and `GET /api/projects/runtime` are unchanged.

Add one Stop control per Project Home card and refresh state on demand. The Home controller performs one stop request at a time under its existing single-owner discipline, tags each request with a generation, and discards any settlement whose generation was superseded. A settled successful stop triggers exactly one additional runtime-state request for the current authoritative list revision, extending the existing on-demand refresh rule that already permits exactly one extra request per Retry activation. No timer, poll, stream, or client health probe is introduced. A transport outcome that cannot be classified enters an explicit unknown phase offering a refresh, never an assumed success. Open, Close, focus, announcement, and navigation semantics are unchanged, and the workbench navigation shell still exposes no lifecycle control.

Announce settled stops only through the `PRD.md` NFR-015 catalog. An accepted stop that claims a generation emits exactly one `runtime.stop.requested`; its settlement emits exactly one terminal event — `runtime.stop.succeeded` on a confirmed release, or `runtime.health.changed` classified `stop-unconfirmed` when release cannot be confirmed. The catalog contains no `runtime.stop.failed`, so none is invented. A rejected request, a successful already-stopped no-op, a `no-managed-runtime` non-success, and a caller that joins an in-flight stop emit no lifecycle event because they produce no public state transition. The stop route's own operational records are not lifecycle events and never substitute for one.

## Alternatives

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| Extend `DELETE /api/projects/:id` with a stop mode | No new route | Overloads the destructive registration-removal route, and a mistaken plain DELETE deletes the registration the issue requires retaining | Stop and close must stay separate operations with separate blast radii |
| Use `DELETE /api/projects/:id/runtime` | Idempotent HTTP verb matches repeated stop | Sits one path segment away from the destructive close route and inherits its DELETE-specific error shaping expectations | Explicit `POST .../runtime/stop` cannot be confused with close |
| Terminate from the route or proxy | Fewer manager changes | Creates a second process owner, allows termination without an exact generation claim, and lets surfaces disagree | The runtime manager must stay the sole process and lifecycle owner |
| Reuse the guarded `running -> failed` transition for a successful stop | No new entry state | Reports a deliberate release as `Failed` and retains a failure that never occurred | A confirmed release is `Stopped`, not a failure |
| Keep the entry `running` while stopping | No new internal state | A concurrent start would reuse and a proxy request would route to a runtime being released | The claim must make the doomed generation unreusable |
| Add a public `Stopping` state | Most literal progress reporting | Introduces a fifth public value that every surface, validator, and client must learn, contradicting the delivered four-value vocabulary | An unconfirmed release is still `Running`; no fifth public state is needed |
| Add `stopped` to the entry or snapshot state vocabulary so one mapping serves both | One vocabulary to learn | Makes a terminal transition target look like an installable entry and an active snapshot state, and would let a projection report a state no entry can hold | Transition targets and entry states are different vocabularies and stay separate |
| Answer both an absent entry and a released `registered` entry with `already-stopped` | Simplest branch, one successful classification | Reports a documented success for a request that resolves to no Ascend-managed runtime, which AC-1 requires to be a documented non-success | The manager can already tell the cases apart; conflating them weakens AC-1 |
| Answer both with a non-success | Simplest branch, one non-success classification | Makes each repeated stop of an already-stopped project an error, which AC-4 forbids and which breaks idempotent client retry | Repeated stop must stay a bounded successful no-op |
| Infer "already stopped" from persisted metadata or from a project's history | No new entry field | Runtime identity and state are memory-only by decision, and persisted metadata says nothing about a release | The release marker must live where runtime state lives |
| Report `Stopped` optimistically when termination is signalled | Simplest client behavior | Reports release before the ownership audit confirms it, which the issue forbids | `Stopped` requires a confirmed exact-ownership audit |
| Return the resulting public state in the stop response | One round trip | Creates a second public-state authority beside the projection endpoint | Public state must come only from the manager projection |
| Cancel an in-flight start when stop is requested | Handles `Starting` | Adds start cancellation semantics and a restart-shaped path the issue excludes | A start in progress returns a bounded non-success instead |
| Clear a retained failure on stop | Uniform "make it stopped" behavior | Erases a real failure and reports `Stopped` for a runtime that failed rather than one released by request | Retained failures keep reporting `Failed` until an explicit recovery story |
| Let a settlement that lost its claim emit its terminal event anyway | Callers always see one event per request | Announces a transition the claimant did not install, contradicting event and state agreement and loser silence | A claimant may only announce state it installed |
| Treat a lost claim as an ordinary race with a reused winner result | Symmetric with the health and exit races | No contract-valid contender can replace a `stopping` entry, so the branch would encode a race that cannot occur and hide a real invariant break | Surface it as an explicit invariant fault instead |
| Let manager shutdown reuse any prior cleanup audit for the same identity | Avoids a second termination | An unconfirmed stop audit suppresses the re-attempt that retaining ownership exists to guarantee, so a leaked runtime is never re-signalled | Reuse only an audit that confirms absence |
| Forbid any second termination or cleanup audit for a generation once its stop phase recorded one | One sentence to state and to assert | Contradicts the retained-ownership re-attempt this decision requires, so an unconfirmed release could never be re-signalled | State cardinality per phase, and forbid concurrent and post-confirmation duplicates instead |
| Return the doomed snapshot from a reuse observation that began before the stop claim | Fewer branches in `start` | Hands a caller a runtime that is being released, and lets the proxy forward to it | Every awaited reuse observation must recheck its exact entry and generation |
| Poll runtime state after a stop until it changes | Guaranteed fresh display | Reintroduces polling that the reporting architecture prohibits | Exactly one on-demand refresh per settled stop is sufficient |
| Emit `runtime.stop.failed` for an unconfirmed release | Symmetric event naming | Invents an event outside the NFR-015 catalog | An unconfirmed release is a `running`-to-`failed` outcome already covered by `runtime.health.changed` |

## Consequences

### Positive
- One authority performs every selected release, so no surface can terminate, report, or classify a stop independently.
- An exact synchronous generation claim makes stop-versus-start, stop-versus-health, stop-versus-exit, stop-versus-proxy, concurrent stop, and shutdown interleavings settle as exactly one terminal outcome for the claimed generation, with exactly one stop-phase termination, at most one stop-phase cleanup audit, and one terminal event.
- A request that resolves to no Ascend-managed runtime is answered as a documented non-success, while a repeated stop of a project this manager released stays a bounded successful no-op.
- `Stopped` is reported only after the exact-ownership audit confirms process, owned process-group, and listener absence.
- Retained ownership after an unconfirmed release or a termination fault is genuinely re-attempted exactly once by manager shutdown instead of being suppressed by its own audit record, and that second termination and audit phase is recorded as intended rather than reported as a duplicate.
- A reuse observation can no longer hand a caller or the proxy a snapshot whose generation a stop already claimed.
- Registration metadata, project directory contents, peer runtimes, and unrelated controls are untouched by every stop outcome, including failures.
- Public disclosure stays inside a small bounded result vocabulary with no process, port, path, command, environment, or message content.

### Negative
- The runtime contract grows: one internal entry state, one entry release marker, one lifecycle transition-target vocabulary, two bounded failure categories, one internal bound, one result vocabulary, and one route.
- A start requested during an in-flight stop fails with a bounded classification instead of waiting, which a user experiences as "try again once it stops".
- An unconfirmed release leaves a retained `Failed` entry that only manager shutdown or a future recovery story can clear.
- After an API restart, a project released before the restart has no manager entry again, so a stop request answers `no-managed-runtime` rather than `already-stopped`; runtime state is memory-only by decision and API-restart reconciliation remains BL-019.
- Project Home performs one additional request per settled stop and must render busy, success, rejection, and unknown outcomes accessibly.

### Neutral
- The proxy remains a consumer of an exact manager-owned running snapshot; its ownership check already rejects a released generation, and no proxy-side stop coordination is added.
- Runtime identity, ports, handles, and state remain memory-only; no schema, migration, configuration variable, or deployment topology changes.
- Restart, automatic recovery, API-restart reconciliation, persisted runtime state, background health monitoring, automatic idle shutdown, bulk operations, arbitrary-process adoption, and running/failed project close remain deferred.
- Amended 2026-08-15: the restart deferral above is spent by [ADR-260815-explicit-workbench-restart-control](./ADR-260815-explicit-workbench-restart-control.md). Three delivered surfaces of this decision change, and nothing else does. `stop()` gains one bounded rejection category, `restart-in-progress`, for a project whose entry is `restarting`, and the stop route gains the matching bounded `runtime_restart_in_progress` 409 category, taking the stop rejection vocabulary to seven members and the stop route error vocabulary to ten. Manager shutdown now awaits every in-flight restart as well as every in-flight stop before it audits ownership, so no owned identity is ever terminated or audited concurrently by a restart and by the sweep. The `stopping` entry, its `Running` projection, the exact synchronous claim, the confirmation rule, the retained-ownership re-attempt rule, the per-phase cleanup cardinality, the two enforcement points, the stop result vocabulary, the stop event pair, and the `failure-retained` rejection of a stop for a retained failure are all unchanged; an explicit restart, not a stop, is what a retained failure is eligible for. A restart never emits `runtime.stop.requested` or `runtime.stop.succeeded`, because it consumes the termination sequencer and the launch primitive directly rather than calling `stop()` and `start()`. API-restart reconciliation (BL-019), running-or-failed project close (BL-020), automatic recovery, persisted runtime state, background health monitoring, automatic idle shutdown, bulk operations, and arbitrary-process adoption remain deferred.
- Amended 2026-08-15: [ADR-260815-api-restart-runtime-reconciliation](./ADR-260815-api-restart-runtime-reconciliation.md) spends this decision's explicit BL-019 deferral. A selected stop applied to a reconciled runtime releases exactly the adopted identity, its owned process group, and its listener through this unchanged sequencer and ceiling. Two bounded rejection categories are added: a pre-acceptance rejection while that project's reconciliation is pending, and an unresolved rejection while it holds an unresolved reconciliation, so no unattributable process is ever signalled. A project whose reconciliation positively established absence now answers the already-stopped no-op instead of the previous no-managed-runtime rejection, because a completed absence observation is the same epistemic state as a confirmed release; a project this manager has never observed still answers no-managed-runtime.
- Amended 2026-08-15 (revision 2 of the BL-019 plan): a selected stop is also one of the delivered on-demand paths that corrects a stale `Running` for an adopted runtime that has since died. Its initial audit answers already-absent and settles the project `Stopped` with zero signals delivered, and the sequencer's delivered pre-signal identity revalidation means a recycled process identity at that recorded identity yields an unconfirmed result rather than a signal to an unrelated process. Nothing about the ceiling, the claim, the confirmation rule, the cleanup cardinality, or the event pair changes.
