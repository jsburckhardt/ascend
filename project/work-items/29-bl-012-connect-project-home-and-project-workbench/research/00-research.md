# Research Brief: BL-012: Connect Project Home and Project Workbench

## GitHub Issue
- **Issue:** #29
- **Title:** BL-012: Connect Project Home and Project Workbench
- **Work Item:** project/work-items/29-bl-012-connect-project-home-and-project-workbench

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Project Home and the full-page project workbench exist as separate delivered surfaces. Project Home lists persisted projects but deliberately leaves card Open actions deferred, while the API already exposes a stable project workbench transport backed by the in-memory runtime manager. Issue #29 requires the one-project transition between those surfaces to preserve the persisted stable ID, browser URL and history semantics, runtime and terminal continuity, direct-navigation behavior, accessibility, bounded recovery, descendant workbench transport, and cleanup boundaries. The requested scope excludes multi-project coordination and lifecycle control expansion.

## Acceptance Criteria
**Core**
- [ ] Project Home is served at `/`; activating Open for a registered project navigates to exactly `/projects/{encodeURIComponent(stableId)}/workbench/`, with one trailing slash and no query or fragment for normal entry, and opens the workbench for that same persisted project identity.
- [ ] A stopped project is started once for entry, while a healthy running project is reused; returning from Home, refreshing, revisiting through browser history, and direct navigation do not create a duplicate runtime for the same stable ID.
- [ ] The full-page workbench includes a minimal Ascend header with a keyboard-operable Projects action that navigates to `/`; it exposes no Stop, Restart, Close, runtime-status, PID, listener, internal-port, or other runtime-identity control or value.
- [ ] Projects navigation returns to Project Home without intentionally stopping or replacing the project runtime, and a bounded continuity observation proves that the exact runtime identity and its active terminal process remain alive while Home is displayed.
- [ ] While the exact in-memory runtime identity is reused without restart, reopening the same project restores the one known file left open in the editor, demonstrated by its visible filename, and restores the one terminal marker with its disposable counter measurably advanced; no broader editor-layout, selection, undo, extension, or arbitrary workspace-state persistence is claimed.
- [ ] The connected workbench exposes the selected project Explorer sentinel, opens the repository-defined Markdown fixture in the native workbench preview, and provides an integrated terminal that reports the registered canonical project directory and executes the bounded marker command with visible counter progress.
- [ ] The designated history workflow creates exactly three Workbench history entries separated by Home visits, performs exactly one workbench document refresh, and performs exactly one Back-then-Forward pair that revisits an existing entry without adding a duplicate; the final visible surface and URL match the traversed history entry.
- [ ] A fresh browser context that shares the running backend but clears storage, cookies, cache, and service workers direct-navigates to the stable workbench URL exactly once and refreshes exactly once; both loads retain the same runtime identity, display the Explorer sentinel, report the registered canonical directory in the integrated terminal, and execute the bounded marker command with visible counter progress without relying on prior client storage.
- [ ] After the upstream workbench document begins, descendant asset, fetch, query, and WebSocket URLs under the stable workbench prefix continue under BL-011 semantics and are not interpreted as top-level Project Home or workbench route changes.

**Edge Cases**
- [ ] A decode failure, empty ID, encoded slash, encoded backslash, encoded NUL, a sibling path outside workbench descendants such as `/projects/{encodedId}/other/`, or decoded ID longer than 128 characters renders a route error and performs zero project lookup and zero runtime start.
- [ ] An unknown or already-closed stable ID remains unchanged in the address bar and renders an accessible error document inside the Ascend shell with a Projects link; it performs no runtime start and does not redirect.
- [ ] A runtime-start failure, upstream-proxy failure, or workbench document-load timeout leaves the same stable URL visible and renders the Ascend error shell; Retry starts one new generation for that same stable ID, while Projects navigates to `/` without starting another generation.
- [ ] Exactly one controlled browser failure episode covers one unknown ID, one runtime-start failure, one upstream-proxy failure, and one document-load timeout; each case uses exactly one Retry or Projects recovery action as applicable, records the resulting URL and generation, and makes no exhaustive-failure claim.
- [ ] Exactly eight concurrent or repeated activation requests for one stopped stable ID join one start generation and produce at most one Workbench history entry for the accepted navigation; the pending state has an accessible status, repeated activation does not move focus unexpectedly, and keyboard activation has the same URL and history outcome as pointer activation.
- [ ] A late success or failure from an older entry or Retry generation cannot replace the document, URL, focus, error, or announcement owned by a newer Home navigation or workbench generation.
- [ ] Long and metacharacter-bearing project names and canonical-path display values remain complete inert text; they cannot change the encoded stable-ID route, create markup or script, expose internal details, or select another project.
- [ ] Home Open, workbench Projects, Retry, and error-shell Projects controls have accessible names, visible keyboard focus, and logical tab order; route or load errors are announced, focus moves to the new surface or error heading once, and stale generations do not steal focus.
- [ ] Browser history contains no duplicate entry from refresh, joined activations, Retry settlement, or stale completion, and Back or Forward never causes a malformed, unknown, or failed project generation to start implicitly.

**Verification**
- [ ] A finite web-component matrix records normal Open, eight joined activations, pending interaction, stale success, stale failure, Home, Back, Forward, refresh, Retry, long/metacharacter display identity, accessible announcements, and focus restoration with deterministic URL, history-length, generation, and focus outcomes.
- [ ] A finite API matrix records valid stopped and running IDs; every listed malformed-route class; one unknown/closed ID; one runtime-start failure; one upstream-proxy failure; and one document-load timeout, including lookup count, start count, generation, public error outcome, and recovery result for each case.
- [ ] The main browser scenario uses exactly one repository-defined project fixture containing one known file and one Markdown fixture, plus exactly one terminal command that writes an increasing timestamp or counter every 250 ms for at most 30 seconds to one disposable output file outside tracked fixture content; evidence records the command PID and counter values before and after a Home visit, and teardown terminates that exact PID and removes that exact output file.
- [ ] The main browser scenario follows this bounded order: start at Home; Open Workbench entry 1; Projects to Home; Open Workbench entry 2; refresh once; Back to Home; Forward to revisit entry 2; Projects to Home; Open Workbench entry 3; no other Workbench history entry, refresh, Back, or Forward action occurs.
- [ ] The designated browser evidence inventories every observed top-level document, descendant request, and WebSocket by bounded safe classification; all Ascend-owned traffic remains on the Ascend origin under the encoded stable prefix, required Management, ExtensionHost, and integrated-terminal channels remain usable, and no browser-visible URL, response, log, or committed evidence contains an internal port or authority.
- [ ] Every browser scenario and matrix declares finite per-operation, startup, document-load, recovery, overall, and cleanup bounds before execution and records the applied bounds and outcome; validation uses no unavailable account, production service, manual judgment, indefinite observation, or destructive action.
- [ ] Teardown evidence inventories the exact browser contexts and pages, terminal command PID and disposable output, proxy sockets, runtime PID and listener, API and web process groups and listeners, database and sidecars, and fixture manifest; all owned resources are absent, tracked fixture content matches its pre-run manifest, and one unrelated listener remains alive at the final checkpoint.
- [ ] Retained evidence maps each criterion to inspectable component, API, browser, history, runtime-identity, traffic, accessibility, fixture-integrity, and cleanup outcomes without retaining source contents, terminal contents, credentials, secrets, raw internal authorities, or personal data.
- [ ] User-facing and operational documentation describes the `/` and stable workbench URLs, Projects and Retry behavior, route and load errors, finite validation bounds, evidence interpretation, and cleanup procedure, and removes obsolete statements that Open performs no navigation or workbench request.
- [ ] The repository-provided focused validation for Project Home/workbench connection and the full repository validation both pass from a clean tracked tree and produce inspectable evidence; a final independent residual audit confirms the cleanup inventory and tracked-fixture manifest.
- [ ] Scope remains limited to connecting one Project Home project to its existing workbench and back; multi-project coordination, lifecycle controls, custom editor, terminal, Explorer or Markdown implementations, public authentication, public networking, TLS, multi-host routing, persisted runtime identity, and runtime-status UI are not added.

- `apps/web/src/App.tsx::App` renders only Project Home. Each project card carries `data-project-id={project.id}`, an accessible `Open <name>` button, and a click handler that announces `Opening the workbench is not available yet.` It renders names and canonical paths as React text and has no workbench shell, route error surface, Projects action, or Retry behavior for workbench entry.

That state machine does not currently own workbench navigation or document-load generations. `apps/web/src/App.test.tsx` and `tests/e2e/project-home.spec.ts` assert that Open leaves the URL unchanged and produces the deferred announcement.
- `apps/web/vite.config.ts` proxies only `/api` to the Fastify target. Root documentation states that development serves web at port 5173 and API at port 3000. In contrast, BL-011 assigns the stable workbench route to the API. `apps/api/src/routes/root.ts` currently serves API health JSON at API `/`, not Project Home. No tracked runtime or deployment configuration currently establishes one browser origin on which `/` is Home and `/projects/{id}/workbench/` is the API-owned proxy.
- Persisted projects contain exactly `id`, `name`, `canonicalPath`, and `createdAt` (`apps/api/src/project-persistence.ts::Project`). `apps/api/src/project-registration.ts` uses `randomUUID` by default, and persistence returns the same durable winner for canonical-path duplicates. `apps/web/src/projects.ts::parseProject` preserves the returned ID and `ProjectLibrary.findById` resolves it server-side.
- BL-010 is implemented by `apps/api/src/project-runtime-manager.ts::createProjectRuntimeManager`. `start` first verifies the persisted ID and exact canonical path, joins an existing in-flight start by project ID, or health-checks and reuses an exact running process identity. Failed starts are evicted from in-flight ownership and permit a later explicit start; post-running exits are retained as bounded failure state without automatic retry. Runtime PID, process-start identity, port, handles, and state remain in memory only.
- `apps/api/src/project-runtime-contract.ts` fixes readiness at a 15,000 ms total bound with 1,000 ms attempts and defines typed startup, health, cancellation, and shutdown failures. `apps/api/src/project-runtime-process.ts::buildRuntimeArgv` launches code-server directly against the stored canonical path, loopback-only, with `--disable-proxy`; shutdown is exact-process-group and listener scoped.
- Application construction in `apps/api/src/app.ts::app` creates the project library, runtime manager, and workbench proxy once. Its `onClose` ordering shuts the proxy down before the runtime manager and persistence owners. Leaving an individual proxy request or browser connection does not call runtime shutdown; `apps/api/src/workbench-proxy-manager.ts` limits disconnect cancellation to the matching proxy operation.
- BL-011 is implemented by `apps/api/src/routes/workbench.ts` and `apps/api/src/workbench-proxy-manager.ts`. Fastify claims `/projects/*`; valid base and descendant workbench paths resolve persisted metadata, call `ProjectRuntimeManager.start`, and forward HTTP or WebSocket traffic under the stable prefix. Suffixes and queries are preserved for descendants. The proxy returns fixed JSON failure envelopes before commitment and contains no Ascend HTML shell or browser Retry/Projects controls.
- Workbench route parsing decodes exactly one ID segment and accepts only `^[A-Za-z0-9][A-Za-z0-9._~-]{0,127}$`. Decode failures, encoded slash/backslash/NUL, traversal-shaped IDs, and overlength IDs are rejected before proxy lookup. Sibling `/projects/*` paths that do not match the workbench grammar also enter the invalid route response. `apps/api/src/workbench-proxy-contract.ts::parseStableWorkbenchRoute` contains the shared pure parser, while `apps/api/src/routes/workbench.ts::parseRoute` currently duplicates the route parsing logic used by Fastify.
- `apps/api/src/workbench-proxy-manager.ts::resolveTarget` performs `ProjectLibrary.findById` before runtime start. Unknown projects return `project_not_found`; persistence and runtime failures map to the fixed 23-row catalog. HTTP response and WebSocket handshake bounds are 5,000 ms. Redirect, cookie, service-worker, forwarding-header, authority-redaction, stream, backpressure, and shutdown behavior are already owned by this boundary.

## Constraints
- The accepted presentation remains full-page code-server with a minimal Ascend header; embedded workbench presentation was rejected by `ADR-260810-full-page-browser-workbench-presentation.md`.
- Ascend owns navigation and lifecycle boundaries, while code-server owns editing, Explorer, Markdown rendering, terminal emulation, Git UI, and extensions (`ADR-260808-typescript-monorepo.md`, PRD NFR-012).
- The stable route and every Ascend-owned descendant HTTP/WebSocket channel remain under `/projects/{encodeURIComponent(stableId)}/workbench/`; internal loopback authorities, ports, protected payloads, and raw development content cannot appear in browser-visible or public evidence surfaces (`CORE-COMPONENT-260812-stable-workbench-proxy.md`).
- Route-invalid input must be rejected before project lookup or runtime start. Valid IDs are one decoded 1-to-128-character route-safe segment; the persisted close API retains a separate opaque-ID contract.
- BL-010 remains the sole owner of runtime processes. Runtime identity and lifecycle state remain memory-only, one project has at most one managed runtime, concurrent starts join, healthy running identities are reused, caller cancellation is local, and no automatic retry loop is allowed (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`).
- Proxy operations own streams and sockets but do not stop or replace runtime processes. Proxy shutdown must finish before runtime and SQLite shutdown (`ADR-260812-in-process-workbench-reverse-proxy.md`).
- Runtime launch uses the persisted exact canonical directory, direct argument vectors, configured non-root host user, deterministic environment, loopback binding, finite readiness, and exact owned-resource cleanup (`CORE-COMPONENT-260808-host-process-environment.md`, `CORE-COMPONENT-260808-filesystem-path-safety.md`).
- SQLite remains four-field project metadata with explicit close ownership and committed migrations; runtime identity, editor state, and terminal state are not persisted there (`CORE-COMPONENT-260810-sqlite-persistence-lifecycle.md`).
- Project names and canonical-path display values are untrusted display text and cannot select routing identity. Existing Home rendering preserves them as inert React text.
- Runtime and proxy logs must be structured and must exclude source, terminal, command output, credentials, secrets, raw canonical paths, and internal authorities (`CORE-COMPONENT-260808-structured-runtime-logging.md`, PRD NFR-010).
- The authoritative browser target is desktop Chromium. Tablet behavior remains non-authoritative and outside this issue.
- Scope remains one Project Home project connected to its existing workbench. Multi-project coordination, lifecycle controls, persisted runtime identity, custom IDE surfaces, public authentication/networking, TLS, and multi-host routing remain excluded by the issue and existing architecture.
- Repository operation and validation remain rooted in `justfile`; harness checks delegates to `just verify`. Harness observation capture remains leaf-worker-only and does not grant lifecycle orchestration (`CORE-COMPONENT-260806-project-command-interface.md`, `CORE-COMPONENT-260806-rpiv-stage-contract.md`).

## Risks and Open Questions
- Development currently has two origins and conflicting `/` ownership: Vite serves Home while Fastify `/` serves health JSON, and Vite proxies only `/api`. The repository does not state the final same-origin ownership that makes both required public paths available in one browser history.
- The accepted header exists only as proof-time DOM injection. No product code currently owns a durable header around a top-level proxied code-server document, and current proof injection is non-interactive.
- Current route failures are JSON transport responses. The repository has no accessible Ascend error document, route-error focus owner, announcement owner, Projects control, or Retry control for workbench failures.
- The term `generation` in the issue is not defined against existing symbols. Runtime manager generations identify process attempts internally, while Home generations identify UI request ownership; proxy request attempts are not exposed as a product generation.
- A start failure permits a later fresh runtime attempt, but an upstream proxy or document-load failure can occur while the runtime is still healthy. The required relationship between Retry generation and preserved or replaced runtime identity is unresolved by current documentation.
- Browser document-load timeout ownership is unresolved. The proxy has a five-second upstream-header bound, code-server startup has a 15-second readiness bound, and Playwright has observation bounds, but there is no product-side workbench-document timeout or public timeout classification.
- Editor-file and terminal-marker continuity across a Home visit is not exercised by current connected browser coverage. Treating it as existing behavior would be inferred only from reuse of the code-server process; this research captured that gap as harness observation `INS-099`.
- Current BL-011 storage-empty contexts prove fresh direct navigation against a shared backend, but they do not include the required single refresh, History API behavior, Home visits, or service-worker clearing within a connected product flow.
- Existing Home and workbench browser suites do not observe history length, duplicate entries, Back/Forward ownership, refresh semantics, stale route settlement, error focus, or exactly eight Home activations. Existing runtime/proxy concurrency coverage is below those browser-history semantics.
- The duplicated route parser in `apps/api/src/routes/workbench.ts` and `apps/api/src/workbench-proxy-contract.ts` creates drift risk for empty IDs, trailing slash canonicalization, sibling paths, and encoded malformed inputs.
- The route-safe grammar is narrower than the general persistence interface, which validates IDs only as nonempty. Default BL-006 UUIDs fit the route grammar, but repository-level compatibility for any preexisting or injected non-route-safe persisted ID is not documented.
- Closing project metadata is currently documented and implemented only for stopped projects. Behavior around an already-closed ID is safe at route lookup, but interaction with an independently running memory-only runtime is outside the merged BL-009 product scope.
- The exact selected project fixture already exists under `tests/fixtures/bl-001`, but the repository has no connected Home registration/history/continuity episode using one known editor file and one bounded advancing terminal marker across Home.
- Existing docs explicitly say Open is deferred and BL-012 is absent. Those statements are accurate now but become a broad staleness surface when the issue changes user-visible navigation and recovery behavior.
- Full verification duration has grown beyond the harness wrapper limit. Until the deterministic 120,000 ms prerequisite gap is resolved outside product acceptance, `harness boot` can report a false readiness failure even when direct `just verify` succeeds.
- Repository search for client routing dependencies was unexpectedly empty and was captured through `harness observe` as `INS-098`; any assumptions about existing route or history abstractions would therefore be unsupported.
