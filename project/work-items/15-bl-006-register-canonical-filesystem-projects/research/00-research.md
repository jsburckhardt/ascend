# Research Brief: BL-006: Register canonical filesystem projects

## GitHub Issue
- **Issue:** #15
- **Title:** BL-006: Register canonical filesystem projects
- **Work Item:** `project/work-items/15-bl-006-register-canonical-filesystem-projects`

## Scope Classification
- **Scope Type:** issue

## Problem Statement

Ascend can durably store four-field project metadata, but it has no in-process registration boundary that turns supported user path expressions into canonical, policy-approved records. Issue #15 owns configuration validation, explicit absolute and configured-home-relative path handling, canonical filesystem validation, opening-policy enforcement, typed safe failures, stable duplicate and concurrency behavior, persistence across reopened services, and non-mutation of user-owned directories. It excludes HTTP/UI behavior, project listing and workbench behavior, scanning, cloning/importing, Git requirements, close behavior, network behavior, and native pickers.

## Acceptance Criteria

**Core**
- [ ] Service construction validates the complete configured-home and allowed-roots set before registration is available. The configured home and every allowed root are accepted only when they are absolute, existing, readable directories; each is canonicalized once for that constructed service, canonically equivalent allowed roots are deduplicated, and an empty allowed-roots set is a valid deny-all policy. Disposable symlink checks prove that later retargeting of an allowed root or configured home does not change the roots or home expansion used by an already constructed service.
- [ ] With valid configuration, registration supports absolute paths plus exactly `~` and `~/...` home notation, expands supported home notation from the configured home before canonicalization, and registers an existing readable directory inside policy as one project. The record has exactly the persisted project fields—stable ID, display name, canonical path, and created-at value—and remains unchanged after all registration and persistence resources close and fresh service instances reopen the same database. The display name is the canonical directory basename, or the canonical root path when no basename exists.
- [ ] An empty or whitespace-only submitted path returns the typed `path_required` category before filesystem access, while a submitted path containing a NUL code point returns the typed `unsupported_path_syntax` category before filesystem access. Nonempty supported paths are not globally trimmed: valid absolute and supported home-relative directory names containing whitespace, including leading or trailing whitespace in a path segment, register with that whitespace preserved in the canonical path and display name. These cases, missing paths, existing non-directory paths, unreadable directories, other unsupported input syntax, and directories outside the opening policy each return their distinct typed validation category where applicable. Every failure identifies only its category and the submitted-input field, includes no stack trace, raw platform error, or configured path value, and leaves project persistence unchanged.
- [ ] Opening-policy decisions use canonical path-segment boundaries: an allowed root and its descendants can register, while prefix-sibling paths, lexical traversal outside a root, and symlinks resolving outside every allowed root are rejected; a symlinked allowed root is evaluated by its canonical target.
- [ ] Sequential registration through absolute, supported home-relative, normalized, or symlinked expressions that resolve to the same allowed directory returns the same four-field existing project record and leaves exactly one durable canonical-path record.

**Edge Cases**
- [ ] Exactly eight concurrent registrations whose expressions resolve to the same allowed directory all return the same four-field project record, including the same stable ID, display name, canonical path, and created-at value, and leave exactly one durable record with no partial row.
- [ ] Any invalid configured home or any invalid allowed root makes the entire service unavailable with one typed `invalid_opening_policy` configuration outcome. The outcome identifies only `configured_home` or the indexed `allowed_roots` field and includes no configured value, stack trace, or raw platform error; valid roots in a mixed set do not remain active, construction leaves the project row count and existing rows unchanged, performs none of the project-content mutations prohibited below, and registration cannot proceed until the complete configuration is valid.
- [ ] Successful, duplicate, concurrent, and rejected registration paths do not create, delete, copy, move, rename, truncate, or write project content and leave fixture tree membership, file bytes, modification timestamps for every fixture node, and permission modes unchanged.
- [ ] Finite repository validation uses disposable fixtures and covers all-valid configuration, canonically duplicate roots, empty roots, one invalid root among valid roots, invalid configured home, non-directory root, symlinked-root and symlinked-home canonicalization and retargeting, empty, whitespace-only, and NUL-containing submitted paths, whitespace-containing directories and path segments, valid absolute and supported home-relative inputs, missing paths, files, traversal, prefix siblings, symlink escape, equivalent paths, and cleanup. A bounded capability probe determines whether the current process can enforce host-permission unreadability: when it can, disposable unreadable-root and unreadable-project fixtures prove both typed outcomes; otherwise validation emits an inspectable skip artifact containing the failed probe result and does not claim host-permission proof. A controlled repository-local denial case always proves denied root and project access map to the unreadable typed outcomes.

**Verification**
- [ ] Documentation records the registration boundary, configured-home and allowed-roots contract, empty-roots deny-all behavior, all-or-nothing `invalid_opening_policy` outcome and safe field identifiers, supported path syntax, canonical boundary and symlink behavior, typed registration categories and safe fields, display-name rule, duplicate and concurrency outcomes, permission-capability handling, non-mutation guarantee, disposable-fixture cleanup, and the out-of-scope boundaries.
- [ ] The repository-configured finite full-validation command exits zero and its finite output identifies passing configuration, registration, persistence, non-mutation, fixture-cleanup, documentation, and permission-capability checks.

## Repository Findings

- `PRD.md` FR-002 requires home expansion, canonicalization, existence, directory and readability validation, canonical-path deduplication, and persistence; AC-002–004 require one canonical project for a readable directory, actionable rejection of missing/non-directory input, and reuse of an existing project for equivalent expressions. NFR-008 requires canonical validation and rejection of traversal outside opening policy. CON-001 keeps projects in their existing host directories, while CON-004 prohibits automatic indexing.
- `docs/README.md` and `apps/api/README.md` explicitly assign filesystem existence, readability, home expansion, and canonicalization to BL-006 and HTTP/API/UI behavior to BL-007. They document no configured-home, allowed-roots, registration-category, or registration-service contract yet.
- BL-005 is merged at `c2f28d0` (`feat(api): persist project library (#14)`) and is present on `main`. `project/architecture/core-components/CORE-COMPONENT-260810-sqlite-persistence-lifecycle.md` defines explicit-path closeable SQLite resources, committed ordered migrations, construction-injected repositories, isolated database paths, and exact cleanup ownership.
- `apps/api/src/project-persistence.ts` defines the persisted `Project` shape as exactly `id`, `name`, `canonicalPath`, and `createdAt`. `createProjectRepository()` validates only persistence fields, stores canonical-path input unchanged, returns `created` or `existing`, and converts unexpected adapter failures to `ProjectPersistenceError` without a raw cause.
- `apps/api/src/db/schema.ts` and `apps/api/drizzle/0000_project_library.sql` define exactly four non-null columns. `apps/api/drizzle/0001_project_canonical_path_unique.sql` and `createDrizzleProjectAdapter()` enforce canonical-path uniqueness with conflict-do-nothing followed by lookup of the durable winner.
- `apps/api/src/project-library.ts` exposes `createProjectLibrary(databasePath)` and `createApplicationProjectLibrary()`. Construction creates the database parent, opens and migrates SQLite, then exposes `create`, `list`, and idempotent `close`; callers must currently supply all four project fields. No registration service exists under `apps/api/src/`.
- `apps/api/test/project-duplicates.test.ts` already proves sequential duplicate behavior and eight concurrent same-canonical-path persistence calls through one library. Those calls deliberately provide different IDs, names, and timestamps; SQLite selects one durable winner and all calls return it, but the persistence layer does not define registration identity or timestamp derivation.
- `apps/api/test/project-library-restart.test.ts` proves complete close and fresh reopen at one database path. `apps/api/test/project-schema-minimization.test.ts` verifies the four-field boundary, and `apps/api/test/project-validation-integration.test.ts` verifies failed persistence validation does not change serialized rows.
- `apps/api/test/project-database-test-helper.ts` provides unique BL-005 database paths, close callbacks, default-database refusal, and deletion limited to a selected database and its `-wal`, `-shm`, and `-journal` sidecars. It does not provide filesystem-project fixtures or opening-policy configuration.
- `apps/api/src/app.ts` and `apps/api/src/server.ts` do not construct the project library or any registration service. Existing routes contain only the health boundary; Issue #15 is therefore an in-process application boundary rather than current Fastify startup or network behavior.
- `apps/api/src/workbench-proof-runtime.ts#validateProjectPath` is a proof-only predecessor: it calls `realpath`, `stat`, and `access(..., R_OK)`. It has no configured-home, syntax, allowed-root, path-boundary, or registration behavior; it maps every `realpath` failure to `project-missing` and includes submitted/canonical paths in error details, which differs from Issue #15’s safe failure contract.
- `apps/api/src/workbench-proof-contract.ts#snapshotFixture` records fixture membership and hashes two sentinel files. It does not record every fixture node’s bytes, modification timestamp, or permission mode required by Issue #15.
- The root `justfile` makes `just verify` the full finite gate and `just verify-focused` the focused Vitest surface. `.harness/engineering-harness.md` delegates checks to `just verify` and lists BL-005 consequences, but neither surface currently identifies registration, opening-policy, project-content non-mutation, filesystem-fixture cleanup, or permission-capability results.
- `package.json` pins Node `>=22 <23`; `.devcontainer/devcontainer.json` selects Node 22 and remote user `vscode`. `docs/workbench-proof.md` defines the designated host as Ubuntu 24.04.4 LTS with non-root `vscode` uid 1000. The inspected process was Node 22.23.2 on Linux as uid/euid 1000 with no permitted or effective Linux capabilities; the Node executable had no file capabilities.
- A bounded disposable probe in the current process changed a user-owned directory to mode `000`: both `fsPromises.access(..., R_OK)` and `fsPromises.readdir()` failed with `EACCES`, then permissions and the temporary tree were restored. This process can enforce host-permission unreadability, but that observation is environment-specific.
- Node 22.23.2 observations matched the official Node v22 documentation: `fsPromises.realpath()` determines the actual location; repeated calls followed a retargeted symlink to different targets, while the earlier returned canonical string remained unchanged. `fsPromises.access()` checks the calling process’s permissions, and Node warns that a separate access-before-operation check has a race. Official references: <https://nodejs.org/docs/latest-v22.x/api/fs.html#fspromisesrealpathpath-options> and <https://nodejs.org/docs/latest-v22.x/api/fs.html#fspromisesaccesspath-mode>.
- Node’s official path documentation states that default semantics vary by operating system, `path.isAbsolute()` is not safe for traversal mitigation, `path.resolve()` uses the current working directory for unresolved relative input and performs lexical normalization, and `path.relative()` reports segment-relative relationships. On this Linux process, `path.basename('/')` returned an empty string, a basename with leading/trailing spaces preserved those spaces, and the relative path from `/allowed/root` to `/allowed/root-sibling` was `../root-sibling`. Reference: <https://nodejs.org/docs/latest-v22.x/api/path.html>.
- On Node 22.23.2, passing a string containing NUL to `access`, `stat`, or `realpath` produced a rejected operation with `TypeError`, code `ERR_INVALID_ARG_VALUE`, and a message containing the submitted value. That platform exception does not satisfy the issue’s typed, value-free outcome contract by itself.

## Constraints

- Registration must remain within FR-002, AC-002–004, NFR-008, CON-001, and CON-004: it operates on explicitly submitted existing directories, does not scan or copy them, and enforces canonical opening-policy boundaries (`PRD.md`).
- Supported submitted syntax is limited by Issue #15 to absolute paths, exactly `~`, and `~/...`; whitespace-only detection occurs before filesystem access, while nonempty supported input cannot be globally trimmed. NUL must be intercepted before Node filesystem APIs expose `ERR_INVALID_ARG_VALUE` details.
- Configured home and every allowed root form an all-or-nothing construction contract. They must be absolute, existing, readable directories, canonicalized once per constructed service, with canonical duplicates removed; an empty root set remains a valid deny-all policy (Issue #15).
- Policy membership is based on canonical path-segment boundaries, not string prefixes or literal-path absoluteness. Canonical targets govern symlinked roots and submitted symlinks (`CORE-COMPONENT-260808-filesystem-path-safety.md`; Node path documentation).
- The global filesystem-safety component requires specific safe validation errors, canonical equivalence, persistence uniqueness, use of stored canonical paths by later runtimes, and no ownership or mutation of project contents (`project/architecture/core-components/CORE-COMPONENT-260808-filesystem-path-safety.md`).
- Registration output is constrained to BL-005’s existing four-field `Project` contract and durable canonical-path uniqueness. Persistence resources must use the explicit-path, closeable, migrated lifecycle and preserve typed repository boundaries (`CORE-COMPONENT-260810-sqlite-persistence-lifecycle.md`; `apps/api/src/project-persistence.ts`).
- Configuration and registration failures may expose only their category and safe field identifier. They cannot expose configured values, submitted path values, stack traces, raw Node/platform errors, or persistence-driver errors (Issue #15; `CORE-COMPONENT-260808-structured-runtime-logging.md`).
- Invalid construction and every rejected registration must leave all existing project rows unchanged; all outcomes must avoid create/delete/copy/move/rename/truncate/write operations on user-owned project content (Issue #15; CON-001; filesystem-path-safety component).
- Runtime launch, project listing, close semantics, routes, UI, network behavior, scanning, clone/import, Git checks, and native pickers are outside this issue. Current Fastify startup intentionally remains separate (`docs/README.md`; `apps/api/README.md`; Issue #15).
- Repository commands remain in the root `justfile`; harness checks delegate to `just verify`. Strict TypeScript, configured lint/format/type checks, Vitest, builds, Playwright, and 80% API coverage thresholds remain active (`ADR-260808-governed-engineering-harness.md`; development-standards and project-command components; `apps/api/vitest.config.mts`).
- Permission claims must be capability-sensitive. The configured user is non-root, and the current process can enforce a mode-based denial, but the issue forbids claiming host-permission proof when a bounded probe fails and still requires a controlled repository-local denial outcome (Issue #15; `docs/workbench-proof.md`; `.devcontainer/devcontainer.json`).
- Node path behavior is platform-dependent. The MVP’s documented designated host is Linux/Ubuntu, and NFR-022 requires platform-specific assumptions to be documented rather than claiming unsupported portability (`PRD.md`; Node path documentation).

## Risks and Open Questions

- The issue names `path_required`, `unsupported_path_syntax`, and `invalid_opening_policy`, but does not provide exact category names for missing paths, non-directories, unreadable projects, unsupported non-NUL syntax, or outside-policy paths.
- The exact safe submitted-input field identifier and indexed `allowed_roots` notation are not specified. The issue fixes `configured_home` and requires an indexed allowed-roots field but does not define its serialized shape.
- Neither the issue nor repository architecture defines how the stable project ID is derived, or how `createdAt` is selected for a first registration. BL-005 accepts both values from its caller and guarantees only the durable conflict winner.
- The concurrency criterion does not state whether the eight registrations share one service/database client or span independently constructed services. Existing BL-005 concurrency coverage uses one `ProjectLibrary` instance.
- “Readable directory” is not further defined in repository contracts. Node exposes separate `R_OK` and `X_OK` checks on Linux, and its documentation warns that access checks can race subsequent filesystem operations.
- Filesystem state can change between canonicalization, type/readability inspection, policy evaluation, and persistence. The criteria explicitly fix configured-home/root symlink retargeting semantics after construction but do not state the expected outcome for submitted-directory retargeting or replacement during registration.
- Current proof-path errors collapse all `realpath` failures into “missing” and include path values. Reusing that proof-only boundary unchanged would conflict with distinct categories and value-free failure requirements.
- Existing fixture snapshots cover membership and two content hashes only. No repository helper currently captures every node’s bytes, modification timestamp, and mode, so current non-mutation checks cannot support the broader Issue #15 claim.
- The current environment’s permission probe passed, but effective permission behavior varies with uid, capabilities, ACLs, mounts, and platform. The repository has no existing registration-specific capability artifact or controlled repository-local denial mechanism.
- The full gate is finite, but its current output does not identify the Issue #15 configuration, registration, non-mutation, fixture-cleanup, documentation, and permission-capability result groups required by the final criterion.
- The issue requires configuration validation before registration is available while BL-005 construction creates/migrates a database and may create its parent directory. Repository contracts do not define ownership or ordering between registration-service configuration validation and persistence-resource construction.
- The display-name fallback for canonical filesystem roots is explicit, and Node returns an empty basename for `/` on the configured POSIX platform; behavior and notation for non-POSIX roots remain outside documented current-host evidence.
