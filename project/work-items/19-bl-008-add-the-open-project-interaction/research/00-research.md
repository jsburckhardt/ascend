# Research Brief: BL-008: Add the Open Project interaction

## GitHub Issue
- **Issue:** #19
- **Title:** BL-008: Add the Open Project interaction
- **Work Item:** `project/work-items/19-bl-008-add-the-open-project-interaction`

## Scope Classification
- **Scope Type:** issue

## Problem Statement

Project Home lists the durable project library but cannot register an explicitly supplied existing host directory through HTTP or the browser. The merged in-process BL-006 boundary already owns canonicalization, opening-policy enforcement, idempotency, persistence, and typed path outcomes. Issue #19 adds the bounded registration interaction while requiring stable-ID reconciliation across success, definite non-transmission, cancellation, uncertain transport outcomes, retry, and authoritative refresh. Existing card Open behavior remains deferred, and workbench, lifecycle, discovery, import, close, search, sorting, tagging, and path-mutation behavior remain outside scope.

## Acceptance Criteria

**Core**
- [ ] The documented project-registration POST operation accepts an exact JSON object containing only one string `path` field; project `name` is returned from BL-006 and is not submitted. Each contract-valid request delegates once to the merged BL-006 registration boundary and does not weaken or replace BL-006 path syntax, opening-policy, canonicalization, idempotency, persistence, or non-mutation outcomes.
- [ ] Every BL-006 created, existing, and typed registration-failure result has one documented HTTP status and exact safe response shape. Success exposes only the stable four-field project record and its created-or-existing disposition; failures expose no partial project, submitted or configured path, raw platform error, stack, SQL, secret sentinel, or internal error text.
- [ ] A finite documented request-size bound is enforced. Empty bodies, malformed JSON, oversized bodies at the bound plus one byte, wrong field types, a missing `path`, and unrecognized fields return stable safe non-success outcomes, invoke no registration, and leave an isolated project library unchanged.
- [ ] Project Home provides a semantic Open Project form for an existing host directory. Its host-path control has a persistent programmatic label and associated supported-notation guidance, preserves the exact user-entered text, and can be corrected after validation or transport failure.
- [ ] Blank and whitespace-only input plus every backend typed path failure produce a specific message programmatically associated with the host-path control, move focus to the correction target when submission cannot proceed, preserve the submitted text, add no card, and expose the error through an inspectable alert or live-status semantic.
- [ ] A normal created or existing response updates Project Home without a page reload by stable project ID: replace the one matching card or insert one card, never duplicate an ID, and restore the documented deterministic card ordering. The exact returned ID card is brought into view, focused at its project action, and announced as created or already registered.
- [ ] Submitting any supported expression equivalent to an already registered canonical path presents and activates the same stable-ID card and leaves exactly one card and one durable record for that ID; display name and path text are never used as identity.
- [ ] Each registration attempt has a client-owned 10-second bound. While an ordinary submission is pending, an active keyboard-operable Cancel action is available and repeated submit activation cannot send another request. Unmount ends ownership of the current attempt and no later completion can update the unmounted page.

**Edge Cases**
- [ ] An outcome for which the client has positive evidence that no usable request was transmitted, a controlled pre-send network-unavailable outcome, or deliberate cancellation of an ordinary submission preserves the input, changes no cards, invalidates every later response from that generation, and restores normal editing and retry controls. Deliberate initial cancellation has this client outcome even if transport completion cannot be observed.
- [ ] After request transmission, timeout, connection reset, truncated body, unreadable or non-JSON body, undocumented status, or JSON that does not match a documented registration response enters a programmatically announced `submission outcome unknown` state. The exact submitted `path` JSON payload is visible and locked, no optimistic card change occurs, and before any successful recovery refresh the only available recovery actions are keyboard-operable `Retry same submission` and `Refresh projects`.
- [ ] While submission outcome is unknown, no different registration payload can be sent. The state ends only through a created-or-existing retry result, a zero-or-one-added-ID authoritative refresh result, or an explicit reset made available after a successful multiple-ID refresh.
- [ ] `Retry same submission` sends JSON bytes equivalent to the locked original payload. A BL-006 created or existing result returns one stable project, exits recovery, upserts only that ID, and brings into view, focuses, and announces that exact card.
- [ ] A retry attempt retains the 10-second bound and active Cancel. Cancelling that retry invalidates its generation and returns to the unchanged submission-outcome-unknown state with the same locked payload and the same two recovery actions; it does not unlock a different submission.
- [ ] `Refresh projects` replaces all cards from the authoritative project-list response and compares stable IDs only with the pre-submit card snapshot. If exactly one ID was added, that card is brought into view, focused, announced as reconciled, and recovery ends.
- [ ] If a successful recovery refresh adds zero IDs relative to the pre-submit snapshot, the page states that no new project was observed, preserves and unlocks the original input, and returns to normal editing and retry without changing the authoritative refreshed cards.
- [ ] If a successful recovery refresh adds multiple IDs relative to the pre-submit snapshot, the page shows the complete authoritative refreshed list and an actionable ambiguous-reconciliation message without selecting an identity from display name or path. The locked payload cannot be edited or resubmitted until the user activates the now-available explicit reset, after which a new submission can be made.
- [ ] If a recovery refresh fails, times out, or returns an invalid list contract, the page remains in submission-outcome-unknown recovery, preserves the locked input and current cards, sends no new registration, and again exposes the same two recovery actions.
- [ ] At most one recovery request is active at a time. Repeated Retry or Refresh activation cannot create parallel registration or list requests or duplicate card updates; controls expose an inspectable pending state, and the registration retry and existing project-list client bounds remain finite.
- [ ] Responses are owned by a monotonic request generation. Cancellation; every ordinary, retry, or refresh timeout; each recovery action; explicit reset; and each newer authoritative list invalidate all older generations. Any later completion from an invalidated generation cannot modify cards, inputs, focus, announcements, validation, or recovery state.
- [ ] User-entered paths, returned names, and returned paths, including long values, whitespace, and HTML or script metacharacters, remain inert complete text and are not interpreted as markup or exposed in unsafe error details.
- [ ] Existing card Open actions remain project-ID-identified, keyboard-operable deferred actions that start no workbench and perform no navigation. BL-010 or BL-012 behavior, picker integration, repository scanning, clone or import, project close, search, user sorting, tags, and path mutation are not added.

**Verification**
- [ ] Finite isolated API validation covers created and existing results, every BL-006 typed failure mapping, malformed and oversized request cases, exact safe response shapes and redaction sentinels, one delegation per accepted request, unchanged persistence on rejection, stable identity, and sequential equivalent submissions.
- [ ] Finite isolated API validation sends exactly eight concurrent equivalent valid POST requests and proves eight bounded responses identify the same complete stable project, exactly one durable record exists afterward, and each accepted HTTP request delegates once without a partial response.
- [ ] Finite component validation covers semantic form labeling and guidance; blank, whitespace, and every typed validation outcome; created and existing stable-ID card updates; deterministic ordering; focus, scroll, and inspectable announcements; 10-second timeout; ordinary and recovery Cancel semantics; repeated-submit prevention; unmount; definite pre-send outcomes; every unknown-outcome trigger; byte-equivalent retry; zero, one, multiple, failed, timed-out, and invalid refresh branches; explicit reset; repeated recovery actions; stale-generation suppression; and inert text rendering.
- [ ] One bounded real desktop Chromium episode uses only keyboard interaction to prove a new valid path, an equivalent-path existing result on the same card, an invalid path with programmatically associated announced error, correction and successful resubmission, no page reload, exact stable card identity, and the still-deferred card Open action.
- [ ] The real-browser episode runs the web and API applications against an isolated database and disposable host-directory fixtures and proves project fixture membership and bytes are unchanged. On success, startup failure, assertion failure, timeout, and interrupted graceful shutdown paths, bounded cleanup removes only episode-owned processes, listeners, database, sidecars, and allocated fixtures and leaves none of them behind.
- [ ] Documentation completely records the registration request, response, size, status, and safe-error contracts; host-path form and validation behavior; created and existing card outcomes; 10-second timeout and both Cancel outcomes; definite versus unknown transport outcomes; payload locking, retry, refresh, reset, stable-ID reconciliation, stale-response ownership, accessibility semantics, scope exclusions, validation commands, isolation, integrity checks, cleanup on every exit path, and the observed bounded browser result.
- [ ] The repository-configured focused validations for the API, component, documentation, and browser matrices and the root full-validation command all exit zero and leave no BL-008 process, listener, database, sidecar, or host-directory fixture behind.

## Constraints

- The issue remains within PRD FR-002 and AC-002 through AC-004: projects are explicitly submitted existing host directories, Git is not required, canonical equivalents identify one durable project, and automatic scanning is excluded (`PRD.md`).
- The HTTP boundary must delegate contract-valid requests to the existing BL-006 service without replacing its syntax, canonicalization, canonical segment policy, typed outcomes, stable four-field record, durable uniqueness, or project-filesystem non-mutation behavior (Issue #19; `apps/api/src/project-registration.ts`; `CORE-COMPONENT-260808-filesystem-path-safety.md`).
- Registration identity is the durable project ID. Current persistence uniqueness is canonical-path based, while current cards are keyed and identified by ID; names and paths can contain duplicate-looking, whitespace-bearing, long, or metacharacter text and cannot serve as browser identity (`apps/api/src/project-persistence.ts`; `apps/web/src/App.tsx`).
- The authoritative list contract is exact, duplicate-ID-free, and ordered by `createdAt ASC, id ASC`; list failures expose no partial projects. Existing list requests have a documented 5,000 ms bound and newest-request-wins/unmount ownership (`apps/api/src/routes/projects.ts`; `apps/web/src/projects.ts`; `apps/web/src/use-project-list.ts`; application READMEs).
- API errors and runtime records cannot expose submitted/configured paths, raw platform or persistence detail, SQL, stacks, credentials, secrets, or development content. Fastify structured logging is the application logging boundary (`CORE-COMPONENT-260808-structured-runtime-logging.md`; `apps/api/src/routes/projects.ts`).
- SQLite application resources remain explicit-path, closeable, migration-ready before repository operations, and idempotently closed. Database validation uses isolated paths, refuses the developer default, and removes only the selected database and `-wal`, `-shm`, and `-journal` sidecars (`CORE-COMPONENT-260810-sqlite-persistence-lifecycle.md`; `apps/api/test/project-database-test-helper.ts`).
- Project directories remain user-owned. Registration and cleanup cannot mutate or broadly remove project contents; repository fixtures use allocation-specific roots and content manifests (`CORE-COMPONENT-260808-filesystem-path-safety.md`; BL-006 fixture helpers).
- Existing card Open remains a stable-project-ID, keyboard-operable deferred action. The accepted full-page workbench presentation does not authorize routing, workbench startup, lifecycle UI, or Project Home integration in this issue (`ADR-260810-full-page-browser-workbench-presentation.md`).
- The application stack remains React/Vite, Fastify, SQLite/Drizzle, Vitest, Playwright, and desktop Chromium in the pnpm TypeScript monorepo (`ADR-260808-typescript-monorepo.md`). Strict TypeScript, repository lint/format/type checks, and 80 percent package coverage thresholds remain active (`CORE-COMPONENT-260808-development-standards.md`).
- Raw operating and validation commands remain root `justfile` recipes. Harness checks continue to delegate to `just verify`, and current harness boot cannot be represented as owning persistent API/web services (`CORE-COMPONENT-260806-project-command-interface.md`; `ADR-260808-governed-engineering-harness.md`; `CORE-COMPONENT-260808-engineering-harness-delivery-contract.md`).
- Issue #19 fixes a client-owned 10-second bound for each registration or retry attempt and preserves the existing finite list-client bound for refresh. Cancellation, timeout, recovery actions, reset, newer authoritative lists, and unmount impose monotonic stale-response invalidation across all visible state, focus, and announcements.
- The real-browser environment is the repository Chromium configuration and must retain exact ownership and cleanup boundaries rather than relying on Playwright `webServer` reuse or unrelated host listeners (`playwright.config.ts`; `tests/e2e/project-home.spec.ts`).

## Risks and Open Questions

- Issue #19 does not name the POST endpoint path, numeric request-size bound, HTTP statuses, success envelope, failure envelopes, validation category vocabulary, or safe message copy. No current repository contract supplies those values.
- Application startup has no configured-home or allowed-root source for BL-006 and no registration-service construction seam. BL-006 currently opens and owns its own `ProjectLibrary`, while Fastify startup separately opens and owns the library used by listing; repository ownership for their shared database lifecycle is undefined.
- BL-006 construction can fail with `invalid_opening_policy`, but the issue specifies mappings for created, existing, and typed registration failures rather than startup configuration-failure behavior. The runtime exposure and startup consequence of an invalid opening policy are unresolved.
- The browser Fetch boundary does not currently classify positive pre-send non-transmission separately from failures after possible transmission. Repository code has no registration transport abstraction or observable transmission marker, so the exact boundary between definite and unknown outcomes is not represented.
- Ordinary cancellation is required to return to normal editing even when server completion cannot be observed. The durable project can therefore change while current cards intentionally remain unchanged, creating a later reconciliation condition that current Project Home state does not model.
- The existing list hook privately owns the only project array and replaces its state only through mount/retry. It has no current interface for stable-ID upsert, pre-submit snapshots, authoritative refresh comparison, focus/scroll targets, locked payload, ambiguous reset, or coordination with a second request family.
- `parseProjectListResponse` validates shape and duplicate IDs but accepts server order. It is unresolved whether an out-of-order otherwise valid recovery list is authoritative, invalid, or normalized for the deterministic ordering requirement.
- Current `loadProjects` collapses HTTP failure, JSON parse failure, and invalid contract to one rejection. No registration client exists to distinguish documented typed responses from undocumented status, truncated/unreadable body, non-JSON body, invalid JSON shape, connection reset, timeout, or definite pre-send failure.
- Byte-equivalent retry is required for the locked `{path}` payload, but no repository contract defines the observable byte representation, encoding comparison boundary, or treatment of equivalent JSON that differs only in serialization details.
- The criteria require exact focus, scroll, and announcements for created, existing, reconciled, validation, zero-ID, and ambiguous outcomes. Current cards have no retained element references or scroll behavior, and the relative ordering of focus and announcement observations is not specified.
- The current browser launcher owns API/web processes and SQLite cleanup but has no registration fault modes, no disposable host-directory allocation, and no fixture membership/byte integrity snapshot. Startup-failure and interrupted-shutdown behavior for a registration-enabled launcher are not represented.
- `playwright.config.ts` enables full file parallelism, while current Project Home uses a serial describe and shared BL-007 artifact path. Isolation and collision behavior for a new registration episode alongside existing browser files is not established.
- Current READMEs and executable documentation checks explicitly describe browser registration as deferred and identify BL-007-specific timeout, controls, launcher fault, artifact path, and observed result. Those facts become stale when Issue #19 behavior exists, but no BL-008 documentation contract currently exists.
- The root gate already runs all package coverage, a duplicated named BL-006 suite, all Playwright files, and workbench audits. The bounded runtime impact and artifact collision behavior of the substantially larger Issue #19 matrices are unknown.
