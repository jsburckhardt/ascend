## ADRs Created
- **ADR-260815-selected-runtime-stop-control** — Release One Selected Workbench Runtime Through a Manager-Owned Stop Control. Issue #39 introduces the first public runtime lifecycle *mutation*. Choosing among a manager-owned stop operation versus route or proxy termination, a dedicated `POST` route versus an overloaded `DELETE`, a new internal `stopping` entry versus keeping the entry `running`, a fifth public state versus projecting an in-flight stop as `Running`, an optimistic `Stopped` versus an audit-confirmed `Stopped`, a stop-response state versus the existing projection authority, and a documented non-success versus a successful no-op for a request that resolves to no managed runtime is a real architectural decision that no existing ADR governs.
- **ADR-260815-termination-sequencer-boundary** — Prove Termination Sequencing Through an Injectable Primitive Boundary. AC-2 requires the graceful bound, the escalation point, and the overall bound to be observable properties of the shipped sequencer. The delivered sequencer is module-private, uses raw signalling, wall clock, timers, and `/proc` scans, and is reachable only through a really spawned process, so choosing where to inject, what to inject, which primitives are trusted and which are treated as fallible, how the bound is enforced inside the sequencer against a primitive that never settles, where each phase window starts, how cancellation and abandonment are made safe, and what the ownership audit is allowed to claim is a second real architectural decision.

## Acceptance Criteria

Stable IDs are assigned in GitHub Issue #39 order. The criterion text is preserved verbatim from the issue body; no condition is weakened, merged, or split away.

- **AC-1:** Stopping a selected running project succeeds only for that project’s Ascend-managed runtime. A successful result identifies the selected project, and a finite ownership audit confirms that its exact pre-stop runtime identity no longer exists, no process remains attributable as its owned descendant, and its listener accepts no connection. A request that does not resolve to a selected Ascend-managed runtime returns a documented non-success classification within a finite bound and leaves registered project metadata, public runtime states, declared peer and control identities, and declared project fixtures unchanged.

- **AC-2:** A stop attempt provides a graceful shutdown opportunity bounded by a documented finite limit before any escalation. A controlled graceful case returns the documented successful classification without escalation. A controlled non-graceful case escalates only after that limit and returns the documented successful classification within a documented finite overall bound. A controlled escalation-failure case that cannot confirm release returns an explicit non-success classification within the same overall bound, does not report the project as `Stopped`, and leaves registered project metadata, declared peer runtime identity and readiness, unrelated controls, and declared project fixtures unchanged.

- **AC-3:** After a confirmed stop, the selected project remains registered exactly once with its stable ID, display name, canonical path, and created-at value unchanged, and the public runtime state observed after that same stop result is `Stopped`.

- **AC-4:** Each repeated stop of the same already-stopped project completes within a documented finite bound with the same documented successful already-stopped or no-op classification, leaves the registered project metadata unchanged and the public state `Stopped`, creates or terminates no runtime identity, requires no restart, and leaves the declared project fixture unchanged.

- **AC-5:** In a bounded two-project scenario with independently ready runtimes, stopping the selected runtime leaves the peer `Running` with the same pre-stop runtime identity and the same successful readiness or health observation, while a declared unrelated control process and listener retain their pre-stop identities and availability. Both projects’ registered metadata remains unchanged. Before-and-after evidence for declared finite fixtures of both projects uses a non-empty manifest schema fixed before execution and shows identical relative tree membership, file content digests, permission modes, and recorded timestamps for every fixture node.

- **AC-6:** Finite, repeatable repository validation executes graceful stop, successful escalation, escalation that cannot confirm shutdown, a request with no selected Ascend-managed runtime, repeated already-stopped stop, two-ready-runtime isolation, metadata retention, and filesystem safety. Inspectable evidence records declared bounds, elapsed outcomes, and result classifications; the selected pre-stop ownership identity and its post-stop descendant/listener audit; unchanged peer and control identities and readiness; unchanged stable ID, display name, canonical path, and created-at values; `Stopped` only after confirmed release; and the before-and-after fixture manifests. A bounded inventory fixed before each scenario enumerates its runtime processes and listeners, controls, registration resources, and disposable fixtures. Assertions distinguish the product registration that must remain during the scenario from validation-owned temporary resources; after evidence capture, final teardown leaves no validation-owned temporary resource behind.

## Selected Stop Contract

This section is the authoritative implementation contract. It is a restatement of `ADR-260815-selected-runtime-stop-control`, `ADR-260815-termination-sequencer-boundary`, and the three updated core-components; it creates no architecture of its own. A required deviation returns to the Plan stage.

### Manager operation

- `apps/api/src/project-runtime-manager.ts` gains `stop(input: { readonly projectId: string }): Promise<RuntimeStopOutcome>` on the `ProjectRuntimeManager` interface and implementation. It is the only producer of a selected release.
- `stop` resolves every classified lifecycle outcome as a frozen typed result. It rejects only on an infrastructure fault — a persistence read failure or the settlement invariant fault below — and the route surfaces that rejection explicitly and never converts it into a success-shaped body.
- No route, proxy, CLI, or browser client signals a process, reads liveness, probes a listener, or derives a stop result.

### Entry states, the release marker, and why absence differs from `registered`

- `ProjectRuntimeEntryState` becomes exactly five values: `registered`, `starting`, `running`, `stopping`, `failed`.
- `RegisteredEntry` gains a required `readonly released: boolean`. `register()` installs `released: false`; only a confirmed selected stop installs `released: true`.
- The distinction is source-grounded on the base SHA. `ProjectRuntimeManager.register` has exactly one production caller: `start()` calls it synchronously immediately before constructing and installing the `starting` entry, with no `await` in between. No registration route, list route, projection route, close service, or proxy path creates a manager entry. Therefore a persisted project that has never been started has **no entry**, and a `registered` entry is observable to `stop` only because a confirmed release installed it or because an in-process caller invoked `register` directly.
- Consequently: absence, or `registered` with `released: false`, means this manager owns no runtime for that project and never released one — the AC-1 case of a request that does not resolve to a selected Ascend-managed runtime, answered `no-managed-runtime`. `registered` with `released: true` means this manager released that project's runtime through a confirmed stop — the AC-4 already-stopped case, answered `already-stopped` repeatably and stably.
- After an API restart the manager's memory is empty, so a project released before the restart answers `no-managed-runtime`. Runtime state is memory-only by decision and API-restart reconciliation remains BL-019; this is documented rather than papered over.

### Result vocabulary, counts, and safe disclosure

- Trusted in-process result (`RuntimeStopOutcome`) is one of:
  - `{ outcome: 'stopped', projectId, release, audit }` where `release` is `RuntimeTerminationOutcome` and `audit` is `RuntimeTerminationAudit`.
  - `{ outcome: 'already-stopped', projectId }`.
  - `{ outcome: 'rejected', projectId, category, release?, audit? }`.
- Frozen vocabularies in `apps/api/src/project-runtime-contract.ts`, with their exact member counts, are the single source of truth for every count stated in code, evidence, and documentation:

| `RUNTIME_STATES` (snapshot states) | `starting`, `running`, `failed` | 3 (unchanged) |
| `RUNTIME_ENTRY_STATES` | `registered`, `starting`, `running`, `stopping`, `failed` | 5 (new export; was an inline 4-value union in the manager) |

### State machine

`stop` resolves the persisted project first, then performs one synchronous section that reads the installed entry and dispatches. No `await` occurs between that read and the entry install.

| Observed condition | Manager action | Result | Entry after settlement | Public state | Lifecycle events |
|---|---|---|---|---|---|
| Manager shutting down | none | `rejected` `manager-shutdown` | unchanged | unchanged | none |
| ID not persisted | none | `rejected` `not-registered` | unchanged (no entry created) | unchanged | none |
| No entry | none | `rejected` `no-managed-runtime` | unchanged (map is not mutated) | `Stopped` | none |
| `registered` entry, `released: false` | none | `rejected` `no-managed-runtime` | unchanged | `Stopped` | none |
| `registered` entry, `released: true` | none | `already-stopped` | unchanged | `Stopped` | none |
| `starting` entry | none | `rejected` `start-in-progress` | unchanged; the start continues | `Starting` | none |
| `failed` entry | none | `rejected` `failure-retained` | unchanged; the original category is retained | `Failed` | none |
| `stopping` entry | join the in-flight operation | the same settled result or rejection | as settled by the claiming stop | as settled | none from the joining caller |
| `running` entry | claim, install `stopping`, terminate the exact claimed ready runtime | `stopped` or `rejected` `stop-unconfirmed`, or an invariant-fault rejection | `registered` (`released: true`) or `failed` (`stop-unconfirmed`) | `Stopped` or `Failed` | one `runtime.stop.requested` plus exactly one terminal event |

- **Claim.** For a `running` entry the manager installs `StoppingEntry { state: 'stopping', projectId, canonicalPath, generation, ready, snapshot, operation }` reusing the entry's exact `generation`, `ready`, and pre-stop `snapshot`. The deferred `operation` promise is created before the entry is installed, following the existing `StartingEntry` construction shape, and is tracked so shutdown can await it.
- **Release.** The operation awaits `ready.process.terminate(config.gracefulShutdownMs, config.forceShutdownMs, ready.port, terminationController.signal)` exactly once, raced against `processDependencies.sleep(runtimeStopOverallBoundMs(config), deadlineController.signal)` as the caller-side backstop.
- **Confirmed success.** `processAbsent && processGroupAbsent && listenerAbsent` is the confirmation, independent of the `release` mode. The manager records exactly one stop-phase cleanup audit, deletes that generation's ownership record, installs `{ state: 'registered', projectId, canonicalPath, released: true }`, and emits one `runtime.stop.succeeded`. `already-absent` (the exact generation exited naturally before the claim, or the owned group was already gone when the graceful signal was attempted, so no signal was delivered anywhere in the sequence) is a confirmed success, not a failure.
- **Unconfirmed release.** Otherwise the manager records exactly one stop-phase cleanup audit, retains the ownership record so manager shutdown re-attempts it exactly once, installs a `failed` entry carrying `stop-unconfirmed` and the pre-stop snapshot, and emits one `runtime.health.changed` with `from: 'stopping'`, `to: 'failed'`, and classification `stop-unconfirmed`.
- **Termination fault.** If `terminate` rejects — including when the sequencer's signal primitive raised an unexpected signalling failure rather than the tolerated target-gone refusal — no audit exists and no cleanup audit is recorded. The operation settles the entry exactly as an unconfirmed release — `failed` with `stop-unconfirmed`, ownership record retained, exactly one `runtime.health.changed` — and then rejects with the underlying failure so the route returns `500 runtime_stop_failed`. The fault is never swallowed into a success, and an entry is never left stuck in `stopping`.
- **Termination deadline.** If the backstop sleep wins, the manager aborts `terminationController`, records no cleanup audit, settles the entry exactly as an unconfirmed release, and resolves `{ outcome: 'rejected', projectId, category: 'stop-unconfirmed' }` — a classified lifecycle outcome, not a rejection. The abandoned termination promise is attached to a handler that records nothing, mutates nothing, emits nothing, and increments a `lateTerminationSettlements` counter exposed by `audit()`, so abandonment is observable rather than silent.
- **Settlement claim-ownership invariant.** Before installing either terminal entry the operation confirms the installed entry is still the exact `stopping` object it created. It is provably still installed for every contract-valid path: `transitionRunningToFailed` compare-and-sets on an exact `running` entry and loses against `stopping`; `start` throws `runtime-stopping` on a `stopping` entry without mutating it; `register` returns early when any entry exists; `failEntry` is reached only from the guarded transition or from a start operation's catch, and no start operation can be in flight for a project whose entry was `running` at claim time; and shutdown awaits every tracked in-flight stop before its ownership sweep and before its entry-deletion loop. A mismatch is therefore an invariant violation: the operation installs nothing, records no further cleanup, emits nothing, and rejects with a dedicated `RuntimeStopInvariantError` that the route maps to `500 runtime_stop_failed`. Joined callers receive the same rejection. No claimant ever emits a terminal event or reports success for state it did not install, and exactly one terminal event exists for every normally owned settlement.

### Termination sequencer boundary

`apps/api/src/project-runtime-process.ts` changes exactly as follows:

- `RuntimeTerminationPrimitives` is exported with exactly seven members in two trust classes, and these exact shapes.
  - **Fallible awaited primitives (4).** `readProcessStartTime(pid: number, signal: AbortSignal): Promise<string | null>`, `readProcessGroupMembers(processGroupId: number, signal: AbortSignal): Promise<readonly number[]>`, `listenerIsAbsent(port: number, signal: AbortSignal): Promise<boolean>`, and `delay(milliseconds: number, signal: AbortSignal): Promise<void>` are asynchronous and each takes a **required** `AbortSignal`. Every one of the four is treated as able to never settle and to ignore its signal, so the sequencer derives no deadline, no confirmation, and no signal from any of them.
  - **Trusted synchronous primitives (3).** `signalProcessGroup(processGroupId: number, signal: NodeJS.Signals): boolean`, `now(): number`, and `scheduleDeadline(milliseconds: number, onDeadline: () => void): () => void` are synchronous and return no promise, so none of them can block the sequence. `signalProcessGroup` returns `true` only when the host accepted the signal for the owned process group, returns `false` only for the expected identity-to-signal race in which that group is already gone, and throws for every other signalling error; only a `true` return is a delivered signal. `now()` is a **monotonic** elapsed-time reading, not a wall-clock timestamp: every termination phase, deadline, and elapsed comparison is computed from it, so it must be unaffected by any wall-clock adjustment, and its values are never compared with or serialized as `Date.now()` values. `scheduleDeadline` is the sequencer's only deadline mechanism: it invokes `onDeadline` at most once, no earlier than `milliseconds` after the call, and returns a synchronous cancellation handle that prevents any later invocation. It deliberately takes **no** `AbortSignal`, because the mechanism responsible for firing the sequencer's abort must not depend on that abort.
  - The trust split is the correctness boundary and must be stated in the same words wherever the primitives are described. The sequencer's bound holds with no cooperation from any of the four fallible awaited primitives and rests only on `now()` and `scheduleDeadline` honouring their contracts. No ADR, core-component, task, test, document, or evidence surface may describe all seven primitives as equally fallible, and none may describe an awaited primitive as a deadline source.
- Every fallible awaited primitive must settle promptly once its signal aborts and must never report an absence it did not observe. `defaultRuntimeTerminationPrimitives` implements that contract over the delivered `/proc`, `net`, and `process.kill` implementations, over `performance.now()` from `node:perf_hooks` as the monotonic `now()`, and over `setTimeout`: the `/proc/<pid>/stat` read passes `{ signal }` to `readFile` and keeps its delivered "no such process" to `null` mapping while rethrowing an abort error rather than mapping it to `null`; the `/proc` directory scan calls `signal.throwIfAborted()` before each entry and throws instead of returning a partial member list; the loopback probe destroys its socket and throws on abort instead of resolving `true`; and `delay` resolves on either timer elapse or abort and always clears its timer. `loopbackListenerIsAbsent` and `readProcessStartTime` keep their exported names and their delivered non-abort behavior.
- `defaultRuntimeTerminationPrimitives.signalProcessGroup` is exactly `try { process.kill(-processGroupId, signal); return true } catch (error) { if ((error as NodeJS.ErrnoException).code === 'ESRCH') return false; throw error }`. The delivered `terminateGroup`'s bare `catch {}` around each `process.kill` is replaced by this contract, so the one tolerated case is narrowed to the expected target-gone race and every other failure — a permission error, an invalid signal, an invalid group — becomes a termination fault instead of a silent no-op.
- `defaultRuntimeTerminationPrimitives.now` is `() => performance.now()`. It is the only clock the sequencer reads. `RuntimeProcessDependencies.now`, which the manager uses for lifecycle timestamps and event elapsed values, keeps `Date.now` unchanged, as do `fetchRuntimeHealthAdapter`'s elapsed measurement, `launchReadyRuntime`'s identity deadline, and every other delivered `Date.now()` use; those record when something happened rather than bounding a termination phase, and this plan changes none of them.
- `defaultRuntimeTerminationPrimitives.scheduleDeadline` is the production deadline mechanism and is exactly `const timer = setTimeout(onDeadline, Math.max(0, milliseconds)); return () => { clearTimeout(timer) }` — a native timer owned directly by the sequencer, independent of every awaited primitive, and cleared on every exit path so no timer survives the call. It is production-backed rather than test-only, and validation exercises the real production wiring as well as a clock-driven injected scheduler.
- The private `terminateGroup` becomes the exported `terminateOwnedRuntimeGroup(request)` where `request` is `{ pid, processStartTime, port, gracefulMs, forceMs, auditAllowanceMs, signal?, primitives? }`. It is the only definition of graceful-then-force sequencing; `primitives` defaults to `defaultRuntimeTerminationPrimitives`. `auditRuntimeResource` takes the same primitives, and `processGroupIsAbsent` is expressed as `readProcessGroupMembers(...).length === 0`.
- `createNodeRuntimeProcessAdapter(primitives = defaultRuntimeTerminationPrimitives): RuntimeProcessAdapter` becomes the factory; `nodeRuntimeProcessAdapter = createNodeRuntimeProcessAdapter()` remains the production default and is still the adapter in `defaultRuntimeProcessDependencies`. The adapter binds the launching `config.stopAuditAllowanceMs` into every `terminate` and `audit` closure it creates, so every termination path passes a real allowance. The standalone `audit(port)` closure runs `auditRuntimeResource` under its own `AbortController` at the deadline `primitives.now() + auditAllowanceMs`, arms that deadline through `primitives.scheduleDeadline`, cancels the handle and aborts the controller on return, and reports the non-confirming all-false audit when any component did not complete — the same discard rule the sequencer applies.
- `OwnedRuntimeProcess.terminate(gracefulMs, forceMs, port, signal?)` gains one optional trailing `AbortSignal`. Existing call sites and existing test fakes remain assignable; no delivered call site changes its arguments except the new stop path.

**Sequencer self-bound mechanism.** The sequencer enforces its own deadline at every point where it can wait, and that deadline is armed by a trusted synchronous scheduler rather than by any primitive the sequencer awaits, so no fallible primitive — including the `delay` used for polling — can make the documented bound false. Implement exactly this; do not substitute another mechanism.

- **Entry.** The sequencer records `startedAt = primitives.now()` and creates exactly one sequencer-scoped `AbortController`, `sequencerController`.
- **Pre-aborted caller signal.** Immediately after creating that controller, and before any audit, identity read, signal send, wait, or deadline arming, the sequencer synchronously evaluates `request.signal?.aborted`. When it is already `true` the sequencer aborts `sequencerController` in that same synchronous step and returns the non-confirming audit with outcome `unconfirmed`, having called no primitive other than `now()`. This entry check is load-bearing: an `AbortSignal` that was already aborted when `terminateOwnedRuntimeGroup` was called never fires a newly added `abort` listener, so the listener alone would leave an already-cancelled termination running to its full deadline.
- **Abort triggers.** When the caller signal is not already aborted, `sequencerController` is aborted by exactly three triggers: the caller's optional `request.signal` through one `addEventListener('abort', ..., { once: true })` registration removed in `finally`; the overall deadline callback; and the sequencer's own `finally`.
- **Overall deadline.** `overallDeadlineAt = startedAt + gracefulMs + forceMs + auditAllowanceMs`, armed exactly once at entry as `overallHandle = primitives.scheduleDeadline(overallDeadlineAt - primitives.now(), () => { deadlineExpired = true; sequencerController.abort() })` and cancelled exactly once in `finally`. Because the trigger is the trusted synchronous scheduler, the abort fires independently of every awaited primitive; `primitives.delay` is the poll interval inside `bounded` only and is never a deadline trigger anywhere in the sequencer.
- **Bounded calls.** Exactly one internal helper performs every awaited primitive call: `bounded<T>(deadlineAt: number, call: (signal: AbortSignal) => Promise<T>): Promise<{ completed: true; value: T } | { completed: false }>`. It returns `{ completed: false }` immediately, without invoking `call`, when `sequencerController.signal.aborted` or `primitives.now() >= deadlineAt`. Otherwise it creates one call-scoped `AbortController`, aborts it from `sequencerController` through one `{ once: true }` listener removed in `finally`, arms one `primitives.scheduleDeadline(deadlineAt - primitives.now(), () => callController.abort())` handle cancelled in `finally`, and races `call(callController.signal)` against that call controller's abort. When the abort wins, the still-pending promise is detached with an inert `.then(() => {}, () => {})` handler and `{ completed: false }` is returned, so the abandoned call's eventual value or rejection is never read, never recorded, and can never produce a signal, an audit field, an outcome, or an entry mutation. The sequencer makes no awaited primitive call outside `bounded`, and `bounded` is the only site of a call-scoped controller and of a per-call deadline.
- A primitive rejection that arrives **before** its call is abandoned is not swallowed: `bounded` propagates it, the sequencer propagates it, and the manager settles that stop through its documented termination-fault path.
- `auditRuntimeResource(deadlineAt, ...)` runs its three reads through `bounded` at the phase deadline it is given and returns `RuntimeResourceAudit | undefined`, yielding `undefined` when any component did not complete. An incomplete audit is discarded rather than defaulted, because a call that did not return is not an observed absence. The sequencer keeps `lastCompletedAudit`, the most recent audit whose three components all completed.
- When the sequencer returns without any completed audit it returns the non-confirming audit `{ pid, processStartTime, port, processAbsent: false, processGroupAbsent: false, listenerAbsent: false }` with outcome `unconfirmed`. A confirmed release therefore always rests on completed observations, and the worst case of a hung primitive set is an unconfirmed release with retained ownership, never a false `Stopped`.
- Every signal send is synchronous and gated in the same step: the sequencer evaluates its gate, calls `primitives.signalProcessGroup(...)`, inspects its boolean result, and — only when that result is `true` — reads the delivering clock position, all with no `await` in between, so no cancelled or abandoned continuation can deliver a signal and no window can be opened by a signal the host refused.
- **Signal delivery, refusal, and fault.** A `true` return is the only delivered signal. The sequencer records it, reads `primitives.now()` in that same step as `sigtermAt` or `sigkillAt`, and fixes that phase's deadline from it. A `false` return delivered nothing: it opens no window, is never recorded, logged, or serialized as a delivered signal, and can never produce `escalated`. A thrown error is not a race: `bounded` is not involved, the sequencer propagates it after its `finally` releases every scheduler handle and abort listener, and the manager settles that stop through its documented termination-fault path, which retains ownership and surfaces the failure.
- **Refused graceful signal.** When the graceful send returns `false`, no signal has been delivered anywhere in the sequence, so the sequencer performs exactly one `bounded(gracefulRefusalDeadlineAt, audit)` call — never a poll loop — where `gracefulRefusalDeadlineAt = gracefulRefusedAt + gracefulMs` and `gracefulRefusedAt` is the `primitives.now()` reading taken in the same synchronous step as that `false` return. Because `gracefulRefusedAt <= preSignalDeadlineAt`, this is exactly the window the delivered signal would have opened, so the overall-bound arithmetic below is unchanged and `forceMs + settlementAllowanceMs` remains unspent. If that one audit completes and all three absences hold, the outcome is `already-absent`, which is honest because no signal was delivered in the sequence; otherwise the outcome is `unconfirmed`. No `SIGKILL` is attempted, because attribution has already been refused by the host.
- **Refused force signal.** When the force send returns `false`, a graceful signal was already delivered, so no member of the four-value outcome vocabulary can truthfully describe a confirmed release: `already-absent` would deny the delivered `SIGTERM`, `graceful` would claim confirmation inside a graceful period that already elapsed unconfirmed, and `escalated` would claim a force signal that was never delivered. The sequencer therefore returns `lastCompletedAudit`, or the non-confirming audit when none completed, with outcome `unconfirmed`, immediately and with no force window opened. Retained ownership and the shutdown re-attempt cover the release.

**Phase windows and the audit allowance.** Every window is measured on the monotonic `primitives.now()` clock from the confirmed delivered signal it bounds, so no window is shortened by the observation work that precedes it, no window is opened by a signal the host refused, no wall-clock adjustment can move an escalation point, and the windows still fit inside the unchanged overall bound.

- `settlementAllowanceMs = Math.max(1, Math.floor(auditAllowanceMs / 10))` and `preSignalAllowanceMs = auditAllowanceMs - settlementAllowanceMs`. With the defaults (`gracefulMs` 2,000, `forceMs` 2,000, `auditAllowanceMs` 1,000) that reserves 100 ms for inter-phase settlement and gives 900 ms to pre-signal observation. Both are derived, not configured: no environment variable, flag, or new configuration field is added.
- Named deadlines, all measured on the monotonic `primitives.now()` clock and all elapsed-time values rather than wall-clock timestamps:
  - `preSignalDeadlineAt = startedAt + preSignalAllowanceMs` — bounds every observation performed before the graceful signal, namely the initial audit and the identity read.
  - `gracefulDeadlineAt = sigtermAt + gracefulMs`, where `sigtermAt` is the `now()` reading taken in the same synchronous step in which `signalProcessGroup(pid, 'SIGTERM')` returned `true`. It does not exist before that confirmed delivery, and a `false` return never produces it.
  - `forceDeadlineAt = sigkillAt + forceMs`, where `sigkillAt` is the `now()` reading taken in the same synchronous step in which `signalProcessGroup(pid, 'SIGKILL')` returned `true`. It does not exist before that confirmed delivery, and a `false` return never produces it.
  - `gracefulRefusalDeadlineAt = gracefulRefusedAt + gracefulMs` exists only on the refused-graceful-signal path and bounds its single settlement audit. It is mutually exclusive with `gracefulDeadlineAt`, so at most one of the two ever exists in a sequence.
  - `overallDeadlineAt = startedAt + gracefulMs + forceMs + auditAllowanceMs` — unchanged, armed at entry, and still the hard cap on every path.
- **Why the phase windows fit the overall bound.** `sigtermAt <= preSignalDeadlineAt` holds by the pre-signal gate, so `gracefulDeadlineAt <= startedAt + preSignalAllowanceMs + gracefulMs`. Every phase-B bounded call carries `gracefulDeadlineAt`, so the graceful poll cannot run past it, and `SIGKILL` is sent in the same synchronous step in which that exit is observed, so `sigkillAt - gracefulDeadlineAt` is synchronous settlement time only. The same holds for the return after `forceDeadlineAt`, and no audit is ever started after `forceDeadlineAt`. `settlementAllowanceMs` is reserved for exactly those two synchronous settlements, so `startedAt + preSignalAllowanceMs + gracefulMs + forceMs + settlementAllowanceMs = overallDeadlineAt` bounds the return. The refusal paths are bounded by the same arithmetic with strict slack: `gracefulRefusedAt <= preSignalDeadlineAt`, so `gracefulRefusalDeadlineAt <= startedAt + preSignalAllowanceMs + gracefulMs`, which leaves `forceMs + settlementAllowanceMs` of the overall bound unspent, and a refused force signal returns synchronously inside the settlement allowance. Neither refusal path can therefore push the return past `overallDeadlineAt`, and the overall deadline remains armed and enforced on both.
- **Pre-signal gate.** When pre-signal observation did not complete — the initial audit or the identity read was abandoned — or `primitives.now() > preSignalDeadlineAt` at the send gate, the sequencer signals nothing, opens no graceful window, and returns `lastCompletedAudit`, or the non-confirming audit when none completed, with outcome `unconfirmed`. Pre-signal observation never borrows time from the graceful opportunity, and an over-running observation is reported as an unconfirmed release rather than as a shortened graceful shutdown.
- **No window without its delivered signal.** A graceful window exists only after `signalProcessGroup(pid, 'SIGTERM')` returned `true`, and a force window only after `signalProcessGroup(pid, 'SIGKILL')` returned `true`. When the escalation gate refuses — the controller is aborted, or attribution no longer holds — the sequencer returns `unconfirmed` immediately rather than waiting out a force window it never opened, and the same holds when the host itself refuses the send.
- Sequence, measured on `primitives.now()`, with every step entered and every loop continued only while `!sequencerController.signal.aborted`:
  1. `bounded(preSignalDeadlineAt, audit)`. If it completes and all three absences hold, return `already-absent` without signalling.
  2. Observe identity through `bounded(preSignalDeadlineAt, ...)`. `attributable` becomes true only from a completed read showing the exact root identity alive, and false again only from a completed read showing the owned group empty while the root is absent; an abandoned read leaves it unchanged.
  3. Evaluate the send gate `!sequencerController.signal.aborted && attributable && primitives.now() <= preSignalDeadlineAt`. On failure apply the pre-signal gate above. On success call `primitives.signalProcessGroup(pid, 'SIGTERM')`. A thrown error propagates as a termination fault. A `true` return reads `sigtermAt` in that same synchronous step, fixing `gracefulDeadlineAt = sigtermAt + gracefulMs`, and continues to step 4. A `false` return reads `gracefulRefusedAt` in that same step and applies the refused-graceful-signal rule above: one `bounded(gracefulRefusalDeadlineAt, audit)` call, then `already-absent` on a completed confirming audit and `unconfirmed` otherwise, with no escalation attempted.
  4. Poll `bounded(gracefulDeadlineAt, delay)` then `bounded(gracefulDeadlineAt, audit)` until `primitives.now() >= gracefulDeadlineAt`, the controller aborts, or a completed audit confirms. Confirmation returns `graceful`.
  5. Evaluate the escalation gate `!sequencerController.signal.aborted && attributable`. On failure return `unconfirmed`. On success call `primitives.signalProcessGroup(pid, 'SIGKILL')`. A thrown error propagates as a termination fault. A `false` return applies the refused-force-signal rule above and returns `unconfirmed` immediately. A `true` return reads `sigkillAt` in that same synchronous step, fixing `forceDeadlineAt = sigkillAt + forceMs`, and records that the force signal was delivered. Because step 4 exits only at `gracefulDeadlineAt`, on abort, or on confirmation, every delivered escalation satisfies `sigkillAt - sigtermAt >= gracefulMs`.
  6. Poll `bounded(forceDeadlineAt, delay)` then `bounded(forceDeadlineAt, audit)` until `primitives.now() >= forceDeadlineAt`, the controller aborts, or a completed audit confirms. Confirmation after a delivered force signal returns `escalated`; `escalated` is unreachable without a `true` force send. No audit is started after `forceDeadlineAt`.
  7. Otherwise return `lastCompletedAudit`, or the non-confirming audit when none completed, with `unconfirmed`.
- The poll interval is the delivered `RUNTIME_TERMINATION_POLL_INTERVAL_MS = 20`, passed to `primitives.delay` through `bounded` at the current phase deadline, so a `delay` that never settles or ignores its signal is abandoned at that deadline instead of stalling the phase or the sequence.
- There are exactly two enforcement points and neither replaces the other: this sequencer self-bound, and the manager's `sleep`-based caller backstop that abandons a `terminate` promise which still has not returned. The sequencer's bound is what makes the shipped sequencer's own claim true; the backstop is what keeps the manager settling if an injected or production primitive set violates its contract in a way the internal race cannot observe.
- Cancellation is checked on entry, before every wait, before every bounded primitive call, and in the same synchronous step as every signal send. After cancellation or the deadline the sequencer sends no signal and returns the last completed audit, or the non-confirming audit when none completed. `bounded` cancels its per-call scheduler handle and removes its abort listener in `finally`, and the sequencer cancels `overallHandle`, removes its caller-abort listener, and aborts `sequencerController` in `finally`, so no scheduled deadline callback, listener registration, detached timer, retry, abandoned primitive continuation, unhandled rejection, or deferred signal survives the return, and nothing can signal a later replacement generation.
- `ProjectRuntimeConfig` and `PROJECT_RUNTIME_DEFAULTS` gain `stopAuditAllowanceMs` (default 1,000 ms) with the same positive-safe-integer validation as its siblings, and `runtimeStopOverallBoundMs(config)` returns `gracefulShutdownMs + forceShutdownMs + stopAuditAllowanceMs`. `preSignalAllowanceMs` and `settlementAllowanceMs` are derived inside the sequencer from `auditAllowanceMs` by the formulas above and are never separate configuration.

### Owned-descendant attribution and its proof ceiling

- **Attribution definition.** A process is an owned descendant of a runtime exactly while it is a member of the process group led by that runtime's exact recorded root identity (PID plus recorded process start time). The audit field keeps its delivered name `processGroupAbsent` and its delivered meaning: no process currently carries the owned process-group identifier.
- **What the product proves.** The bounded `/proc` scan enumerates every process whose process-group identifier equals the owned identifier, so `processGroupAbsent` proves that no attributable owned descendant remains at audit time. Combined with `processAbsent` (exact root identity) and `listenerAbsent` (bounded loopback connection attempt), that is the complete AC-1 confirmation triple.
- **Recorded ceiling.** A descendant that calls `setsid` or `setpgid` before the scan samples it leaves the owned group and is no longer attributable to the runtime by any bounded local mechanism Ascend has; Issue #39 excludes adopting or terminating processes Ascend cannot attribute, so BL-017 neither claims nor pursues them. Signalling is additionally restricted to an attributable group, so a process-group identifier that could have been recycled is never signalled; the residual window is bounded by kernel PID-space wraparound and is recorded, not hidden.
- **Where a stronger proof is honest.** The designated real-host episode captures the owned group's exact members with their own process start identities immediately before the stop, and asserts each recorded member absent after it. The independent residual-audit CLI re-probes the root identity, every recorded member identity, the owned group, and the listener out of process. That closure is identity-bearing and measured, so it lives in the disposable designated artifacts, never in the deterministic committed matrix.
- Documentation, the evidence schema, the designated episode, the residual audit, the validator, and the mutation table state the definition and the ceiling in the same words. No surface renames process-group absence into a stronger descendant claim.

### Reuse-observation ownership recheck

- `start()`'s running-reuse branch gains one helper, `reuseOwnershipFailure(current): RuntimeFailure | undefined`, defined exactly once and called exactly twice: immediately after `await current.ready.process.isAlive()` and immediately after the awaited health verdict.
- The helper returns `undefined` only when `entries.get(current.projectId)` is the exact `current` object with state `running` and the same `generation`. Otherwise it classifies:
  - `shuttingDown` → `RuntimeFailure('manager-shutdown')`.
  - installed entry is `failed` → that entry's retained failure, so the caller sees the winner-consistent failure.
  - any other mismatch — `stopping`, `registered`, absent, `starting`, or a different `running` generation — → `RuntimeFailure('runtime-stopping')`, because the only contract-valid replacements of an exact `running` entry are the guarded terminal transition, a selected stop claim and its settlement, and shutdown.
- When the helper returns a failure the caller throws it immediately: no snapshot is returned, `transitionRunningToFailed` is not called, nothing is terminated, audited, mutated, or emitted. The delivered BL-016 source guard therefore still counts exactly one `transitionRunningToFailed` definition and exactly three call sites (two with `current`, one with `entry`).
- Both winner orders are covered: a health verdict that resolves *before* the stop claim reuses normally, and a success or failure verdict that resolves *after* the claim yields the bounded stop-in-flight failure. The proxy, which calls `start` and then `ownsSnapshot`, receives its existing bounded typed precommitment failure, and a released generation already fails `ownsSnapshot`, so no stale forwarding is possible.

### Shutdown interaction and the cleanup re-attempt rule

- `shutdown()` keeps its memoization, its `starting`-entry abort, its running-entry termination loop, its audit aggregation, its tracked-task settlement loop, and its zero-count post-conditions.
- Two changes are made, in this order inside the existing sequence: after awaiting the `starting` operations and **before** the ownership sweep, shutdown awaits every tracked in-flight stop operation; and the sweep's memoization test is corrected.
- Corrected sweep rule: a prior cleanup audit may be reused for an ownership record only when it matches that exact `pid:processStartTime:port` key **and** reports `processAbsent && processGroupAbsent && listenerAbsent`. An unconfirmed or missing prior audit forces `record.process.terminate(...)` for that exact record and records its own audit. The retained ownership left by an unconfirmed stop or by a termination fault is therefore genuinely re-attempted, including when the entry is now `failed` and the running-entry loop skipped it.
- Awaiting in-flight stops is bounded twice over: the sequencer abandons any primitive still pending at its own deadline, and the manager backstop abandons a `terminate` promise that has not returned by the overall bound, so shutdown cannot block on a non-settling termination or on a non-settling primitive.
- **Cleanup cardinality is per phase, not per identity.** One claimed generation has exactly one stop-phase termination and at most one stop-phase cleanup audit; two cleanup attempts for one exact owned identity never run concurrently, because shutdown awaits every in-flight stop before its sweep; and no path terminates or audits an identity again once a cleanup audit confirmed its release, because that generation's ownership record is deleted. A generation whose stop phase ended unconfirmed, faulted, or deadline-abandoned deliberately retains its ownership record and is re-attempted **exactly once** by the sweep, which therefore records a second termination and a second cleanup audit for that same generation by design. Evidence asserts these per-phase counts; it never asserts that an identity is terminated or audited at most once overall, and it never records the intended re-attempt as an uncontrolled duplicate.
- Per-phase cardinality is recorded as evidence rather than asserted loosely:

| Scenario | Stop-phase terminate / cleanup | Shutdown-phase terminate / cleanup | Final shutdown status |
|---|---|---|---|
| confirmed stop, then shutdown | 1 / 1 | 0 / 0 (ownership record deleted) | `ok` |
| unconfirmed stop, then shutdown | 1 / 1 | 1 / 1 (prior audit does not confirm absence) | honest: `ok` only if the re-attempt confirms absence |
| termination fault, then shutdown | 0 / 0 | 1 / 1 (no prior audit) | honest, from the re-attempt's audit |
| termination deadline, then shutdown | 0 / 0 | 1 / 1 | honest, from the re-attempt's audit |
| shutdown during an in-flight stop | 1 / 1 (awaited to completion) | 0 / 0 when confirmed, 1 / 1 when not | honest |

- A peer project's ownership record and a later replacement generation are unaffected: the sweep iterates exact ownership keys, and every termination revalidates its exact root identity before signalling.

### Concurrency contract

| Interleaving | Required settlement |
|---|---|
| Concurrent same-project stops | Exactly one claim. The second and later callers join the installed `stopping` operation and receive the same settled result or rejection. Exactly one `runtime.stop.requested`, one stop-phase `terminate` call, at most one stop-phase cleanup audit, one terminal event. |
| Stop versus `start` for the same project | If stop claims first, a later `start` finds `stopping` and throws `RuntimeFailure('runtime-stopping')`; it never reuses the claimed snapshot, cancels the release, or launches a replacement. If `start` installed a `starting` entry first, stop returns `rejected` `start-in-progress` and the start continues to readiness. |
| Stop versus an awaited reuse observation | The observation rechecks its exact entry and generation after each await. If the stop claimed or released that generation, the observing caller receives `runtime-stopping` and never the doomed snapshot; if a terminal winner installed a retained failure, it receives that failure; if shutdown began, it receives `manager-shutdown`. The observation mutates, terminates, audits, and emits nothing. |
| Stop versus reuse-health failure | Both contend on the exact entry and generation. Exactly one wins. A losing health contender mutates nothing, terminates nothing, audits nothing, emits nothing, and surfaces the winner-consistent failure to its caller. A losing stop returns `rejected` `failure-retained`. |
| Stop versus post-readiness exit settlement | Same discipline. If the exit contender wins, the entry is `failed` with its exit category and stop returns `rejected` `failure-retained`. | Stop versus proxy acquisition | The proxy is a consumer only. | Stop versus a replacement generation | A replacement can only be created after the stop settles, and the settled stop holds only the claimed `ready` object. | Stop versus manager shutdown | A stop requested while `shuttingDown` returns `rejected` `manager-shutdown`. | Stop versus a peer project | Entries, operations, claims, cleanup results, ownership records, and events are keyed by stable project ID; a stop touches only its own key and its own owned process group. |

### Bounds

- Graceful opportunity: `ProjectRuntimeConfig.gracefulShutdownMs` (default 2,000 ms), measured on the monotonic termination clock from the `SIGTERM` send the signal primitive confirmed delivered, not from sequencer entry and never from a wall clock. The full period is offered after that delivered send and no escalation occurs before it elapses, so `sigkillAt - sigtermAt >= gracefulShutdownMs` on every delivered escalation.
- Escalation window: `ProjectRuntimeConfig.forceShutdownMs` (default 2,000 ms), measured the same way from the `SIGKILL` send the signal primitive confirmed delivered, so the full force window follows that delivered send.
- Refused signals: a send the host refuses because the owned group is already gone opens no window. A refused graceful signal is bounded by one settlement audit inside `gracefulRefusedAt + gracefulShutdownMs`, which leaves the force window and the settlement allowance unspent; a refused force signal returns synchronously. An unexpected signalling failure is a termination fault and settles through that path, not through a window.
- Audit allowance: `ProjectRuntimeConfig.stopAuditAllowanceMs` (default 1,000 ms), validated as a positive safe integer, bound into every adapter-created `terminate`, and enforced by the sequencer's overall deadline. It is an internal runtime bound, not an environment variable, flag, or deployment setting. The sequencer splits it into `settlementAllowanceMs = Math.max(1, Math.floor(auditAllowanceMs / 10))` (100 ms by default), reserved for the two synchronous inter-phase settlements and the final return, and `preSignalAllowanceMs = auditAllowanceMs - settlementAllowanceMs` (900 ms by default), which bounds all pre-signal observation. A pre-signal observation that cannot complete inside its allowance returns `unconfirmed` without signalling instead of shortening the graceful window.
- Documented finite overall bound: `runtimeStopOverallBoundMs(config)` = 5,000 ms by default, unchanged, measured on the monotonic termination clock, and it still bounds the sum of the pre-signal allowance, the full graceful window, the full force window, and the settlement allowance; both refusal paths settle strictly inside it. Every accepted stop — successful, unconfirmed, faulted, or deadline-settled — settles within it, enforced at exactly two independent points: the sequencer's own deadline, armed by the trusted synchronous scheduler independently of every awaited primitive, which aborts the sequencer and abandons any bounded call still pending, and the manager's `sleep`-based backstop, which abandons a `terminate` promise that has not returned. Neither point is removed in favour of the other.
- Rejected, no-managed-runtime, and already-stopped results settle without process work and are bounded by one persistence read plus one synchronous map read.

- Each row records: `scenario`; `executionIds` (`runtime`, `api`, `home`); `outcome` (`stopped` | `already-stopped` | `rejected` | `invariant-fault` | `not-attempted`); `rejectionCategory` or `null`; `releaseMode` (`already-absent` | `graceful` | `escalated` | `unconfirmed` | `null`); the `auditTriple` or `null`; `attribution` (`ownedGroupSampled`, `ceilingRecorded`); `signalOrder` (ordered `graceful` / `force` classes), `forceAfterGracefulBound`, `signalDelivery` (`graceful` and `force` each one of `delivered`, `refused`, or `not-attempted`, plus `signalFault` of `none` or `raised`), `signalTimeline` (`sigtermAt`, `sigkillAt`, `gracefulWindowMs = sigkillAt - sigtermAt`, `forceWindowMs`, `preSignalMs`, each a monotonic elapsed reading recorded as a declared-bound class rather than a measured duration or a wall-clock timestamp, and each present only for a `delivered` signal), and `primitiveBounding` (`awaitedCallsBounded`, `abandonedCalls`, `incompleteAuditsDiscarded`, `deadlineSource` of `trusted-scheduler`, `clockSource` of `monotonic`, `callerPreAborted`, `signalsAfterDeadline: 0`, `timersSurvivingReturn: 0`, `unhandledRejections: 0`) or `null`; `elapsedClass` (`zero` | `within-graceful` | `within-overall`) with `withinDeclaredBound: true`; `runtimeState`, `apiState`, `homeState`, and `failureCategory`; ordered `events` with cardinality counts and `loserEventCount`; `terminateCallsByPhase` and `cleanupRecordsByPhase` for the `stop` and `shutdown` phases; `identitiesCreated`, `identitiesTerminated`, `restarts`; `registrationRowCount` and `registrationDigests` (`before`, `after`); `peerDigests` and `controlDigests` or `null`; `fixtureDigests` per declared fixture; the pre-declared four-class `inventory`; `residualCount`; and `assertionCount`.
- Serialization is deterministic: stable key order, fixed `bl017-<surface>-<scenario>` execution IDs, no wall-clock timestamps, no measured durations, no absolute paths, PIDs, ports, authorities, or tokens. Every `signalTimeline` position is a monotonic elapsed class, never a civil-time value, and is labelled monotonic wherever it is documented or read. Measured values live only in the disposable timing artifact.
- The matrix test writes the disposable copy, asserts SHA-256 equality with the committed copy, re-reads the committed copy, reparses and revalidates it, and asserts that serializing the same validated matrix twice is byte-identical. Regeneration therefore leaves the tracked file unmodified.
- The validator rejects: a wrong schema version; a missing, duplicate, or reordered scenario; a duplicate execution or event ID; a `Stopped` state without a complete confirmed audit triple; an unconfirmed release reported `Stopped`; an `already-stopped` outcome recorded for a scenario whose entry was not released by a confirmed stop; a `no-managed-runtime` row recorded as a success; a force signal recorded before the declared graceful bound; a `signalTimeline` whose graceful window between the recorded `SIGTERM` and `SIGKILL` is shorter than the declared `gracefulMs`, or whose force window is shorter than the declared `forceMs`, or whose pre-signal span exceeds the declared pre-signal allowance; a `deadlineSource` other than `trusted-scheduler`; a `clockSource` other than `monotonic`, or a `signalTimeline` position expressed as a wall-clock value; a `signalTimeline` graceful window, force window, `sigtermAt`, or `sigkillAt` recorded without the matching `signalDelivery` value `delivered`; a `signalDelivery` of `refused` or `not-attempted` recorded as a delivered signal, a `signalOrder` entry, or an escalation; a `releaseMode` of `escalated` without `signalDelivery.force` equal to `delivered`; a `releaseMode` of `graceful` without `signalDelivery.graceful` equal to `delivered`; a `releaseMode` of `already-absent` recorded alongside any `delivered` signal; a row whose refused graceful signal records more than one settlement audit, opens a graceful or force window, or attempts an escalation; a row whose refused force signal records a force window or any outcome other than `unconfirmed`; a `signalFault` of `raised` recorded as anything other than the documented termination-fault settlement; a row recording a signal, an audit, or a wait for a termination whose caller signal was already aborted on entry; a non-zero `timersSurvivingReturn` or `unhandledRejections`; a signal recorded after cancellation, after the sequencer deadline, or from an abandoned primitive continuation; a confirmed release derived from an audit whose component observations did not all complete; more than one stop-phase termination or more than one stop-phase cleanup audit for one generation; concurrent stop-phase and shutdown-phase cleanup for one exact identity; a shutdown-phase termination for a generation whose stop-phase audit confirmed absence; more than one shutdown-phase re-attempt for one retained generation; a shutdown phase that reuses an unconfirmed prior audit instead of re-attempting; an `invariant-fault` row carrying a terminal event, an entry mutation, or an extra cleanup record; a non-catalog event name; a wrong terminal-event count; a non-zero loser event count; an attribution record whose ceiling is absent or whose field claims more than process-group membership; a changed registration or fixture digest; a changed peer or control digest; an empty inventory; a non-zero residual count; and any protected-value match.

### Inventory, ownership, and cleanup

- Each scenario declares, **before execution**, a non-empty bounded inventory with four classes: runtime processes and listeners, declared unrelated controls, registration resources (database plus sidecars), and disposable fixtures. The matrix records the inventory alongside the scenario result; an empty or post-hoc inventory fails validation.
- Every inventory item is classified `product-registration-during-scenario` or `validation-owned-temporary`. Assertions require product registrations to survive the scenario and require every validation-owned temporary resource to be absent at final teardown, recorded as `residualCount: 0`.
- Fixture manifests reuse the existing `apps/api/test/project-registration-fixture-helper.ts` schema (relative membership, node type, permission mode, recorded timestamps, content digest, symlink target). The schema is fixed before execution; before-and-after digests must be equal for every node of every declared fixture.

### Proof ceilings

- Manager-level race ordering, join behavior, shutdown interleaving, idempotency, and the deadline backstop are proven with the existing injectable process, port, health, clock, and event dependencies. This is deliberate: deterministically producing a real host race with a fixed winner is neither repeatable nor bounded.
- AC-2's graceful bound, escalation point, force window, audit allowance, and cancellation are **not** proven by a fake's returned label. They are proven by executing the shipped `terminateOwnedRuntimeGroup` over injected termination primitives that record every identity read, group read, listener probe, signal send with its delivery result, and delay against a controlled clock standing in for the production monotonic source, so validation runs the same control flow production runs. Because the injected clock is the same trusted `now()` contract the production `performance.now()` binding satisfies, the phase arithmetic proved deterministically is the phase arithmetic shipped; what the injected clock cannot prove — that the production binding is monotonic rather than `Date.now` — is proved by the source and contract guard instead. The self-bound is proven against a primitive that never settles and against a primitive that ignores its cancellation signal — including the `delay` the sequencer polls with — not merely against a slow-returning one, so the sequencer's deadline is shown to hold without any cooperation from any awaited primitive. The deadline itself is armed by the trusted synchronous scheduler, and both the injected clock-driven scheduler and the real production `setTimeout` wiring are exercised, so the mechanism proved is the mechanism shipped. A fake `terminate` may still order manager-level races, but it may never be the evidence for AC-2 sequencing.
- The designated-host episode proves what fakes cannot: that a selected stop of a real Ascend-managed code-server leaves its exact recorded PID/start-time identity absent, every process-group member recorded immediately before the stop absent, its owned process group absent, and its loopback listener refusing connections, with the registration and fixture unchanged. It is one bounded scenario; exhaustive host-process proof is explicitly not required.
- Descendant attribution is bounded by process-group membership. A descendant that leaves the owned group before the audit samples it is unattributable, and BL-017 does not adopt or terminate unattributable processes. That ceiling is recorded in the ADR, the core-component, the evidence schema, the designated episode, the residual audit, and the shipped documentation, in the same words.
- The independent residual-audit CLI re-probes the retained identities and listener out of process, so the episode is not self-certifying.
