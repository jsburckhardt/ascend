## Problem Statement

Issue #45 concerns a selected registered project whose authoritative runtime is `Running` or `Failed`, including an API-restart-reconciled adopted runtime. Delivered Close removes the stopped project's registration only. The issue requires selected runtime resources to be resolved before a completed Close while preserving the project directory. Its stated exclusions are archive, undo, bulk Close, project-file deletion, automatic lifecycle policy, recovery beyond delivered API-restart reconciliation, persisted runtime handles or state, multi-host operation, and adoption or termination of a process Ascend cannot exactly attribute.

Research context is branch `feat/45-close-a-running-or-failed-project` at `2f51f768c2fa8b80b2d8cb0347ee22196e9f9e13`. Before this artifact was created, there were no `project/work-items/45-*` directories; this is the sole resolved work-item directory for Issue #45.

## Repository Findings

### Current Close boundary

- `apps/api/src/project-close.ts` accepts a non-empty stable ID and calls its metadata-only `ProjectCloseRepository`; it has only `invalid_project_id` and `project_close_failed` errors and has no runtime manager, process, proxy, or reconciliation dependency.
- `apps/api/src/project-persistence.ts` serializes `closeProject` with `closeTail` and runs a transactional `deleteById`. Its complete result vocabulary is `{ disposition: 'closed', id }` or `{ disposition: 'project_not_found' }`; `apps/api/src/project-library.ts` delegates directly to it.
- `apps/api/src/routes/projects.ts` maps `DELETE /api/projects/:id` to `200 { id, disposition: 'closed' }`, `400 invalid_project_id`, `404 project_not_found`, or `500 project_close_failed`. It emits `project.closed` immediately after durable deletion and never accesses `fastify.projectRuntime`.
- `apps/api/test/project-close-service.test.ts` and `apps/api/test/project-close-route.test.ts` cover one-row deletion, transaction rollback, safe/redacted response shapes, repeated absence, and eight concurrent DELETEs with one 200 plus seven 404s. They do not construct a running, starting, failed, adopted, reconciling, or proxy runtime.
- `apps/api/test/project-close-non-mutation.test.ts` proves stopped-scope Close paths preserve a non-empty recursive fixture manifest (membership, bytes or non-dereferenced link targets, modes, and mtimes) across cancel, success, unknown, persistence failure, retry, absence, and concurrent DELETEs. It does not inventory an active runtime, listener, proxy connection, lifecycle operation, or reconciliation record.

### Current behavior by state

- **`Stopped`:** Close deletes the library row only. A `registered`/`released` manager entry has no active runtime, but Close neither reads nor removes that memory entry. Existing stopped Close removes one registration, returns the delivered 404 result after removal, and does not launch or signal a runtime.
- **`Running`, including adopted:** Close can return 200 without an exact process identity claim, group release, listener probe, ownership cleanup, proxy drain, or runtime-state coordination. `ProjectRuntimeManager` retains its entry and ownership. Fresh stable-route acquisition calls `ProjectLibrary.findById` in `WorkbenchProxyManager.resolveTarget`, so the removed registration yields unknown-project rather than a new runtime; existing HTTP/WebSocket proxy resources are only drained in global proxy `shutdown()`.
- **`Starting`:** `ProjectRuntimeManager.start` installs `starting`, then later installs a running snapshot. That settlement does not re-read the registration after Close deletes it; Close neither aborts the start controller nor invalidates its generation. A later running entry/listener can consequently be installed for a deleted registration.
- **Retained `Failed`:** a failed manager entry can retain exact ownership after unconfirmed Stop or Restart release, a pending admission, a quarantined identity, and cleanup evidence. Close neither reads nor resolves those structures and can remove the row while they remain in memory.
- **Reconciliation pending or unresolved:** `apps/api/src/app.ts` begins required reconciliation before routes register. Reconciling projects publicly project `Starting`; unresolved projects project `Failed` with `reconcile-unconfirmed`. Stop and Restart have bounded reconciliation rejections; Close has no equivalent check. An adopted runtime becomes a normal manager-owned running entry, and `docs/api-restart-reconciliation.md` documents its lack of automatic exit watching.
- **After API interruption:** reconciliation uses `ProjectLibrary.list()`. A Close-deleted project is absent from reconciliation order, and current code has no selected survivor exclusion, release, or retained public result for its prior runtime.

### Lifecycle, proxy, public state, and UI observations

- `apps/api/src/project-runtime-manager.ts` is the single current-process lifecycle owner. It holds stable-ID keyed entries, `pid:processStartTime:port` ownership, cleanup outcomes, start/Stop/Restart operations, admissions, quarantines, reconciliation, and generation guards in instance memory.
- `apps/api/src/project-runtime-contract.ts` limits public state to `Stopped`, `Starting`, `Running`, and `Failed`. `reportPublicStates()` is a synchronous read-only projection: missing/registered is `Stopped`; starting/restarting/reconciling is `Starting`; running/stopping is `Running`; retained failure is `Failed`. Persisted metadata remains exactly `id`, `name`, `canonicalPath`, and `createdAt`.
- `apps/api/src/routes/project-runtime-state.ts` orders its projection from durable library IDs. A retained manager entry after current Close has no public row: current library and runtime-state observations can therefore omit an owned runtime.
- Stop and Restart claim exact entries synchronously, join same-project work, maintain generation and admission safeguards, and perform bounded exact release/audit. `apps/api/test/runtime-stop-manager.test.ts` and `apps/api/test/runtime-restart-manager.test.ts` prove retained-failure, stale-settlement, incomplete-release, admission, quarantine, and shutdown behavior. Close has no comparable manager operation or result.
- `apps/api/src/project-runtime-process.ts` owns launch, exact process-start identity, group attribution, listener audit, bounded graceful/force termination, and launched/adopted cleanup. The delivered release observation is `processAbsent && processGroupAbsent && listenerAbsent`; processes outside the exact recorded group are not attributable.
- `apps/api/src/workbench-proxy-manager.ts` accepts a persisted project plus exact running snapshot, inventories HTTP work, raw sockets, and bridged WebSockets by opaque project token, and drains them only in its global five-second shutdown. It has no per-project Close operation.
- `apps/api/src/app.ts` separately creates library, manager, proxy, Close service, and registration. Global shutdown orders proxy, manager, registration, then library. Existing Close is not in that order.
- Existing Close emits `project.closed`/`project.close.failed`; no manager outcome precedes `project.closed`. The NFR-015 event contract and `CORE-COMPONENT-260808-structured-runtime-logging` reserve typed Start, Stop, Restart, health, and reconciliation names and require opaque tokens, bounded categories, redaction, and no raw runtime details.
- `apps/web/src/App.tsx` renders Close for every registered card regardless of public state and disables it only for that card's pending Restart. `apps/web/src/use-project-home.ts` keeps Close in the global Home owner lane; `openClose` refuses another ordinary owner, an existing Close dialog, or a same-ID pending Restart, while `beginClose` uses the 10,000 ms `closeProject` transport in `apps/web/src/projects.ts`.
- Pending Close blocks Start-like registration and Stop through that global owner, and blocks Restart for every project through `value.close !== undefined`; rendered controls are not uniformly disabled by those guards. The controller neither checks runtime state before Close transmission nor refreshes runtime state on Close success.
- The existing dialog is `aria-modal`, non-destructive, keyboard/focus-trapped, cancels before transmission, presents pending state, prevents duplicate confirmation, recovers focus, and gives safe failure/unknown messages. `apps/web/src/App.close.test.tsx` and `apps/web/src/use-project-close.test.tsx` prove those stopped-scope flows. Unknown Close refreshes only the project list, not runtime state; `apps/web/src/runtime-state.ts` accepts only the four public values and requires exact list alignment.

## Risks and Open Questions

- **Success ordering:** current Close commits deletion and emits `project.closed` before any resource fact; running, starting, retained-failed, adopted, reconciling, or unresolved manager state can therefore disagree with library and public list observations.
- **Stale lifecycle work:** Close does not claim or invalidate a manager entry. Start, Stop, Restart, reconciliation, readiness, exit, proxy, persistence, or cleanup continuations have no Close-specific ownership guard and can settle after deletion.
- **Interruption:** post-deletion API reconciliation has no durable subject against which to account for a selected survivor.
- **UI admission/recovery:** the global Close lane and per-project Restart lanes have non-equivalent rendered and controller admission behavior; unknown Close currently refreshes list only.
- **Proof ceiling:** existing Close proof is stopped metadata/non-mutation proof, while Stop/Restart/reconciliation prove separate lifecycle contracts. There is no existing Close evidence that joins runtime, proxy, state, event, reconciliation, interruption, privacy, peer, and residual facts required by the issue.
- **Architecture assessment belongs to Plan:** this is classified as an `issue`, not an architecture decision or core component. It crosses accepted lifecycle, persistence, proxy, event, reconciliation, and Home boundaries; Plan must assess whether an existing global contract needs an ADR or core-component change. Research makes no decision and proposes no artifact, API shape, state machine, task, test, or solution.
