# Research Brief: BL-014: Preserve sessions while switching among projects

## GitHub Issue
- **Issue:** #33
- **Title:** BL-014: Preserve sessions while switching among projects
- **Work Item:** project/work-items/33-bl-014-preserve-sessions-while-switching-among-projects

## Scope Classification
- **Scope Type:** issue

## Problem Statement
Issue #33 closes the gap between immediate three-project isolation and the MVP persistence hypothesis. A user must start exactly three registered projects once, leave and revisit them through Project Home, and retain each original runtime identity and project-specific terminal, file, editor, Git, and navigation context. The bounded scenario also distinguishes runtime/server-owned continuity from browser-local restoration and exercises history, reload, fresh-context direct linking, and client closure without expanding into lifecycle controls, performance, broader scale, or multi-user behavior.

This scope directly implements PRD `GOAL-003`, `FR-010`–`FR-013`, `AC-015`–`AC-018`, and Metric 2. The PRD requires a three-project switch with no lost or wrongly associated terminal/editor context and targets 100% preservation in MVP acceptance runs (`PRD.md:365-372`, `PRD.md:521-566`, `PRD.md:1126-1166`, `PRD.md:1508-1519`).

## Acceptance Criteria

**Core**
- [ ] One designated Chromium scenario registers exactly three repository-defined Git fixtures A, B, and C; starts each project exactly once through the existing Home/Open stable-route flows before switching begins; and records each project’s initial immutable runtime identity (PID, process start time, port token, and stable route) plus project-specific Explorer, editor, terminal, and Git evidence.
- [ ] In A, the scenario opens one known file and starts one repository-defined long-running terminal command that emits an increasing sequence every 250 ms to the visible terminal and disposable untracked output, with a maximum 90-second run. The command PID and a visible sequence value are recorded before leaving A.
- [ ] After all three initial starts, with A displayed, the scenario navigates A→Home→B→Home→C→Home→A using keyboard-only Projects/Open actions. Exact URLs, focus targets, start/reuse/stop counts, and runtime identities are recorded at every transition; every Home navigation has zero runtime stop or shutdown invocations.
- [ ] In B and C, the scenario opens distinct known files and runs bounded project-specific terminal commands that prove `pwd -P`, `git rev-parse --show-toplevel`, branch/status, and a unique sentinel. B’s and C’s state does not appear in A or in each other.
- [ ] While A is not the displayed workbench, the scenario independently samples A’s command PID/process liveness and output sequence at least twice. The same command PID remains live and the sampled values advance; evidence collection does not interact with A’s browser workbench in a way that restores it.
- [ ] When the scenario returns to A, the runtime identity and long-running command PID match the initial records, the visible terminal shows a later sequence, the same known file remains visibly open, and the canonical cwd, Git, and sentinel values remain A-specific. A has no second runtime or start.
- [ ] After that switching sequence, the scenario revisits B and then C once each and proves that each retains its original runtime identity, known open file, terminal state/output, canonical cwd, Git, and sentinel. Together with the B, C, and A entries in the preceding post-start switching sequence, these are exactly five Projects/Open Workbench re-entries, and all five use reuse only; reload, history, and client-reconnection checks are recorded separately from this count.
- [ ] Project Home remains keyboard-usable through the recorded Projects/Open actions while all three runtimes are active, lists each project card exactly once with the expected project identity and focus target, and renders no runtime-control UI beyond the existing Open/Close boundaries. Close, Stop, and Restart are not invoked.

**Edge Cases**
- [ ] One bounded Back-then-Forward browser sequence during switching restores the correct Home or Workbench surface without a duplicate start, a stop, cross-project state, or a runtime-identity change.
- [ ] One controlled page reload on A and one fresh browser-context direct link to B prove server-owned runtime/session reconnection. The fresh context clears client storage, cache, and service workers and must reconnect to the same B runtime. Evidence records exactly one closed outcome for visible server-owned file/terminal restoration: restored by the existing workbench, or unsupported by the existing workbench with the bounded observed behavior retained. Browser-local editor restoration is classified separately and does not broaden the server-session claim.
- [ ] A and C remain usable when the B browser page or context is closed. Closing the client connection does not stop B’s runtime; reopening B reuses the same runtime identity and server-owned state, with visible file/terminal restoration evaluated under the same closed restored-or-unsupported outcome defined for the fresh-context check.
- [ ] For each Workbench entry and reconnection, event and network evidence uses safe project tokens, identifies the exact Management and ExtensionHost socket roles, remains under the stable project prefix, exposes zero internal ports or authorities on public surfaces, and has unambiguous project attribution.

**Verification**
- [ ] Bounded unit, component, and API validation executes navigation generation, history, no-stop rules, and runtime-manager per-ID reuse. Evidence validators reject assigned or static identity/state rows, duplicate starts, cross-token events, and unchanged sequence constants.
- [ ] Retained evidence maps every transition and project to runtime, command, file, Git, sentinel, socket, event, focus, and URL values; includes A’s away samples, return assertions, browser close/reconnect, measured cleanup, and pre/post fixture-manifest equality; and complies with the existing restricted/public evidence policy.
- [ ] Cleanup terminates the scenario’s terminal commands, browser contexts/pages/sockets, all three runtime groups/listeners, API/web services, databases/sidecars, and fixtures. The scenario-owned residual audit reports zero for every project/resource class, while the unrelated control listener remains unchanged until its separate cleanup.
- [ ] Documentation records the exact switching sequence, persistence ownership and limits, no-stop semantics, the server-versus-browser state boundary, commands and finite bounds, artifacts, cleanup, and observed result. It explicitly defers BL-015 performance benchmarking and lifecycle features.
- [ ] The repository’s full validation and the existing BL-010, BL-011, BL-012, and BL-013 regression gates all complete successfully.

## Constraints

- The issue is bounded to exactly three projects and the exact interaction/counting semantics in its criteria. BL-015 performance benchmarking, lifecycle UI and Stop/Restart, API restart reconciliation, more than three projects, auto-sleep, cross-browser/tablet coverage, and multi-user behavior are excluded.
- Project Home and the existing stable URL are the navigation boundaries. Home/Projects and client disconnection must not call runtime stop or application shutdown; only application close currently invokes proxy/runtime shutdown (`apps/api/src/app.ts`).
- There may be at most one active Ascend-managed runtime per stable project ID. Reuse requires the same live process identity and passing health check. Runtime failure permits only a later explicit replacement, not automatic retry (`CORE-COMPONENT-260808-runtime-lifecycle-error-handling.md`).
- Runtime identity, port, owner token, process handles, and lifecycle state remain memory-only. API shutdown stops owned runtimes; continuity across API restart is not part of Issue #33. Runtime-scoped user data is ephemeral and removed with the runtime.
- Existing architecture delegates files, editors, terminal processes, Git UI, and restoration behavior inside a running workbench to code-server. Ascend owns navigation, stable routing, and runtime lifecycle; browser UI state and server-owned session state are not interchangeable.
- Browser-visible routes use the percent-encoded stable project ID; lifecycle/proxy events use one deterministic opaque project token. Raw canonical paths, internal ports/authorities, credentials, commands, terminal output, payloads, and reconnection tokens are excluded from public logs/evidence except for the existing narrowly bounded restricted artifact policy.
- All Ascend-owned requests and WebSockets remain same-origin under `/projects/{projectId}/workbench/`; the existing exact Markdown webview exception remains separate. Management and ExtensionHost roles are classified from control payloads and payload/token values are discarded.
- The designated environment is desktop Chromium on the repository Ubuntu host with code-server 4.131.0. Existing proof configuration disables extension marketplace traffic with `EXTENSIONS_GALLERY={}`.
- Long-running and project-specific commands, browser operations, cleanup, and the complete scenario must remain finite. The A sequence command has the issue-defined 250 ms cadence and 90-second maximum.
- Cleanup must use exact owned PID/start identity, groups, listeners, sockets, contexts, databases, fixtures, and command identities; process-name killing and port sweeping are prohibited by existing runtime and proxy contracts.
- Root `justfile` recipes are the project command interface. Full validation includes all merged BL-010 through BL-013 regression gates and the baseline terminal parity proof.
- The two supplied pre-flight failures are full-suite validation stability gaps, not product failures. The request permits a later Plan to include only minimal prerequisite corrections needed for stable full-suite validation; this Research Brief selects no correction or implementation approach.

## Risks and Open Questions

- **Full-suite stability:** The two pre-flight runs failed in different already-merged regression areas while focused/other tests passed. Root causes remain unknown. Their recurrence under the longer Issue #33 scenario could prevent the required full-validation result even when product assertions pass.
- **Failure-1 event race:** It is unresolved whether the missing/mismatched category event reflects suite contention, incomplete operation settlement, shared generated state, or another test-orchestration interaction. No product conclusion is supported yet.
- **Terminal-parity timeout:** The second failure artifact identifies only the episode deadline, not the slow operation. It remains unknown whether contention affected workbench startup, browser readiness, terminal command capture, tool execution, or another bounded step.
- **Mutable evidence state:** Unit residual validation can overwrite ignored BL-012 browser evidence with fixture-shaped data before a later designated gate regenerates it. A full run that exits early can therefore leave current artifacts unsuitable as proof of the last successful designated browser run.
- **Server versus browser ownership:** Existing code and BL-012 behavior strongly support terminal process/layout continuity on the running server, including a fresh storage-cleared context. The ownership and fresh-context visibility of open editor files/tabs remain unresolved and must be reported only as the issue-defined restored-or-unsupported observed outcome. Browser-local editor restoration cannot expand the server-session claim.
- **Reconnection terminology:** Existing BL-011 fresh workflows require `reconnection=false` in the VS Code control request, while Issue #33 uses “reconnection” for returning/reloading/direct-linking to the same server runtime. Whether any browser action invokes protocol-level reconnection rather than a fresh Management/ExtensionHost pair is an observed-runtime question, not established by terminology alone.
- **Runtime replacement boundary:** The port-qualified ephemeral user-data directory is deleted when a runtime exits. Session preservation therefore applies only while the original runtime remains running; it cannot be inferred across failure, explicit replacement, application shutdown, or API restart.
- **Timing headroom:** The issue A command has a 90-second maximum while three initial starts, exact switching, five re-entries, history, reload, fresh context, client close/reopen, evidence retention, and cleanup all share finite bounds. Current repository evidence does not establish the duration distribution of that combined scenario.
- **State contamination:** Existing BL-013 proves immediate A/B/C isolation in separate contexts, but not repeated single-page Home switching. The exact point at which browser or server workspace state is selected on repeated stable-route acquisition remains an observation to classify without assuming isolation implies persistence.
- **Architecture documentation impact:** The stable-proxy core-component and runbooks currently state that BL-014 continuity is excluded. It is unresolved which existing architecture documents require factual scope updates after delivery; Research makes no architectural decision.
- **Generated fixture definition:** The issue requires repository-defined Git fixtures A/B/C. BL-013 currently creates disposable Git repositories at runtime rather than keeping three tracked Git fixture directories. The precise meaning of “repository-defined” versus “repository-tracked” is not further specified by repository documentation.
