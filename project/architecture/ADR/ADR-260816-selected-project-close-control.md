# ADR-260816-selected-project-close-control: Remove One Selected Project Through a Manager-Owned Close Control That Confirms Release Before Durable Removal

## Status

Accepted

## Context

FR-014, AC-019, AC-020, DD-004, CON-005, and NFR-018 require Close to remove a project from Ascend, stop its Ascend-managed workbench resources, and leave the project directory unchanged. BL-009 delivered only the metadata half of that requirement: `DELETE /api/projects/:id` deletes one library row through `ProjectCloseService`, emits `project.closed`, and never touches `fastify.projectRuntime` or `fastify.workbenchProxy`. Every subsequent runtime issue narrowed its own scope and deferred the rest to BL-020: `ADR-260815-selected-runtime-stop-control`, `ADR-260815-explicit-workbench-restart-control`, `ADR-260815-public-runtime-state-projection`, and `ADR-260815-api-restart-runtime-reconciliation` each record that deferral explicitly.

Issue #45 spends it for a selected registered project whose authoritative public state is `Running` or `Failed`, including a runtime adopted by the delivered API-restart reconciliation. The delivered code cannot satisfy that requirement, and the gap is an ordering gap rather than a missing feature:

- Close commits the durable deletion and emits `project.closed` before any resource fact is known, so a `running`, `starting`, `stopping`, `restarting`, `reconciling`, or retained `failed` manager entry can outlive the registration that justified it.
- `ProjectRuntimeManager` keys every entry, ownership record, pending admission, quarantined identity, and cleanup audit by stable project ID in instance memory. Nothing removes those structures when the row disappears, and `routes/project-runtime-state.ts` orders its projection from durable library IDs, so a retained owned runtime becomes invisible to both the project list and the public runtime projection.
- `ProjectRuntimeManager.start` installs a `starting` entry and later installs a running snapshot without re-reading the registration, so an acquisition in flight across a close can install a live runtime and a loopback listener for a registration that no longer exists.
- `WorkbenchProxyManager` inventories HTTP work, raw sockets, and bridged WebSockets by opaque project token but drains them only in its global five-second `shutdown()`. There is no per-project drain, so a close leaves the selected project's connections in the proxy's own maps.
- API-restart reconciliation enumerates `ProjectLibrary.list()`. A project deleted while its runtime survived is absent from that enumeration, so the next API process has no durable subject against which to account for the survivor, and the survivor is neither adopted, released, nor reported.

An issue-scoped fix inside the existing close service is not available. Confirming release before removal, refusing every lifecycle operation that could install a new generation while a close is in flight, and preventing a late settlement from resurrecting a retired project are decisions about which boundary owns the operation, in what order its effects occur, and what vocabulary it may report. They belong in one architectural decision.

Out of scope and unchanged: archive, undo, bulk close, project-file deletion, automatic lifecycle policy (BL-021), recovery beyond the delivered one-shot API-restart reconciliation (BL-022), persisted runtime handles or state, multi-host operation, and adoption or termination of any process Ascend cannot exactly attribute.

## Decision

Add one manager-owned selected close operation, make the existing close service its only composer, and give the durable removal a confirmed-release precondition.

**Make `ProjectRuntimeManager.close()` the single authority for the whole operation.** Add one required interface member:

```
close(input: {
  projectId: string
  drainConnections: (signal: AbortSignal) => Promise<WorkbenchProxyAudit>
  auditConnections: () => WorkbenchProxyAudit
  commitRemoval: () => Promise<CloseProjectResult>
}): Promise<RuntimeCloseOutcome>
```

The manager owns admission, the exclusive claim, the phase order, every bound, the confirmation rule, the settlement, and the retirement. The three effects it does not own — draining the proxy's per-project connections, re-observing them, and deleting the durable row — are supplied as callbacks by the close service, which is the only component that legitimately depends on the library, the manager, and the proxy at once. This avoids the circular dependency that a manager-held proxy reference would create, keeps persistence out of the lifecycle boundary, and still leaves exactly one component responsible for ordering. A two-phase ticket API that lets a caller claim a project and forget to settle it is rejected: the manager always settles its own claim. `auditConnections` is deliberately **synchronous**: the final confirmation must read the authoritative per-subject connection counts and reach `commitRemoval` in one uninterrupted synchronous region, and an asynchronous re-observation would reintroduce exactly the window it exists to close.

**Serve the operation from the unchanged `DELETE /api/projects/:id` route.** Close is one project-level operation, not a runtime operation, and splitting it would create a second destructive route. The route keeps its path, its method, its empty request, its `200 { "id", "disposition": "closed" }` success body, and its `{ "error": { "category" } }` failure shape. It gains bounded categories only.

**Claim the project exclusively for the whole operation.** Close resolves the persisted project, then performs one synchronous section that reads the manager's installed entry and installs a close claim keyed by stable project ID. No `await` occurs between that read and that install. While a claim is installed the project is closed to every other lifecycle path: `start()` throws the new bounded `runtime-closing` failure, `stop()` returns the new bounded rejection `close-in-progress`, `restart()` returns the new bounded rejection `close-in-progress`, and `register()` refuses. The claim, not the entry state, is what makes the operation exclusive, so a retained `failed` entry is never misreported as `Running` merely because a close is in flight.

**Re-evaluate the claim after every `await` on any path that can hand out or install a runtime.** A single refusal at the top of an acquisition is not sufficient, because a claim can be installed while that acquisition is suspended. `start()` therefore re-evaluates the claim after every `await` on its running-reuse path — after the persisted-project lookup, after a reconciliation join, after a `starting` join resolves, after the liveness probe, and after the health probe — and once more immediately before it returns an existing snapshot, refusing with `runtime-closing` at whichever point it first observes the claim. The same rule binds every other late-acquisition seam: no entry may be installed, no ownership record revived, and no snapshot returned after the last point at which the claim was observed absent. This is the delivered `reuseOwnershipFailure` discipline — which already re-checks entry ownership after each of those same awaits — extended to the claim, and it is what makes the drain's zero audit meaningful rather than stale.

**Do not add a fifth public state and do not add an entry state.** The public vocabulary stays `Stopped`, `Starting`, `Running`, `Failed`, projected by one synchronous read-only pass over the manager's entry map. The internal entry vocabulary stays at seven members. A claimed project keeps projecting the entry it already has, which is the truthful answer: a `running` entry whose release is not yet confirmed is still `Running`, and a retained `failed` entry is still `Failed`. A completed close removes the registration, so the project has no public row at all rather than a synthetic terminal state.

**Admit or refuse from one fixed evaluation order.** After resolving the persisted project, close evaluates, in this exact order: manager shutdown; persisted absence; an installed close claim; a `reconciling` entry; a retained `failed` entry classified `reconcile-unconfirmed`; a `starting` entry; a `restarting` entry; a `stopping` entry; then the releasable cases. Manager shutdown yields `manager-shutdown`. Persisted absence yields the successful-no-op outcome `already-absent`, which the route reports with the delivered `404 project_not_found`, so an unknown or already-closed project keeps exactly the delivered behaviour. A pending or unresolved reconciliation yields `reconcile-in-progress` or `reconcile-unresolved` and never signals, adopts, routes to, or claims the absence of an unattributed candidate. An in-flight start, restart, or stop yields `start-in-progress`, `restart-in-progress`, or `stop-in-progress`; the registration is retained and the contending operation keeps its own delivered outcome, so at most one externally effective release of a generation ever occurs. **Every one of those eight conditions settles before the exclusive claim exists**, because the claim is installed only in the ninth, releasable case: manager shutdown, persisted absence, a joined contender, a `reconciling` entry, a `reconcile-unconfirmed` retained failure, a `starting` entry, a `restarting` entry, and a `stopping` entry are the eight — and only the eight — settlement sites reachable ahead of the claim. Those eight sites are a closed set that a consumer MAY enumerate and MUST NOT extend without amending this decision. A settlement's outcome classification alone does not say which side of the claim it fell on: manager shutdown is also reachable from every re-read inside the phases, `already-absent` is also reachable when a confirmed release finds the durable row already gone, and a joined contender inherits whichever bounded rejection the winner produced. Anything that must distinguish an admitted close from a refused one MUST therefore discriminate by the settlement site, never by the settled category.

**Join a contender to the winner and never let it report success.** A close that finds a claim already installed does not open a second operation, does not release anything, and does not delete anything. It awaits the claim's settlement and then derives its own outcome from the durable fact the winner established: `already-absent` when the winner removed the registration, and otherwise the winner's own bounded rejection. Exactly one close of a project therefore performs the release, exactly one performs the durable removal, and exactly one reports `closed`; every other concurrent request settles inside the same bound with a truthful non-success. Eight concurrent closes of one running project therefore produce one `200` and seven `404`s, which is the delivered concurrent-close behaviour of the stopped path, unchanged.

**Run the phases in one fixed order, and confirm before removing.** An admitted close runs: (1) drain the selected project's proxy connections; (2) resolve any pending replacement admission and any quarantined ownership for the project; (3) release the exactly attributable owned runtime; (4) sweep every remaining ownership record attributed to the project; (5) verify zero selected-project residual; (6) commit the durable removal; (7) retire the entry and record the tombstone. Draining precedes releasing so no proxy operation is awaiting an acquisition that the claim has already refused and no stream is torn down by a process exit it could have avoided. Removing is last so the durable registration is the last thing to disappear.

**Define confirmation exactly, and never weaken it.** Step (5) is a re-observation, not a recollection of step (1). It first calls `auditConnections()` synchronously; if any of the five per-subject counts is non-zero it invokes `drainConnections(signal)` **at most once more**, under the same single `closeDrainAllowanceMs` deadline armed at step (1), and then re-observes. An admitted close therefore invokes `drainConnections` at most twice and `auditConnections` at most twice, and never arms a second drain deadline. The final confirmation is then one uninterrupted synchronous region ending in the call to `commitRemoval`, and it requires all of: the re-observed per-subject connection audit reports zero pending operations, zero upstream HTTP requests, zero upstream HTTP responses, zero raw sockets, and zero bridged WebSockets for that project's opaque token; no ownership record attributed to the project remains; no quarantined ownership attributed to the project remains; no pending admission for the project remains; no in-flight start, stop, restart, or reconciliation operation for the project remains; the claimed entry is still the exact entry and generation this close claimed, or the `registered` entry this close installed; the project is not already retired; and every generation the close released produced a cleanup audit whose root process, owned process group, and loopback listener are all absent. A project with no managed runtime — no entry, a `registered` entry in either released state, or a retained `failed` entry whose owned identity is positively absent — satisfies step (5) without any signal being sent, which is exactly the delivered stopped-project behaviour and is what makes it safe. Absence is never inferred from entry state alone: a retained `failed` entry whose ownership record still exists is audited, and an audit that cannot confirm the triple is an unconfirmed release, not an absence. A per-subject connection resource that appears after the first drain is caught by the re-observation and, if the single permitted re-drain does not clear it, settles the close as `release-unconfirmed` with the registration retained. **What that residue actually is, stated exactly:** the participating connection boundary registers its per-subject operation *before* it requests the acquisition it needs, and it releases that registration only when the operation unwinds, so an acquisition that arrives after the first drain holds an audited per-subject resource for the whole time it takes that arrival to unwind — even though the refusal guarantees no new upstream connection is ever opened. **Made exact in plan revision 7:** an arrival unwinds either through the refusal the claim raises at the acquisition path's head, before any suspension point, or through the cancellation the re-drain itself issues when the drain reached the arrival first. Both are ordinary, both leave the first drain's zero audit stale at confirmation, and evidence MUST report each as the settlement its own mechanism produced rather than relabelling one as the other. An arrival suspended before the point at which it could observe that cancellation does not unwind at all, which is precisely how a resource the single permitted re-drain cannot clear arises. The first drain's zero audit is therefore stale at confirmation for an ordinary, fully refused arrival, which is exactly why step (5) re-observes. A reuse that escaped the claim and opened a live upstream connection is the *stronger* case the same re-observation catches, and it is reachable only if a post-`await` recheck is removed. The operation fails closed; it never removes a registration whose connection audit it could not re-confirm.

**Discharge each confirmation clause from subject-keyed state, and compare identity by reference.** Two clauses of the confirmation name facts that a boundary can only establish about *one* subject, and both MUST be read from state keyed by that subject. The in-flight-work clause is the conjunction of: the subject's own entry being absent or in a non-transient state; no pending admission for the subject; and no late work observed for the subject since its claim was installed, counted on the claim itself. It MUST NOT be discharged from an aggregate that is not keyed by subject — the delivered in-flight operation sets are sets of promises, so reading them would both refuse a correct close while an unrelated project's stop was settling and admit a close whose own suspended acquisition holds no promise in any set. The identity clause compares the value the claim captured at install — by reference, and permitted to be absent — against the value installed now, so "absent then and absent now" is distinguishable from "absent then, installed since"; entry values are immutable and every transition installs a new value, which is what makes reference identity the exact generation test. A state label, a truthiness test, or a structural comparison is not sufficient and is prohibited.

**Count only identity-bearing late work, and refuse a harmless late acquisition without poisoning the claim.** The in-flight-work clause's late-work counter is incremented by exactly three events: a refused entry install, an ownership registration observed for a claimed or retired project, and every late or reordered settlement accounted as a stale settlement for that project. It is **not** incremented by an acquisition, join, or registration that is refused before it produces identity-bearing state — before it installs an entry, registers or revives an ownership record, creates a pending admission, mints a generation, or returns an existing snapshot to its caller. Those refusals are the *intended* behaviour of the post-`await` claim rechecks: they are the mechanism by which a suspended acquisition is stopped, they mutate nothing, and they are already fully covered by the connection re-observation, the ownership, quarantine, and pending-admission clauses, and the reference-identity clause. Counting them as late work would make every correct close unconfirmable the moment any caller merely asked for the project while the claim was held, converting the delivered refusal path into a denial of the close itself. They are counted instead on a boundary-wide refused-acquisition counter reported by the manager audit, which is evidence — and a *production-observed* witness that the recheck seam was actually reached — and is never read by the confirmation predicate.

**Give the manager one entry-install authority, and seal it between confirmation and removal.** Exactly one lexical site in the manager writes the entry map, and that site is the install helper that consults the retirement set and the claim map before writing. Every entry transition in the manager — registration, every start install and settlement, every stop settlement, every restart install and settlement, and every reconciliation install — calls that helper; no path writes the entry map directly. A caller that receives a refusal installs nothing and MUST NOT emit an event, register ownership, record cleanup, register a task, or report success on the strength of a write that did not happen; an install that is unrefusable by construction, because it occurs in the same synchronous region as its own path's refusal check, asserts the helper's success with that path's invariant error rather than discarding it. The claim additionally carries a seal set inside the confirmation region: while the seal is set the install helper refuses **every** caller including the close that owns the claim, and an ownership registration for the project does not enter the ownership index but is recorded as a quarantined identity so the manager shutdown sweep still reaches it. The seal is lifted only by the close itself, only on the branch where `commitRemoval` failed, and only immediately before it installs its released `registered` entry; a completed removal leaves the seal superseded by the tombstone. This closes the window that accounting alone cannot close: a counter incremented after the predicate has been read cannot change the outcome it was read for.

**Reuse the delivered release machinery unchanged.** Step (3) terminates through the one termination sequencer decided in `ADR-260815-termination-sequencer-boundary`, with its delivered graceful window, force window, audit allowance, monotonic clock, trusted synchronous deadline scheduler, signal-delivery contract, cancellation contract, and exact-attribution rule. Close introduces no second terminator, no new signal path, no new liveness probe, and no new listener probe, and it may not adopt, signal, or claim any process it cannot exactly attribute.

**Bound the operation from one origin, one arithmetic, and a declared cardinality cap.** Step (4) sweeps *every* ownership record attributed to the project, and a project can hold more than one: an unconfirmed stop or restart release retains its record, and a later successful start adds another, so two retained records are reachable with no quarantined identity involved at all. A release bound that covers a single termination is therefore untruthful. Three configuration members are added to `ProjectRuntimeConfig`: `closeDrainAllowanceMs` (default `5_000`), `closeSettlementAllowanceMs` (default `1_000`), and `closeOwnershipSweepCap` (default `4`), all internal with fixed defaults, none an environment variable, flag, or deployment setting. Two derived bounds are added:

```
runtimeCloseReleaseBoundMs(config, requiresQuarantineResolution, sweepUnits)
  = (requiresQuarantineResolution ? restartQuarantineReleaseBoundMs(config) : 0)
  + sweepUnits * runtimeStopOverallBoundMs(config)

runtimeCloseOverallBoundMs(config, requiresQuarantineResolution, sweepUnits)
  = config.closeDrainAllowanceMs
  + runtimeCloseReleaseBoundMs(config, requiresQuarantineResolution, sweepUnits)
  + config.closeSettlementAllowanceMs
```

`sweepUnits` is **not** an attacker-controlled multiplier. It is `max(1, ownershipCardinality)` where `ownershipCardinality` is frozen inside the same synchronous section that installs the claim, by counting the ownership records attributed to the project at that instant; the claim then refuses every path that could add another. A close whose frozen cardinality exceeds `closeOwnershipSweepCap` is refused immediately with the bounded rejection `ownership-cardinality-exceeded`: it drains nothing, signals nothing, terminates nothing, removes nothing, installs no failure, emits no event, leaves the entry and all four durable fields exactly as they were, and releases its claim. That is the fail-closed branch, and it is the only branch in which the multiplication could otherwise grow without limit. Both bound functions pass through `checkedRuntimeBound`, so every product and every sum is asserted to be a positive safe integer.

At defaults `runtimeStopOverallBoundMs` is 5,000 ms and `restartQuarantineReleaseBoundMs` is 15,000 ms, so a single-ownership close is bounded at 11,000 ms without quarantine resolution and 26,000 ms with it — the delivered single-generation values preserved exactly — and the caller-visible ceiling at the cardinality cap is 41,000 ms. `requiresQuarantineResolution` is true exactly when a pending admission or a quarantined ownership record exists for the project at admission time, which is the same predicate explicit restart already uses. Every deadline on the close path, including the drain deadline, is armed from the manager's trusted synchronous `RuntimeDeadlineScheduler` and measured on its monotonic clock; no fallible awaited delay primitive paces any close phase, and the proxy does not self-time its per-project drain: it declares no deadline, reads no clock, and measures no elapsed time, and the one fixed observation gap across which it re-reads its own counts (Plan revision 5) can neither end its wait nor extend it past the manager's signal. The overall bound is the operation's declared, documented, fixed-before-execution bound.

**Settle every non-success into a truthful entry and keep the registration.** A close that cannot confirm step (5) within its bound returns `release-unconfirmed`, does not call `commitRemoval`, retains every ownership record so manager shutdown re-attempts exact cleanup, records at most one close-phase cleanup audit per generation it terminated, and installs a retained `failed` entry carrying the new bounded failure category `close-release-unconfirmed`. A close whose `commitRemoval` throws returns `removal-failed`; because release was already confirmed, it installs a `registered` entry that records the release, so the project reports `Stopped`, offers Stop as `already-stopped`, and can be closed again safely without any runtime being recreated or signalled. A close whose `commitRemoval` returns `project_not_found` has an absent registration and a confirmed-absent runtime, which is the terminal fact `already-absent` describes; it records the tombstone and reports no second removal. Under no non-success does the registration disappear, and under no outcome does an unregistered project retain a live or unresolved Ascend-owned runtime resource.

**Retire a closed project and never revive it.** After a confirmed removal the manager deletes the project's entry, deletes its recorded cleanup outcomes, and records its stable project ID in a close tombstone. Every entry-installing path — `register()`, `start()`'s installs, stop and restart settlements, reconciliation installs, and every late or reordered continuation — consults the tombstone and refuses. Because a stable project ID is a persisted identifier that is never reissued after its row is deleted, the tombstone can only grow with the number of successful closes in one API-process lifetime, and it is what makes a late settlement report an explicit stale non-success instead of resurrecting a removed project, installing a runtime for it, routing to it, or mutating another project.

**Bound disclosure with a small vocabulary.** `RuntimeCloseOutcome` is `closed`, `already-absent`, or `rejected` with exactly one of nine categories: `start-in-progress`, `stop-in-progress`, `restart-in-progress`, `reconcile-in-progress`, `reconcile-unresolved`, `release-unconfirmed`, `ownership-cardinality-exceeded`, `removal-failed`, or `manager-shutdown`. The route publishes eleven categories: the delivered `invalid_project_id` (400), `project_not_found` (404), and `project_close_failed` (500, carrying `removal-failed`), plus `runtime_start_in_progress`, `runtime_stop_in_progress`, `runtime_restart_in_progress`, `runtime_reconcile_in_progress`, and `runtime_reconcile_unresolved` (409), `runtime_release_unconfirmed` (500), `runtime_close_ownership_unresolved` (500), and `runtime_manager_shutdown` (503). Release mode, termination audits, process identities, ports, internal authorities, and pre-close snapshots stay inside the trusted in-process result and retained validation evidence and never reach a public payload, a log record, or a browser surface.

**Announce a close only as a close.** A completed close emits exactly one `project.closed`; nothing else emits it. Close emits no `runtime.stop.*`, `runtime.restart.*`, `runtime.start.*`, or `runtime.reconcile.*` event, because it is not a stop, a restart, a start, or a reconciliation — the same reasoning by which `ADR-260815-explicit-workbench-restart-control` already decided that a restart emits no stop or start events while consuming the same primitives. The one lifecycle event a close may emit is `runtime.health.changed` from `running` to `failed` classified `close-release-unconfirmed`, and only when it genuinely installs that retained failure for a `running` entry; that is the delivered announcement for a real transition to `Failed`, not a synthesized success. A rejected close, a joined contender, an `already-absent` outcome, and a `removal-failed` outcome emit no lifecycle event. The route's `project.close.failed` operational record is not a lifecycle event and never substitutes for one.

**Add two runtime failure categories, and publish each where it is actually reachable.** `RUNTIME_FAILURE_CATEGORIES` gains `runtime-closing` and `close-release-unconfirmed`, each with a safe operator message. They are not symmetric. `runtime-closing` is an **acquisition failure only**: it is raised by `start()` and `register()` when they meet a claimed project, it is never written into an installed `failed` entry, it is therefore never read by the public projection, and no project ever reports `Failed` because of it. `close-release-unconfirmed` is the only new **retained** classification: a close that could not confirm release installs it on a `failed` entry, and it is projected as `Failed` through the existing `failureCategory` field. Both are nonetheless proxy-reachable — the first when an acquisition meets a claimed project, the second when an acquisition meets the retained failure — so `WORKBENCH_FAILURE_TABLE` gains exactly two rows in declared category order, `runtime:runtime-closing` at `503 workbench_closing` and `runtime:close-release-unconfirmed` at `503 workbench_release_unconfirmed`, both `503` because a later explicit action can clear them. The web client mirrors both categories and both notices. The table hash changes, so the published failure matrix is re-executed rather than re-declared.

**Give the proxy one per-project drain and no authority over time.** `WorkbenchProxyManager` gains `closeProject(projectId, signal)`, which aborts that project's pending operations, destroys its upstream requests and responses, terminates its bridged WebSockets, destroys its raw sockets, and returns the per-token audit the caller must find zero. It touches no other project's token, it does not set `shuttingDown`, it does not resolve targets, it does not start runtimes, and it is bounded only by the caller's signal, so the manager's trusted scheduler remains the single timing origin for the close. It ends on exactly two conditions — the selected token's five counts observed zero, or the caller's signal aborting — and it may re-read those counts across one fixed non-authoritative observation gap that declares no deadline, measures no elapsed time, counts no attempt, and releases its scheduled handle and abort listener before the drain settles.

**Keep the Close control usable and honest on Project Home, and end the dialog at transmission.** A modal dialog and a usable peer control are mutually exclusive by definition: while a dialog holds `aria-modal` and traps focus, no other project's control is operable. The delivered dialog stays open through the pending, retry, unknown, and refreshing phases, so keeping it exactly as delivered *and* requiring peer controls to stay usable during a pending close is not a stricter requirement — it is a contradiction. This decision resolves it in one direction and states the whole model.

The confirmation dialog is **exclusive and short-lived**. At most one close dialog is open at a time, it is modal, it traps focus, and it exists only for the two phases in which nothing has been transmitted: `confirming`, and `pending` before transmission. `Escape` and Cancel remain safe throughout its life, because its life ends at transmission. The moment the request is transmitted the dialog is dismissed, focus moves deterministically to that card's own close status region, and the close continues as a **per-card, per-project** pending state carrying the visible pending text, exactly as the delivered restart lane already does for a pending restart. Failure and unknown outcomes surface as per-card regions with that card's own retry and refresh controls, never as a reopened modal.

A pending close is therefore scoped to its own project in every sense. While a close for project P is pending, every other project's Open, Close, Stop, and Restart control remains admitted by the controller and rendered enabled, another project's close may be opened, confirmed, and transmitted, and two closes may be in flight at once; each has its own transport, cancellation signal, generation, and settlement, and neither settlement touches the other's record, focus, or announcement. Only the confirmation dialog and the browser's list-bearing work are serialized, and only P's own runtime controls are disabled while P's close is in flight. The list-bearing group — registration, list load, list retry, recovery refresh, and the per-card refresh that resolves an unknown close outcome — keeps the delivered single global owner lane, because each of those replaces the whole authoritative list and two concurrent replacements have no defined winner; the per-project runtime controls take no global owner at all, which is exactly the group the peer-usability requirement is about. Because a close now settles outside that lane, the lane's own guarantee is restated rather than lost: a list response that was issued before a close settled and resolves after it MUST be discarded and re-issued rather than applied, and every applied list response MUST be filtered through the client's set of already-closed identifiers, so a successfully closed project can never be re-added to the rendered list and the settlement-triggered runtime-state read can never be aligned against a list the close already invalidated. That filter is sound because a stable project identifier is minted once at registration and never reissued. A second confirmation or a second transmission for the *same* project is refused. Every close announcement is attributed to its project name so two concurrent settlements are never ambiguous. And a control is rendered disabled only when activating it would be refused, so no rendered-enabled control is a silent no-op. A settled successful close increments a close settlement version that triggers exactly one additional read-only runtime-state request for the current authoritative list revision, extending the delivered on-demand refresh rule; no timer, poll, or stream is introduced. An unclassifiable transport result stays in the explicit unknown phase, preserves the selected card, and offers the manual refresh that resolves it against fresh authoritative project-list and runtime-state observations, never an assumed success and never an automatic repeat.

**Raise the close transport bound above the manager bound.** The delivered 10,000 ms client close bound was chosen against a metadata-only operation. The manager's honest overall close bound is 11,000 ms for a single-ownership close, 26,000 ms when a quarantined identity must be resolved, and 41,000 ms at the declared ownership-cardinality cap with quarantine resolution — the caller-visible ceiling. A client bound below that ceiling would abort while the manager was still legitimately working and would turn an ordinary successful close into the `unknown` outcome. `PROJECT_CLOSE_TIMEOUT_MS` becomes `45_000`, which strictly exceeds the caller-visible ceiling, and that relation is stated wherever either bound is documented. This is the same rule `ADR-260815-per-project-lifecycle-activation` established for the restart transport.

**Persist nothing new.** The persisted project record stays exactly `id`, `name`, `canonicalPath`, and `createdAt`. No runtime identity, ownership record, claim, tombstone, release marker, admission, or public state is persisted, and no schema change or migration is introduced. Durable removal remains one explicit serialized transaction that deletes exactly one row and rolls back as a unit.

**Touch no project directory.** No close path creates, modifies, moves, or deletes anything inside a registered project directory or reads its contents, and no close path is given a filesystem write capability.

## Alternatives

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| Delete the row first, then release the runtime | Smallest change to the delivered close; the user sees the card disappear immediately | The interruption window leaves an absent registration with a live survivor, which the next reconciliation cannot even enumerate; a failed release then has no durable subject to report against | AC-016 prohibits an absent registration with any surviving candidate, and only release-before-removal makes that prohibition an invariant instead of a hope |
| Have close call the delivered `stop()` and then delete the row | Reuses the entire proven BL-017 release contract with no new manager operation | The gap between the stop settling and the delete committing is exactly the window in which a proxy acquisition installs a new generation for a still-registered project; and the emitted `runtime.stop.*` events attribute a close's work to Stop | Exclusivity must span release and removal, and a close must not be announced as a stop |
| Keep the ordering in `ProjectCloseService` and expose manager primitives | Persistence stays out of the lifecycle boundary; no callbacks | The claim, the phase order, and the bounds would live outside the boundary that owns entries, so a service that forgets to settle leaks the claim and permanently bricks the project | The lifecycle boundary must own its own claim lifetime |
| Give the manager a direct `WorkbenchProxyManager` reference | No callbacks; the manager owns every phase directly | The proxy is constructed with the manager as a dependency, so the reference is circular and would have to be late-bound through mutable state | Callback injection expresses the same ordering without a construction cycle |
| Add a fifth public state such as `Closing` | Most literal reporting of an in-flight close | Breaks the four-value public vocabulary that every client, route, matrix, and evidence artifact is built on, for a state that lasts at most seconds and whose truthful answer is already available | The delivered projection is unchanged; a claimed project keeps reporting the entry it has |
| Add an internal `closing` entry state | Symmetric with `stopping` and `restarting` | A retained `failed` entry claimed for close would project `Running`, which is false; and a seventh internal state must be projected, evented, and mapped for no behavioural gain | The claim is orthogonal to the entry, so the entry keeps telling the truth |
| Let concurrent closes join and all report `closed` | Simplest contender rule | Produces eight `200`s and eight `project.closed` records for one removal, which is a duplicate successful-close event by any reading | AC-009 requires exactly one durable removal and no duplicate successful-close event |
| Reject a contender with a dedicated `close-in-progress` category | Most literal description of the contender's situation | Changes the delivered stopped-path concurrency evidence from one `200` and seven `404`s to one `200` and seven `409`s | AC-004 requires the delivered stopped-project close behaviour preserved exactly |
| Join an in-flight `stop()` instead of rejecting `stop-in-progress` | A close could still succeed while a stop is settling | Folds the stop bound into the close bound, and adds a second joining path whose failure modes are not covered by any delivered proof | Rejecting is bounded, truthful, symmetric with restart's delivered `stop-in-progress`, and both orderings still satisfy the contention criterion |
| Drain the proxy after terminating the runtime | Fewer aborted streams to classify | Every in-flight upstream operation fails on a dying socket first, so the drain's own audit cannot distinguish a released connection from a broken one | Draining first makes the zero-residual audit meaningful |
| Let the proxy self-time its per-project drain with `shutdownTimeoutMs` | No new configuration member | Creates a second timing origin whose arithmetic the manager cannot see, which is exactly the defect class BL-019 revision 5 had to repair | One trusted scheduler owns every close deadline |
| Emit `runtime.stop.succeeded` for the close's release | Announces the real state transition with an existing name | Attributes a close's release to the Stop operation, which no stop performed | AC-008 prohibits misattributing Stop events; restart already set this precedent |
| Add `runtime.close.*` event names | Most explicit announcement | The NFR-015 catalog is a product requirement; inventing names in an issue is a silent product change | `project.closed` already names this operation |
| Clear the tombstone after some interval | Bounded memory | A stable project ID is never reissued, so expiry can only create a window in which a late settlement revives a removed project | The tombstone grows with successful closes only, which is the same order as the entry map |
| Bound the ownership sweep at one termination | Smallest arithmetic; matches the delivered stop bound exactly | Step (4) sweeps every record attributed to the project, and two retained records are reachable with no quarantine, so a correct close could exceed its own declared bound | A declared bound a correct execution can exceed is not a bound |
| Multiply the sweep bound by the observed ownership count with no cap | Always covers the real work | The multiplier is an in-memory count that accumulates from unconfirmed releases, so no finite ceiling could be published or compared against a client bound | Bounds must be declarable before execution; a cap plus a fail-closed refusal keeps them so |
| Keep the confirmation dialog open through settlement and call peer controls "usable" because they are still rendered | No UI change at all | A trapped-focus modal makes every peer control unreachable, so the claim would be false as rendered | The criterion asks for usable peer controls, and only dismissing the modal at transmission delivers them |
| Allow one modal per project so several dialogs can be open at once | Literal per-project symmetry | Two simultaneous `aria-modal` dialogs have no defined focus owner and no defined assistive-technology reading | Exclusive confirmation plus concurrent per-card pending states gives the same capability with defined semantics |
| Confirm removal against the step (1) drain audit | One observation, no re-drain | A running-reuse acquisition that passed its claim check before the drain can open an upstream connection after it, so the recorded audit can be stale at the instant of removal | Confirmation must be a re-observation taken synchronously immediately before removal |
| Keep `PROJECT_CLOSE_TIMEOUT_MS` at 10,000 ms | No client change | Aborts below the manager's honest bound, so an ordinary successful close renders `unknown` and the accessible classified outcomes become unreachable | The client bound must exceed the manager bound it is waiting on |

## Consequences

### Positive
- A close success now means what FR-014 says it means: the registration is gone and the Ascend-managed resources are confirmed gone, in that order.
- An interruption at any instant leaves either a registered project with a truthful lifecycle outcome or an absent registration whose resources were confirmed absent before removal; an absent registration with a surviving candidate is unreachable by construction. The registered case is then settled on the next boot by [ADR-260815-api-restart-runtime-reconciliation](./ADR-260815-api-restart-runtime-reconciliation.md)'s own unchanged conjunction — a live, exactly attributable survivor is adopted and reported `Running`, one whose conjunction cannot be proven is retained `Failed` classified `reconcile-unconfirmed` — and this decision requires no other outcome of it.
- One exclusive claim replaces four separate races (close against start, stop, restart, and reconciliation) with four bounded, named, observable outcomes.
- The proxy gains a real per-project drain, so peer projects, their connections, and their runtimes are provably untouched by a selected close.
- Every close outcome is reportable through the delivered four-value public projection, the delivered route shape, and the delivered event catalog; no client, matrix, or evidence artifact needs a new state concept.
- A retired project cannot be revived by any late or reordered settlement, which closes the whole class of stale-work defects the issue enumerates.

### Negative
- `ProjectRuntimeManager` and `WorkbenchProxyManager` each gain one required interface member, so every typed test double must migrate; the migration is mechanical but broad.
- Adding two runtime failure categories changes `WORKBENCH_FAILURE_TABLE_SHA256`, so the published failure matrix must be re-executed rather than re-declared.
- The declared close bound is materially larger than the delivered metadata-only close, and the client transport bound more than quadruples; a user waiting on a quarantined identity at the ownership-cardinality cap can wait up to 41 seconds before a classified outcome.
- The Close confirmation dialog no longer reports the outcome: the pending, retry, and unknown states move onto the card. That is a visible change to a delivered flow, and it is the price of usable peer controls during a pending close.
- A project holding more retained ownership records than the declared cap cannot be closed until a shutdown sweep, a successful stop, or a successful restart reduces them; the refusal is bounded and named, but it is a state a user cannot clear from Project Home.
- The close service now depends on the library, the manager, and the proxy, so `AppOptions.createProjectCloseService` changes shape and every construction site migrates.
- The tombstone set grows for the lifetime of the API process, bounded by the number of successful closes.

### Neutral
- The persisted schema, its migrations, the durable removal transaction, the route path and method, the success body, and the `project.closed` event name are unchanged.
- The delivered stopped-project close outcomes, including the eight-concurrent one-`200`-and-seven-`404` behaviour and the already-absent result, are preserved exactly.
- BL-017 Stop, BL-018 Restart, and BL-019 reconciliation keep their operations, bounds, vocabularies, and events; each gains exactly one bounded rejection for a close-claimed project.
- BL-021 automatic lifecycle policy, BL-022 durable or distributed recovery, archive, undo, bulk close, project-file deletion, persisted runtime state, and multi-host operation remain deferred.

## Revision — Plan revision 2, 2026-08-16 (pre-implementation)

Independent review of Plan revision 1 found five decisions in this ADR that were either unsound against the delivered sources or mutually contradictory. They are corrected in place above rather than left standing with a footnote, because no implementation has begun and a decision a reader must mentally patch is worse than one that is right. What changed, and nothing else did:

1. **Confirmation is a re-observation.** Revision 1 confirmed removal against the step (1) drain audit. `start()`'s running-reuse path can pass a close claim across an `await` and hand a live snapshot to the proxy, so that audit can be stale at the instant of removal. The close input gains a synchronous `auditConnections` callable, step (5) re-observes and may re-drain at most once inside the existing drain allowance, and every acquisition seam re-checks the claim after every `await`.
2. **The release bound is cardinality-aware.** Revision 1 bounded step (4) as though it released one generation, but two retained ownership records are reachable through an unconfirmed stop release followed by a fresh launch, with no quarantine involved. The bound is now a frozen, capped cardinality multiplied by the delivered stop bound, with `closeOwnershipSweepCap` and a fail-closed `ownership-cardinality-exceeded` refusal.
3. **`runtime-closing` is not a projected state.** Revision 1 described it as a second bounded category reported as `Failed`. It is raised by acquisition and never installed on an entry, so it can only surface through the workbench failure table and the client notice vocabulary. `close-release-unconfirmed` is the only new retained `Failed` classification.
4. **The Close dialog ends at transmission.** Revision 1 kept the delivered modal through settlement *and* required peer controls to remain usable. Those cannot both hold. Confirmation is now exclusive and pre-transmission only, the pending, retry, and unknown states are per-card, and concurrent closes for different projects are supported explicitly.
5. **The client bound follows the real ceiling.** With the cardinality cap the caller-visible ceiling is 41,000 ms, so `PROJECT_CLOSE_TIMEOUT_MS` is 45,000 ms rather than 30,000 ms.

The claim, the admission order, the phase order, the release-before-removal rule, the joining rule, the retirement rule, the event discipline, the persistence boundary, and the filesystem boundary are unchanged.

## Revision — Plan revision 3, 2026-08-16 (pre-implementation)

Independent re-review of Plan revision 2 returned no blockers and eight residual ambiguities. Six were plan phrasing and are corrected there. Two were statements of *this* decision that an implementer could satisfy two different ways, so they are made exact here, in place, above. Nothing else changed, and no decision was reversed.

1. **Confirmation clauses are discharged from subject-keyed state.** Revision 2 required that no in-flight lifecycle work for the subject remain and that the claimed entry still be "the exact entry this close claimed", without saying what may be read to establish either. The delivered boundary's in-flight-operation sets are not keyed by subject, so an implementation that consulted them would be wrong in both directions. The confirmation paragraph now states the subject-keyed conjunction and the by-reference identity comparison, including the absent case.

That left the ordering between a settled close and a list response already in flight undefined, which is precisely the interleaving that re-adds a card the close removed. The Project Home paragraph now states lane membership by kind, the discard-and-re-issue rule for a superseded list response, and the closed-identifier filter, none of which serializes a per-project runtime control.

Every other element — the claim, the admission order, the phase order, the release-before-removal rule, the cardinality cap, the joining rule, the retirement rule, the event discipline, the vocabularies, the bounds, the persistence boundary, and the filesystem boundary — is unchanged.

## Revision — Plan revision 4, 2026-08-16 (during implementation, T-3 return to Plan)

Implementation of the manager close operation reached a contract contradiction that Plan revision 3 could not settle from its own text, so T-3 returned to Plan. Two statements of *this* decision were under-specified in a way that made a correct implementation impossible; both are made exact here, in place, above. No decision is reversed, no vocabulary, count, bound, phase, admission step, or outcome changes, and the release-before-removal rule is strengthened rather than relaxed.

1. **Late work is now classified by what the arriving work produced.** Revision 3 required "no late work observed for the subject since its claim was installed, counted on the claim record itself" without saying which arrivals count. Read literally it included the post-`await` claim refusals that the same decision *mandates*, so any exercised refusal permanently made the claim unconfirmable — the close could never confirm precisely because its own exclusivity mechanism worked. The decision now distinguishes a refused acquisition, which produced no identity-bearing state and is counted only for evidence, from real late work — a refused entry install, an ownership registration under a claim, and an accounted stale settlement — which fails the confirmation closed. The predicate is unchanged in strength against every case it was written to catch, and it is now satisfiable in the cases the decision expects to succeed.
2. **The entry-install authority is single and is sealed across the removal.** Revision 3 required every entry-installing site to consult the retirement set and the claim map, which a boundary can satisfy while still writing the entry map from many places, and it said nothing about the window between the confirmation region and the durable removal's settlement. The decision now requires one lexical entry-map write inside one install helper, an explicit refusal contract for its callers, and a claim seal that refuses every install and keeps any ownership registration out of the ownership index for the whole of that window, lifted only on the failed-removal branch.

Every other element — the claim, the admission order, the phase order, the confirmation clauses themselves, the cardinality cap, the joining rule, the retirement rule, the event discipline, the vocabularies, the bounds, the persistence boundary, and the filesystem boundary — is unchanged.

## Revision — Plan revision 5, 2026-08-16 (during implementation, T-10 return to Plan)

The evidence contract built in T-10 turned this decision's phrase "no clock of its own" into a source guard that forbids every timer in the per-project drain, and that guard cannot be satisfied by the architecture this decision itself describes: the proxy's five resource maps are mutated from independent host stream and WebSocket-library callbacks and publish no aggregate settlement event, so the drain can observe settlement only by re-reading the same synchronous per-token audit its caller uses. One statement is therefore made exact here, in place, above. No decision is reversed, and no vocabulary, count, bound, phase, admission step, confirmation clause, or outcome changes.

1. **The drain owns no authority over time, which is not the same as owning no timer.** The prohibition is on declaring, deriving, inheriting, or inferring a deadline, on reading a clock, on measuring elapsed time, on counting attempts or retries, and on any fallback — that is, on anything that could decide whether the drain succeeded or when it ended. The drain terminates on exactly two conditions, the selected token's five counts observed zero or the caller's signal aborting, and it may re-read those counts across one fixed non-authoritative observation gap whose delay is never read, compared, accumulated, or counted, and whose scheduled handle and abort listener are released before the drain settles. Making the maps event-driven instead was considered and rejected: a settlement notification that can be missed turns an ordinary drain into an unconfirmed release, which is strictly weaker than re-reading live state, and it would add a cross-cutting notification surface to eleven independent mutation sites to buy no bound the caller's signal does not already provide.

The manager's trusted synchronous scheduler remains the single timing origin for the whole close, the drain remains bounded solely by the signal the manager gives it, and the claim, admission order, phase order, confirmation predicate, cardinality cap, joining rule, retirement rule, event discipline, vocabularies, bounds, persistence boundary, and filesystem boundary are unchanged.

## Revision — Plan revision 6, 2026-08-16 (during implementation, T-11 return to Plan)

Executing the deterministic matrix against a genuine harness — an isolated SQLite library, the production manager, proxy, and Fastify route over loopback HTTP, real upstream listeners, and a recording deadline scheduler — showed that two statements of *this* decision were read into the evidence contract in ways the delivered ordering cannot satisfy, so `T-11` returned to Plan. Both are made exact above, in place. No decision is reversed, and no vocabulary, count, bound, phase, admission step, confirmation clause, terminal case, or outcome changes.

1. **The admission order's first eight conditions all settle before the claim exists.** Revision 2's evidence rule was read as though only three settlements precede the claim — the shutdown head, persisted absence, and a joined contender. Execution of the nine-step order shows eight: the five sibling-lifecycle refusals are returned before the claim-installing synchronous section as well. The decision now names the eight sites, declares them closed, and states that a settled outcome classification cannot discriminate an admitted close from a refused one, because manager shutdown and `already-absent` are each reachable on both sides of the claim and a contender inherits the winner's category verbatim. Discrimination is by settlement site.

2. **The residue a late acquisition leaves is the participating boundary's registered operation, not an escaped upstream connection.** Revision 2 justified the confirmation re-observation with a running-reuse acquisition that passes the claim and then opens a new upstream connection after the first drain. Against the delivered proxy that ordering is unreachable: the proxy registers its per-subject pending operation before it requests the acquisition, and the drain does not settle until every per-subject count including that one reaches zero, so no acquisition can both escape the first drain and open an upstream connection under a claim that refuses it. The re-observation is still required, and for a stronger reason: an ordinary arrival that the claim refuses correctly still registers an audited per-subject resource before it is refused, so the first drain's zero audit is stale at confirmation on the *normal* path rather than only on a defective one. An escaped live upstream connection remains reachable exactly when a post-`await` recheck is removed, which is what makes that recheck's removal observable.

The claim, the nine-step admission order, the seven phases, all eight confirmation clauses, the cardinality cap, the joining rule, the retirement rule, the event discipline, every vocabulary, every bound, and the persistence and filesystem boundaries are unchanged.

## Revision — Plan revision 7, 2026-08-16 (during implementation, second `T-11` return to Plan)

Executing revision 6's own replacement choreography, and the interruption scenario beside it, showed that two statements of this decision were still read into the evidence contract in ways the delivered system does not satisfy. Both are made exact above, in place. No decision is reversed, and no vocabulary, count, bound, phase, admission step, confirmation clause, terminal case, or outcome changes.

1. **A late arrival's registration is held until it unwinds, and it can unwind two different ways.** Revision 6 said the residue is held “for the whole time its refusal takes to unwind”, which reads as though every late arrival is refused. The drain aborts every selected pending operation synchronously at its head, so an arrival the re-drain reaches first is *cancelled* rather than refused, and an arrival suspended before it can observe that cancellation does not unwind at all. The two settlements prove different mechanisms and must be recorded as what they are. A consequence follows for proof design and is stated here because it is a property of this ordering rather than of any one scenario: no single arrival can both be accounted by the first drain and still be registered at the final re-observation, so a proof that needs both facts uses two arrivals with disjoint declared roles.

2. **An interruption's recovered state belongs to the reconciliation decision.** This decision's interruption consequence guarantees no false deletion and an enumerable registration. It does not, and must not, fix what the next boot decides about the survivor: `ADR-260815-api-restart-runtime-reconciliation` adopts a live, exactly attributable, ready survivor, and requiring an unresolved or `Failed` outcome instead would contradict the decision this ordering exists to protect. The close's own invariants at an interruption are no false removal, no signal to a resource it had not confirmed, an enumerable registration, and a truthful recovery result; the recovered state is stated as the reconciliation contract's conditioned disjunction, with the branch and its deciding element recorded, and signals are attributed to the phase that delivered them rather than aggregated across the episode.
