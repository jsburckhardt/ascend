# Research Brief: Require APS-governed harness integration across RPIV agents

## GitHub Issue
- **Issue:** #23
- **Title:** Require APS-governed harness integration across RPIV agents
- **Work Item:** project/work-items/23-require-aps-governed-harness-integration-across-rpiv-agents

## Scope Classification
- **Scope Type:** core_component

## Problem Statement
The APS generator and RPIV agent family do not currently share a durable generated-agent contract for engineering-harness behavior. Lifecycle seams exist in the coordinator and friction capture exists in part of Implement, but the contract is not applied consistently to Research, Plan, Implement, and Verify and is not covered by the APS generator lint inventory. A future generated update can therefore omit, misplace, or silently bypass harness behavior while still preserving the visible RPIV stage sequence.

The repository must retain the existing ownership boundary while this gap is addressed: the coordinator owns lifecycle orchestration, every stage worker remains a leaf with its current RPIV responsibility, and worker harness activity is limited to qualifying `harness observe` capture.

## Acceptance Criteria
**Core**
- [ ] `.github/agents/aps-v1.2.2.agent.md` contains one explicit, reusable RPIV harness-profile contract that is applied when generating, updating, or linting the RPIV coordinator and Research, Plan, Implement, and Verify workers.
- [ ] The harness profile assigns lifecycle orchestration only to the coordinator, assigns qualifying friction capture to every stage worker, and preserves the existing Research, Plan, Implement, and Verify responsibility boundaries.
- [ ] On the initial pass, the coordinator’s executable flow attempts real `eng-harness-flow` pre-flight after branch preparation, pre-coding after the existing Plan handoff validation succeeds and before Implement, post-coding after the existing Implement handoff validation succeeds and before Verify, and post-flight only after successful Verify.
- [ ] Every Implement correction cycle repeats pre-coding before Implement and post-coding before Verify, and a Plan correction returns through the same required downstream seams.
- [ ] Every lifecycle-seam attempt uses the single `eng-harness-flow` front door with a supported executable command shape; no child harness skill or unsupported `INVOKE` DSL appears in the RPIV definitions.
- [ ] An unavailable host skill, unavailable tool, or non-success result at any lifecycle seam produces an explicit pipeline error that identifies the seam and prevents the next stage from being dispatched; no success-shaped fallback is reported.
- [ ] Research, Plan, Implement, and Verify each define the same bounded friction triggers: retry or backtrack, tool wait over 30 seconds, unexpectedly empty search, ambiguous failure, inferred-only runtime behavior, eyeballed constraint, hidden setup, and magic-wand reflex.
- [ ] Each stage worker accepts the same governed observation kinds—coordination, confusion, difficulty, gift, improvement-suggestion, insight, magic-wand, and win—rejects every other kind before execution, and passes non-empty shell-sensitive description text as a literal value to a real executable `harness observe` path.
- [ ] Each stage worker defines finite capture checkpoints that attempt every pending qualifying event by stage completion and attempt explicit failures immediately when they match one of the eight qualifying triggers and observation is available. Within one worker execution, an event with the same trigger, description, and kind is captured at most once; a change to any of those values remains independently capturable.
- [ ] Each stage’s evidence distinguishes successful capture from an unavailable, empty, malformed, or failed observation result; failed attempts preserve the qualifying event and failure details for the next declared checkpoint and never become a success-shaped fallback.
- [ ] Research, Plan, Implement, and Verify never invoke pre-flight, pre-coding, post-coding, or post-flight. Harness integration does not expand their current frontmatter tool lists, does not grant agent or subagent dispatch, and uses their existing terminal-execution capability only for their own `harness observe` action.

**Edge Cases**
- [ ] Repeated observation checkpoints do not duplicate an already successful event capture. A lifecycle transition is identified by its hook, target stage, and coordinator stage-attempt number: retries of that transition do not duplicate its successful call, while each incremented correction attempt receives its own required lifecycle call.
- [ ] Empty descriptions and invalid observation kinds are rejected before command execution; shell-sensitive descriptions are preserved literally, and empty or malformed command output is recorded as a failed attempt without losing the event.
- [ ] Lifecycle seam calls are serialized: an overlapping or repeated transition cannot dispatch the next stage or start a second seam call until the active call has an explicit result.
- [ ] Harness guidance remains advisory to the human, but the coordinator and stage workers do not silently skip required lifecycle calls or observation attempts.

**Verification**
- [ ] APS generated-agent validation explicitly checks harness-profile placement, executable command shape, host, tool, and frontmatter availability, lifecycle order, correction-cycle seams, the stage no-hook boundary, and friction-trigger and observation-kind parity.
- [ ] The RPIV coordinator and all four stage workers each pass the full APS target-file lint inventory, including section order, instruction discipline, symbols, IDs, `where` ordering, formats, VS Code frontmatter and tool allowlists, worker input/output contracts, and the harness profile.
- [ ] A repository-local, read-only contract-evidence matrix covers every harness-profile rule against `.github/agents/aps-v1.2.2.agent.md`, the RPIV coordinator, and all four stage workers and produces inspectable pass/fail evidence.
- [ ] Contract evidence includes deterministic negative fixtures that fail for missing or misordered lifecycle hooks, missing correction seams, stage lifecycle-hook leakage, unsupported observation kinds, fake observation commands, and absent capture checkpoints. These checks are repository-local, read-only, and require no production access, external account, or unsupported host.
- [ ] Repository-local regression evidence shows that the existing RPIV issue parsing, work-item resolution, stage order and handoffs, validation delegation, documentation evidence, commit handoff, and Verify pull-request contracts retain their prior outcomes except for the required harness calls and evidence.
- [ ] Plan records whether the existing RPIV stage core-component is sufficient or one cross-cutting harness contract is required. The selected contract records coordinator lifecycle ownership, seam order, the worker no-hook boundary, and observation-failure evidence; `project/architecture/ADR/DECISION-LOG.md` registers every affected contract and its decisions, and a repository-local search of tracked documentation for the RPIV agent names, lifecycle hook names, `eng-harness-flow`, and `harness observe` finds no statement that assigns lifecycle ownership or seam order contrary to the selected contract.
- [ ] The repository’s declared full-validation recipe completes successfully and its command result is retained as inspectable evidence.

## Constraints
- Preserve the exact Research → Plan → Implement → Verify order and the responsibility and correction ownership in `AGENTS.md` and `CORE-COMPONENT-260806-rpiv-stage-contract`.
- Keep lifecycle orchestration in the coordinator. Worker definitions cannot invoke pre-flight, pre-coding, post-coding, or post-flight and cannot receive dispatch capability.
- Keep `eng-harness-flow` as the only lifecycle front door. The fixed host vocabulary is pre-flight, pre-coding, coding, post-coding, and post-flight; coding observation executes through the CLI rather than a child skill.
- Preserve the current worker frontmatter tool lists. All four workers already have terminal execution, so observation capture must remain within that existing capability.
- Treat harness guidance as advisory to the human while retaining explicit agent attempts and failure-shaped results. Existing harness contracts prohibit silent skips and fabricated success envelopes.
- Accept only the eight CLI observation kinds. The installed executable also imposes a description minimum of 10 characters, which is stricter than merely non-empty text.
- Preserve shell-sensitive observation text literally. The host-process contract prohibits unsafe shell interpolation, and the issue explicitly requires rejection before execution for invalid kind or empty description.
- Follow APS normative section order, instruction discipline, identifier, symbol, `where:`, format, runtime-tool, and fatal-error rules as well as the VS Code frontmatter and portable leaf-worker contracts.
- Keep raw validation ownership in the root `justfile`; `harness checks` wraps `just verify` rather than replacing it (`ADR-260808-governed-engineering-harness`; `CORE-COMPONENT-260806-project-command-interface`).
- Preserve the resolved work-item directory. Research may write only this brief and cannot select architecture, define implementation work, or define validation artifacts.
- The issue requires repository-local behavior with no production access, external account, or unsupported host dependency.

## Risks and Open Questions
- **Blocking validation nondeterminism:** repeated full parallel API runs can disagree on early-exit/readiness-timeout and cancelled/early-exit while focused suites pass. This makes the issue requirement for retained successful `just verify` proof nondeterministic. It remains unresolved whether Plan scope includes a prerequisite stabilization of this sensor or whether that prerequisite must be owned separately before implementation can produce reliable acceptance evidence.
- **Architecture sufficiency:** the RPIV stage contract covers all five agents but has no harness rules; the harness delivery contract has relevant rules but presently scopes agent behavior to the coordinator and Implement. Plan must record whether an existing component is sufficient or whether another cross-cutting contract is required, without Research selecting that outcome.
- **Host invocation availability:** the repository contains the `eng-harness-flow` skill under `.agents/skills/`, but the VS Code adapter registry and coordinator frontmatter do not expose `eng-harness-flow` as a tool. The supported executable host shape and the failure envelope available to a VS Code coordinator remain unresolved.
- **Current strict-lint baseline:** overlength symbols and prose-only worker interfaces predate this issue. It is unresolved how much of that baseline is within scope when every target must pass the full APS inventory while prior RPIV outcomes remain unchanged.
- **Observation side effects and stage boundaries:** `harness observe` writes an ignored transient buffer. The interaction between that required side effect and stage-specific write restrictions, especially Research writing only its brief and Verify not changing implementation content, needs explicit Plan treatment without expanding worker responsibility.
- **Failure persistence:** the current Implement flow records an event as observed without inspecting command output. No current worker contract defines where unavailable, malformed, empty, or failed observation details persist across checkpoints while preserving stage handoff boundaries.
- **Transition identity and serialization:** the coordinator has no stage-attempt identity or active-seam state, so successful transition deduplication and overlap handling are absent from current repository behavior.
- **Contract drift:** governance currently names only Implement for coding observations, the decision log records only Implement capture, and no executable agent contract reads all five targets. Partial updates can therefore leave APS, governance, architecture, and agent definitions inconsistent.
